## Verdicts and Step Limits

Two mirror-image defects to #363, both found in one `mcp_config add` run that succeeded and was then undone by the agent that performed it.

**A success with a caveat must not read as a failure.** `mcp_verify` opened with `✓ … connected` and then appended a `⚠ … NOT loaded … Restart Bernard`, so a healthy just-added server produced output that was simultaneously success and warning. The `mcp-manager` specialist read the ⚠ as failure, **removed the config it had just written correctly**, then spent its remaining steps hunting a transport problem that never existed — guessing an SSE endpoint, then re-issuing `remove` on an already-absent key four times. Every result now leads with one unambiguous `VERDICT:` line and the detail lines are indented context, never a competing signal.

The root cause underneath it was in `MCPManager.getLiveRegistration`, which returned `connected: status?.connected ?? false` — conflating two opposite situations. A server **added since launch** has no `serverStatuses` row because this session never attempted it, so "not loaded" is the expected, healthy state and a restart is the ordinary next step; a server that was **in the config at launch** and is still not connected actually failed, and `error` says why. `knownAtStartup` (`status !== undefined`) separates them. A name collision is treated as needing attention in either case, because it needs a decision from the user: MCP registration is last-writer-wins, so two servers exporting `browser_click` means one silently shadows the other.

**Running out of steps must not surface as `parse_failed`.** A dispatch cut off at `maxSteps` never reaches the turn where it writes its JSON, so `wrapWrapperResult` sees empty text and reports "did not produce valid structured output" — true, and useless: it blames the output format for a budget problem. `runDefinition` already computes `stepLimitHit` (it is how MCP delegation decides to escalate); `tool-wrapper-run` was discarding it. **`reclassifyStepLimit`, described below, was DELETED with #370** — it inferred the dispatch fact from the model-written `error` string and was wrong in both directions; `relabelStepLimit` (`framework/agents/tool-wrapper.ts`) reads `meta.stepLimitHit` directly and is what ships. The reasoning it records still holds, and the persona path gained the same rule in #557. It re-labels two shapes, both meaning "cut off with nothing to say": a `parse_failed`, and — for `wantStructured: false` specialists, which never parse — an `ok` whose result is absent, which otherwise hands the parent an empty **success**. Only an _absent_ result counts: testing `typeof !== 'string'` would sweep up every successfully-parsed structured result, discarding exactly the work the guard exists to preserve. A run that hit the limit but returned real content is left alone — the model may have wrapped up on its last step. `step_limit` is a real `ToolErrorType`, not a bare string. Adding the label without the taxonomy entry looked tidy and was a **regression**: `classifyError('step_limit')` matched nothing and returned `unknown` — `retryable: false`, playbook _"the error did not match any known pattern"_ — where the `parse_failed` it replaced was `retryable: true` with concrete advice. Three consumers act on that classification (`wrap-with-specialist`'s user-facing print, the `[failure: …]` hint prepended to what the model sees next turn, and cron alert severity), so the change would have improved the string a human reads in the JSONL while degrading the structured signal. It sits beside `pool_exhausted`, its exact sibling — an internal budget failure: `low` severity, retryable, **not** correctable, since exhausting a budget is not a call-shape mistake and must not enter the correction queue. The message in `reclassifyStepLimit` is read from that playbook rather than hand-written a second time.

**And the same event must not be a failure at two formatters and a success at four (#406).** `task` and `tool-wrapper` mint the `status: 'error'` envelope above, which `detectResultFailure` reads as a failure; `sub`, `specialist`, `pac-actor` and `mcp-delegate` return PROSE — the reconstructed activity log — and prose that is not an error reads as a success. So a run cut off at its budget logged `status: 'ok'`, registered its truncated output as **citable evidence** and bumped the tool's `successCount`: the accounting #395 closed for _empty_ delegate returns, reproduced for truncated ones. Saying something is what made them look successful.

- **The marker, not an `Error:` prefix**, which is the fork #406 posed and left open. Nothing had to be invented: `failureMarker()` / `parseFailureMarker()` and the `[failure: <category>]` convention already exist in `error-taxonomy.ts`, and `step_limit` is already a `ToolErrorType` whose row says exactly what "incomplete" needs — **low severity, retryable, not correctable**. So all four consumers land correctly with no third state beside success and failure: `successCount` does not bump, the failure goes to `ToolProfile.dismissed` rather than to bad examples, evidence registration stops, and `ToolFailureHint` renders it in the low-severity colour rather than as an alarming red error. An `Error:` prefix would have bought the detection and framed partial-but-useful work as a failure, which is why #404 recorded the fork instead of guessing.
- **One site, because `appendActivitySummary` is the one function all four share.** It stamps the marker on its own line with the model-facing playbook riding on it — the format `wrap-with-specialist.ts` already mints and `stripFailureMarker` already knows how to remove — so the human preamble survives on the line below and the parent model gets the recovery advice from the taxonomy rather than from a fifth hand-written wording.
- **Only the EMPTY case**, matching `relabelStepLimit` rather than overriding it: a run that hit the limit and still returned real content may simply have wrapped up on its last step, and calling that a failure throws away work that did happen.
- **`specialist.ts`'s own `Error: step_limit —` prefix is gone with it.** #557 had fixed one of the four in place, which made this definition a second producer of a verdict `appendActivitySummary` now stamps for all four. Its test correspondingly asserts the PROPERTY — `detectResultFailure` is truthy and `parseFailureMarker` says `step_limit` — where it used to pin the `/^Error:/` mechanism.
- **The marker is matched against the SNIPPET, not the whole result.** `detectResultFailure` runs on every tool call and a result can be megabytes (`shell` at a 10 MB `maxBuffer`), so an unanchored regex over the whole value is the cost `mcpFailureText` already refuses one branch over. Both producers put the marker at the front, and `formatWrappedResult`'s mid-string `Error (<marker> …)` never reaches that line because the `Error` prefix test catches it first.

## Environment Variables

- `BERNARD_PROVIDER` — anthropic | openai | xai (default: anthropic)
- `BERNARD_MODEL` — Model name (default: provider-specific)
- `BERNARD_MAX_TOKENS` — Response token limit (default: 4096)
- `BERNARD_SHELL_TIMEOUT` — Shell command timeout ms (default: 30000)
- `BERNARD_TOKEN_WINDOW` — Context window size for compression, 0 = auto-detect (default: 0)
- `BERNARD_MAX_STEPS` — Max agent loop iterations per request (default: 25)
- `BERNARD_HOME` — Override all XDG directories with a single flat path
- `BERNARD_MCP_CONNECT_TIMEOUT_MS` — Per-server MCP connect + handshake + tool-listing timeout at startup and reconnect (default: 15000). A server that never completes the MCP `initialize` handshake (e.g. an HTTP/SSE server misconfigured as stdio) is marked failed and skipped — its spawned stdio child is killed and the REPL starts without it — instead of blocking startup forever (#254). Applies to both the REPL and the cron daemon. A slow server (e.g. a cold `npx @playwright/mcp@latest` that takes >15 s the first time) can time out at startup yet connect fine on a later fresh probe — the "healthy but not there" trap. To surface it, the `mcp_verify` tool reconciles its fresh isolated probe against the **live** session via `MCPManager.getLiveRegistration(name, probeToolNames)` (registered per-process by `setActiveMCPManager`, returning a `LiveRegistration`): each probed tool is classified `live` (routed to this server now), `shadowed` (another server exported the same name and won the last-writer-wins race in `connect`), or `missing` (not in the session's tool-set snapshot). So a server that is healthy in isolation but not actually loaded/callable is reported as such, instead of a misleading "✓ 23 tools". `knownAtStartup` (from `serverConfigs`, which is written once at launch — not from a `serverStatuses` row, which `doReconnectServer` can push to at runtime) then says whether being unloaded is a _fault_: see **Verdicts and Step Limits**.
- `BERNARD_DISPATCH_TIMEOUT_MS` — Opt-in per-`runAgent` **wall clock** (default: unset), and still unset by default after #607, which is the one thing that entry must not change. When set to a positive integer the runner fires `agent:dispatch:timeout {dispatchId, model, ms}` to the debug log and aborts the dispatch. It is the only budget in the family that counts time spent **inside tools** — a sub-agent, an MCP call, `ask_user` — which is exactly what makes it an operator's decision rather than a default: any value low enough to end a hang promptly is low enough to kill a person thinking about an `ask_user` question. Its abort is deliberately **not** branded as a stall, so `runWithStallRecovery` does not retry past it; retrying past a wall clock the operator set would defeat what they asked for. Leave unset in normal operation: reasoning models can legitimately sit on a single step for 60–90 s, and since #607 every dispatch has a liveness guard that ends a hang without one. Sub-dispatches inherit independent timers (one per `runAgent` invocation). Note the chained `AbortController` it used to build only when set is now built on every dispatch (the liveness budget needs the same controller), and the listener it puts on the caller's signal is **removed when the dispatch unwinds** — the caller's signal is one turn-scoped controller shared by every dispatch in the turn, so a `{once}` listener nobody removes retains one controller per dispatch until the turn ends. Invisible without looking: an `AbortSignal` emits no `MaxListenersExceededWarning` unless someone calls `events.setMaxListeners` on it.
- `BERNARD_PROVIDER_STALL_TIMEOUT_MS` — Time-to-first-byte cap on every LLM completion (#302), default `90000`; `0` or a non-numeric value disables it. A provider can accept the POST and then go silent — no headers, no bytes, and no error for the SDK to surface. Nothing bounded that: the only backstop was **undici's 300 s `headersTimeout`**, and since the AI SDK retries by default a single stall could wedge a turn for ~15 minutes (observed: a 300,837 ms request, then a retry, then the user pressed Esc). The guard (`src/providers/stall-guard.ts`) is injected as a custom `fetch` into every built-in and custom client from `src/providers/index.ts`, and covers the **header** await plus, since #350, a separate body-inactivity budget (`BERNARD_PROVIDER_BODY_IDLE_TIMEOUT_MS`). This entry used to say it "covers only the header await — once the response exists the body streams untimed", and that was **false for four months**: the budget was an `AbortSignal.timeout` passed as `init.signal`, and a signal handed to `fetch` stays bound for the whole response lifetime, so it was also a hard 90 s deadline on the BODY. Real traffic came within 4.5 s of it — a step measured 85,447 ms returning 1,295 bytes, a reasoning model working correctly. Worse, because `await fetch(...)` had already resolved, the `catch` never ran: a stalled body surfaced as a raw `TimeoutError` with none of the message below, and no `provider:stall` line. The fix is one `clearTimeout` in a `finally` — pinned by a test that needs all three of a short header budget, headers that beat it, and a body that then legitimately outlives it, since every other test in that file uses a generous budget and a mutation check found them all green with the leak reinstated. 90 s is 3.3x the worst legitimate TTFB measured across 1,230 real requests (p50 1.8 s, p99 13.3 s, max 27.4 s). A dead connection now costs **one** budget, not three: the guard throws a plain `Error`, and the AI SDK only retries a `TypeError('fetch failed')` that it wraps as a retryable `APICallError` — so a stall is never retried. (That is also what produced the original ~15 min: undici's timeout _does_ surface as `TypeError: fetch failed`, so it was retried twice.) Both the budget and the underlying `fetch` are resolved **per request**, never captured at module load — `.env` is parsed later by `loadConfig`, and `installInstrumentedFetchIfDebug()` patches the global later still, so capturing either one broke it silently (the second disabled the `http:*` events documented above for diagnosing this very failure). The thrown error is deliberately **not** an `AbortError` — the REPL treats those as "user pressed Esc" and renders nothing, so a stall surfaced that way would silently swallow the turn; it is a plain `Error` whose message contains "timed out", which `error-taxonomy.ts` classifies as `timeout` for free. A caller's own abort still propagates untouched, so Esc keeps reading as Esc.
- `BERNARD_STREAM_STALL_TIMEOUT_MS` — Mid-stream stall cap on the streaming branch (#325), default `120000`; `0` or a non-numeric value disables it. The sibling of the first-byte guard above: that one bounds the wait for _headers_, this one bounds the silence _after_ they arrive. A stream that dies mid-body was previously bounded only by undici's 300 s `bodyTimeout` — five minutes of a dead turn, unattended. The guard reuses the existing `agent:dispatch:stuck` watchdog, which needed two changes to work. First, **its progress signal was wrong**: `lastStepEndAt` moves only at step boundaries, so it climbs monotonically while tokens pour in and aborting on it would kill healthy long steps. `runStreaming` now stamps `lastProgressAt` on every part pulled off `fullStream` — the one point in the process that knows a byte arrived — stamped _before_ per-part branching so part types the switch ignores (`reasoning`, `step-start`) still count as liveness. Second, **the watchdog was debug-gated**, which would have meant the guard protected only sessions someone already suspected, never the unattended cron run that needs it; it now runs whenever a budget is set (still `unref()`ed, so it cannot hold the event loop open). The clock **pauses while a tool is executing** (`inFlightTools`, counted from `tool-call` / `tool-result` parts): `fullStream` goes silent for the whole span of a `task` / `subagent` / MCP call, which is legitimately minutes, so pausing keeps the guard's teeth instead of raising the budget past the false positive. A tool-result that never arrives leaves the count above zero and disables the guard for the rest of that dispatch — fail-open, because losing the guard costs a slow failure while a false abort costs completed work. 120 s is deliberately **above** the 90 s first-byte budget: an agent loop runs every step inside one `streamText` call, so the HTTP round trip opening step N+1 happens _inside_ the stream with no parts flowing, and a lower budget would race the first-byte guard and misreport a slow-but-live request. The watchdog tick tracks `min(30 s, budget)` so a user-configured small budget isn't silently rounded up to the 30 s period. **Scope, precisely: this is main-agent-only.** `useStreaming` is `sink !== null` and the sink is registered only by `<App>`; `streaming: true` is declared on exactly one definition (`main`). So the guard covers the main agent in a mounted Ink REPL and nothing else — not cron, sub-agents, tool wrappers, PAC phases, or delegate helpers, which are all non-streaming and resolve `stallMs === null` (and therefore register no watchdog at all). That is the opposite of where an unattended hang hurts most, and it is a property of the layer rather than an oversight: a per-part clock can only exist where parts exist, and `generateText` is one opaque await. Those paths were covered by the first-byte guard plus step boundaries, and are covered by a liveness guard of their own since #607 (`BERNARD_DISPATCH_STALL_TIMEOUT_MS`) — which answers the follow-up this entry filed, differently. It proposed moving body-inactivity detection down to `providers/stall-guard.ts`; #350 did that, and it was necessary without being sufficient, because the failure that remained is `generateText` sitting on a fetch that already settled, which no layer under `fetch` can observe. It also predicted that a transport-level guard would make `inFlightTools` unnecessary. That is true per REQUEST and false per DISPATCH: the non-streaming guard needs the pause exactly as this one does, because a step's tool execution is silence at the dispatch level whatever the transport sees. Like #302 the abort is re-shaped into a plain `Error` containing "timed out" rather than surfacing as a bare `AbortError` (which the REPL renders as nothing), so `error-taxonomy.ts` classifies it as `timeout` for free.
- `BERNARD_DISPATCH_STALL_TIMEOUT_MS` — Liveness cap on the **non-streaming** branch (#607), default `180000`; `0` or a non-numeric value disables it. The sibling above bounds silence between two BYTES; this one bounds silence between two **step boundaries**, net of the step's own tool calls. Until #607 the non-streaming branch had no liveness guard at all — which is every dispatch that is not the main agent in a mounted REPL: cron, sub-agents, tool wrappers, PAC phases, delegate helpers — so a wedged `task` or `subagent` stalled its parent with nothing but an unset `BERNARD_DISPATCH_TIMEOUT_MS` between it and forever, and the parent's own guard disabled by its pending tool count.
  - **The issue proposed a wall clock derived from the step budget. Measurement says that is the wrong instrument**, for a reason that only became true once #302/#325/#350/#594 had all landed: every layer beneath a dispatch is now individually bounded — 90 s to first byte, 120 s of body silence, 60 s per MCP call, `shellTimeout` per shell call — so a dispatch's total time is already the product of a bounded per-step ceiling and its step budget. A wall clock over that product is `13 × 120 s ≈ 26 minutes` for a 13-step sub-agent. It bounds the failure; it does not end it in any time a person would call bounded. And it has to count time inside `ask_user`, which `mcp-delegate`'s own prompt tells a helper to call and which is legitimately unbounded — the false positive #302's criteria forbid, minted by the instrument itself.
  - **What was actually missing is that nothing noticed when a step made no progress AT ALL** — the one failure the transport guards structurally cannot see, because it is `generateText` sitting on a fetch that already settled. `runNonStreaming`'s defensive abort race was written for exactly that shape ("some providers leave the stream pending after the underlying fetch is cancelled") and nothing ever fired the signal it races. A liveness clock catches the same population at three minutes instead of twenty-six, from a fixed budget derived from nothing.
  - **The `inFlightTools` exemption is preserved, and it is what carries the recursion.** A dispatch that never returns is either stuck inside one of its own tools, or stuck outside them — and only the second is this guard's. The first is covered rung by rung: the MCP deadline for a `tools/call`, `shellTimeout` for `shell`, `FETCH_TIMEOUT_MS` for `web_read` / `web_search`, `MAX_WAIT_SECONDS` for `wait`, `BERNARD_EMBEDDING_IDLE_TIMEOUT_MS` for `knowledge` and every RAG search, and a nested dispatch's own copy of this guard for `subagent` / `task` / `specialist_run` / `delegate_<server>`. `ask_user` is the deliberate exception: paused forever, on purpose, because a person is thinking. Each rung is the pause, which is why widening the guard to ignore in-flight tools would break it rather than strengthen it.
    - **The last rung was missing, and it is closed rather than documented.** `knowledge` and every RAG search reach `getEmbeddingProvider()`, whose first call may DOWNLOAD the model with nothing timing it out — a dispatch could sit there forever with this guard correctly paused for a tool call. The pause was right; the inner bound was absent, and acceptance criterion 1 was not met on that path. The bound is now in `embeddings.ts`, where #594's argument puts it: at the layer that knows what is running, so it protects `bernard facts` and the semantic cache too rather than only dispatches.
      - **Measured first, because the two regimes are wildly different.** Warm, **180 ms**; cold, **1.2–1.7 s** for a 23 MB download at ~18 MB/s on this machine. The same 23 MB is ~3 minutes at 1 Mbit/s and ~12 at 256 kbit/s, so a DURATION budget has no defensible value — anything that survives a slow link is not a bound, and anything that bounds is a hair trigger on one. That is #350's argument about a response body, and a model download **is** a response body.
      - **So the clock measures silence**, and `pipeline`'s `progress_callback` — which this file previously passed as an explicit `undefined` — is the signal. Measured: 1,478 events over 1,170 ms cold with a **maximum gap of 279 ms**, 17 events over 123 ms warm with a maximum gap of 55 ms, and a tail silence of **zero** in both, because `ready` fires last. One number covers both regimes with nothing fitted to either. The number is `DEFAULT_BODY_IDLE_TIMEOUT_MS`, imported rather than restated because it is the same question about the same kind of bytes, and 430x the worst gap measured. `BERNARD_EMBEDDING_IDLE_TIMEOUT_MS` overrides; `0` disables.
      - **Abandoned, not cancelled, and that residue is better here than elsewhere.** `pipeline()` takes no `AbortSignal`, so the race is all there is and the background load keeps running. transformers.js writes each file only once it has the whole buffer, so an interrupted load leaves completed files and no partial one — verified by killing a cold load mid-download and loading again from the same cache, which reused the three finished files and re-fetched only the missing model. So "retrying continues it" is literally true at file granularity, and the message says so.
      - **An abandoned load is NOT cached.** `cachedProvider = null` was permanent, which is right for a library that will not import — a property of the install — and catastrophic for a load that went quiet: one bad minute would leave a process that can never embed again, days of it for the cron daemon and the applet host. The shared slot is cleared instead.
      - **The load is shared between concurrent callers now, which it was not.** The cache held the RESULT, assigned after the await, so two callers both saw `undefined` and both loaded. Measured: two `pipeline()` calls against a cold cache emit eight `download` events for four files and return two different objects — transformers.js dedupes nothing — so a pair of concurrent dispatches fetched 46 MB instead of 23. Four dispatches run concurrently by default and each one's RAG search awaits this. Sharing also decides where the deadline belongs: on the LOAD, so every waiter gets the same verdict, because the load really did go quiet for all of them.
      - **The caller is told WHICH failure it was.** `getEmbeddingProvider` answers `null` for a broken install and for a cut-off download, whose remedies are opposite, and `knowledge` reported "the embedding model is unavailable" for both. `embeddingUnavailableReason()` is the shape `RAGStore.retrievalDisabledReason` already uses — state rather than a print, since this is reachable from a background pass while Ink owns the screen — and deliberately **not** latched, unlike that one: a model mismatch cannot change within a process and an abandoned download can succeed on the next call.
      - **Completeness is now a sweep, not an invariant**, and that is the honest status. Every built-in reaching the network does so through `web.ts`, `web-search.ts`, MCP, the provider clients or `getEmbeddingProvider` — checked by walking `src/tools/` for `fetch` and for a dynamic import. Nothing mechanical stops a sixth arriving unbounded: "does this tool have a bound" is not decidable from the registry the way `meta-coverage.test.ts`'s checks are.
  - **The busy signal is the WIDEST bracket available, and the first cut's was not.** `runTracked` sits inside `runOrdered`, which sits after both permission gates, so a dispatch parked on a `confirmAction` prompt had no finished step **and** a zero count: measured, the guard killed it at the budget with the prompt still on screen and `execute` never entered — a person not having answered yet, read as a wedged provider. The streaming branch never had that window, because `inFlightTools` counts the `tool-call` PART, which the SDK emits before `execute` is entered. So the two branches' busy signals are not an equivalent substitution, and `in-flight.ts` now carries **two** registries rather than one field: the call list keeps the narrow bracket `pendingCallNotice` needs (a read parked on the write barrier must not out-rank the write it waits on — #594's rule), and a per-dispatch **wrapper-depth counter** takes the wide one. `augmentTools` applies that outer bracket as a **post-pass over the built registry**, after both branches, so neither can be the one that forgets it and a third branch would inherit it; in-body it would have re-indented ~150 lines of the hottest path in the product for a two-line concern. The depth key is deleted at zero, because a dispatch id is never reused and the cron daemon stays up for days.
  - **The busy signal comes from the tool registry, keyed on the dispatch id** (`inFlightForDispatch`, `src/tools/in-flight.ts`). `augmentTools` brackets every tool call in every dispatch — `runAgent` has exactly one caller, `runDefinition`, which always augments — and `runWithDispatchId` survives into `tool.execute`, measured rather than assumed. Keying on the dispatch is what makes the recursion work: a parent blocked on `subagent` pauses on its OWN tool while the child's tools belong to the child's clock. Counted globally, one busy dispatch would silence every other dispatch's guard for as long as it ran, and four run concurrently by default. Cost, measured: a `Map` lookup per watchdog tick; 0.31 µs per tool call for the outer bracket; and 1.75 µs of fixed per-dispatch overhead for the chained controller and the `unref`ed interval — all beside a dispatch whose MCP connect alone is 1.1–1.6 s.
  - **No timestamp is needed beside the count, and that is a measured fact about the SDK.** `onStepFinish` fires immediately after the last tool of a step resolves (`prepareStep → doGenerate → tool.execute → onStepFinish`, probed against `ai@4.3.19`), so the runner's own progress stamp lands microseconds after the count returns to zero. There is no window in which the clock is both running and stale, which is what lets the guard be a count rather than a per-dispatch activity log with a lifecycle to clean up.
  - **180 s, not the stream guard's 120**, and the difference is what the two measure. A byte resets the stream clock, so it never has to cover a whole generation; this one must cover one model round trip plus, at most, `makeRepairHook`'s single retry — a second full round trip inside the same step. 180 s is twice the 90 s first-byte budget, so a step's model call and a repair can each run to the very edge of a guard that already ships and still not trip this one; the retries the AI SDK _does_ make cost almost nothing here, since a 429 or a 5xx answers immediately and the slow failures are our own guards, which throw a plain `Error` the SDK does not retry. Measured against the same quantity: **1,605 telemetry records** from the seven sites that build no tool registry at all (`rewriter`, `recall-filter`, `reference-resolver`, `compressor`, `specialist-detector`, `speech-normalizer`, `memory-contradiction`), which is where `latencyMs` IS one round trip and nothing else — p50 4.5 s, p95 9.7 s, p99 13.0 s, max **41.7 s**, exactly one over 30 s and none over 60. The PAC phases are deliberately **not** in that set even though they look like single-shot helpers: `pac-planner` and `pac-critic` both declare `tools()`, so their `latencyMs` can carry tool time and would flatter the ceiling — the first cut of this measurement included them and read 46.4 s. **The residual, stated rather than padded away**: a step spending ~90 s on the model call AND ~90 s on a repair sums to exactly this budget. Two consecutive round trips within a second of a guard that has never been within 48 s of firing is not a case worth widening a default for, and `0` is the off switch for anyone who meets it.
  - **Two knobs rather than one**, though the parse and the `min(configured, override)` are shared. They bound different quantities, so tightening one must not silently tighten the other: below a plausible inter-token pause the stream guard only kills genuinely silent streams, while below a single completion this one kills every dispatch there is.
    - **The same argument applies to the retry ceiling, and the first cut got it wrong.** `AgentSpec.stallTimeoutMs` has one producer — `STALL_RETRY_BUDGET_MS`, 30 s, sized explicitly against _time to first byte_ ("above the 27.4 s worst legitimate TTFB measured across 1,230 instrumented requests"). Three of its four consumers measure that quantity and take the number as given; this one does not, and applying it unscaled collapsed the factor of two the budget rests on — budgeting a whole step at 30 s against a **measured 41.7 s maximum for a single round trip with no repair at all**. A ceiling the measured maximum already exceeds is not a ceiling. `stallCeilingFor` scales it by `STEP_ROUND_TRIPS` on the non-streaming branch, and the field's doc now states its scale, because a number handed to two consumers whose budgets differ by 2x has to say which one it is in. New with this change: before it, `configuredStallMs` was `null` off the streaming branch, so the override reached the transport guards and never a dispatch watchdog.
  - **The tick is self-checking, because this clock measures one process's silence and can be frozen by work that is not this dispatch's.** `shell` is `spawnSync`, which blocks the whole process and is raisable to `MAX_SHELL_TIMEOUT_MS` (10 min) through the timeout offer — a hazard `timeout-offer.ts` already names. Four dispatches run concurrently, so while A sits in a synchronous spawn, sibling B cannot stamp `lastProgressAt`; and on resume the **timers** phase runs before the **poll** phase, so the interval fires with a `sinceProgress` covering the freeze and kills B before B's already-arrived response is delivered. Measured: a 900 ms freeze on a 300 ms budget rejected a dispatch whose `readFile` completion was queued and waiting. A wall-clock jump does it for free — a lid closed for an hour makes every non-streaming dispatch look stalled at the first tick after resume. **Restarting the clock, not crediting the overrun**: the watchdog knows the EXCESS over its period was frozen and cannot know how much of the period before it was, so crediting the excess alone still charges one whole period of somebody else's spawn — the entire budget for any budget at or below the 30 s tick, and measured to still fire at exactly 300 ms with the credit in place. Restarting is the fail-open direction this guard already chose, and the cost is bounded: the only blocking call in the product is `spawnSync`, itself bounded by `shellTimeout`.
  - **The streaming branch is deliberately NOT moved onto the same registry**, even though it would be strictly better there — `runTracked` decrements in a `finally`, so the part-counted fail-open the entry above documents ("a tool-result that never arrives leaves the count above zero") cannot happen. #350's rule: removing a working liveness guard in the same change that adds another doubles the blast radius. Available, not taken.
  - **`phase: 'dispatch'` is its own `ProviderStallInfo` value** rather than reusing `'stream'`, because `stall:recovery:retry` / `:declined` log it and a triage that cannot tell which guard fired cannot tell a wedged SDK await from a silent socket. Recoverability needs no new rule: `producedOutput` is minted `partsSeen > 0` on both branches — always `false` off the streaming one — and the existing correction in the catch widens it with `stepsCompleted`, so a stall at step 0 retries and one at step 7 declines `work-already-done`.
  - **The risk ordering here is the inverse of the usual, which is worth stating.** Cron has `BERNARD_CRON_JOB_TIMEOUT_MS` (30 min), `bernard script` has `--timeout`, an applet action has the action's own budget. So the hole this closes was worst in the **interactive REPL** — the one place a human can actually press Esc — because its sub-agents are the dispatches nothing else bounds.

- `BERNARD_PROVIDER_BODY_IDLE_TIMEOUT_MS` — Body-inactivity cap at the transport layer (#350), default `120000`; `0` or a non-numeric value disables it. Measured **between chunks**, never from request start, and that distinction is the whole point: a fixed deadline cannot tell a model generating steadily for 85 s from a connection that said nothing at all, and every chunk restamps the clock so only the second trips it. Implemented as a `TransformStream` wrapped around `res.body` in `stall-guard.ts` — verified that re-wrapping survives `.clone()`, which #350 names as the risk, since the AI SDK clones responses and breaking it would break every provider call rather than only a stalled one. The controller is errored with our own branded error **before** the socket is torn down, so the consumer sees a stall rather than racing us to a bare `AbortError`. Unlike `BERNARD_STREAM_STALL_TIMEOUT_MS` this covers **every** dispatch — cron, sub-agents, tool wrappers, PAC phases, delegate helpers — because it sits under `fetch` rather than at the `fullStream` abstraction, which closes the asymmetry #350 documents. It needs no `inFlightTools` equivalent for the reason that issue gives: the AI SDK issues its own request per agent step and the body closes before tool execution begins, so at this layer there is no tool-execution silence to pause for. Only `res.ok` responses are guarded — an error body is small and read immediately by the SDK's own error path, so watching it adds a failure mode and protects nothing. `producedOutput` is reported conservatively as "any chunk at all arrived", because a chunk that reached the SDK may already have become a `text-delta` on screen. **The two body guards overlap rather than nest and either may win**: this one is per-request and cannot see across the several HTTP requests one `fullStream` is assembled from; the runner's can, but pauses for tools and exists only on the streaming branch. Both brand their error identically, so recovery does not care which fired. The runner's `inFlightTools` watchdog is deliberately **not** retired here — removing a working liveness guard in the same change that rewrites the layer beneath it doubles the blast radius.
- `BERNARD_EMBEDDING_IDLE_TIMEOUT_MS` — Idle budget for loading the embedding model (#607), default `120000` (`DEFAULT_BODY_IDLE_TIMEOUT_MS`, imported rather than restated); `0` or a non-numeric value disables it. Measured **between signs of progress**, never from the start of the load — see the `BERNARD_DISPATCH_STALL_TIMEOUT_MS` entry's last rung for the measurement, the reason a duration cannot work here, and what happens to a caller whose download is cut off. Bounds `knowledge`, every RAG search, the semantic cache and `bernard facts` alike, because it sits at the layer that knows what is running rather than at the dispatch — #594's argument for putting the MCP deadline in `mcp.ts`.

- **How the transport budgets nest** (#329, #607), outermost first: `BERNARD_DISPATCH_TIMEOUT_MS` (opt-in, whole dispatch, the only one that counts time spent inside tools) → the liveness pair, exactly one of which applies per dispatch — `BERNARD_STREAM_STALL_TIMEOUT_MS` (120 s, silence between bytes of one `fullStream`, streaming dispatches, i.e. the main agent in a mounted REPL) or `BERNARD_DISPATCH_STALL_TIMEOUT_MS` (180 s, silence between step boundaries, every other dispatch), **both paused while that dispatch has a tool of its own in flight** → `BERNARD_PROVIDER_BODY_IDLE_TIMEOUT_MS` (120 s, silence within one HTTP response body, every dispatch) → `BERNARD_PROVIDER_STALL_TIMEOUT_MS` (90 s, wait for that response's headers, every dispatch). The per-call budgets sit **inside** all of these: `BERNARD_MCP_CALL_TIMEOUT_MS` (60 s, one `tools/call`), `BERNARD_EMBEDDING_IDLE_TIMEOUT_MS` (120 s of silence, one embedding-model load — the only one of these that is an inactivity budget rather than a duration, for the reason its entry gives), `PROBE_TIMEOUT_MS` (15 s, `model-validate.ts`), `BERNARD_MCP_CONNECT_TIMEOUT_MS` (15 s), `FETCH_TIMEOUT_MS` (5 s, `catalog.ts`), and `config.shellTimeout` (30 s). Only the three stall guards are recoverable — see the recovery loop below; a dispatch timeout is a wall clock the operator set and retrying past it would defeat what they asked for, which is why `runner.ts` brands the stall arm and not the timeout arm. **The tool pause is what carries the ladder down a rung**: the two liveness budgets stop the clock for the waits that are legitimately unbounded (a person answering `ask_user`, or a permission prompt — the wide bracket that makes the second of those true is `in-flight.ts`'s wrapper-depth counter, not the call list), and every way a dispatch can sit inside a tool **that has a bound at all** is bounded one rung down, including a nested dispatch, which is bounded by its own copy of the same guard. The last built-in bounded by nothing — `getEmbeddingProvider()`'s cold-cache model download — is bounded too since the review pass, by silence rather than by duration; the entry above has the measurement and the reason.
- **A stall is retried, not fatal** (`src/framework/agents/stall-recovery.ts`). Both stall guards brand their error via `markProviderStall` (`error-taxonomy.ts`), and `runWithStallRecovery` wraps the single `runAgent` call at the end of `innerIterate` — the point at which `system` and `messages` are already materialised, so a retry re-sends byte-identical input with no context re-assembly and `recordDispatchContext` records once for all attempts. Three attempts total. **The gate is `producedOutput`**: `OutputSink` is append-only with deliberately no reset, so re-running a dispatch that already emitted a `text-delta` prints a second copy beside the first and the answer visibly stutters. That is not a narrow carve-out — a provider that goes quiet usually does so before saying anything, which is exactly the observed incident (`stepsCompleted: 0`, zero parts) — and it carries the accounting too, since with no step finished no hook ran and there is no usage row to double-count. Known under-count, stated rather than hidden: the dead attempt's prompt tokens _were_ billed and are recorded nowhere; small next to the cache-read rate (49,152 of 49,493 prompt tokens were cache reads in the incident), and the alternative is inventing a usage row for a call that produced no usage report. **Retries get a shorter clock** (`STALL_RETRY_BUDGET_MS`, 30 s) threaded as `AgentSpec.stallTimeoutMs` and applied as `min(configured, override)` everywhere, so it can only shorten and an off switch stays off: three attempts at the full budget is a six-minute spinner, which is a worse product than the bug, while 30 s still clears the 27.4 s worst legitimate TTFB. Backoff is ~1 s then ~3 s with jitter — deliberately small, since the failure already cost a 90–120 s budget. **Retries are silent**; only exhaustion announces, as an `<ErrorPanel>` whose message contains `timed out` so `classifyError` supplies the title and `playbook.user` hint with no new vocabulary. The loop lives in the caller because `AgentSpec`'s own docstring says _"the runner is intentionally policy-free: retry loops … live in the caller"_; the runner only reports which guard fired and whether anything reached the sink. The exhausted error **keeps the original error's name**, so a mid-stream stall still carries `DISPATCH_ABORT_NAME` and the five dispatch boundaries unwind rather than handing the model a stall dressed as a successful tool result. It must never become SDK-retryable (still a plain `Error`, never a `TypeError`), or Bernard's three attempts multiply with the SDK's three into nine requests — the over-billing #308 measured.
- `BERNARD_CRON_JOB_TIMEOUT_MS` — Per-job wall clock for headless cron runs (#326), default `1800000` (30 min); `0` disables. Overridden per job by `CronJob.timeoutMs`. Cron used to call `runDefinition` with **no `abortSignal`** — it had none to give — and nothing in `src/cron/` was a job-level clock (`shellTimeout` is per-tool). Two consequences, the second much worse than the first: `runNonStreaming` skips its defensive abort race entirely when the signal is undefined (`if (!abortSignal) return gen`), so headless runs had _less_ protection than interactive ones; and `Scheduler.executeJob` increments `runningCount`, awaits, and decrements only in `finally`, so a hung job held its slot forever — once `runningCount` reached `maxConcurrent` every later fire went onto `this.queue` and never drained, because `drainQueue` only runs from a completing job's `finally`. One stuck job silently stopped the whole scheduler, with no operator present and the store row reading `lastRunStatus: 'running'` until the next daemon restart's stale sweep. Defaulted rather than opt-in because every job that exists predates the field, and those are exactly the ones that can wedge the scheduler. The abort is re-shaped into a message the taxonomy reads as `timeout`, and **severity is escalated to `critical` at that one site**: `timeout` is `low` in `error-taxonomy.ts`, which is right for an ordinary tool timeout and wrong for a job that was holding a scheduler slot and queueing every later fire behind it. Escalating in the cron runner rather than in the shared table keeps the taxonomy from having to know about cron — `Classification.severity` is documented on the interface as "Drives cron alert severity", and cron is in fact its only live consumer today (the other consumer is the in-thread failure hint added by #353, which colours `category · recovery hint` by severity). Severity and the user-facing alert text are keyed on the same fact and so are resolved together; split across two ternaries, an edit to one reads as complete. The scheduler carries a second, longer backstop (`SLOT_RELEASE_GRACE_MS`) that releases the slot even when the hang is somewhere the job's own abort cannot reach — the timer starts after `mcpManager.connect()` and the pre-run RAG search, and `mcpManager.close()` runs after it is cleared, so a stdio child ignoring SIGTERM would otherwise still wedge the queue. The two layers answer different questions: the abort stops the _work_, the race guarantees the _slot_ is freed.
- **Child dispatch cancellation (#327, #351)** — `subagent`, `specialist-run`, `delegate-dispatch`, `task` and `tool-wrapper-run` each wrap their `runDefinition` call in a catch-all that shapes the error into a tool result. That is right for a work failure — a failed MCP call is a legitimate tool result the model should see, and stringifying it preserves the useful behaviour where a model recovers from a failed sub-task on its own — and wrong for a cancellation, which arrives at the parent as a _successful_ tool result it reads as data and loops on. Most visibly, a user's Esc during a child dispatch became `Sub-agent failed: Aborted` while the parent kept running until its own signal tripped. Note there are **five** such boundaries: the first pass patched three, and the two it missed (`task`, `tool-wrapper-run`) both pass `abortSignal` too — an identical two-line paste missing 40% of the sites is the signature of a fix that wants to be one layer down. **Since #351 that layer exists**: `runDispatchOrFail(fn, onFailure)` (`src/tools/dispatch-failure.ts`) owns the try/catch, the re-throw and the `err instanceof Error ? err.message : String(err)` extraction, and delegates only the shaping; the five sites read `withSlot(() => runDispatchOrFail(work, shape), exhausted)`. `onFailure` is a callback for the same reason `withSlot`'s `onExhausted` is: three sites owe the model a string whose `Error:` prefix `detectResultFailure` reads (#364), `task` a `ToolResult` envelope, `tool-wrapper-run` a `WrapperResult` — shapes their own contracts dictate and tests assert verbatim, converging only in that `error-taxonomy.ts` classifies all of them. It is a sibling module of `agent-pool.ts` rather than part of it: the two compose at every site but answer different questions (slot lifecycle vs. failure shaping), and `agent-pool.ts` is a leaf with nothing behind it but `node:async_hooks`. It does **not** own the try SCOPE — `delegate-dispatch` deliberately protects its tool-registry assembly and PAC self-escalation branch too, so each site passes the region it means to protect. The guard against a sixth boundary omitting it is behavioural, not structural: a call site can still hand-roll a catch and typecheck, so each of the five pins the re-throw with its own cancellation test (removing the re-throw from the combinator fails all five). #351 also deleted `framework/dispatch.ts`'s `createDispatchTool` — a zero-caller "shared factory" with no try/catch, no pool handling, no pre-flight guards and no `telemetrySite` passthrough, which two of these files already carried comments explaining why they could not use. `isDispatchCancellation` (`src/error-taxonomy.ts`) is the single predicate all five consult, and it matches on `Error.name` only: a real `AbortError` (the user's signal or a provider-side cancellation), or `DISPATCH_ABORT_NAME`, which the runner stamps on aborts it fired itself (the stall guard, `BERNARD_DISPATCH_TIMEOUT_MS`). **"Any timeout" is deliberately not the rule.** It was, briefly, and an existing test caught it: `new Error('network timeout')` classifies as `timeout`, and the taxonomy itself marks that category `retryable: true` — a provider network blip is exactly the failure a model should be told about and work around, not a reason to unwind the turn. Our own aborts therefore need a distinct **name**, because neither alternative works: not `AbortError`, since the REPL renders nothing for those and the turn would vanish silently; and not the message, since ours and the provider's both say "timed out". `classifyError` alone cannot answer even the `AbortError` half — a `DOMException` named `AbortError` carries the message `"Aborted"`, matching neither `\bcancelled\b` nor `aborted by user`, so it classifies as `unknown`. Re-throwing is safe for the pool because `runHoldingSlot` (#317) releases in a `finally`. The predicate **walks `cause`**, because one of these boundaries can sit inside another and the AI SDK rewrites the error in between: a throw out of `tool.execute` is wrapped in `ToolExecutionError` (`name: 'AI_ToolExecutionError'`) — directly on the non-streaming path, and via an `error` part that `runStreaming` re-throws on the streaming one. Reachable today as main → `agent` → `delegate_<server>`, since sub-agents carry delegate tools; without the walk a cancellation stops propagating after exactly one level — the same bug, one frame up. The walk is depth-bounded rather than `while (cause)`: error chains are built by providers and MCP servers, and a cycle would hang the catch handler. **A provider stall anywhere in the chain is a failure, never a cancellation, and it is checked before the name.** Both kinds of stall carry something that reads as a cancellation: the first-byte guard ends a silent request by aborting its own fetch, so its error's `cause` is the `AbortError` that fetch rejected with; and a stall the runner fires itself — mid-stream, or the non-streaming liveness guard — is named `DISPATCH_ABORT_NAME`, as is the exhausted-retries error wrapping it. Read as cancellations, "xAI never answered" was treated as the user pressing Esc and unwound every dispatch above it, ending the turn where the parent should have been handed a failed tool call. Observed twice in one session: a Gmail helper, two levels down, killed the whole turn. What still unwinds is the user's Esc (an `AbortError` with no stall behind it) and the operator's own wall clock, `BERNARD_DISPATCH_TIMEOUT_MS`, which carries the name and no stall brand.

- `BERNARD_SPECIALIST_RECALL` — Let each specialist remember what it learned from its own work (#501, default **on**; `false`/`0` to opt out). At session close the main agent has always had a pass that extracts facts from its transcript; a specialist got nothing, because its dispatch transcript was discarded — so the one agent that most needs to remember its own mistakes could not. **Reads the reasoning log rather than a new buffer**: every dispatch writes an entry there now, so the transcripts are already durable and already survive the process that produced them; a per-session in-memory buffer would be a second mechanism holding the same bytes and would lose them on a crash. **A third independent gate**, for the reason `consolidateMemory` is a second one: it needs neither a transcript in the payload nor RAG enabled, and hanging it off either would make it silently never run for settings with nothing to do with what a specialist should remember. **One model call per specialist, not four** — `extractDomainFacts` fans out one call per domain over the frozen registry, and telemetry shows four distinct specialists in a single real session, so mirroring that shape would be sixteen extra calls at exit; a specialist's memories are domain-scoped _by definition_, so the fan-out buys nothing. Grouped per specialist rather than per dispatch, so one that ran five times gets one extraction that can see all five. **It WRITES where consolidation proposes**, and the asymmetry is deliberate: consolidation's records are the user's own and shared, so a wrong retirement changes behaviour everywhere and silently, while these are private to one specialist and are deleted with it — and reviewing N specialists' proposals at every startup is a queue nobody drains. The gate is the marker's inclusion CUTOFF rather than the run time, the shape #529 had to correct once, because storing the run time makes the trigger set and the input set exact complements. A note for a specialist that no longer exists is skipped: it would be owned by an id nothing resolves, unreadable the moment it landed and swept by nothing, because the sweep already ran. **The specialists fan out under `Promise.allSettled`**, the shape `extractDomainFacts` already uses for its per-domain calls: they are independent, cheap-tier latency measures p50 4.7 s, so four cost ~19 s in sequence and one round trip in parallel — and this arm otherwise decides how long the detached worker lives. Settled rather than `all`, so one rejected extraction does not discard work its siblings already did in a process nobody is watching. **The transcript is rendered NEWEST-first and stops at the budget**, which fixed two things in one line: the previous `map().join().slice()` built 825 KB to keep 75 KB on a real log — the bound-during-construction rule `truncateResult` (#347) already states — and, worse, the log is oldest-first, so a front slice fed the model the OLDEST 7 of `shell-wrapper`'s 265 runs and discarded the 258 most recent. **The queue IS the work now — no cursor, no clock, no window.** Every dispatch enqueues itself when it finishes (`recordDispatch`, one function rather than two calls at each producer, because a dispatch in the log and not in the queue is one a specialist never learns from silently), so the set to process is exactly the files present and acknowledgement is per item. A failed extraction retries **its own** items: the shared cursor had to retreat behind the oldest failure, which re-did every specialist newer than it — duplicate model calls and duplicate notes on the COMMON path, since `extractSpecialistNotes` fails closed and a timed-out cheap-tier call is indistinguishable from "nothing worth remembering". `renderTranscript` returns the items it used alongside the text, so the runs its 12 KB budget drops come back instead of being marked processed. A deleted specialist's items are acknowledged rather than retried — the owner is never coming back. `SPECIALIST_RECALL_MARKER`, `RECALL_LOG_SCAN`, `readReasoningLogSince` and `readJsonlSince` are all deleted; `readCutoffMarker`/`writeCutoffMarker` stay, because `MEMORY_CONSOLIDATED_MARKER` is a **change detector** over a store rather than a cursor over items and is deliberately not absorbed. **Migration:** an upgrading install starts with an empty queue, so the last pre-upgrade session's dispatches are never extracted from — one-time and silent, and cheaper than back-filling from a log the queue no longer depends on.
  - **Superseded, and kept here because the reasoning is still right one layer down.** The paragraph below describes the cursor this replaced. **The log is bounded.** `rotateReasoningLog` had no production caller anywhere in the tree, so the file grew forever — 6.7 MB / 2,354 entries on a real install — and `readJsonlTail`'s limit bounds the PARSE, not the read, so everything between the marker and the window's start was dropped. `readJsonlSince` reads backwards from EOF in chunks and stops at the caller's cursor, so every dispatch since the last pass is seen however many precede it and nothing older is parsed. **An entry whose `ts` will not parse is KEPT**: on an append-only log the only thing worse than re-reading one is not reading it. The first run has no marker and keeps the tail — reading a whole rotated log to extract from a session that already ended is paying for history nobody asked for.
  - **`reachedCursor` comes back from the reader, because a caller cannot infer it.** Every entry `readJsonlSince` returns is newer than the cursor BY CONSTRUCTION, so the obvious truncation test — "is the oldest one already newer than the marker?" — is a **tautology** that fires on every ordinary session. The first cut shipped exactly that, which would have turned the one loss signal into noise. `false` means the scan ran out of file or out of ceiling without meeting the cursor: rotation evicted records, or there are more than one pass will carry.
  - **An exact reader with an unconditional commit still loses work.** `extractSpecialistNotes` fails closed, so a timed-out cheap-tier call came back indistinguishable from "nothing worth remembering" — and the marker then advanced past those dispatches, which are never seen again. That is the same failure the cursor was introduced to stop, moved onto the COMMON path. It returns `{notes, failed}` now, and the marker retreats to just before the oldest entry of every failed group: at-least-once, with "nothing to learn" still advancing so a quiet session does not re-pay forever.
  - **`appendJsonlBounded` (`jsonl.ts`) is the pairing, because the hand-written form was measured at 25.7 ms per dispatch.** Three loggers had each written `appendJsonl` + `rotateJsonlByCount` by hand — and rotation pins a file _at_ `keep` rows, which is exactly the size that forces a full read-split-rewrite on the next append. On the real 6.7 MB log that is a 5.4 MB read plus a 5.4 MB write, synchronously, inside the awaited return of every dispatch; Ink throttles rendering at 32 ms, so one log write ate most of a frame. The two pre-existing callers never felt it because their rows are ~250 bytes against the reasoning log's ~2.8 KB — which is precisely why copying their shape transferred the code and not the cost. Amortising at 25% slack measures **0.020 ms** against 6.32 ms on the same file (316×), one rewrite per `keep / 4` appends, and the file bounded within 25% of what the caller asked for. `rotateJsonlByCount` also moved to `atomicWriteFileSyncUnique`, which `fs-utils.ts` prescribes wherever two processes can write one file — this log has four writers.
  - **A count budget is only honest if EVERY field is capped.** The first cut capped four of five, leaving `toolCalls[].args` out on the argument that the renderer bounds it — a _prompt_ bound, not a disk one. Measured, `args` is where the mass is: the largest real one is a 15.7 KB `shell` invocation and a `file_write` carries a whole file. `boundValue` (lifted out of `cron-step-recorder.ts`, which had the only copy) handles the two fields of unknown shape, so a value that fits keeps its structure and stays replayable while an over-budget one comes back marked. `specialist-recall:window-truncated` stays, because rotation can still evict between two passes and that is bounded and honest rather than silent.
  - **Two bugs the pass shipped with.** `ReasoningLogEntry.error` has existed since the log did and reached the prompt **nowhere** — only the coarse `status` label — so the pass whose first instruction is "a mistake it made and what the correct approach turned out to be" was shown that something failed and never what. And `specialist-run.ts` called `captureToolCalls` with **no tool registry**, which is what that function reads `ToolMeta.sensitiveArgs` / `sensitiveResult` from — so a persona's `shell` command or an MCP tool's credentials went verbatim into the log, and since #501 those bytes are read back and fed to a model. The wrapper path passes its own `childTools` and was never affected. Two things make it a closed class rather than a fixed instance: the parameter is **required**, so a third dispatch path that forgets is a compile error instead of a silent leak; and what `RunDefinitionResult` publishes is a `ToolMetaLookup`, not the registry — the first cut exposed `rawTools`, which is every tool's `execute` with the deny, write-scope and confirm gates stripped off, on the public result of every dispatch in the product, so one consumer could read two booleans. Same rule as the `toolBytes: () => number` accessor beside it: publish the answer, not the thing that can answer. **Known limit, stated rather than fixed:** a persona that fails SEMANTICALLY returns a normal string and is logged `status: 'ok'` — the `Error:`-prefix inference is all that path has.

- `BERNARD_MCP_RESULT_SHAPING` — Structure-aware MCP result cap (#297, #458): `off | cap` (default `cap`). `cap` bounds an over-budget MCP tool result before it enters an agent's context so a large list/body doesn't re-bill on every subsequent step. Small results (≤ budget) pass through untouched, by identity. Applied in the `MCPManager.getTools()` execute wrapper right after `normalizeToolResult`. `summarize` (LLM digest on the cheap tier) is a documented follow-up, not wired.
  - **The structure-aware paths were dead for the shape that actually arrives (#458).** A `CallToolResult` is `{content: [{type:'text', text:'<json>'}], isError?}` — the payload is JSON encoded **as a string**, so there was no structure to walk: the envelope is a plain object whose only array is `content`, `capArray` will not drop a sole leading element, and the whole thing fell to the `{_truncated, preview}` wrapper, whose preview was a **front slice**. For a Gmail `messages.get?format=full` the front is SMTP noise (`Received`, `ARC-Seal`, `DKIM-Signature`) and `From`/`To`/`Cc`/`Subject` sit after it. Measured on a real-shaped payload at the 8,000-char budget: 27,233 chars in, 4,344 kept, **no `Cc`**. Bernard reported that a CC it had sent was dropped, **sent a duplicate email to fix it**, and reported it dropped again. The failure is silent and indistinguishable from a real answer — a truncated body reads as a truncated body, a truncated header block reads as a message with no CC.
  - **Parsing `content[].text` was necessary and NOT sufficient**, which is the part worth knowing before "improving" this again. The same payload **already parsed** measured 26,882 → 4,182, still no `Cc`: `largestArrayKey` is **top-level only**, and a Gmail message keeps its bulk nested (`payload.parts[].body.data`, a base64 blob) and its identifying fields nested too (`payload.headers`). The top-level scan finds `labelIds`, saves nothing, and falls through. Head-and-tail preview alone does not fix it either — the `Cc` sits ~6 KB into a 27 KB payload, neither head nor tail.
  - **So the order is: unwrap → existing top-level paths → recursive shrink → wrapper.** `shrinkLargest` walks the tree for every array/long-string slot, sorts by size, and spends the **largest** one first, repeatedly. That ordering is what protects the small identifying fields: the blob is orders of magnitude bigger than any header, so it is consumed long before a header is reached. It is a property of these payloads, not a guarantee — hence the `null` return that hands anything it cannot bound back to the wrapper rather than returning it over budget. Result: 7,982 chars kept, all 34 headers intact. The wrapper is now the **last** resort and keeps head **and** tail.
  - **Re-emitting the envelope, rather than returning the bare payload,** is what keeps `detectResultFailure`'s `mcpFailureText` walk working and `isError` meaningful downstream (#363). Per-entry fields are preserved (`{...entry}`), because a real server flags `isError` on a `content` entry as well as on the envelope. Only a **single** text entry is unwrapped: a multi-entry result is several values whose relative importance this module cannot know, and shaping them from one object would have to invent that ordering. Non-JSON text is left alone — plenty of servers return prose.
  - **Two costs, stated rather than discovered.** The `JSON.parse`/`JSON.stringify` round trip is **lossy** — insignificant whitespace and number formatting are gone, and an integer past `Number.MAX_SAFE_INTEGER` loses precision; it is paid only by results that were going to be truncated anyway. And shrinking a base64 blob leaves a **non-decodable** string carrying a marker — more honest than silently losing `Cc`, but not a body a caller can decode.
  - **The budget is re-measured on the ENCODED envelope.** The shaped payload goes back as a JSON string _value_, so its quotes and backslashes are escaped a second time — the same ~2x inflation `truncatedWrapper` already documents. Budgeting the payload alone let the envelope overshoot (measured 8,294 against a 8,000 cap); the loop re-budgets by the observed overshoot ratio and converges in one or two passes.
  - **The feasibility bail is budgeted against the passes that are left.** One pass shrinks exactly one slot, so the most still reclaimable is the sum over the largest `MAX_SHRINK_PASSES - pass` slots — and the slot list is sorted descending, so that slice IS the best case. Summing _every_ slot instead answers a question nobody asked: 30 fields of 200 KB can clear a 6 MB gap in principle and cannot in 24 passes, so the shrink ran all 24, re-serialising a 6 MB tree each time, and returned `null` to the wrapper that was the answer from the start — **317 ms of pure loss**, against 66 ms with the bail, on the browser accessibility-snapshot shape this file already names as reachable. Outcome-identical: across a sweep over the 24-pass boundary only the kept LENGTH changes, never whether a payload shrinks or wraps. Still an over-estimate (nested slots are counted twice), which is the safe direction — it can decline to bail on something it might have shrunk, never bail on something it could have. `MIN_SHRINK_SLOT` alone catches neither case: 500 eighty-character fields each clear the floor individually and only their sum does not (11.8 ms → 1.3 ms).
  - **The top-level scans are a fast path, not distinct coverage**, and the comment says so because the mis-statement is what invites a fourth special case. Measured, the recursion **subsumes** the object path and the large-element array path; the one shape it cannot reach is a bare root array of small elements, because `collectSlots` visits root's children and never root itself. They are kept because they land in one exact-budget pass where the recursion pays a `structuredClone` and a re-serialise per pass on inputs that can be megabytes — and for their honest strategy labels.
  - **Never throwing is an invariant, so the clone is guarded too.** `JSON.stringify` DROPS a function silently, so a result carrying one measures finite, clears the cycle guard and makes `structuredClone` raise `DataCloneError`. `mcp.ts` calls the shaper inside the try whose catch reconnects the server, so a throw is indistinguishable from a failed tool call and tears down a healthy stdio connection — the reason `truncatedWrapper` and the observer each carry a catch, and the reason the new hot path needed one.
  - **Single-entry unwrap is conservative, not principled.** The rule the code actually wants is "if a text entry carries JSON, unwrap it", which has no arity in it — unwrapping each entry needs a budget split, not the ordering the restriction is usually justified by. Single-entry is what Gmail and the common servers emit. A multi-entry result is still bounded by the ordinary paths and nothing is lost unnamed, but its inner payload is cut as opaque text, so "never severs JSON mid-token" holds for the envelope and not for that inner value.
  - **Termination and untrusted input.** A cyclic value measures `Infinity`, so the shrink refuses it up front and lets the wrapper's own `catch` handle it; the walk is depth-bounded and the pass count is capped. `__proto__` is never taken as a slot: MCP output is untrusted and `JSON.parse` — which the unwrap now runs on a server's own text — makes `__proto__` a genuine own property, unlike an object literal. Benign today (the own property shadows the inherited setter), which is exactly why it is refused rather than relied on. Shaping is non-mutating; the under-budget path returns the caller's value by identity.
- `BERNARD_MCP_RESULT_SHAPING_MAX_CHARS` — Character budget for a `cap`ped MCP result (default 8000; generous so only genuinely large payloads are bounded).
- `BERNARD_MAX_PERSISTENT_MEMORY_CHARS` — Character budget for the whole `<persistent_memory>` context section (#307), default `24000` (≈6k tokens, ~3.5x its current size). Whole entries are dropped past the budget — never truncated mid-entry, since a fact that stops mid-sentence still reads as authoritative — and a visible `### (truncated)` note plus a `context:memory-capped` debug line say so. Read once at module load from `process.env` rather than `BernardConfig`, matching `BERNARD_SUBAGENT_RESULT_MAX_CHARS`: `context-message.ts` is deliberately a pure function of its inputs, which is what keeps the byte-stable-prefix reasoning tractable. Configurable because memory is the most user-curated content in the prompt — a large hand-written set should not hit a wall the user cannot raise.
- `BERNARD_MAX_SPECIALIST_ROSTER_CHARS` — Character budget for the whole `<specialists>` context section, default `12000` (≈3k tokens). Its sibling above bounds curated memory; this bounds the **generated** roster, and the two differ in what makes dropping safe. The roster sits in the volatile context message — after the prompt-cache breakpoint — so it is re-billed on every **step**, not once per turn, and it had no cap of any kind: measured on a real 45-record install it was **9,993 chars (~2,498 tokens)**, and `MAX_SPECIALISTS` was the only thing bounding it. Raising that cap to 100 would have taken it to ~4,600 tokens per step with nothing to stop it, which is why the two changed together — with entries bounded, the record count and the context cost become independent. Whole entries are dropped, ranked by the match score `matchSpecialists` already computed for the turn, so the survivors are the ones the turn could plausibly use; `matchSpecialists` only returns scores ≥ 0.4, so on most turns nothing is ranked and the order falls through to smallest-first exactly as `packMemory` does with no `memoryPriority`. **Dropping is safe here in a way it is not for memory**, which is what licenses the tighter budget: a dropped memory is invisible to the agent, while a dropped roster entry is still reachable through `specialist { action: 'list' }` — and the truncation note says so, because an agent that does not know the list was cut has no reason to go looking. The note is a **count**, not a key list, unlike `<persistent_memory>`'s: the dropped entries are the least relevant by construction, and naming them would spend the budget the drop just reclaimed.
- `BERNARD_COST_GUARDRAIL_TOKENS` — Provider-aware cost guardrail (#298, milestone 9): token threshold (default `60000`; `0` disables). Once per session, when the active provider has **no prompt-cache discount** (`providerSupportsPromptCache` is false → custom endpoints; `anthropic`, `openai` and `xai` all cache, the last because every xAI catalog entry publishes a `cacheReadPerMTok` rate) and a completed turn's main-agent prefix (`spinnerStats.latestPromptTokens`) exceeds the threshold, the REPL flashes a one-time toast that the prefix is being re-billed at full price every step (suggesting delegation or a caching provider). Pure decision in `src/cost-guardrail.ts` (`noPromptCacheHint`); latched via a session ref in `App.tsx`. `cacheReadTokens` is already captured per step and inspectable via `bernard usage`.
- `BERNARD_ASCII_OUTBOUND` — Fold typographic characters to their ASCII equivalents in the **prose arguments of emitting MCP tools** on the way out (default **on** since #442; `false`/`0` disables). Em/en dash → `-`, curly quotes → `'`/`"`, ellipsis → `...`, NBSP → space, bullets → `*`. Accented letters, CJK, emoji and currency signs are deliberately **not** folded — they break in a naive consumer exactly the same way, but folding them destroys meaning rather than normalizing it, and `é` cannot become `e` on Bernard's initiative.
  - **It shipped folding every argument, that default was reversed, and #442 is what put it back — narrowed.** The blanket fold was wrong because an MCP argument is not reliably prose and `mcp.ts` cannot tell: the schema belongs to the server. Measured, folding corrupts a JSON document into one that no longer parses (`"q":"“x”"` → `"q":""x""`), turns `‹note›` into real angle brackets, rewrites a URL or a path so it addresses something else, changes an ellipsis in a regex from a literal into "any three characters", and breaks a `browser-control`/`playwright` selector written against real page copy, which routinely uses a curly apostrophe.
  - **The deciding argument is the fold's own exclusion principle.** `file_write` is excluded because "folding an em dash out of a document the user asked for is corruption, not normalization" — and a filesystem MCP server's `write_file`, or Notion, or a Gmail body, is that same operation through a different door. The boundary was drawn around the implementation rather than the operation. The mojibake fix stands on its other two legs: the sender (the Gmail server now RFC 2047-encodes its headers) and the reader (the CP1252 repair). That entry then named the way back — _"a narrowing to prose-shaped arguments — per-tool opt-in, or driven by the JSON-Schema description"_ — and **`src/mcp-prose-args.ts` is that narrowing**, which is what made default-off a worse answer than a narrow default-on: #442 is a live, recurring defect, and a mitigation nobody enables mitigates nothing.
  - **Why it exists.** A Gmail MCP server wrote raw UTF-8 into a `Subject:` header, where RFC 5322 requires US-ASCII, so a plain em dash arrived as `Ã¢Â€Â”` — two UTF-8-to-CP1252 round trips, one per hop, and it compounds (a thread sent and read back repeatedly reached FOUR generations). That server was fixed; the next one cannot be, so Bernard hands it nothing that can break.
  - **Two gates and a value guard, and the fold is nothing without all three (#442).** (1) The TOOL must emit — `emitsProse` is `!isReadOnlyMCPToolName && hasEmitVerb`, reused rather than re-derived, and that predicate's own docstring is the argument: _"a message is sent, a calendar event is created, a row is appended — each repeat is a new artefact somebody receives"_, which is exactly the population whose text lands in front of a human through a transport we do not control. `write_file` and `edit_file` carry write verbs and NOT emit verbs, so they are ineligible by construction. **It does NOT exclude "a filesystem server", and an earlier version of this line said it did**: `create` and `add` are emit verbs, so `create_file`, `create_note`, `create_page`, `create_document` and `add_note` all pass this gate — measured. What stands between a document store and a rewritten document is (2), not (1), and getting that backwards makes the allowlist read as belt-and-braces. The conjunct with the read test is load-bearing for a different population than it looks: `EMIT_VERBS` is not a subset of `WRITE_VERBS`, so `get_email` / `search_email` are READS carrying an emit verb, and `hasEmitVerb` alone would fold a search term. (2) The ARGUMENT must be named in `PROSE_ARGS`: `subject`, `body`, `text`, `message`, `description`, `summary`, each with its reason on the row. An allowlist, so a new argument on a new server is not folded until somebody declares it; the failure directions are wildly asymmetric, a miss costs one em dash and a false positive silently rewrites data. `content` and `title` are deliberately absent and the table says why — a filesystem `create_file(path, content)` DOES emit, and a page title is an identifier as often as a sentence. So a `create_note(title, body)` server folds only `body`, which is a judgement rather than an oversight (a note body is prose somebody reads); a store whose `body` is a document needs a per-server declaration, not a wider verb set. (3) The VALUE must be prose: a body that parses as a JSON object or array, or that is nothing but a URL, is refused even under a declared name, because both are decidable and both are on the measured corruption list.
  - **Completeness is pinned in both directions**, the `APPLET_COLOR_TOKENS` shape. `mcp-prose-args.test.ts` drives a case table through the real fold and then asserts (a) every `PROSE_ARGS` entry appears in a case that actually folds — record → cases, so an entry added with no case fails; (b) every folding case names an argument in `PROSE_ARGS` — cases → record, which is the direction the mistake is made in, since someone widens the walk and writes a case to match; and (c) the measured hazards (`url`, `path`, `selector`, `xpath`, `pattern`, `query`, `content`, `title`) are absent from the table, because their refusal is by omission and nothing in the code says they are dangerous.
  - **`emitsProse` and `ToolMeta.nonIdempotent` are the same expression, and that has a consequence.** Both are `!isRead && hasEmitVerb`, because they are the same question asked twice. So every tool whose arguments the fold touches is also a tool #594 refuses to retry, which makes the fold on `mcp.ts`'s reconnect path provably a no-op — `mcp.test.ts` explains an absent test by it, and `mcp-prose-args.test.ts` pins the coincidence so a later divergence fails a test rather than silently reopening that gap.
  - **Known limit, stated because it is the one thing the guard cannot see:** a URL _embedded inside_ prose is folded along with the prose around it, so a path segment carrying an en dash is rewritten. Nothing short of parsing the body catches that, and a body is prose by declaration.
  - **MCP arguments only, and that scope is the decision.** This is the boundary where text crosses into a third-party process with unknown encoding discipline. `file_write` / `file_edit_lines` are excluded because folding an em dash out of a document the user asked for is corruption, not normalization; applet HTML is excluded because Bernard's own host serves it with `charset=utf-8`; the `shell` command string is excluded because it round-trips losslessly (measured) and folding could change the meaning of a `sed` or `jq` script. `augmentTools` is the tempting single chokepoint and is the wrong one precisely because it cannot tell those cases apart.

## Tool-Wrapper Specialists

Specialists have a `kind` field: `persona` (default, historic behavior), `tool-wrapper` (fronts a concrete tool or CLI with OS-aware examples and strict JSON output), or `meta` (operates on other specialists).

- **`tool_wrapper_run`** — Dispatch tool that the main agent uses to invoke tool-wrapper or meta specialists. Returns strict JSON `{status, result, error?, reasoning?}`. Isolates tools by `targetTools` so e.g. `shell-wrapper` cannot call `web_read`.
- **`web_search`** — Provider chain (Brave → Tavily → DuckDuckGo scrape); returns `[{title,url,snippet}]`. Used by `web-wrapper` and `specialist-creator`.
- **Bundled specialists** seeded on first run into `specialists/`: `shell-wrapper`, `file-wrapper`, `web-wrapper`, `correction-agent`, `specialist-creator`, `mcp-manager`. They are **protected** (see `src/specialist-authority.ts`): non-deletable, definition non-editable, and not enable/disable-toggleable — only the correction flow may append learned examples. `.seeded-v1` (+ per-file `.seeded-<id>`) markers prevent re-seeding.
- **Correction flow**: when `tool_wrapper_run` returns `status: 'error'`, the error is classified via `src/error-taxonomy.ts`; only **correctable** failures (call-shape mistakes: `invalid_args`, `exec_failed`, `not_found` in shell context) are enqueued onto the correction queue (`src/correction-queue.ts`). Environmental failures (HTTP 404, `rate_limit`, `auth`, `pool_exhausted`, `parse_failed`, etc.) are refused at the boundary and never become items. At REPL shutdown the `correction-agent` proposes a fix and emits `proposedGoodCall: {specialistId, input}` alongside `applied: true`; the orchestrator (`src/correction.ts`) verifies the **captured** envelope rather than re-executing — the agent's own validation step already ran the call once, and a second run would double any side effects. Good/bad examples are capped at 10 each, oldest drops.
  - **It was a per-item store with the three defects a queue exists to prevent**, and all three are now structural. **No retry**: a provider timeout or an exhausted pool was written as `invalid` and never looked at again — an environmental failure recorded as a verdict on the candidate; it goes back on the queue now and parks after a bounded number of tries. **No retention**: `pruneOld` existed on two of the four candidate stores and not this one, so terminal rows accumulated for the life of the install and every `listPending()` read and parsed all of them. **Newest-first**: `list()` sorted descending and the drain took the first five, so with six pending the oldest starved permanently — `claim` is oldest-first.
  - **The four terminal statuses went with it, deliberately.** `applied` is durable on the specialist record, so there is no row to keep; `dismissed` was only ever set by `dismissNonCorrectable`, which had no production caller; and `rejected`/`invalid` are what `parked/` is for — bounded, inspectable, and out of the working set. A DECLINE is acknowledged rather than retried: the agent validated the fix and chose not to commit, which is a decision, and asking again puts the same question to the same model.
- **Organic tool discovery**: the `specialist-creator` meta-agent researches unknown tools via `shell` (man/--help), `web_search`, and `web_read`, drafts a new tool-wrapper, validates it with `tool_wrapper_run`, and only then commits. Invoke via `tool_wrapper_run { specialistId: 'specialist-creator', input: 'create a specialist for jq' }`.
- **`targetTools` scopes every kind, not just wrappers (#507).** `specialistDefinition.tools` never read the field, so a `persona` dispatched through `specialist_run` received the **entire worker registry** — `shell`, `file_write`, `web_read`, every MCP delegate — whatever its record declared. Worse than a missing feature, because `createSpecialistTool` **rejects** a `tool-wrapper`/`meta` that declares none (`tools/specialist.ts:54-64`) while `action: 'read'` prints `Target tools: …` with **no kind check**, so `/specialists`, the tool's own read output and `agent-builder`'s rules all presented it as a fence. It was dead data shaped like one. `scopeToTargetTools` (`framework/agents/specialist.ts`) now applies `buildChildTools` on the same terms the wrapper path uses.
  - **It covered more than personas, and the filter closes only part of that.** `invocationRefusal` checks only `disabled` and `boundTo`, so `specialist_run` will run a `tool-wrapper` record too — and that record bypassed its own `targetTools` through the same door. The filter fixes the scoping third. **The other two thirds remain, and calling that door "a call that works today" was wrong:** compared against `toolWrapperDefinition`, a wrapper dispatched through `specialistDefinition` also loses `formatExamples` (its whole good/bad few-shot block, i.e. the point of the correction flow), `osPromptBlock()`, `STRUCTURED_OUTPUT_RULES` + `wantStructured` (so no JSON last-step enforcement), and `wrapWrapperResult` / `relabelStepLimit` (so a step-limit cutoff returns an empty **success** rather than `step_limit`). It is a silently degraded run. The honest options are a `kind` check on `invocationRefusal` — whose stated purpose is exactly "one decision about who may invoke this record", and which already owns `disabled` and `boundTo` — or routing a wrapper record to `dispatchToolWrapper`. Neither is done here; recorded on #507 so the remaining degradation is not mistaken for a closed door.
  - **Absent and empty both mean unchanged, and that was settled from records rather than argued.** `buildChildTools` reads `[]` and `undefined` identically (#331) — right for a wrapper, since the creation boundary refuses an unscoped one and the case is unreachable; wrong here, because `targetToolsScopeError` returns `null` for a persona **before** its length check, so `[]` is a value records carry that nobody decided. Measured on a real install: of 30 personas, 28 declare nothing, one declares two real tools and had been receiving everything, and one declares `[]` while its own system prompt says to use the browser-control MCP tools. Honouring that `[]` leaves it running, answering, and answering **badly** — failure as a bad answer rather than an error. So only a non-empty list scopes. **And `[]` is now refused where it is created**, not merely reported: `targetToolsScopeError` rejects it on a persona the same way it already rejects a missing list on a wrapper, which stops the population growing and fixes every surface — `/specialists`, the tool's own `read` output, `agent-builder` — rather than the dispatch alone. The dispatch's `debugLog` is correspondingly a migration aid for records that predate this, not a permanent report. An ABSENT list still means everything the surface allows.
  - **The lookup space is the resolved surface PLUS the raw MCP bag.** With delegation on, `surface.mcpTools` holds only `delegate_<server>` keys while `ctx.mcp.tools` holds raw namespaced names, and **the two share no keys** — which is why `dispatchToolWrapper` passes the raw bag exclusively (`tool-wrapper-run.ts:324-328`). It can afford that because every record reaching it is scoped; here both spellings are live, so both are offered. This widens only what a name may **resolve to**: `buildChildTools` still admits nothing that was not named, so nothing unnamed rides in on the merge.
  - **`plan` / `think` / `evaluate` are added after the filter and so sit outside the scope by construction.** They are reasoning affordances, not capability grants — `plan` writes to a dispatch-scoped `PlanStore`, `think` is a scratchpad, `evaluate` records a verification claim, and none touches the world. They also appear in **zero** `targetTools` lists anywhere (13 bundled records and all 42 on a real install), so no record could name them, and `buildStrategy`'s enforcement loop re-prompts the model to resolve plan steps — which it can only do by calling `plan`. Filtering them would break the strategy this same definition declares.
  - **Which definitions scope by record is an exhaustive table**, the sibling of the one #510 built for retrieval. That table is the answer to "then no definition can forget" — the strongest argument for putting scoping in `runDefinition` instead, which does not survive contact: a runner-level hook would filter `rawTools` **after** `def.tools()` returned and so strip `plan`/`think`/`evaluate`, needing either tool-name knowledge in the runner (exactly what `resolveToolSurface` exists to avoid) or a second `toolScopeExempt` field — two fields for one policy, with one implementor, since `tool-wrapper` scopes through `dispatchToolWrapper` and the other definitions carry no record at all.
  - **The test had to supply its own store.** `_mcp-delegation-fixture.ts` backs `stores.specialists` with `new Proxy({}, { get: () => () => [] })`, so `get(anything)` returns a truthy `[]` whose `targetTools` is `undefined`, and `inputFor` supplies no `specialistId` — every existing case in `tool-surface.test.ts` and `child.mcp-delegation.test.ts` takes the declares-nothing branch and would stay green with the filter deleted. Assertions are on an **exact key set**, never `toContain`, since the bug was extra tools and a containment check cannot fail on presence.

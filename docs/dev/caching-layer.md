## Caching Layer

In-memory TTL caches (#171) cut latency and tokens across three layers. All are opt-in or opt-out via flags — never on by default for write-effecting tools.

- **Tool result cache** (`src/framework/tools/result-cache.ts`): a tool is cacheable only when its `ToolMeta` declares `deterministic: true` and either `sideEffect: 'none'` or `cacheable: true` (the `isCacheable` predicate). Per-tool TTL via `cacheTtlMs`, default 5 min; `cacheTtlMs: 0` = session-lifetime. Keys are stable JSON over the args; secrets in `meta.sensitiveArgs` are redacted before hashing. The cache check runs **after** the read-only block gate (#179) and risk-based confirm gate (#144), so policy guarantees are preserved on hits. Only `status: 'ok'` envelopes are stored, so errors/denies don't poison. Current opt-ins: `time_range`, `time_range_total`.
- **LLM subcall cache** (`src/llm-cache.ts`): standalone module keyed by `{siteName, modelId, providerOptions, system, userContent}` with a 10-min default TTL. Wired at the pure-deterministic call sites: `rewriter`, `reference-resolver`, `specialist-detector`. The `modelId` is pulled from the AI SDK `LanguageModel` so model-mode (#170) re-tiers automatically partition the cache.
- **RAG search cache** (`RAGStore.turnSearchCache` in `src/rag.ts`): per-turn, cleared at the REPL turn boundary (`ragStore?.clearTurnCache()` before `agent.processInput`) and whenever `addFacts` mutates the store. Avoids re-embedding the same query when both the agent and the reference resolver run a RAG lookup in the same turn. Read directly from `process.env.BERNARD_CACHE_ENABLED` so `RAGStore` doesn't carry a config dependency.

Hit/miss telemetry: every layer emits a `debugLog` line — `cache:tool:hit`/`miss`, `cache:llm:hit`/`miss`, `cache:rag:hit`, `cache:semantic:hit`/`miss` — visible with `BERNARD_DEBUG=1`. Global opt-out: `BERNARD_CACHE_ENABLED=false`.

**Provider prompt caching (#269)** is a distinct, lower layer from the application caches above: instead of skipping the call, it discounts repeated _input tokens_ on the call. `src/providers/prompt-cache.ts` marks the main agent's request with Anthropic `cache_control` ephemeral breakpoints — the system string is converted into a leading cached `{role:'system'}` message (which also caches the tool block that precedes it in document order; `@ai-sdk/anthropic@1.2.12` has no tool-level marker), plus a rolling breakpoint on the last stable message before the volatile `<system_provided_context>` block. Two prerequisites keep the cached prefix byte-identical so it actually hits: the per-turn timestamp was moved out of `buildSystemPrompt` into the `<current_datetime>` context section (`src/agent-prompt.ts`, `src/context-message.ts`, scoped to the main agent via `buildMainContextInputs`), and the tool set is session-stable (`evaluate` gated on `isReactPossible(config)` rather than the per-turn `isReactEffective`) — an invariant now pinned by `main.tool-block-stability.test.ts`, which asserts the serialized tool block is byte-identical across differing per-turn policy decisions. The rule is **main-agent-only**: `promptCacheActive` requires `historyMode === 'persistent'`, so `sub` / `task` / `specialist` / `pac-actor` / `cron` / `tool-wrapper` are deliberately not cache-marked (a one-shot dispatch would pay the 1.25x write surcharge for a read that never comes) and are therefore free to carry a reduced tool surface — which is what `createTools({surface:'worker'})` does (#253). Scoped to the built-in `anthropic` provider via `isAnthropicPromptCacheActive`; OpenAI caches automatically (and benefits from the same stable-prefix ordering), xAI/custom ignore the markers. Cache read/write token counts surface via `step.providerMetadata.anthropic.cache{Read,Creation}InputTokens` → the per-turn `SpinnerStats` odometer (`N⚡cached` in the spinner) and the `step:end` debug log. Gated by `BERNARD_PROMPT_CACHE` (default on).

**Semantic response cache (#269, Layer 3)** — `src/semantic-cache.ts`, opt-in via `BERNARD_SEMANTIC_CACHE` (default off). Reuses the local embedding stack (`getEmbeddingProvider`) to answer near-identical read-only Q&A turns from a prior response without a model call. Consulted/populated only for `isPureQuestion` turns with no images and no tool actions; cosine ≥ 0.95, 10-min TTL, 200-entry cap. Fails open when no embedding provider is available.

- **Half an emoji poisons a session, so no request may carry one (`src/framework/well-formed.ts`).** A watcher's observation block was cut at `MAX_OBSERVATION_CHARS` with a bare `.slice`, landing between the halves of a `reactionKey` emoji. A lone surrogate cannot be encoded as UTF-8, xAI answered `400 Bad Request`, and because the message was already in persisted history every later turn re-sent it: **eight consecutive failures over six hours**, each in under a second, and the screen said only "Bad Request" because the provider's own explanation (`APICallError.responseBody`) was discarded. Three layers now, because the first alone is whack-a-mole: the two producers found (`watchers/wake.ts`, `redact.ts`'s `boundedStringify`) cut through `safeCutIndex`; `toWellFormedValue` repairs every lone surrogate to U+FFFD at the request boundary in **both** runner branches and again in `HistoryStore.load`, so a file written before the fix heals on resume; and `providerErrorDetail` appends the provider's reason to the turn error. The guard returns values **by identity** when nothing needs repair — the common case — so the byte-stable prefix the prompt cache relies on is untouched and nothing is copied. U+FFFD is what a UTF-8 encoder must emit for a lone surrogate anyway, so the repair loses nothing the wire could have carried.
- **Mojibake repair reads CP1252, not Latin-1 (`src/text.ts`).** `normalizeToolText` repairs UTF-8 bytes that a consumer decoded as a single-byte code page. For four months it gated on a C1 code point (U+0080–U+009F) — the **Latin-1** signature — and therefore **never once fired on real input**: real-world mojibake is CP1252, which maps those byte positions to printable characters (`0x80` is `€`, `0x94` is `”`, `0x92` is `’`). Measured across this install's session logs, the real sequences contain zero C1 code points, so the repair block was skipped and a bare `.normalize('NFC')` ran. `Buffer.from(s,'latin1')` cannot express the fix either — it truncates each code point to its low byte, so U+20AC becomes `0xAC` — hence the explicit `CP1252_TO_BYTE` map.
  - **The tests were green the whole time, which is the part worth remembering.** `encodeMojibake` synthesized the Latin-1 form, including the case named "the exact observed mojibake example", which did not reproduce the observed bytes. There are now two generators and both forms are covered; a test file with only one is how this recurs.
  - **Detection matches SEQUENCES, not characters**, and that is load-bearing. `€`, `—`, `’` and `…` are ordinary prose — this install holds 952 em dashes and 1045 curly quotes in perfectly correct strings — so a character-level gate would fire on nearly everything, where the old C1 gate was self-limiting by accident. A candidate is a UTF-8 **lead** character followed by the right number of **continuation** characters: `café €5` matches nothing, `â€”` matches.
  - **Neither acceptance gate survived, and the safety argument is elsewhere.** This bullet used to say "the two acceptance gates (no U+FFFD, result must shrink) are unchanged" — both are gone. `TextDecoder(…, {fatal: true})` throws per candidate rather than producing a U+FFFD to notice afterwards, and per-match replacement shrinks by construction, so the shrink check is unreachable (a mutation proved it dead). What carries the safety is `strongMatches` plus `IMPLAUSIBLE`, which refuses a decode landing on an unassigned, private-use or surrogate code point.
  - **Strength is a property of the MATCH, not the string**, and this is the one place it is easy to get catastrophically wrong. The gate shipped as a whole-string boolean, so one strong match licensed replacing every candidate — including the weak two-character ones the gate exists to protect: `"Subject: CafÃ© news — from JOSÉ's car"` became `"… from JOSɒs car"`, with `Ã©` vouching for a name three words away. The pinned adversarial cases all passed, because they pin each string in ISOLATION, and mixed provenance is the normal shape for this data. `src/text.test.ts` now carries a mixed-string table beside the isolated one.
  - **Known gap: leads `Ä`/`Å` are not covered.** Rule 2 matches `Â`/`Ã` — UTF-8 leads `0xC2`/`0xC3`, i.e. U+0080–U+00FF, Latin-1 Supplement and nothing more. It used to claim "most of Latin Extended-A", which is false: that block's leads are `0xC4`/`0xC5`.   - **It iterates**, bounded at `MAX_REPAIR_PASSES = 6`, because the observed worst case is quadruple-stacked. The bound makes `normalizeToolText` **non-idempotent past it** — at depth 7, `f(x)` is still visibly mojibake and `f(f(x))` is clean — which matters because three boundaries call it, so "already normalized" is not a safe assumption anywhere. Within the bound there is no oscillation and no growth (400k random strings over leads, continuations, CP1252 punctuation and ASCII produced zero of either).
  - **Inbound coverage is the fix for "the model emits bad characters".** It mostly does not — but `web_read` and `file_read_lines` were never normalized, so mojibake on a web page entered context verbatim and the model reproduced it faithfully in whatever it wrote next. That is the real explanation for corrupt characters in GitHub issue bodies. `file_edit_lines` is deliberately **not** normalized: it rewrites the whole file, so repairing there would change bytes the user never asked to touch. **That leaves the file half-repaired, and the gap is recorded rather than closed**: the model is shown a repaired line, hands it back edited, and the edit path writes those repaired bytes beside the mojibake on every untouched line — with the `diff` presenting the encoding change as part of the requested edit. Nothing can detect it, since `file_read_lines` returns no hash of what it showed and `old_hash` is computed from raw bytes. Line NUMBERING cannot drift, which was checked: `normalizeToolText` can neither add nor remove a newline.

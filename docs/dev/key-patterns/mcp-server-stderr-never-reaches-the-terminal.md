# MCP server stderr never reaches the terminal.

- **MCP server stderr never reaches the terminal.** `Experimental_StdioMCPTransport` defaults `stderr` to `'inherit'`, so a third-party MCP server's output goes straight to Bernard's terminal, outside Ink — into the alternate screen buffer Ink believes it owns under `BERNARD_FULLSCREEN`, and interleaved with the transcript even inline. Nothing routed it anywhere: connect failures are already reported via `serverStatuses` / `mcp_verify`, so those bytes were pure noise, up to and including a crashing server's stack trace scrolling over the REPL (`@browsermcp/mcp@0.1.3` recurses `server.close` into itself on stdin close — i.e. every time Bernard shuts down — and dumps a `RangeError`). `startConnect` passes `mcpStderrTarget()`, and is the single transport-construction site, so the isolated `verifyMCPServer` probe is covered by the same call. **`'pipe'` is not the fix**: the transport keeps its child private, so nothing can drain the pipe and a chatty server blocks for good once the ~64 KB kernel buffer fills — a hang traded for a cosmetic bug. It must be a real descriptor, which needs no reader. The file itself is minted by `openSessionSidecarFd` (`src/logger.ts`) rather than here: the session id, the directory latch and the retention budget are all owned there, and a caller opening its own file would re-derive the naming convention and then have to be separately remembered by rotation — which is exactly how the first cut of this ended up with a literal `.log` in `rotateSessionLogs` coupled to a filename in `src/mcp.ts` by nothing. Retention is correspondingly per **session**, not per file: `pruneFileGroupsByMtime` (`src/jsonl.ts`) ranks a session's files as one unit, so a new sidecar is covered the day it is added, a sidecar is never retained past the transcript it belongs to, and `MAX_SESSIONS` keeps meaning what it says instead of silently becoming a per-extension budget. **Bounded _within_ a session too, on a clock (#587).** Rotation counts SESSIONS and runs once per process, so a process that never restarts never rotates — the cron daemon and the applet host, which is the population every unbounded thing in this tree hides in. `watchSidecars` installs one `unref`ed interval on the first successful open and `boundSidecar` truncates an over-budget file **in place**. **In place is not a preference.** The child holds the descriptor in `O_APPEND`, so the tmp+rename that `rotateJsonlByCount` and `CronLogStore.rotate` both use bounds nothing — the child keeps writing to the renamed inode, and we are left rotating a file nobody appends to. `ftruncateSync` is the only option that preserves the descriptor, which is why the fd is opened `a+` rather than `a` (`a` is write-only and could not read back its own tail) and why it is deliberately never closed. The test that carries this is the one asserting the child's fd still writes to the bounded file: mutation-checked, a naive rename rotation leaves the size assertion PASSING while the disk fills with an inode nothing can see. **Why a clock rather than an event.** The file is written by a process we do not observe, so every trigger available to us measures _Bernard's_ activity instead: `debugLog` would put an `fstatSync` on the highest-frequency logging call in the tree and still go quiet exactly when the child is loudest (a server we have stopped calling because it is broken is the one dumping stack traces), and checking at open covers a daemon's per-run connect churn while missing the REPL shape entirely — one child, held for days. It costs nothing on any hot path: one `fstatSync` per open sidecar per 30 s, and only in a process that has both debug on and a spawned stdio child. It keeps the **tail**, `CronLogStore.rotate`'s policy, because a sidecar exists to be read after a child misbehaved; it realigns to a line boundary and names the dropped bytes at the head. **Two race windows, accepted and stated rather than claimed closed**, and the descriptor being SHARED is what makes them likelier than one server suggests — `mcpStderrTarget` hands the same fd to every stdio MCP server. A write between the read and the truncate is lost (and is missing from the dropped-bytes count, which is computed from the pre-truncate `fstat`; re-`fstat`ing would narrow that without closing it, for a precision the number still would not have). A write between the truncate and the restore survives but lands before the restored block — which is why the restore is **one** `writeSync` of header+tail rather than two: with two, such a write was stranded BETWEEN them, newest line at the top with half a megabyte of older output after it, measured at index 1 of 262,144. One write narrows the stranding to the header's length and does not close it, because truncate-then-restore cannot be atomic on a descriptor somebody else is appending to. The test injects that append through a second real descriptor after the first restore write, so it reproduces the inversion rather than counting syscalls. Both are bounded by a syscall or two on debug output from which we just deliberately discarded seven eighths. Every other child-process spawn in the repo (`voice-service.ts`, `cron/notify.ts`, `cron/client.ts`, `index.ts`'s rag-worker, `tools/shell.ts`) already passes an explicit `stdio`, so this was the one leak, not an instance of a general one.

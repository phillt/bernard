# A read must not rewrite the store (#533).

- **A read must not rewrite the store (#533).** `RAGStore.search()` ended with `if (capped.length > 0) this.persist()`, and `persist()` is a `JSON.stringify` of the whole embedding array plus a write. Measured on the real store — 3,664 records / 31 MB — **188 ms to serialize**, ~27 ms to write, synchronous, on the turn's critical path, to record an `accessCount++` and a timestamp. End to end that is **225.8 ms → 3.9 ms** per search, measured against the same store before and after. In the REPL the old cost was Ink's render loop and the streaming reply; across this machine's session logs it was 174 searches over 51 sessions, 26 in the busiest single one — about 5.6 s of dead air in one conversation.
  - **#532 is what made it urgent rather than what caused it.** The call count is unchanged; what changed is that retrieval became a declared once-per-dispatch step resolved in `runDefinition`, so a four-way `withSlot` fan-out front-loads four of these at dispatch start.
  - **Only bookkeeping is deferred, and that is checkable rather than asserted.** Every field `bumpAccess` touches is decay metadata: `accessCount`, `lastAccessed` — which has **no reader anywhere in the repo** — and `expiresAt`. Losing an unflushed bump costs at most one TTL extension. `addFacts`, `clear` and `deleteByIds` write CONTENT and stay eager: a crash must not lose a fact, only the note that a fact was useful. `recordAccess` shares the debounce rather than growing a second mechanism — once per turn is defensible on its own, but it writes the same fields for the same reason and should not be the one bookkeeping path still costing a 31 MB rewrite.
  - **The `unref`ed timer and the explicit flush are both required; neither is sufficient.** The timer follows `inbox/watcher.ts` so a pending flush can never be why a process will not exit — which is exactly why it cannot be trusted as the mechanism. `flush()` is public because `persist()` was private with no external caller, so nothing could say "I am about to exit": it is called from the REPL's per-store cleanup loop, from `runHeadless`'s `finally` (the store lives and dies with the run, and a cron daemon runs many and exits between none), and nowhere else. The exit worker needs none — it only calls `addFacts`, which stays eager — and `bernard facts` needs none either, since `deleteByIds`/`clear` are eager and its search path is the non-persisting `searchWithIds`.
  - **The writer set in the issue is wrong and is corrected here.** It names four processes including the applet host and `bernard script`; **neither writes this file** — both dispatch through `apps/dispatch.ts`, which omits `ragQuery` and never constructs the store. The real four are the REPL, the detached exit worker, the cron daemon (per job run) and `bernard facts`.
  - **The temp path was shared, and debouncing widens the window.** `persist()` wrote to a fixed `MEMORIES_FILE + '.tmp'`, so two concurrent persists write one file and rename it twice. It goes through **`fs-utils.atomicWriteFileSyncUnique`**, which is `tools/file.ts`'s own hand-rolled version lifted rather than copied a fifth time — that file had reached the same conclusion independently and its comment named `fs-utils` as the thing to avoid, while the copy in `rag.ts` then omitted the half that matters. **The unlink-on-failure is what makes a unique name safe**: a fixed suffix left one orphan that the next write overwrote, while a unique one leaves a distinct ~31 MB file per failure and `cleanupStaleTemp` sweeps only `.pending-*.json`. The store-wide read-modify-write remains last-writer-wins; that is #516's territory and is not claimed fixed.
  - **The flush state is one object shared by reference, and #511 is why.** A scoped RAG view (`scoped()`) is a shallow clone, so a per-field `dirty` flag is COPIED into it: the view's search marks the view dirty, the exit hooks call `flush()` on the root — whose flag is still false — and the explicit half of "both halves are required" silently stops applying to every fenced dispatch. A copied `flushTimer` is worse: the view's `markDirty` sees the root's live handle, early-returns, and never schedules its own. Holding `{dirty, timer}` in one object that rides the spread by reference makes the interaction unrepresentable rather than remembered, and it is pinned by a test that a view's pending bookkeeping is flushed by the root.

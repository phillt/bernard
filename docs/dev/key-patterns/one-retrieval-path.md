# One retrieval path (#510)

- **One retrieval path (#510)** — "what knowledge does this task need?" had six answers in six files, three of them byte-near-identical copies of the same try/catch around `ctx.rag.search(input.task)` (`sub.ts`, `task.ts`, `specialist.ts`). The fourth, `pac-actor.ts`, still logged its errors under **`'subagent:rag'`** — the copy-paste showing through, since the label was never changed. `AgentDefinition.retrievalQuery` is now the declaration and `resolveRetrieval` (`framework/agents/retrieval.ts`) the resolver, called once per dispatch beside `resolveToolSurface`. Same refactor, same chokepoint, and `run.ts:146-153`'s reasoning transfers unchanged — except that retrieval's version of the failure is quieter: a definition that forgot to search does not error, it answers worse.
  - **The issue's cron acceptance criterion is not achievable as written, and the substitute is better.** It promises _"cron and sub-agents get the enriched query the REPL gets"_ — but `buildRAGQuery`'s inputs are the last two **user turns** plus recent tool context, which a dispatch does not have. With neither, it returns `currentInput.slice(0, DEFAULT_MAX_QUERY_CHARS)`: the **enrichment** is a no-op, though calling the whole call one is wrong — what it still does is bound the query at 1000 characters. What a dispatch DOES have and was throwing away is **`input.context`** — the string the caller wrote precisely to say what the task is about. So `buildRAGQuery` stays main-only because its inputs are main-only, and the dispatch query is task + context, which is strictly more than before.
  - **Absent means no retrieval**, matching the pre-#510 behaviour of every definition that did not search, so omitting the field cannot silently start one. `main` and `cron` declare none **because they already retrieve elsewhere**: `main` searches in the `Agent` class with `applyStickiness`, `provenance.add` and `previousRAGFacts`, all main-only and all invisible to a runner-side search; `cron` searches in `headless.ts`, which deliberately starts it **before** `mcpManager.connect()` so the cold embedding load overlaps a measured ~1.1-1.6 s connect. The merge is `extras.ragResults ?? retrieved` in that order for exactly that reason, and keeping `main` a pass-through is also what stops `buildMainContextMessages` — the **synchronous** preflight estimator called twice in `agent.ts` — desynchronising from the wire payload, which is the trap the issue warns about.
  - **Once per dispatch, not once per iterate — a real behaviour change, and the intended one.** `contextInputs` is called inside `innerIterate`, so a multi-step dispatch re-searched on every LLM call, saved only by `RAGStore.turnSearchCache`, which no headless path ever clears. **Observing it needs a strategy that iterates twice**: a test with one mocked `generateText` passes with retrieval back inside `contextInputs` and proves nothing — the first draft shipped exactly that and the mutation check caught it, which is why the assertion lives in `run.test.ts` with a two-iterate strategy rather than in `subagent.test.ts`.
  - **The dispatch query is bounded, and the bound was never there before.** `sub.ts` called `ctx.rag.search(input.task)` raw and `RAGStore.embedQuery` applies none of its own, so this is not a bound being discarded — it is one that never existed, and appending `input.context` is what makes its absence matter, since `subagent.ts` declares `context: z.string().optional()` with no `.max()`. `MAX_RETRIEVAL_QUERY_CHARS` is a local literal pinned by a test against `DEFAULT_MAX_QUERY_CHARS`, because importing `rag-query.ts` costs an edge to `context.ts` — the edge `token-estimate.ts` exists to refuse — which is the same answer `docs-store.ts`'s `MAX_DOC_CHARS` gets. **Task first, and it is never the part cut:** the embedder truncates at 256 word pieces whatever is sent, so priority order decides what survives, and a task cut in half retrieves for a different question.
  - **Retrieval and tool assembly start together.** They are independent, and awaiting retrieval first put the whole tool-module load strictly behind it — measured, `createTools` costs **144 ms** on a process's first dispatch (the deferred loads #452 exists to recover) against ~10 ms warm for a search and ~230 ms when it persists access metadata. This is the pattern `headless.ts:229` already uses for this exact pair, for the reason it states. `Promise.all` rather than a deferred await, because `def.retrievalQuery(input)` is called outside `resolveRetrieval`'s own try and a throwing thunk would otherwise be an unhandled rejection.
  - **The guard table has three states, not two.** A boolean collapsed two opposite facts into one word: `main` and `cron` DO retrieve — just not here — while `pac-critic` and `tool-wrapper` deliberately go without, and both read `false`. `'runner' | 'input' | 'none'` forces a new definition to say which, and a companion test asserts the partition is exact — a definition either declares `retrievalQuery` or its caller supplies `ragResults`, never both. That fails the day someone gives `main` a `retrievalQuery` thinking its `false` meant "does not retrieve".
  - **`task` keeps its `contextInputs` solely for `includeScratch: false`** — the one thing a careless collapse of the four copies drops, and it had **no test at all** until the mutation check found that removing it changed nothing. Scratch is a scratchpad for the session the caller is in, not for a task delegated out of it.
  - **`pac-critic`'s opt-out survives untouched** and needed no special case: it declares no `retrievalQuery`, so it does not even search, and its `contextInputs: () => null` still short-circuits before the merge. Handing it ambient recalled context is precisely what that opt-out exists to refuse.

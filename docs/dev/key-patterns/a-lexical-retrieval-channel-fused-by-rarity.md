# A lexical retrieval channel, fused by rarity (#526).

- **A lexical retrieval channel, fused by rarity (#526).** `RAGStore.search` was pure cosine over 384-dim MiniLM and there was **no lexical channel anywhere** — `tokenize()` in `specialist-matcher` and `verification-tracker` are stop-word bags for Jaccard matching, not indexes. The LIMIT result (arXiv 2508.21038) is a _dimensional impossibility_ rather than a quality gap: on 50k documents with deliberately trivial queries BM25 scores R@100 **93.6** against 4.8–10.0 for frontier embedders at 3072–4096 dims, and Bernard is at 384. The repo had already written the conclusion — `src/tools/docs.ts` argues that when search arrives it _"should be LEXICAL — over headings and symbol names — not embeddings"_.
  - **`src/lexical.ts` is a pure leaf with no imports at all**, so `rag.ts` acquires no edge and BM25 is testable without a store, an embedder or a filesystem. No new dependency, and deliberately **not** `node:sqlite` FTS5 — that is #516's territory, and coupling to it would make the highest-value retrieval fix wait for the largest build in the milestone.
  - **The tokenizer is the whole value, and reusing the existing one would have defeated it.** `specialist-matcher.tokenize` splits on every non-alphanumeric, so `applet-hosts.json` becomes `applet|hosts|json` and the exact term — the one with maximal IDF, and the only thing this channel can match on — is gone. `lexicalTokens` emits the **whole identifier and its pieces**, so one index serves both query shapes: an exact term matches on the whole, a prose query on the pieces.
  - **The rarity gate is the difference between a strict improvement and a regression, and it was measured.** Ungated, fusing BM25 with cosine recovered both identifier misses **and destroyed paraphrase ranking** — MRR 0.75 → 0.22 on the #524 corpus — because a paraphrase query shares only ordinary words with its answer, so BM25's tail of weak matches took ranks dense retrieval had right. **Sweeping the RRF constant and a channel weight could not separate them**: every setting that helped identifiers hurt paraphrase, and the two best paraphrase settings destroyed long-tail instead. Gating on whether the query names anything _rare_ separates them cleanly, because it is the same property LIMIT is about — a term in essentially one document is exactly the subset a 384-dim space cannot single out, and exactly where IDF is maximal.
  - **The threshold is `df ≤ 1% of the corpus`, and the channel does not engage below 20 records.** Relative rather than absolute because an ordinary word sits at df≈2 in a tiny corpus and df≈2000 in a large one. The floor exists because IDF is a statement about a _population_: on a one-document store every term appears in 100% of it while `df ≤ 1` still calls it rare, so the gate opened on every query and BM25 returned the sole record for anything — including queries cosine had rejected as below threshold. Adding a second document then closed the gate and the result vanished. An existing cache test caught exactly that, asserting that adding a fact cannot REDUCE what a search returns.
  - **`similarity` stays cosine.** It is the scale `threshold` is calibrated on, the scale `applyStickiness` adds its 0.05 boost to and clamps at 1.0, and the number `bernard facts` prints; a fused score there would decalibrate all three silently. Fusion changes which records come back and in what order, and does not redefine the field. **The lexical channel is correspondingly not subject to `threshold`** — that number means nothing on a BM25 score, and applying it would drop every lexical-only hit, which is the entire population this exists to recover.
  - **`scoreAndRank` now takes the query string as well as its embedding.** BM25 works on terms, not vectors, and threading the string to the one place that consumes the corpus is what keeps `search` and `searchWithIds` from drifting into two different rankings. The final re-sort is by **fused position**, not similarity — sorting by similarity there would let the lexical channel decide membership and then throw it away, which is the quiet way this could ship looking correct and doing nothing.
  - **`RRF_K` is 60 and is documented as UNTUNED**, which is what #526 asks for: the 2009 paper says it _"was fixed during a pilot investigation and not altered during subsequent validation"_, Elastic measured k≈20 better, and Bruch et al. found RRF sensitive to its parameters. Once the rarity gate is in place the channel weight stops mattering (1.0 and 0.5 measure identically), so RRF's constant is the only parameter left and it is left at the recognisable default rather than fitted to a ten-query corpus.
  - **Known limitation, named rather than discovered:** `applyStickiness` re-sorts by `similarity`, so on the main agent's legacy retrieval path the fused order is replaced by a cosine order. `recall-filter` — default-on and the primary path — calls `searchWithIds` and never touches stickiness, so it gets the full benefit. Fixing it means giving `RAGSearchResult` a rank field and teaching stickiness to respect it, which belongs with whatever reconsiders stickiness.

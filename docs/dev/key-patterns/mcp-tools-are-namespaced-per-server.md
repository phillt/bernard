# MCP tools are namespaced per server (#413).

- **MCP tools are namespaced per server (#413).** `MCPManager` used to keep one flat `tools` bag plus a parallel `toolName -> server` map, both last-writer-wins, so two servers exporting `browser_click` could not coexist — and the loser did not merely lose priority, it vanished from its own per-server list, because `getServerToolMap()` built that list by **inverting** the collapsed map. Measured on a real four-server config, `playwright` reported 24 tools and kept 17; the seven it lost to `browsermcp` were click, type, hover, navigate, snapshot, select_option and press_key, so `delegate_playwright` was a browser agent that could resize and screenshot but not click or open a URL — advertising in its system prompt exactly the tools it no longer had. Now `serverTools: Map<server, Record<name, tool>>` is the **one authored registry** and everything flat is derived from it by `flattenServerTools`; the flat bag and the per-server map cannot disagree about a key because there is only one place a key is written. Same config after: 62/62, 2/2, 24/24, 12/12, and the flat bag grew from 93 tools to 100.
  - **The join is deleted, not policed.** `dispatchServerDelegate` used to iterate a name list and pull each object out of the flat bag behind an `if (t)`, so any disagreement produced a helper holding only `ask_user` while its prompt still listed the tools — the #305 failure shape. `serverTools` carries the tool **objects**, so `childTools` is a spread with nothing left to mismatch. `flattenServerTools` lives in the pure leaf `src/mcp-names.ts`, not beside `MCPManager`: importing `mcp.ts` for a pure object operation drags `@ai-sdk/mcp`, `node:fs` and the whole `config` chain behind it (it broke `delegate.test.ts` at import time on the first attempt), which is the edge `tool-bytes.ts` and `tool-result-shape.ts` exist to refuse. Both delegation fixtures derive `mcp.tools` through that same function, so a fixture cannot encode a disagreement the real assembler could never produce.
  - **`<sanitizedServer>_<6hex>__<tool>`, and both halves of that are load-bearing.** **Prefix, not suffix**: `isReadOnlyMCPToolName` (`risk.ts`) matches a read verb at any SEGMENT of the tool name, so a suffix would put the server label inside the segmented span and, before #612 widened the match, would have silently reclassified every read-only MCP tool as a write. The classifier strips the namespace itself before segmenting either way — a coupling worth keeping visible rather than a coincidence to lean on. **The hash buys stability, not collision-avoidance**: server names are already unique as `mcp.json` object keys, but their _sanitized_ forms are not (`my.server` and `my-server` both collapse to `my_server`), and the previous answer was a numeric suffix assigned in iteration order — so editing `mcp.json` could renumber a **different** server's key, and that key is persisted in permission grants and tool-profile filenames. `mcpToolName` guarantees ≤ 64 characters (Anthropic and OpenAI enforce that server-side, and neither SDK validates locally, so a violation is a runtime API 400 rather than a startup error) via a three-rung ladder: R0 readable, R1 drops the human label but keeps the hash and the whole tool name, R2 cuts the tool through the middle around a 4-hex hash of the original. Today's worst case is R0 at 54 chars. Risk is classified from the **raw** name kept on a `RegisteredTool` envelope rather than re-derived from the key, because an R2 key ends in the tool's tail, not its verb.
  - **The read/write classification is the SERVER's answer now, and the name is the fallback (#570, #612).** `isReadOnlyMCPToolName` was a guess, and `risk.ts` said so in its own docstring; the blocker was `@ai-sdk/mcp`, whose conversion loop destructured `annotations` and forwarded only `.title`, so `readOnlyHint` never reached the constructed tool. **1.0.82 forwards all four hints to `tool.metadata.annotations`** — verified over a real stdio transport against both versions, where 1.0.21 leaves `tool.metadata` undefined — so the bump is the whole of what unblocked it. `classifyMCPTool` (`risk.ts`) owns the precedence: `readOnlyHint: true` reads, `readOnlyHint: false` **writes even when the name reads like a lookup** (the direction #570 calls the worse of the two, where our own regex silently overrules a server that marked its tool destructive), absent falls back to the name unchanged. It answers `nonIdempotent` from `idempotentHint` the same way, which is where `mcp.ts`'s old `!isRead && hasEmitVerb(raw)` conjunction moved so the next caller cannot recombine it wrongly. **The spec's pessimistic default is deliberately NOT inherited** — an unannotated tool is supposed to be assumed destructive and non-idempotent, and applying that would turn the reconnect retry off for effectively every server in the wild and hand `duplicate-guard.ts` a population it was never measured against.
    - **`destructiveHint` and `openWorldHint` are read by nothing, and the type does not declare them.** `destructiveHint` maps onto `kind: 'dangerous'` → `high` risk → auto-denied headlessly under cron's default posture, so reading it would start failing cron jobs that work today. That is a tightening worth making and a decision of its own; a declarable field with nothing enforcing it is a lie on disk.
    - **The name guess ALSO had to widen, and the annotation does not cover it.** #569 moved the match off a suffix and onto "a read verb at either END"; a server that prefixes its own tools pushes the verb into the MIDDLE, and `google-mcp` does exactly that. Measured, `google_gmail_list_emails`, `google_gmail_list_unread_emails`, `google_gmail_get_email` and `google_calendar_get_events` were all writes, so a watcher refused to poll a Gmail inbox and the user fell back to cron (#612). **That server declares no annotations at all across its 61 tools** — checked in its source — so #570 fixes nothing for the case that reported it, which is why both halves shipped together. The consequence was never only the watcher gate: `google_gmail_get_email` also measured `nonIdempotent: true` and eligible for the outbound typography fold, so Bernard was rewriting a LOOKUP's arguments, which is the harm `mcp-prose-args.ts` names in as many words. Both close from the one classification, because both are ANDed with `!isRead`.
    - **Widening moved the burden onto `WRITE_VERBS`, and what that set can actually do is far narrower than "refuse a write".** Its docstring used to bound itself — "a name with no read verb at either end is already refused … do not treat it as a general vocabulary of writes" — and matching any position widens the population to every co-occurrence wherever the read verb sits. The tempting conclusion is that every mutation verb must therefore be in it, and that is **measurably false**: a mutating tool is named for its mutation, so `merge_pull_request`, `share_file`, `sync_folder` and `send_message` carry no read verb and are refused by ABSENCE — checked for all twenty candidates considered, every one still refused with its verb removed. An entry can only ever fire on a name that CO-OCCURS a read verb, i.e. the compound shape (`github_pr_get_status_and_merge`) and nothing else. **And the co-occurrence shape that exists in the wild is a READ**: `get_X_status`, `list_X_requests`, `get_X_link`, `list_X_keys` is how vendors name lookups, while the compound was found on no real server. So the rule for adding is not "is it a mutation" but "does a real read name co-occur it" — `@zereight/mcp-gitlab` answers yes for `merge` (twenty read tools) and `trigger` (two), and ten verbs were dropped on that test, recovering 22 real reads while leaking none of that server's 104 real write names. Keeping `merge` would have refused a watcher on GitLab merge requests with the same sentence, for the same reason, that #612 is about — this change fixing Gmail and breaking GitLab. Twelve entries remain. **`email` is refused entry permanently**: it is an emit verb, and putting it here makes `google_gmail_get_email` a write, which is #612 again. `risk.test.ts` carries a negative case per entry generated from the declaration in source, the real GitLab names the drop recovered, and the accepted cost — those ten verbs now let their compounds through.
    - **A first-verb-wins rule scores better on real names and was not taken.** Measured against the shipped any-position veto over 107 real names from the five configured servers: identical. Over the realistic set it is wrong on one instead of nine. The one is `github_pr_get_status_and_merge`, where it fails **OPEN** — a compound that mutates, classified read — which is the direction this whole entry refuses everywhere else. Recorded as the trade rather than as a rejected idea, because the names it wins on are the ones the verb drop above already recovers.
    - **A declared write is authoritative at the watcher gate too, and that took a second change.** `watchableToolRefusal` accepted `meta.kind === 'read'` OR the name, so a `readOnlyHint: false` tool called `list_things` would have been waved through by the very guess the annotation exists to replace. It consults `shouldBlockInReadOnly(meta)` — the predicate `risk.ts` already owns for "does this mutate" — rather than a second `kind === 'write'` test, which is also what keeps `inert` falling through to the name exactly as before.
    - **`mcp:classified` says which source decided, once per server per connect.** `{server, tools, readFromServer, idempotencyFromServer, overrideCount, overrides}`, emitted from `namespaceTools` because that is the one function both `connect` and `reconnectServer` pass through, and NOT from `getServerTools`, which runs on every watcher poll and every dispatch. `overrides` names the tools where the server contradicted the guess — the set someone hunting a misclassification is looking for, bounded at ten with the true count beside it. All zeroes is the other useful answer: this server declares nothing, so everything under that line is a guess.
    - **A malformed hint is guarded three times and only one of them can fire, which is worth stating so the other two are not mistaken for coverage.** `readToolAnnotations` type-checks at the boundary, `classifyMCPTool` type-checks at the decision, and `@ai-sdk/mcp@1.0.82` types the hints `z.optional(z.boolean())` so a non-boolean fails `listTools()` before Bernard sees the tool. Only the middle one is observable: measured, replacing the boundary check with a bare cast leaves all 224 tests across the four touched files passing. It is kept because it is what discharges `unknown` honestly — without it the return type needs an `as boolean | undefined` asserting something about untrusted server data that nothing established — and it is recorded as unobservable-by-construction with the condition it rests on asserted elsewhere, the `argSpecsSince` precedent. The first cut of this shipped a test comment claiming the boundary guard changed the `readFromServer` count; it does not, because that count keys on `MCPToolClassification.readSource`, which the DECISION layer sets.
    - **Two vendor workarounds were re-measured and both stay.** `callWithDeadline`'s TIMEOUT race has no replacement at any version — `MCPClient.callTool` hard-codes its request options to `{signal}` and never passes the `timeout` its own `request()` accepts, and 1.0.82 sits on an unanswered `tools/call` indefinitely exactly as 1.0.21 did. The SIGNAL race becomes belt-and-braces rather than load-bearing: 1.0.21 checked `signal.throwIfAborted()` once at entry and then only when a response arrived, so a dead server ignored Esc outright, while 1.0.82 registers a real abort listener and rejected 8,042 ms into an 8,000 ms abort. It is kept because `MCPCallAbandoned.cancelled` is what the retry gate branches on and the SDK's own rejection is an untyped `MCPClientError`. `startConnect`'s manual `Promise.race` + `transport.close()` stays too: against a stdio server that accepts the connection and never answers `initialize`, `createMCPClient` is still pending at 5 s in **both** versions and `transport.close()` is the only thing that tears the child down. One residue did narrow — 1.0.82's abort listener calls `cleanup()`, so the `responseHandlers` leak this file records now applies to the timeout path only, since our deadline firing does not abort the caller's signal.
    - **Known gap, deliberate:** `browser-control` names its tools in kebab-case (`get-tab-web-content`, `get-list-of-open-tabs`), and the classifier splits on `_` only, so every one of its reads is still a write. Splitting on `-` as well looks like the obvious finish and has a demonstrated false read in the very corpus that motivates it: `find-highlight-in-browser-tab` carries a read verb and mutates the page, and `highlight` is in no verb set. That needs its own decision.
  - **Two invariants that would fail silently.** `meta.name` must move with the registry key — the permission and block gates key on the registry key while `framework/tools/result-cache.ts` keys on `meta.name`, so namespacing one without the other splits them; a test asserts they are equal for every registered tool. And `getLiveRegistration` maps probe names **forward** (`own[mcpToolName(name, t)]`): `verifyMCPServer` probes a server in isolation and reports the **raw** names it exports, so comparing them against namespaced keys reports every tool of every healthy server as `missing`, which `mcp_verify` renders as ⚠ — the signal the `mcp-manager` specialist has previously answered by deleting a correct config (see **Verdicts and Step Limits**). `mcp-verify.test.ts` mocks `getLiveRegistration`, so it cannot catch that; the guard is an integration test in `mcp.test.ts` driving the real function with real raw probe names.
  - **`LiveRegistration.shadowed` is gone**, along with the "Name collision / last-writer-wins" copy in `mcp-verify.ts`. It could only ever have been `[]`, and a permanently-empty field feeding user-facing prose about a mechanism that no longer exists is worse than no field. An MCP tool also can no longer shadow a Bernard **built-in** through `createTools`' trailing spread (`shell`, `memory`, `web_search`, `wait`, `cite`, `file_write` were all reachable, replacing Bernard's gated implementation _including its risk metadata_) — that hazard closed for free rather than needing a guard.
  - **Migration is a lazy alias, never a rewrite.** Three persisted surfaces name a tool as a plain string: profile permission grants (`profiles.json`, matched by strict equality in `permissions/engine.ts`), specialist `targetTools` (exact lookup, **silent** drop — `{}` is a supported state since #331), and tool profiles. A stored bare name resolves only when exactly one live server exports it; ambiguous fails closed and the user is asked again. `makeAliasResolver` (`mcp-names.ts`, called once by `MCPManager.snapshot()`) builds the index from the whole live surface — **the whole live surface, never the caller's registry**: inside a `delegate_<server>` helper the dispatch's registry holds one server, so a locally-built index would call an ambiguous name unambiguous and honour a grant the user made while a different server owned it. Tool profiles additionally seed forward (`ToolProfileStore.ensureSeeded`), because `resolveProfileKey`'s `includes('__')` branch was **dead** — Bernard registered bare names — so 109 profiles on one real install were keyed indistinguishably from built-ins and would have been orphaned wholesale. Seeding runs in its own try: sharing `recordOutcome`'s catch meant any failure silently skipped the record that followed. `buildToolProfilesPrompt` now takes `liveKeys` and drops superseded and orphaned `mcp.*` profiles — it is otherwise unfiltered and sorts by `errorCount` descending, so a dead high-error profile outranks live tools at the 4000-char budget. Its comment claiming "the registry is not in scope here anyway" was stale; the live call site `framework/agents/main.ts` has `ctx`.
  - **Removing a server sweeps what it left behind, and the namespace is the only reason it can (#377).** `removeMCPServer` deleted one key from `mcp.json` and did nothing else, from **both** call sites — the `mcp_config` tool and `bernard remove-mcp`. `ToolProfileStore` had no deletion path of any kind, so a profile created on first use lived forever. `src/mcp-lifecycle.ts` is the sweep, a flat sibling of `mcp.ts` on `specialist-lifecycle.ts`'s precedent rather than a one-file `src/mcp/` beside a file of the same name; **`removeMCPServer` now has exactly one caller in the tree**, which is what makes the sweep unbypassable rather than merely applied. It removes the config row, the server's tool profiles, and its rules in `ProfileSettings.toolPermissions` and `appToolGrants` — in **every profile**, not only the active one.
    - **The attribution is `mcpNameOwnedBy`, and it works on bytes alone.** That constraint decides the whole shape: `bernard remove-mcp` has connected nothing, and the server being removed is frequently the one that no longer starts, so no live surface exists at the moment the decision is made. Four spellings, every one Bernard actually minted — R0 `<label>_<hash6>__<tool>`, R1/R2's bare `<hash6>__<tool>`, `delegate_<label>_<hash6>`, and the pre-#413 `delegate_<server>`. The un-hashed `<label>__<tool>` form is **deliberately refused** though `aliasesOf` answers to it: Bernard never minted it (pre-#413 it registered bare names, and that alias exists only because the `@ai-sdk/mcp` convention would have produced it), so matching it can only fire on a hand-written record while costing a real false positive — the label is lossy, so `my_server__t` names two servers and removing either takes the other's grant. Measured on a real install: 193 profiles, 71 namespaced.
    - **A bare name is never attributed, and that is the feature.** Over `list()`'s 144 live profiles there: 71 namespaced, 11 `delegate_*` — which **are** attributable and **are** swept, since both delegate rungs match — and **62** carrying a bare tool name with no server in it. `browser_click` was exported by two of the five configured servers, so guessing deletes a live server's learned history. Those 62 are **left alone, which is not the same as reported**: no field names them and `describeMCPRemoval` never mentions them, because naming them on a _particular_ server's removal would be the guess this refuses to make — `bernard tool-profiles` lists them like any other profile and that is the whole of their visibility. Same answer `makeAliasResolver` gives one layer up when an alias resolves to `null`.
    - **The naive cascade is WORSE than doing nothing, and that is what `legacyAncestors` exists for.** `ensureSeeded`'s `seedFrom` left the pre-#413 file on disk for rollback and recorded the link as `supersedes`; `list()` hides an ancestor only while something supersedes it. So deleting the successor alone **un-hides** it — back into `bernard tool-profiles` and back into the system prompt, where `filterLiveProfiles` waves a bare uncategorised key through precisely because it cannot be told from a built-in. An ancestor therefore goes with its successor unless a **surviving** profile still claims it: measured, `browser_click`, `browser_type`, `browser_snapshot` and `browser_navigate` are each claimed by both `playwright` and `browsermcp`. **It is a refcount, deliberately not `buildMCPAliasIndex`'s tombstone**, and the comparison is wrong in the direction that matters: a tombstone _persists_ by definition, because an entry that stopped saying "no" would let a third claimant silently un-ambiguate an alias. Here the opposite is wanted — the ancestor goes the moment the last claimant does, which is what makes `remove-mcp browsermcp` after `remove-mcp playwright` finish the job rather than leave a file nothing can collect. **The residual**, stated because the asymmetry would otherwise claim more than it delivers: a survivor is a profile that _claims_ the ancestor through `supersedes`, and that link exists only once the other server has recorded an outcome — so a live server exporting the same bare name that has never been called for it is not a survivor, and the shared pre-#413 history goes with the removal. Closing it needs the live registry no CLI path has; measured, it does not occur on the reference install.
    - **`ToolMeta.category` was never persisted for a fresh profile**, which this had to fix before its own reporting could work. `ensureSeeded`'s guard read `category && category !== seeded.category` — **always false**, since that line is only reached when `get(toolKey)` found nothing and `getOrCreate` has just assigned that exact category to that exact field. So the profile was created in memory carrying its server and written to disk without one by the next `getOrCreate(toolKey)`, which passes no opts. Measured: of 144 live profiles only 53 carry a category and every one came through the `supersedes` branch; **every `delegate_*` profile had none**. That left #413's own `filterLiveProfiles` unable to drop an orphaned MCP profile from the prompt, and #377's orphan report blind to any server with no pre-#413 predecessor.
    - **The category strings are minted and parsed in one place now** (`mcpToolCategory` / `mcpDelegateCategory` / `serverFromCategory`), the same join `mcpProfileKey` already documents one field over. They were spelled out in six places across five files — minted in `mcp.ts` and `tools/delegate.ts`, parsed in `tool-profiles.ts`, `tools/in-flight.ts` (as a bare `slice(4)`) and twice in the sweep. `serverFromCategory` reports **which kind** it found rather than collapsing them, because `filterLiveProfiles` must stay scoped to `mcp.<server>`: `liveKeys` is the live TOOL surface and holds no delegate names, so widening it to `mcp-delegate.<server>` — the natural "finish the job" edit — would drop every LIVE delegate profile rather than the orphaned ones. Pinned by a test in both files.
    - **Grants are swept in every profile, because `mcp.json` is global and grants are not.** `saveActiveSettings` writes one profile entry and `appToolGrants` goes through the same accessor, but there is one `mcp.json` and removing a server removes it for everyone — so an active-profile-only sweep leaves the grant alive in every profile that happened not to be live, reachable by switching and by nothing else, since `/tool-permissions` shows only the active profile. It is not inert debris either: `mcpServerSegment` hashes the server name **alone**, which is the stability property `mcp-names.ts` was built for, so re-adding the server under the same key **re-arms a grant the user believes they revoked**. `profiles.updateAllProfileSettings` is the writer — one pass, one write, so a failure cannot leave a profile's own rules swept and its app grants not, and it returns `null` for an untouched profile so a no-op sweep does not re-stamp every `updatedAt`. Editing a profile the user is not looking at is acceptable **here and not in general**, which is why that function says so at its own declaration: this only ever removes an entry addressing a tool that no longer exists anywhere, so it never widens a grant and never adds one. `DroppedRule` carries `{label, profile, app?}` and the report names the profile only when it is not the active one.
    - **The next grant the REPL wrote used to resurrect everything the sweep dropped.** `index.ts` hands the gates `getToolPermissions: () => config.toolPermissions`, a live array the REPL mutates mid-session, and `App.tsx`'s three writers each composed the new list **from that in-memory copy** — so one "always allow for this profile" answered after a removal wrote every swept rule back, silently and permanently. Surviving the sweep alone was harmless (the server is gone, its tools are not callable); the write-back was not. `saveAppGrants` never had the bug for the reason copied: it calls `readAll()` on every write, so it has no in-memory master to go stale. The writers now compose from `profiles.loadActiveProfileRules`, which also closes the pre-existing case of a **second process** — the cron daemon, `bernard script` — writing grants while a REPL is open. **Residual, stated:** `config.toolPermissions` is still a read cache that goes stale between an external write and the next in-memory one, so the gates can consult a stale `allow` for a tool of a removed server until then. Harmless by construction, and threading a live config into a tool built by the byte-stable `createTools` is exactly what #332 cautions against.
    - **A dangling fence has a standing surface, not just a one-shot line.** The removal report fires once — it scrolls past on the CLI, and on the `mcp_config` path it goes to the _model_, which decides whether to relay it — while `buildChildTools` drops an unmatched fence entry silently (#331), so a specialist can sit permanently degraded. That is the argument `orphanedMCPServers` already makes two functions down (_"nobody can name a key they have already forgotten"_) applied to the other half. `unownedMCPNames` (in the leaf, so the caller supplies its own server list rather than acquiring an edge to `mcp.ts`) backs a `⚠` on `specialist { action: 'list' }` and a line under `Target tools:` in `read` — `read` because that is what an agent calls before editing a record. Config only, never a live registry: a fence pointing at a server that is merely down this session is not dangling. A **bare** name is never flagged, for the reason it is never attributed — it is indistinguishable from a built-in from here, and flagging every built-in in every fence would bury the one entry that matters.
    - **The sweep runs even when the row is already gone**, `cron/lifecycle.ts`'s rule, and here it is also the product: every install predating this carries debris from servers removed the old way, so `bernard remove-mcp <key>` against a config that no longer mentions `<key>` IS the retroactive cleanup, and `bernard tool-profiles` footers the keys worth naming — read from the stored category, the only place a removed server's name survives in full, since the key carries only a hash of it. The CLI keeps a non-zero exit for the one case that is genuinely a typo (no row **and** nothing swept), because that is what `removeMCPServer`'s throw was worth; a run that swept real debris exits 0, or the cleanup would report success and a failing status in the same breath.
    - **Specialists are reported and never edited**, which makes the headless behaviour defined rather than incidental. #377 sketches a confirm-and-delete flow for a fully-orphaned specialist; deleting user-authored configuration as a side effect of a config edit is not recoverable where an orphan is, and the CLI path is frequently scripted with nobody watching — so this takes the issue's own recommendation for the headless case (_"remove the server, leave every specialist intact, and report which are now degraded"_) **everywhere**, and needs no prompting machinery in a path whose two call sites have two different affordances. Fully-orphaned and degraded are distinguished because `buildChildTools` returns an empty registry when a fence matches nothing (#331) and says nothing about why, so the first answers badly rather than erroring; bundled records are marked protected rather than attempted, since `assertCanDeleteSpecialist` throws and would fail the whole removal over a record the sweep was never allowed to touch. Measured, nothing is lost today: of 17 specialists with a `targetTools` fence, none names an MCP tool.
    - **Known gaps, stated.** An orphaned `delegate_*` profile is still injected into the prompt until someone sweeps it — `filterLiveProfiles` cannot cover it for the reason above, and the fix is removal from disk rather than a wider filter. And a bare profile that no namespaced successor claims can never be attributed from disk at all; naming it on a specific server's removal would be a guess, so only `bernard tool-profiles`'s own listing shows it.

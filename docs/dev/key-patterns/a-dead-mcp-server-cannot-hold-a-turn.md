# A dead MCP server cannot hold a turn (#594).

- **A dead MCP server cannot hold a turn (#594).** One `send_message` against a proxy whose upstream had gone away held a turn for **35 minutes**, ended only when the user pressed Esc, and finally errored **63 minutes after it started** — 28 of them after the turn was already over. Nothing was sent. The vendor's half is theirs: `@beeper/mcp-remote` logged `ECONNREFUSED` to stderr and never wrote a JSON-RPC error back down stdio, so the request id stayed open forever. Four things had to be missing at once on our side.
  - **There was no clock on a `tools/call`.** The handshake has had one since #254 and the provider path since #302/#325; the tool call was `await originalExecute(args)` with nothing behind it. `BERNARD_MCP_CALL_TIMEOUT_MS` (default 60 s, matching the MCP SDK's own request timeout; `0` disables, a typo falls back) races it in `callWithDeadline`, and the refusal names the tool AND the server, because the model's next move depends on which one died.
  - **The abort signal was dropped one parameter position from the fix, and forwarding it is NOT sufficient.** `augment.ts` has always passed `execOptions` into the legacy branch — the branch MCP takes — and the wrapper's `execute: async (args)` discarded it. It is forwarded now. But `MCPClient.request` **registers no abort listener**: it calls `signal.throwIfAborted()` once at entry and then checks `signal.aborted` only when a response ARRIVES, so for a server that never answers the promise stays pending however the signal is set. That is why the signal is also **raced** in our wrapper. The issue's suggested shape had only the forwarding half, which would have fixed nothing for the case it was filed about.
  - **Abandoning is all that is available, and the residue is stated.** Nothing in `@ai-sdk/mcp` can withdraw an in-flight JSON-RPC request, so the deadline and the abort are races: the request id stays registered in the client's `responseHandlers` for the life of the connection, one entry leaked per abandoned call. What the race buys is that Bernard's await ends — the loop moves on, the turn finishes, and Esc ends the _call_ rather than only the turn.
  - **The reconnect retry is gated, and that is the highest value per line in the change.** `mcp.ts`'s reconnect-and-retry re-executed on any failure with no idempotency check, while `nonIdempotent: !isRead && hasEmitVerb(raw)` was computed **43 lines below it in the same function body**. In the trace it fired for `send_message` twice; it happened to fail, and a send that timed out but actually LANDED would have been sent again. `nonIdempotent` is computed above the wrapper now and the retry refuses three causes: the caller cancelled (re-issuing what Esc just stopped is the opposite of what Esc means), our own deadline expired (waiting again is not a remedy for having waited too long, and it doubles the ceiling the budget imposes), and the tool emits. **The third refuses every cause rather than only the unknown-outcome ones**, because at this layer almost none are knowable — a throw out of `callTool` is a closed client, a transport send failure, a parse failure or an abort, and only the last is certainly a no-op. The asymmetry decides it: a wrong retry duplicates a message somebody receives, a wrong refusal costs the model one turn. **`duplicate-guard.ts` does not cover this**, which is easy to assume: that gate records SUCCEEDED calls, and the first attempt here never succeeded.
  - **The user was shown nothing, and the fact was computed 70 times.** `agent:dispatch:stuck` fired every 30 s carrying `inFlightTools: 1`, into a `debugLog` that is a no-op unless somebody had already suspected a problem and restarted with `BERNARD_DEBUG=1`. `src/tools/in-flight.ts` is the always-on channel: `augment.ts` registers every call for its duration and `<Spinner>` names one that has been running over 10 s. **It lives at the augment layer, not in the runner**, because `progress.onPart` sees a part TYPE and can count tool calls but cannot name one — and because the runner's watchdog covers only the streaming main dispatch, which excludes cron, sub-agents and delegate helpers. **It reports the most recently STARTED call over the threshold, not the longest running**: the incident nested `delegate_beeper` → `specialist_run` → `beeper.send_message`, so longest-running is the outermost, and naming a frame that is merely waiting on another frame says less than naming the one that is blocked. `runTracked` goes INSIDE `runOrdered` for the same reason — a read parked on the write barrier has not started, and registering it there would make it out-rank the write it is waiting for. Module-level following `providers/request-counter.ts`, and global rather than per-dispatch unlike `write-barrier.ts` beside it: that module orders calls, so mixing dispatches would serialize unrelated work, while this one answers "what is the user waiting on" and the user is waiting on all of them at once. Read from `<Spinner>` rather than lifted into `App` state because that component already re-renders every 80 ms, so it adds no timer and no whole-tree re-render.
  - **The stall guard's tool exemption was re-examined and KEPT, which is a decision rather than an omission.** `runner.ts`'s `inFlightTools === 0` gate is written not to fire while a tool is in flight, so it excluded this hang by construction, and #594 names it as one of the four gaps. It stays, because that layer cannot tell the two cases apart: it knows a part type and a count, and whether five minutes of silence is a wedged proxy or a sub-agent doing its job is a property of WHICH tool is running. A budget imposed there would have to exceed the longest legitimate sub-agent — longer than the hang was worth tolerating — or kill real work, which is #302's acceptance criteria written backwards. So the deadline went where the knowledge is. **The exemption's other inhabitant is closed by #607**, and not by the per-dispatch wall clock this line predicted: the non-streaming branch gets the same liveness guard the streaming one has (`BERNARD_DISPATCH_STALL_TIMEOUT_MS`), with the tool pause kept and its busy signal read from the tool registry rather than from parts. The exemption then stops being what makes the ladder leaky and becomes what makes it complete — see that entry for the recursion.

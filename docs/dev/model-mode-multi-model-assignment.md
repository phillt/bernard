## Model Mode (multi-model assignment)

`config.modelMode` (#170) tiers the (provider, model) used by each LLM call site within the active provider's model lineup. Three presets:

- `optimize-tokens` — aggressive cost-saving. Main uses **mid**, every sub-agent/wrapper/router site uses **cheap**.
- `balanced` (**default**) — main **premium**; specialist/tool-wrapper/compressor **mid**; rewriter/reference-resolver/recall-filter/specialist-detector **cheap**.
- `optimize-performance` — every site uses **premium**.

**There was a fourth, `off`, and this file documented it as live for months after it stopped being one (#606).** It meant "every site uses `config.provider`/`config.model`" and went away with #225, which moved tiering onto user-defined lineups; `DEFAULT_MODEL_MODE` (`src/config.ts`) is `balanced`, and the `BERNARD_MODEL_MODE` entry below said `off` until #606 while this line already said otherwise — two statements in one file disagreeing about the most expensive setting in the product. The default is worth stating on its own terms because it decides blast radius: under `balanced` the lineup's `premium` slot is what every main-agent turn resolves to, so a bad slot is the live path for every install rather than an opt-in.

`normalizeStoredModelMode` still migrates a stored `off` → `optimize-performance` and must keep doing so — the value is on disk for anyone who chose it before #225. **The reason the target is `optimize-performance` and not the default is SHAPE, not re-tiering**, and this line said the wrong thing first: "refusing it would re-tier them silently" is true of migrating them too, and `DEFAULT_MODEL_MODE` is `balanced`, so refusing would land them somewhere _cheaper_ than this does. What decides it is that `off` meant one model for every site, and one tier everywhere is closer to that than a ladder is. **The migration is a best-effort read of an old preference, not a faithful one**: `off` meant `config.model` everywhere, while it lands on the active lineup's premium slot, the same model only when the lineup is the seeded one for that provider. Best effort is right for a value already written and wrong for a row somebody is picking now — and the wizard was still offering that row, `tier: 'quick'`, as one of the three questions a first run asks.

**So it says so, because there are two more populations and neither is "read once" (#606).** `BERNARD_MODEL_MODE=off` exported in a shell profile is not an old preference — it is RE-PICKED at every launch, from a surface with no label in front of it at all, and `config.ts` reads it through the same normalizer on every start. And `tier: 'quick'` has been on that field since #582, so anyone whose first run took the broken row has `modelMode: 'off'` in `profiles.json` **now**; they did not choose it before #225, they chose it from the defect. The two are indistinguishable on disk, which is a reason not to guess between them and a better reason to say something. `legacyModelModeNotice` is a pure decision over the two RAW values, joining `startupNotices` beside `lineupRepairNotice`; `index.ts` reads them unparsed rather than through `loadPreferences()`, which normalizes — `loadProfiles` casts its settings blob rather than validating it, so the `'off'` survives on the profile and no latch inside the normalizer is needed. It deliberately does **not** claim the migrated value is in force: `prefs.modelMode ?? envModelMode` means a stored answer beats an exported one, so a session can carry a dead `BERNARD_MODEL_MODE=off` while running `balanced`, and a confident sentence about a setting that is not what it says would be this entry's own subject one level down.

What `off` named is still reachable: a lineup whose slots all name the same model puts every site on it under any mode. That is the removal argument, so it is measured rather than asserted — `model-policy.test.ts` → "a lineup with one model in every slot" resolves all 15 sites across all three modes and requires `source: 'policy'`. **It was true of the resolver and false of the affordance**, and #618 closed that on both doors rather than restating it: binding one model everywhere was 18 slots (6 roles × 3 tiers) edited one role at a time, with no "apply to all" row anywhere.

- **`bindEverySlot` / `uniformSlot` / `LINEUP_SLOT_COUNT` (`lineups.ts`) are the value, the detector and the count.** `bindEverySlot` is composed from `replicateAcrossRoles` rather than written beside it — a uniform lineup IS a ladder whose three rungs are one slot, replicated — which is also what made `cloneRoleSlots`' shallow `params` spread reachable: every replicated cell pointed at ONE params object, latent (nothing mutates params in place, and `saveLineup` serialises) but contradicting that function's own "no shared slot refs". The count is **derived**, because three surfaces say "all 18 slots" in prose and `model-roles.ts` advertises a 7th role as a one-place additive edit.
- **`uniformSlot`'s equality includes `params`, with keys SORTED.** Two cells naming `openai/gpt-5.5` at different temperatures are not one binding, and the surface whose whole job is to say "every slot is X" must not say it falsely. Sorted rather than read off `PARAM_IDS`, because `isLineupSlot` does not validate `params` — a hand-edited `lineups.json` can carry a key that list lacks, which iterating the known ids would silently call identical — and it keeps the module off a runtime edge to `providers/model-params.ts`, which it needs only as a type. It returns the slot, not a boolean, so a caller can name the model without re-deriving it; **phrasing is deliberately each caller's**, since the `/lineups` row, the editor card and `lineup_edit`'s matrix differ in voice and width, and a shared label would be the lowest common denominator of three surfaces that legitimately differ.
- **`tier: 'all'` was the tool-side half, and the agent needed 3 calls, not 18.** `SlotSchema.role` already accepted `'all'`; there was no tier equivalent, so "use X for everything" was three entries. `role:'all' + tier:'all'` is now one. Each axis's `describe` states its own fan-out and the combined form is named once, in the top-level description where the call is chosen — measured, spelling it in all three cost ~95 bytes of a prompt-cached prefix to repeat a fact the model had already been told. Net **3,777 → 4,019 bytes** on `lineup_edit` (+6.4%, ~60 tokens once per session) to remove 17 of 18 round trips.
- **The editor row is `Bind all slots…`, and its length is measured rather than chosen — at a stated width.** The split layout's panes are content-sized and shrink against each other, so a label's own length decides how much room the detail card has. **Measured through the real `/lineup` inside `<App>`** (the `App.test.tsx` harness, a 98-column frame): the card's border sits at column 24, leaving the left pane 21 columns, at which `5. Classifier /` and `10. Save as new` already wrap today. "Bind every slot to one model…" fit none of that — it wrapped onto a second unindented line **and** widened the pane. The width has to be named rather than implied, because the same rows do NOT wrap in a bare `MenuOverlay` rendered at 100 columns, where the left pane gets 55 and the rejected label costs the card ten columns instead of five. Both measurements are real and they are different mount contexts; what survives either is that 15 characters is free. So the sentence lives in the card, which also carries the current state (`Every slot is currently openai/gpt-5.5`) — the legibility half, at the point of decision. The toast names the count, which is the "did I cover them all?" confirmation the issue asks for.
- **`renderLineupDetail`'s `actionDetail` is `Record<LineupAction, …>` — and keying the record was necessary and not sufficient.** It was `Record<string, …>`, so a kind with no entry destructured `undefined` and threw the moment the cursor landed on the row: invisible in review, loud at runtime, on the one path where the row is new. The record makes that `TS2741` in **both** directions (a member with no entry, an entry with no member, plus `TS2353` for the latter as an excess property). What it does not make an error is the way the row is actually added: `MenuEntry.value` is `unknown` and `renderLineupDetail` CASTS it, so `{ label: 'Duplicate lineup', value: { kind: 'duplicate' } }` type-checked cleanly, the cast laundered the kind, and the same `undefined` destructure threw at the same moment — the trap closed for a reader already editing the union, open for the one who adds a row and stops. **So every row carries `satisfies LineupMenuValue`**, which reports `TS2322` naming the bad kind _at the row that declared it_; `satisfies` rather than an annotation because the array is `MenuEntry[]` and `value` must stay `unknown` for every other menu in the product. It also makes the handler's `if`-chain exhaustive by construction — that array is the only producer, so a `never` check at the bottom would guard against something unconstructible. All three directions mutation-verified.
- **`pickLineupSlotInk` takes a whole `slotLabel`** instead of a `(tier, roleLabel?)` pair. `tier` fed nothing but the title, the `roleLabel`-absent branch had no call site, and the pair had no honest form for a pick belonging to no single role and no single tier.
- **Not built: a creation-time preset.** The `/lineups → + Create new lineup…` draft opens the same editor and the row sits above the `isNew` ternary, so a uniform lineup is name → one row → provider → model. A second surface would be a second copy of one decision.

The wizard's description carries the signposting half, because the clause that went ("off ignores the lineup") was the only place that walk said the word _lineup_ out loud. **`src/model-modes.ts` owns the vocabulary** — the type, the predicate, the migration, the startup notice and the rows — in the `coordinator-modes.ts` / `tool-modes.ts` shape and at `src/` root for the reason those record. It is a **zero-import leaf**, and that is load-bearing rather than tidy: `model-policy.ts` → `config.ts` → `profiles.ts` is a value cycle, so a predicate living in `model-policy.ts` is one `profiles.ts` cannot import — and duly re-spelled by hand, twice. All three of that menu's mode questions drifted; the other two already became tables, and this is the one whose drift reached a value the runtime does not have — and did not refuse, which is the part that made it expensive.

**Five hand-written copies of a three-member list, now one.** `isKnownMode` (private), `normalizeStoredModelMode`'s own inline list four lines below it, `config.ts`'s `isModelMode` — a third copy with **no caller at all**, every sibling guard being used by `parseSettings` while this one was not, because `modelMode` goes through the normalizer — and two in `profiles.ts`: `ProfileSettings.modelMode` re-declaring the union rather than naming `ModelMode` (the more durable of the two, since it is the type the wizard WRITES, so the persisted shape and the runtime type could diverge with no error), and a **second `'off'` migration** in `readLegacyPreferences`. That last was redundant rather than wrong — its output passes through `normalizeStoredModelMode` afterwards — but it carried the failure mode the others had: a fourth mode added everywhere else was silently DROPPED there, since it has no `else` and the field simply stays unset.

Rows are typed `ModelMode`, so a value the runtime does not have is now a compile error. `settings-coverage.test.ts` → "model mode rows" carries what the type cannot see: each row by ROUND TRIP through `normalizeStoredModelMode` (`f(v) === v`, which catches a value that is _rewritten_ as well as one that is refused, and rewriting is what actually shipped), the union read out of the source so a mode the runtime has and nothing offers fails too, and — **both** surfaces reading the table. That last is the half a first cut left open: pinning the table makes the TABLE sound and does not make a surface read it, so `/agent-options` was free to go back to a literal with every other assertion green. The wizard is pinned by import and `/agent-options` by a source scan of `runModelModePrompt`'s body, which is what is available across the `src/ui` boundary; a scan is weaker than an import and that file says why, and it is strictly stronger than what that surface had, which was nothing. The sibling tables are in the same position and neither pins `App.tsx` — house convention rather than a lapse, and this is the change that found out what it costs. `model-modes.test.ts` holds the table's own properties, including the **60-character note bound** `coordinator-modes.test.ts` already pins on this shape: it was stated in prose here and checked nowhere, and the longest row had already drifted to 53.

Per-provider tier → model mapping — `DEFAULT_TIERS` in `src/lineups.ts`, which is
what seeds a lineup and what `config.ts` derives `FALLBACK_PROVIDER_MODELS` from:

| Provider  | premium       | mid             | cheap                     |
| --------- | ------------- | --------------- | ------------------------- |
| anthropic | claude-opus-5 | claude-sonnet-5 | claude-haiku-4-5-20251001 |
| openai    | gpt-5.5       | gpt-5.2         | gpt-5.4-nano              |
| xai       | grok-4.6      | grok-4.3        | grok-4-1-fast-reasoning   |

**This table is curated, and it used to be derived (#447).** Seeding ranked the
Vercel AI Gateway catalog by output price and took the extremes, which is unsound
for choosing ids to hand a _direct_ provider SDK: the gateway serves models the
provider's own API does not, and price extremes are where those live. It seeded
Anthropic's premium as `claude-opus-4` — retired, still listing its legacy
$75/MTok price, therefore top of the sort, and not dispatchable — so with
`balanced` mapping `main → orchestrator → premium`, every turn of every fresh
install failed. `deriveTiers` is kept, and only to _recognise_ such a seed so
`repairBuiltinLineups` can rewrite it; do not restore it as a producer.

**Catalog membership is not a dispatchability check, in either direction**, which
is the trap when editing rows above. Probed: `grok-3-mini` dispatches and is in no
catalog snapshot; `grok-4.1-fast-reasoning` is in the snapshot and returns
`not_found`. Only `bernard validate-lineup <id>` answers the question. Note also
that xAI id punctuation varies **by family** — `grok-4.6` and
`grok-4-1-fast-reasoning` are both correct — so the two comments in
`providers/catalog.ts` that generalise about xAI dots are both wrong.

Custom providers fall back to `config.model` for every site (no tier mapping). Invocation-level overrides and per-specialist `provider`/`model` records always win over the policy. When `modelMode !== 'off'` and a specialist is created with **neither** an explicit provider/model **nor** a `role`, the policy-resolved `specialist`-tier model is persisted onto the new record so later mode changes don't silently re-tier it.

**A specialist declares either a binding or an intent, never both (#423).** `provider`/`model` is a binding — a specific model was chosen. `role` is a `RoleId` (`src/model-roles.ts`) — a kind of work was chosen, and the active profile picks the model, now and after every re-tier. Declaring both is rejected at the `specialist` tool rather than merged, because a record carrying both would behave according to `resolveSiteModel`'s internal ordering rather than anything anyone declared; setting a role via `update` clears any existing pin, or the state `create` refuses is reachable through the back door. Declaring neither is the legacy third state above, kept so existing callers are unaffected.

The rung is one line at `model-policy.ts`: `SITE_ROLE[site]` becomes `specialist.role ?? SITE_ROLE[site]`, below the pin short-circuit — so `override > pin > record role > site` is a property of the existing control flow rather than a rule imposed on it. The role is **validated against `ALL_ROLE_IDS`, not trusted**: it comes off a user-editable JSON file, and `lineup.roles[<garbage>]` is `undefined`, so `undefined[tier]` would throw inside the function every dispatch calls — it falls back and logs `model-policy:unknown-role`, the same posture as the `isKnownMode` normalization two lines above. Two consequences worth knowing: a dropped off-lineup pin now falls through to the record's role rather than the site default (strictly better — the specialist's own intent beats the generic one), and a role-declaring specialist resolves on the `'policy'` branch, so it gets a **real tier bucket** in `bernard usage` where an auto-pinned one was bucketed `pinned`.

**`Specialist.boundTo` ties a specialist to one applet action (#423)**, so an agent built for a button is reachable only through that capability. Three call sites, **one decision** — `invocationRefusal` in `specialist-authority.ts`, the invocation counterpart to `permissionsFor`. `specialist_run` and `tool_wrapper_run` refuse a bound record outright; an app dispatch does the **inverse** — it permits the matching `(appId, action)` and refuses every other caller, which is the one place this is easy to write backwards, so the permit case is tested first. A mismatch is `specialist_not_bound`, not `unknown_specialist`: the record exists, and saying it is missing sends an integrator after the wrong bug. Discovery is closed at `getSummaries()` rather than in `matchSpecialists`, because that one function feeds **both** the matcher and the `<specialists>` prompt block — filtering only the matcher would leave a bound specialist advertised and unmatchable, inviting a refused call every turn. `list()` is untouched, so `/specialists` still shows it: a user must be able to see what an applet is running. Binding is **one-way**: settable at create, or on update for a record that is not yet bound, and refused on one already bound. The property that matters is that a model cannot RE-bind — stealing a specialist from the applet it belongs to is a model writing a policy field. Forbidding `update` outright, as the first cut did, made the builder's own loop impossible: validation goes through `tool_wrapper_run`, which refuses a bound record, so a create-bound specialist could never be validated by execution. `agent-builder` therefore creates unbound → validates → binds, and its record test pins that order. Sharing the decision also **closed a pre-existing hole**: an applet action dispatches through `runHeadless`, not `dispatchToolWrapper`, so the `disabled` refusal never covered it and a specialist the user disabled in `/specialists` kept running behind every applet button. Writing a new gate beside a check that was already missing a door is how three copies become four; the call sites keep only their own error _shapes_, which is the sole thing that legitimately differs.

The single source of truth is `resolveSiteModel(config, site, opts?)` in `src/model-policy.ts`. Every `generateText` call site routes through it. Set `BERNARD_DEBUG=1` to see `model-policy:resolve` log entries per site.

Every `BERNARD_DEBUG=1` session log starts with a `model-policy:snapshot` event capturing the full `{site → {tier, provider, model, source}}` baseline for the active lineup (emitted by `logSiteModelSnapshot(config, 'session-start')` in `src/ui/App.tsx`). Mid-session mutations — `/lineup` save, `/lineups` create/edit/switch, `/agent-options` model-mode change, `/profiles` switch — each emit a follow-up `model-policy:snapshot` with a per-site diff (or `changed: []` when nothing moved). `model-policy:resolve` lines also now fire when a specialist's persisted `provider`/`model` overrides the lineup, so off-lineup calls (e.g. an OpenAI 429 surfacing on an xAI-only lineup because a specialist hardcoded `provider: 'openai'`) are visible in the log without code reading.

**Off-lineup specialist pin guard**: when `config.activeLineupId` is set and a specialist's persisted `provider` isn't bound to any tier of that lineup, `resolveSiteModel` drops the pin (provider + model together) and falls through to the policy tier instead. This catches stale pins from specialists created under a different lineup or provider — e.g. a tool-wrapper specialist baked at `provider:'openai', model:'gpt-5.5'` during an OpenAI session, surfacing as 429s on an xAI-only lineup because the OpenAI quota is exhausted. Invocation-level overrides bypass the guard (those are explicit and trump persisted intent), and the guard never fires when no `activeLineupId` is set (no explicit lineup → the pin is the strongest signal). Emits `model-policy:specialist-off-lineup {site, specialistProvider, specialistModel, lineupId, lineupProviders, reason}` to the debug log on each drop.

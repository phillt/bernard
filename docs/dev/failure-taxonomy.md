## Failure Taxonomy

`src/error-taxonomy.ts` is a central classifier that turns a raw tool error (message, optional `toolName`/`errno`/`httpStatus`) into `{category, correctable, retryable, severity, playbook: {user, model}}`. Categories: `invalid_args | exec_failed | not_found | auth | rate_limit | permission | timeout | transient | parse_failed | pool_exhausted | cancelled | unknown`. `not_found` is correctable only when `toolName === 'shell'` (a command-not-found mistake the model can fix) — for web tools a 404 is "the URL is gone," not learnable.

The same classification drives four surfaces:

- **Correction queue gate**: `src/tools/tool-wrapper-run.ts` only enqueues a candidate when `cls.correctable === true`. Non-correctable failures are logged and dropped.
- **Profile gate**: `src/tools/augment.ts` only records bad examples when `cls.correctable === true`; success always bumps `recordSuccess`.
- **User render** (#353): `toolFailureFor` (`src/tool-failure.ts`) projects a result to `{category, hint: playbook.user, severity}`, and `<ToolFailureHint>` (`src/ui/Thread.tsx`) renders it as a `category · recovery hint` line under the red result, coloured by severity. **Derived at render, not carried on the sink event**: it is a total pure projection of the result, so caching it would need two producers — `commitNewHistory` and `buildResumeSeed`, which rebuilds from disk with no event to copy — and a drift bug between them. It also keeps one definition of "did this fail". Both render paths derive it, which matters because streaming events are replaced by static items at turn commit. Because it hangs off `detectToolError` rather than the wrapper shim, it covers **every** tool, not the four the shim routes. `classifyToolFailure` trusts an embedded `[failure: <category>]` marker over the patterns: re-classifying an already-annotated result is not idempotent (measured, `auth` round-trips to `unknown`, dropping severity `critical` → `low`), because the string then holds playbook prose rather than the original error. The predecessor `printToolFailure` was an empty stub from the Ink cutover, so this whole surface silently did not exist — and the _model's_ playbook leaked into the result the user read in its place.
- **Model hint**: the same shim prepends `[failure: <category>] <playbook.model>` to the error string the model sees on its next turn.
- **Cron alerts**: `src/cron/runner.ts` classifies any job-level throw and fires `sendNotification({severity, ...})` with the user-facing playbook so headless jobs surface failures with the right urgency.

Severity map — `critical`: `auth`, `permission`; `normal`: `rate_limit`, `not_found`, `invalid_args`, `exec_failed`; `low`: everything else.

- **A wrapper failure is classified from the DIAGNOSTIC, never the label (#565).** `WrapperResult.error` is a label the specialist writes freely — `STRUCTURED_OUTPUT_RULES` tells it to "put the cause in `error`", which is why `ReasoningLogEntry.status` is typed `string` — while `result` carries the prose. Both classification sites preferred the label, so a 90 s provider stall arrived as `{error:'runtime_error', result:'Provider timed out …'}` and classified **`unknown`**: not retryable, severity dropped, and the playbook _"the error did not match any known pattern"_ printed on the line directly above the sentence naming the cause. The agent retried anyway, which means the guidance was not merely wrong, it was ignored. `classifyWrapperFailure` is the one decision, a sibling of `classifyToolFailure` in the same file for the same reason: a rule with two call sites in two modules is how the two drift.
  - **It was two sites, not the one the issue names.** `wrap-with-specialist.ts` decides what the MODEL is told; `tool-wrapper-run.ts` decides what the correction flow LEARNS, via `cls.correctable`. A shell wrapper failing `runtime_error` / `bash: fooo: command not found` classified `unknown` there — not correctable — so the single failure a wrapper could genuinely learn from was dismissed, which is #366's `dismissed` counter counting the wrong thing. Fixing only the first site leaves that half untouched.
  - **The fallback is by OUTCOME, and its honest scope is narrow.** Exactly three `ToolErrorType` names are spelled literally in `pickCategory`'s patterns — `pool_exhausted`, `step_limit`, `parse_failed` — and each is there because Bernard itself emits it. A free-form label classifies as nothing: `rate_limit` misses, because the pattern is `rate[\s-]?limit` and has no underscore. So consulting the label second preserves Bernard's own three and little else, which is precisely why consulting it FIRST was a defect rather than a defensible second-best. A test pins that `rate_limit` and `invalid_args` as bare labels stay `unknown`, so the scope cannot quietly be overclaimed again.
  - **What the fallback protects is MODEL-authored output, not Bernard's own.** Checked: all nine producers in the repo set an informative `result` (`No specialist found with id "x"`, `Maximum concurrent agents (4) reached.`), so if those were the only sources the label could be ignored outright. But `wrapWrapperResult` parses a `result` the specialist wrote and nothing constrains it — a model may leave it empty or fill it with prose the taxonomy cannot read while labelling the failure correctly. Worth stating because the first draft of this entry cited the pool refusal as the empty-prose case; it is not, and only a test fixture carries `result: ''` there. Both directions are mutation-checked — label-first fails 4 assertions, prose-only fails 2.
  - **The classification is measured, not bounded.** `proseOf` runs `JSON.stringify` on an arbitrary `unknown`, but `result` originates as model output capped by `maxTokens` (~16 KB at the 4096 default): 0.078 ms per call at that size, once per FAILURE. Slicing to a window would risk cutting a pattern at the boundary for no measured gain, so it is left whole.
  - **It is TWO tiers, not one rule, and review found the flat version inverting.** `AUTHORITATIVE_LABELS` — `pool_exhausted`, `step_limit`, `parse_failed` — are minted by Bernard and spelled literally in `pickCategory`, so they are read FIRST; every other label is free-form and is consulted only after the prose fails. A flat prose-first rule breaks on the one shape `structured-output.ts` documents as legitimate: a specialist reporting a DOWNSTREAM parse failure as `{error:'parse_failed', result:'The upstream API returned 404 not found…'}`. Measured, the prose matches `not\s*found` first, so it classified `not_found` — **correctable** for a shell wrapper, buying a correction-agent run for a failure no call-shape change can fix, where the old rule gave the non-correctable `parse_failed`. The other two cannot invert either way, and that asymmetry is the reason: `tool-wrapper.ts` and `tool-wrapper-run.ts` both OVERWRITE `result` when they set their label, so a model cannot author prose beside it, while nothing overwrites it on the model-authored `parse_failed` path. Membership is DERIVABLE rather than a judgement, which is what makes it checkable — but the derivation took **three attempts, and the first two were wrong in ways that looked right.** A label belongs iff Bernard MINTS it, it is a `ToolErrorType`, and it is **not correctable**. Said plainly, the three members are facts about Bernard's own MACHINERY — ran out of slots, ran out of steps, could not parse its own child's output — where `not_found` and `invalid_args` are facts about the request or the world, which is why a model can legitimately write them and why they are exactly the two that feed `isCorrectable`. The correctability condition is what bounds trusting model text: `wrapWrapperResult` passes a specialist's JSON through and nothing can tell a Bernard-minted label from a model-written one (the typed channel #365 would add), so a mislabelled correctable category enqueues a correction candidate and teaches a shipped specialist from a failure that was never a call-shape mistake — #565's own defect re-entering through the door built to fix it. **The two rejected rules are recorded at the code, because both look right.** The first was "mints it AND classifies to itself", justified by the claim that a non-round-tripping member "would resolve `unknown`" — **false**, since `build` assigns the category it is handed and never classifies; and the filter was accidental, excluding `not_found` purely because `not\s*found` cannot match an underscore, letting a spelling accident decide which of Bernard's own statements it may believe. The second, proposed in review once that was found, dropped the filter for "mints it AND is a `ToolErrorType`" — which admits both correctable labels, and a test caught it: a specialist mislabelling a provider stall as `invalid_args` would then beat prose saying `Provider timed out` and be told to retry with a different call shape. `invalid_args` is the worse of the two, being correctable on ANY tool where `not_found` is narrowed to a shell context. **The completeness of that list is a test, not a comment**: `error-taxonomy.test.ts` scans the three producer files, derives the expected set and compares both directions, so a fourth minted label cannot silently fall to the prose tier and reintroduce the inversion — with a guard-the-guard case, because a renamed producer would otherwise make the scan pass vacuously. Incidentally **156x cheaper** for those three (0.0004 ms against 0.0626 at a 16 KB result), because the early return skips `proseOf`'s `JSON.stringify` entirely.
  - **One decision point, because the marker is authoritative downstream.** `classifyToolFailure` trusts an embedded `[failure: …]` marker over re-running the patterns, so the single call in the shim fixes the category into the model's playbook, the user's `ToolFailureHint` severity colour and the pool fall-through at once. Nothing re-derives it later — which is why the wrong answer was so durable.
  - A stale comment went with it: `wrap-with-specialist.ts` claimed the classified string was "the same fallback for display". It never was — display is built independently by `formatWrappedResult`, which reads `error` and `result` as separate fields, so the classified string has exactly one consumer and there was no display fallback to preserve. Left in place it would have argued against the fix.

- **`web_search` distinguishes "no provider configured" from "the web has nothing" (#565).** With neither key set the chain falls through to the DuckDuckGo scrape, and a zero-result answer said `Try different or broader terms` — so the model rephrased four times in one observed turn, once with a `site:` operator, against the one provider that was never going to improve. The buckets already existed; what did not was the distinction between "tried and failed" and "never had a key", because both Brave and Tavily returned a bare `undefined` for each. `ProviderOutcome` is the three states (`answered` / `unconfigured` / `failed`), the shape `KnowledgeSearchResult.skipped` already uses and for its stated reason — so the difference is legible to the model, not just to a human.
  - **The zero-match result stays a SUCCESS.** #364's reasoning is untouched: a provider really did answer, marking it a failure would teach the profile that an obscure query is a usage mistake, and it would suppress evidence registration for a search that ran. What was wrong is the ADVICE, not the classification, so only the advice changed — and `detectResultFailure` matches `startsWith('Error')`, so the new wording is pinned as non-failing by tests in two files.
  - **The advice switches on whether a keyed provider ACTUALLY RAN**, not on whether every keyed provider is unconfigured — a strictly narrower question that comes apart the moment one key is set and that provider 500s. Review reproduced it: Brave configured and failing, Tavily unset, DDG empty gave "try different terms" and dropped the key hint entirely, so the one missing key was never named — the conflation this change exists to remove, surviving inside the branch that handles the mixed state. That state is ordinary: a half set-up install meeting an ordinary transient. `keyHint` now rides the generic return too, because a missing key is worth naming whenever there is one, even where rephrasing is also sound. A configured provider answering empty still keeps the rephrase wording, because there the query IS the variable worth changing.
  - The keyed set is derived from the CHAIN rather than from `SEARCH_PROVIDER_ENV_VAR`'s size — a provider added to one and not the other would otherwise make the test permanently false, failing in the direction that tells the model to rephrase when nothing real ever ran.
  - **`tried:` now means tried.** It used to list providers skipped for want of a key, which names the wrong remedy. The test guarding that was called _"lists only tried providers (skips providers with no API key)"_ while its body asserted the unconfigured ones ARE listed — it documented the conflation rather than guarding against it, and is rewritten to assert the split.
  - **The key hint names the exact variable**, because telling someone to set `BRAVE_API_KEY` when it is Tavily that is missing is the same class of wrong advice this change exists to remove. `conjoin` takes its conjunction from the caller: a list of missing providers is a fact about all of them ("brave and tavily"), a list of variables is a menu of remedies ("or").
  - **The all-fail message has always exceeded `ERROR_SNIPPET_MAX`** (212 characters now, 214 before), so `detectResultFailure` truncates the diagnostic snippet. The test in `tool-profiles.test.ts` passed only because its literal was hand-shortened to fit — a false green that held whatever production actually emitted. It asserts a prefix now, and says why.

# The typed text is on screen before the pipeline runs (#613).

- **The typed text is on screen before the pipeline runs (#613).** `Prompt` empties the input synchronously on Enter, and the next thing to reach the transcript was `runAgentTurn`'s turn-start `commitNewHistory` — on the FAR SIDE of `runPreTurnPipeline`, i.e. up to three serial LLM round trips. So the screen went blank for exactly the window `pre-turn:end` already measures, on every send, and the more the pre-turn passes were doing the longer the gap. `runAgentTurn` now pushes the user's own words as a `StaticItem` before anything is awaited, and marks the canonical history message as already on screen so the commit skips it.
  - **`drainNextTurn`'s shape, which is the one this file already proves.** Push the item, then add the message `processInput` pushed to `alreadyOnScreenRef` — ONE write, never revised into a different message and never removed, which is what makes it `<Static>`-safe. The issue's other sketch (commit a placeholder, swap it for the canonical slice later) is not available in an append-only log, and a pending row in the DYNAMIC region is worse than the bug: the timestamp footer appears on commit, so the row reflows under a reader mid-sentence, and it needs a second mount in both transcript surfaces.
  - **`alreadyOnScreenRef.add` is unconditional now, where it was gated on `announced`.** Every turn paints before that line, so the flag decides which SURFACE did it — the echo, or the `WakePanel` `drainNextTurn` already pushed — never whether one did. The flag's only remaining job is suppressing the echo for a wake, since a `❯` bubble beside that panel is the exact duplicate the panel exists to prevent.
  - **It rests on one invariant, and that invariant went from one path to every path.** `agent.getLastUserMessage()` is only the message THIS turn pushed because `processInput` pushes synchronously before its first await — verified, there are zero `await`s between `processInput`'s signature and the push. The old code exercised that only on the wake path.
  - **Built with the two builders `processInput` uses, not by hand.** `timestampUserMessage` is what `parseUserMessage` reads for the footer under the bubble, so a bare string would have made every bubble in the product silently lose its time — a regression on every turn, where the one below is only on rewritten ones. It is minted at SUBMIT rather than at dispatch, which is both the truer answer to "when did I say this" and, at `formatFriendlyTimestamp`'s minute granularity, almost always the same string. `attachTo` keeps the `[image]` marker on an image turn. `wrapUserMessage` is deliberately absent — an LLM-only detail `parseUserMessage` strips anyway, and leaving it off keeps the timestamp at position 0, so a message whose own first line is `# Request` is not mistaken for the wrapper.
  - **The `✎` marker survives by REVISION, and only in the surface that can repaint.** The rewriter runs after the echo is painted, so the marker `/agent-options` promises by name cannot be decided at paint time — the information does not exist yet. `commitNewHistory`'s `rewriteForLastUser` is correspondingly dead and gone; what replaces it is a `.map` over `staticItems` patching `rewriteOriginal` onto the echo. It changes no DISPLAYED text (`rewriteOriginal` is the same raw text the echo already shows, and `UserMessage` reads it only to pick `display` and to decide the marker), and it can neither duplicate a row nor remove one — but **the guarantee is about ORDERING, not about length**, and stating it as length licenses a real failure. Ink's `<Static>` memoizes `items.slice(index)` on `[items, index]`; `items.length` is only the dep of the `useLayoutEffect` that ADVANCES `index`. So a same-length identity change does invalidate the memo and re-render — what makes it harmless is that `index` already equals `items.length`, so the slice recomputes to `[]`. And it always does: the log is append-only, and Ink creates its container in **legacy (sync) mode**, so each `setState` outside a React event handler flushes its own commit and the layout effect pushes `index` to `items.length` before the next update is seen — measured, two `setStaticItems` calls in one `setTimeout` body are still two commits. `index` is therefore always ahead of anything a `.map` can touch. Written as "same length re-renders nothing" the rule reads as a STRUCTURAL guard, and a later editor may revise an item in the same commit that appends it and expect a no-op; there `index` is still behind, the slice is non-empty, and the revision really is written. `<TranscriptViewport>` re-renders from `staticItems` every frame and shows it; under `BERNARD_FULLSCREEN=false` it does not, the same accepted tradeoff `Thread.tsx` already records for rows that do not rewrap on resize. **Stated rather than discovered**: that is a real divergence, and the alternative was worse — dropping the marker everywhere makes the `/agent-options` description false for everyone and leaves `rewriteOriginal` / `REWRITE_ICON` dead, i.e. a feature removal this ticket did not ask for.
  - **#478's window is where the echo could paint TWICE**, and `recordInterruptedInput`'s return value is what stops it. That method has always handed the message back "so the caller can mark it as already rendered" and no caller ever had a reason to; this is the first. Without it the echo and the `finally`'s `commitNewHistory` both render the same words. The sibling #478 assertion is a `toContain`, which is true of one bubble and of two, so the guard needs a COUNT — mutation-checked, since it is the one window where two features write the same text.
  - **An empty commit no longer re-renders the tree.** Nothing to append is the common case at turn start now rather than a rare one, and `setStaticItems` with a fresh array is a new reference either way — so every turn start was re-rendering to say nothing. The cursor still advances; only the state update is skipped.

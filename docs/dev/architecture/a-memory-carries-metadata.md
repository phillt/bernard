# A memory carries metadata (#513)

- **A memory carries metadata (#513)** — a memory used to be a file with text in it and nothing else. Not a timestamp, not an author, not an access count, not a schema version. The only derivable fact was filesystem `mtime`, and nothing read it. So "the newer one wins" could not be stated, supersession could only be expressed by **destroying** a record, and #373's write-time contradiction check had nothing to compare recency against. `MemoryRecord` (`src/memory.ts`) adds `key`, `writtenAt` and `supersededBy`.
  - **Front matter through `src/front-matter.ts`, a shared pure leaf.** The parser was first written as a copy of `docs-store.parseDoc` — same fence regex, same field loop, same quote strip, same untouched-body rule — and the copies had **already drifted**: `parseDoc` matches field names with `/^([a-z]+):/`, lowercase only, so a camelCase key in a doc's front matter is silently dropped, while a memory needs `writtenAt` and `supersededBy`. Copy-versus-import-the-heavy-module was a false choice; this repo's third option is a leaf, which `tool-bytes.ts`, `mcp-names.ts`, `token-estimate.ts` and `headless-posture.ts` all are. `splitFrontMatter` has no imports at all, so neither caller acquires the other's graph — `memory.ts` is imported almost everywhere including worker dispatches, and `docs-store.ts` reaches `docs-generated.ts` and from there four more modules. **Policy stays with each caller**, and the two answer differently on purpose: `parseDoc` returns `null` and its callers drop the doc; a memory file is the user's and cannot be dropped.
  - **`writtenAt` and `supersededBy` are DISCRIMINATORS, and `key` alone is not.** A fence counts as metadata only when it carries one of them, because `key:` is an ordinary line in prose about YAML and these files are model-written — a memory documenting a config format would otherwise be silently decapitated. Both are written by `serializeMemory` and by nothing else, so no hand-authored fence carries one by accident. This is what turns "we measured that no current file collides" into "no file can collide": the first cut treated any recognised key as metadata, and `key` was the ambiguous one. Measured first all the same: **zero of the 30 files on a real install start with `---`**, so every one classifies as legacy on first read and there is **no migration step anywhere in this change**.
  - **`sanitizeKey` is deliberately untouched**, and that is what shapes the collision fix. `CronNotesStore.sanitizeJobId` imports it, so changing it silently renames cron notes files too. Instead the **raw key is recorded**, and a write whose target file records a _different_ raw key is refused with that key named — `AppletBriefStore`'s stated policy (_"a repaired id addresses a different store than the caller named"_) reached without touching the shared function. The sanitizer **deletes** rather than replaces, so `"foo bar"`, `"foobar"` and `"foo/bar"` all address `foobar.md`; two files on a real install are visible scars of it. **Its limit is stated rather than discovered:** a legacy file recorded no raw key, so its collision is undetectable — the hole closes per key on the first write, never retroactively, and a test asserts exactly that.
  - **Supersession is in place and filtered on read**, copying `ToolProfileStore.list()` — _"superseded is a property of the record, not of one reader"_ — rather than a `superseded/` subdirectory: one mechanism instead of two, the file stays where a user can find it, and one deleted front-matter line undoes it. **The DIRECTION is the opposite of that precedent, deliberately.** `ToolProfile.supersedes` sits on the NEW record and names its ancestor, which suits a key rename. Here the retiring record carries `supersededBy`, because a memory is frequently retired in favour of one that **already exists** (three files encoding one standing rule — keep the best), so there is no new record to hang the pointer on; and opening the file then tells you it was retired and where to look, which is what makes an archive better than a delete. Cycles are refused: `A→B` then `B→A` leaves both filtered out of every listing with neither reachable.
  - **Deleting instead of archiving is not the cheaper option, and the numbers settle it.** Measured on the real store: 6,199 chars across 30 files, **26% of the 24,000 budget**, with every retirement candidate totalling **424 chars** — deletion moves it 26% → 24%. A superseded record already costs **zero** context because it is not rendered, so there is no token pressure to unlink, and deletion is irreversible on content the user wrote. See #528 for the drop-order half.
  - **The read cache is validated by `stat` — `mtimeMs` AND `size` — not invalidated by our own writes.** `getContextMessages` is awaited **inside `innerIterate`**, so one turn was a `readdir` plus a `readFileSync` per entry _per LLM call_, plus a full sweep each in `recall-filter` and `reference-resolver` (`recall-filter.ts:138-140` documents the hazard and fixes it only within its own pass). Validation rather than write-invalidation because a **separate `bernard` process** — the cron daemon, the applet host, `bernard script` — can write memory while the REPL is open, and a write-invalidated cache would serve that session stale memory for its whole life. `size` joins `mtimeMs` following `apps/app-csp-grants.ts`'s `readCached`, which validates the same way and says why: mtime granularity can miss a same-millisecond external write — which is exactly the scenario this cache exists to catch, so mtime alone would leave it reachable. Cost: 26 test files mock `node:fs`, and three of them exercise this path and needed `statSync`.
  - **One pass per sweep, and that is what makes the cache a win rather than a cost.** `listMemory()` has to `load()` each key to read `supersededBy`, and the first cut's `getAllMemoryContents` then called `readMemory` per key, loading again — the cache made the second READ free but not the second `stat`. Measured on one harness at 30 files: **0.159 ms two-pass against 0.098 ms single-pass**, and at 300 files **1.24 ms against 0.68 ms**; the independent efficiency pass measured the two-pass form at 0.146 ms against **0.137 ms for the uncached code it replaced**, i.e. a small net REGRESSION on a path that runs once per LLM call. `liveEntries()` is the single private traversal both `listMemory` and `getAllMemoryContents` go through.
  - **`writeMemory` was the only store in the repo still doing a bare `writeFileSync`**, with `saveRewriterHint` performing a read-modify-write on top of it — the exact hazard `apps/brief-store.ts` and `paths.ts` both call out. It goes through `atomicWriteFileSync` now.
  - **The API is additive, so nothing downstream moved.** `readMemory` and `getAllMemoryContents` keep their signatures and return **bodies**, which is what leaves `renderPersistentMemory`, `recall-filter`, `reference-resolver` and `context-message.test.ts`'s two-method fake untouched; `readRecord` and `listAllMemory` are the metadata-aware additions. A metadata-aware BULK reader is deliberately absent until something reads it — the consolidation pass (#529) is the first candidate, and a public method with only a test behind it is the shape #499's audit spent a section listing. The `memory` tool reads through `readMemory`, so **the model never sees front matter** — it would otherwise appear both in the transcript and as the provenance `contentPreview`.
  - **The write gate is symmetric identity at ONE chokepoint, and the read gate is not (#501).** `ownsOrShared` — `owner === undefined || owner === this.owner` — is right for a READ, because an unowned record is the user's standing instruction and everyone should see it. It is catastrophic for a write: it is true when the record is unowned, so a specialist writing a key the user already used **overwrote the user's memory and stamped its own name on it**, making the note invisible to `main`, to `/memory` and to consolidation forever. The keys are model-invented and written unattended at session close, which is the worst place available for a silent overwrite. `assertOwns` compares `(existing.owner ?? null) !== this.owner` and is called by every persistent mutation — `writeMemory`, `supersede`, `retire`, `deleteMemory` — so a fifth cannot be admitted by default, which is the `readOnlyWrap` / `storeErrorGuard` lesson applied to the write side. Deliberately **not** folded into `assertWritable`: that one also gates scratch, which is in-memory and has no owner, so checking ownership there would mean loading a persistent file to write a scratch note. `MemoryOwnerCollisionError` also had to join `storeErrorGuard`'s instanceof chain — without it the one refusal a specialist meets most often escaped as an AI-SDK `ToolExecutionError`.
  - **`asOwner` is deliberately NOT monotone, and the reason is nesting rather than convenience.** A persona that delegates to a second persona must give the child its OWN name, not inherit the parent's, or two specialists share one namespace and the fence means nothing between them. Safe because the owner comes from `def.recordId` via `resolveDispatchProfile` — returned alongside the profile, the `resolveRetrieval` shape, so a definition-supplied thunk is not called twice per dispatch — and can be neither supplied by a caller nor influenced by a model.
  - **`supersede` needed its own tool action, and that exposed a live fail-open.** `readOnlyWrap` (`framework/pac/read-only-memory.ts`) hardcoded `action === 'write' || action === 'delete'` — a second copy of a decision `meta.isWriteAction` already makes for the read-only block gate (#179) and the confirm gate (#144) — so a new mutating action was **admitted by default**, and a PAC Critic could have retired a user's memories from the one phase whose whole contract is that it cannot write. It calls **`shouldBlockInReadOnly` (`src/risk.ts`)** now — the function the real block gate already uses at `augment.ts:630`. Reading `inner.meta.isWriteAction` directly was the first fix and stopped one rung short: it took three implementations to two, when `risk.ts` already owned the answer. The difference is the fallback for a tool declaring no predicate — refusing every action, as that first fix did, is a FALSE refusal on a `kind: 'read'` tool, where the shared function consults the declared classification instead. For a `kind: 'write'` tool the two agree exactly, so the substitution kept every assertion. The `memory` and `scratch` parameter schemas had to split for the same reason — they shared one object, so `supersede` would have been advertised on `scratch`, where it means nothing. This is the class #527 exists to sweep.

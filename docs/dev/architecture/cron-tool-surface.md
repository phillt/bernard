# Cron tool surface (#333)

- **Cron tool surface (#333)** — `cronDefinition.tools()` (`src/framework/agents/cron.ts`) now calls `createTools(..., surface)` plus its own four tools (`notify`, `cron_self_disable`, `cron_notes_read/write`), instead of hand-rolling a registry. It was the **only** definition that received a resolved tool surface and used just the MCP half — `historyMode: 'ephemeral'` already resolves it to `'worker'` — which is how it ended up without `web_search`, `file_read_lines` or `cite` for no recorded reason. **`file_edit_lines` is withheld**, and the reason is a gate asymmetry, not a judgement about unattended writes: a default cron job runs `toolMode: 'write'` / `confirmThreshold: 'high'`, where `shell` (`kind: 'dangerous'` → high) has its write-shaped invocations **denied** headlessly, while `file_edit_lines` (`kind: 'write'` + `sideEffect: 'local'` → medium) would pass **unprompted**. Handing it over would give every existing job an unbounded filesystem write through the one door that isn't gated. The asymmetry itself — arbitrary local file write classified below a shell write — is the real defect, but raising it to high changes interactive behaviour for every user and needs its own decision. The per-job `toolMode` / `confirmMode` / `skipPermissions` controls are unchanged. It also now passes `ctx.provenance` (it previously passed none to anything), so cron's web reads and memory lookups register as citable sources like every other dispatch, and `cite` appears. The system prompt's tool list and step budget are **derived** from the registry `runDefinition` hands `systemPrompt`, not written out: the prose list sat ~180 lines from the registry it described and the prose budget said "20 steps" against `config.maxSteps` — already drifted for anyone who changed it. Pinned by `tool-surface.test.ts` → "advertises exactly the tools it was handed".

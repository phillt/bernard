# Cron step-log result cap (#347)

- **Cron step-log result cap (#347)** — `truncateResult` (`src/framework/hooks/cron-step-recorder.ts`) bounds each persisted tool result at `CRON_RESULT_MAX_LEN` (10 KB). It used to test `typeof result === 'string'` and return anything else untouched, which made the truncating branch effectively **dead**: every Bernard tool returns an object — `shell` → `{output, is_error}` (10 MB `maxBuffer`, no cap on `output`), `file_read_lines` → `{lines: [...]}` (bounded only by the 50 MB `MAX_FILE_SIZE`), MCP → `{content: [...]}`. Full results landed in `CronLogStore` verbatim, per step per run for every job — and cron is unattended, so nobody saw the growth; `cron_logs_get` then read it all back into an agent's context. Sibling of #343, which made a _preview_ uninformative the same way; this one made a _persisted_ log unbounded. The fix serializes before measuring and bounds **during** serialization via the same replacer idiom as `previewOfResult`, because the inputs are unbounded: a plain `JSON.stringify` of a 10 MB `shell` result costs ~39 ms and ~20 MB transient before the slice discards it. A truncated result is returned as a **string** with a `... (truncated, N chars total)` marker — a truncated object is not a valid instance of its own shape, and the marker is what distinguishes a bounded entry from a complete one; results that fit keep their structure so readers that walk it still work. The `REDACTED` short-circuit stays ahead of serialization.

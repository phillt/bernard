# One packer decides what memory fits (#528)

- **One packer decides what memory fits (#528)** — past `MAX_PERSISTENT_MEMORY_CHARS` the renderer drops whole entries, and _which_ ones was decided by **`readdir` order**: `aaa.md` in, `zzz-never-do-this.md` out, no judgement anywhere in the path. The file stays on disk, so it is worse than a deletion in one respect — the user believes the memory is there, it _is_ there, and Bernard cannot see it. `packMemory` (`context-message.ts`) is now the single decision, and `memoryBlock` the single definition of what one entry costs, so the budget cannot describe a block nobody renders.
  - **Three callers had three measures, and two of them disagreed by construction.** `recall-filter` decided whether to even ASK the curator for a ranking by summing `key.length + content.length`; the renderer drops on the **rendered** block — `### `, a newline, XML escaping. The rendered form is strictly larger by 5 chars per entry, so there was a band below the cap in which entries were dropped and **no ranking was ever requested** — drop-by-filename at precisely the boundary the ranking exists to fix. Measured on the real 30-entry store at **162 chars (2.4%)**, and it widens with entry COUNT rather than bytes, so a store of many small memories opens it wide. The fix is not a matching formula but a call: `needsRanking` now _is_ `packMemory(...).dropped.length > 0`, so there is one measure and it cannot drift.
  - **The `rewriter-hints` exclusion moved to the prompt, where its reason applies.** `readCuratedMemory` deleted the key and one caller then used that map for two different questions — what to SHOW the curator, and how much memory there IS. The second is about the agent's budget, and the agent is shown the hints. Latent today (`saveRewriterHint` has **zero production callers** and no such file exists, so half of #512's stated gap cannot currently fire), which is exactly why it is pinned by a test rather than left to be rediscovered.
  - **Order is the ranking, then size.** Only the second half is new; smallest-first is argued from the store rather than from taste — the two largest entries on a real install are one-off logs of specific emails, 1,498 of 6,177 chars, while the standing rules are small, so dropping by size drops the episodic records and keeps the most standing facts per byte.
  - **`break` was tried and is worse, which is why the `continue` stays.** #528 reads first-fit as making the ranking advisory, since a large rank-1 entry can be skipped while small low-ranked ones get in. Stopping at the first non-fit honours the ranking as a cut and hands one oversized memory the power to **blank the whole section**: a single 25,000-char entry ranked first evicts everything. Worked through on a four-entry example it is not even reliably better by relevance — after the cut, filling the residue by size can keep a _lower_-ranked entry than the greedy pass would have. So the anomaly is answered where it hurts instead: the dropped keys are named.
  - **`injectedMemoryKeys` was every key on disk, merely re-sorted.** So on the one turn a memory was dropped — the only turn anyone inspects — the Prompt & Context viewer reported it as injected, which is the surface a user consults to answer "why didn't Bernard use that memory". It is now the packer's own `kept`. Computing it in `agent.ts` rather than threading a report out of `buildContextMessage` keeps the plumbing at zero and cannot disagree: same pure function, same two inputs. It also deleted `orderMemoryKeysForDisplay`, a duplicate of `orderForPacking` that had **no test**.
  - **#528's "superseded first, then oldest" is already moot**, and the issue should not be inherited on that point: `liveEntries()` filters retired and superseded records before the renderer ever sees them (#534), so they cost zero context. The ordering question is only ever about live entries.
  - **The user is told, once per session, and by name.** `src/memory-notice.ts` is a pure decision in the `cost-guardrail.ts` shape. It is a `pushAssistantNotice`, **not** a toast — a toast is cleared by the next submit and "Bernard cannot see three of the things you wrote down" has to outlive a keystroke, the argument `catalog-notice.ts` already records for `provider-wiped`. It names the keys because "3 entries were omitted" is not actionable and `pr-review-workflow` is, bounded because the store is not, and it names `BERNARD_MAX_PERSISTENT_MEMORY_CHARS` rather than restating the cap's value, which is env-overridable and would go stale for exactly the users who raised it.

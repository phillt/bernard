# A specialist record addresses the runtime it already has (#508).

- **A specialist record addresses the runtime it already has (#508).** The audit's finding is that `AgentDefinition` _is_ the target runtime and a `Specialist` can address **4 of its ~20 fields** — prompt, model, tools, and a boolean about the result envelope. Everything else about how a specialist runs is a constant chosen by whichever definition dispatches it: every specialist gets `0.5 × maxSteps`, nothing can opt into ReAct, and the only tool-surface exception in the tree is `tool-wrapper`'s hardcoded one, picked for three bundled wrappers and inherited by every wrapper written since.
  - **Three fields, and the omissions are the decision.** `stepRatio`, `strategy`, `toolSurface` — each has an existing resolution point in `runDefinition` and needs no new machinery. `memoryScope`, `knowledgeScope`, `delegates`, posture and `outputSchema` stay out until there is an enforcer to honour them (#501, #505, #511): **a declarable field with nothing enforcing it is a lie on disk**, and worse than the constant it replaced, because the record now claims something.
  - **All four `RoleId` properties, not just the shape.** Intent rather than a binding — `stepRatio` is a FRACTION of `config.maxSteps`, never a count, so it scales with `BERNARD_MAX_STEPS` instead of going stale against it the way a `provider`/`model` pin goes stale against a lineup. Resolved per dispatch against live config. **Validated, not trusted**, with the `model-policy.ts` unknown-role idiom verbatim — every value comes off a user-editable JSON file and this runs before every dispatch in the process, so a throw here is one broken record taking down every turn that touches it. And provenance logged, in **two** lines rather than one: `dispatch-profile:invalid` is a bug report about a file on disk, `dispatch-profile:resolved` is why a step count differs from the site default, and folding them makes the first invisible in the noise of the second.
  - **`AgentDefinition.recordId?(input)` is how the runner finds the record**, copying `retrievalQuery?(input)` — the newest and best-shaped precedent — for its three reasons: `input` is the only place a record id lives, a function keeps the input shape checked per definition, and **optional means omission fails closed**. Only `specialist` and `tool-wrapper` declare it, which is what makes `main`, `sub`, `task`, `cron` and the PAC phases provably unaffected. It also could not have gone anywhere else: `def.stepBudget(config, input)` receives no `ctx`, so it cannot reach a store, and `resolveToolSurface(ctx, def)` receives no `input`, so it cannot know which record — the resolution has to be central, which is what #508 asks for anyway.
  - **Per-field, not all-or-nothing.** One typo must not silently discard a declaration the user got right, so `stepRatio: 99` alongside `strategy: 'react'` keeps the strategy.
  - **The definition keeps what the ratio is a fraction OF, and its own floors.** The record says "half the usual work", the site says what usual is; `tool-wrapper`'s `Math.max(2, …)` stays its own, because below two steps a wrapper cannot call a tool and then report — a property of the shape, not of any record's preference. The record beating `def.toolSurface` is likewise deliberate: `'full'` was chosen for three bundled wrappers and applies to every wrapper anyone has written since, so a record must be able to say "not me". Widening is bounded by `targetTools`, a fence for every kind since #530. **And that justification only holds because `dispatchToolWrapper` reads the record too**: it assembles `childTools` before `runDefinition` runs and `toolWrapperDefinition.tools()` returns them verbatim, so the centrally-resolved profile never reaches a wrapper's registry — the field would have been inert for exactly the kind whose hardcoded `'full'` justifies the precedence. Both readers go through `declaredToolSurface`, so they cannot disagree about what a valid value is.
  - **A declared strategy rides `BuildStrategyOpts.strategyId`**, the seam #167 already built for per-turn variation, rather than a second mechanism. `tool-wrapper` returned `new NormalStrategy()` unconditionally, so ReAct was unreachable from a record; it is routed through the builder **only** when a record declares one, so a wrapper that declares nothing gets the same object it always did rather than whatever `coordinatorMode` happens to say.
  - **The refusal at the creation boundary is not redundant with the fallback.** The resolver falls back silently by design; without a refusal in the `specialist` tool, `stepRatio: 50` is stored, ignored forever, and leaves only a debug line nobody reads. The creation boundary is where a model can still be told — the same division `targetToolsScopeError` makes against `buildChildTools`' silent drop. The cap of 2 is a typo guard rather than a safety limit: `config.maxSteps` is the real budget.
  - **The telemetry gap, folded in and confirmed.** `specialistDefinition` declared neither `site` nor `telemetrySite`, and its `resolveModel` returns no `site` key — so `run.ts`'s `def.site ?? 'main'` default stood and **every specialist's spend folded into the `main` layer of `bernard usage`**. The one number that could tell you a persona was expensive said the main agent was. Fixed at both levels: `site: 'specialist'` on the definition as the fallback, and `telemetrySite: \`specialist:${id}\``at the`specialist_run`call site, which is what #299 already did for`tool-wrapper:<id>`and`mcp:<server>`. **And `AgentDefinition.site`is now REQUIRED**, which is the actual fix: it was optional with a`def.site ?? 'main'`default at three call sites, so a definition that simply did not mention a site billed its whole spend to the main layer, silently. #299 paid for that once and`specialist`was the second time; requiring it makes the third a compile error rather than a wrong number.`cron`declares`'main'`explicitly now — it was the default by omission, which is exactly what made`specialist`'s omission invisible. Pinned on the real registry rather than by the type alone, since `tsc` excludes tests.
  - **Not fixed, named instead:** `specialist-run.ts` and `tool-wrapper-run.ts` each pre-flight `resolveProviderAndModel`, which disagrees with `resolveSiteModel` by construction whenever there is no pin and no override — `run.ts` already says so in the vision gate's docstring. Removing it has its own blast radius (two different failure envelopes). This change adds no fourth resolution path, which is the part that matters.

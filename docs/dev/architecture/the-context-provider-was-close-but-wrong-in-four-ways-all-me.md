# The context provider was close-but-wrong in four ways, all measured in one session.

- **The context provider was close-but-wrong in four ways, all measured in one session.** (1) **Recalled facts carried no date.** `RAGSearchResult` had no `createdAt`, so the curator and `<recalled_context>` saw a five-month-old episode ("the Daily Blaze goes to john@", retrieved 197 times) exactly as they saw this morning's — while the renderer's own caveat said facts "may be outdated". Both now render `[YYYY-MM-DD]` through `text.factDatePrefix`, in **local** time (facts are stamped UTC, so slicing the stamp dates an evening fact to tomorrow, which is the very "yesterday read as today" confusion), the curator is given today's date beside them, and both prompts say the newer fact wins and an episode describes its own day. The curator also stopped stripping `id` from what it keeps, which had been silently reverting #549's provenance address to a content prefix on the default path. (2) **The resolver stopped at the first phrase it could not place** and threw away the ones it could — `ambiguous`/`unknown` discard `entries`, and the Ink call site falls open on both — so "the priorities document" went unresolved because "his virtual assistant" came first. It now returns `resolved` whenever anything resolved — told so in the prompt, and enforced in the parser, which returns any valid `entries` whatever status came with them, since a cheap model does not always follow the rule. (3) **The resolver blended sources and described rather than named.** It saw the first 40 memory notes by `readdir` order, each cut at 140 chars, and filled the rest from knowledge-base facts — so "our daily blaze" resolved to the OLD format and repo under a memory key's name, and the rewriter inlined that into the user's own words. Every live key is now listed, the ones sharing words with the request are previewed at 400 chars (`lexical.rankByTermOverlap`), the prompt requires one source per entry and a NAME rather than a description, and a `resolvedTo` over `MAX_RESOLVED_TO_CHARS` is dropped in code — a paraphrase there becomes something the user appears to have said. (4) **Dispatches dropped their most relevant memory first.** Only main gets a curator ranking; every dispatch packed smallest-first, so the Daily Blaze specialist ran with `daily-blaze-format-brian` cut on every run because it was the biggest note. `ContextMessageInputs.memoryRelevanceQuery` (the dispatch's own retrieval query, from `run.ts`) is handed to `packMemory`, which ranks memory by shared words — **only when something would be dropped**, so under budget the section is byte-identical, and entries sharing nothing are left unranked so the rest still pack smallest-first, which is what keeps short standing rules. Known gap: a dispatch with no retrieval query (tool-wrappers, or RAG off) still packs by size.

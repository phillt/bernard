# Cron fires off the wall clock, and says what it dropped (#400, #401).

- **Cron fires off the wall clock, and says what it dropped (#400, #401).** A `0 */2 * * *` job ran **twice in 24 hours** and nothing anywhere recorded that eleven fires had been dropped. `cron.schedule` arms one `setTimeout` straight to the next matching instant — measured at 3,360,246 ms for an hourly job — and Node timers run on `CLOCK_MONOTONIC`, which does not advance while a Linux machine is suspended. On the reporting machine the clock lost **55 of 71 hours** that way, matching `journalctl`'s six suspend cycles to within 2 ms.
  - **The execution model, stated because the acceptance asks for it.** The cron daemon is an ordinary local process. While the machine sleeps it does not run, and nothing catches up _during_ the sleep. On wake it notices within one tick and decides per job. Powered off means not run — there is no OS-level wake here, deliberately: `wakealarm` is root-owned, Windows `DisallowStartIfOnBatteries` defaults true, and Bernard ships no systemd unit or launchd plist for the daemon, so a wake route is a packaging change rather than a scheduling one (deferred on #400).
  - **The fix is the WAIT, not the clock.** `MAX_TICK_WAIT_MS` (30 s) caps every wait, so the next check is at most that far away in _awake_ time whatever the operating system did, and the decision it then makes is re-derived from `Date.now()` against a persisted boundary. It repairs all three platforms at once — macOS and Windows count sleep in their monotonic clocks and so fire promptly-but-late rather than drifting, and the same cap bounds both. The wait is `min(cap, time to the earliest boundary)`, so a seconds-granularity expression is still exact and an idle daemon still wakes twice a minute.
  - **`onMissedExecution` is deliberately NOT used**, against the issue's own first framing. `runner.js` advances `expectedNextExecution` and _then_ reports the advanced value, so it names a boundary that already ran and never names the first one that did not; node-cron 4.x removed catch-up on purpose.
  - **So `src/cron/schedule-clock.ts` is a pure leaf that answers "the next instant after an arbitrary date"**, which node-cron cannot: `getNextRun()` is `getNextMatch(new Date())`, always from now, and `TimeMatcher` is unreachable because the package's `exports` map exposes only `.` — the deep-import refusal `src/ui/keys.ts` already records for Ink. The parse mirrors node-cron's accepted syntax because `cron.validate` stays the gate at every write, including two inherited semantics it would be wrong to "fix": day-of-month **AND** day-of-week (Vixie ORs them), and local time. What is not inherited is the walk — `MatcherWalker.matchNext` resolves a weekday mismatch by incrementing the **year**, so it answers 2034 for `0 12 * * sun` and 2027-03-01 for `0 0 29 2 *`. A differential test drives node-cron's own `getNextRun()` and pins agreement on the expressions it gets right; the weekday and February cases pin ours instead, with the divergence named.
  - **Coalesced, opt-in, and lateness is what decides.** `catchUp` runs **one** missed fire on wake, never the queue: a laptop shut over a weekend owes an hourly monitor 60 fires, and replaying them is 60 passes over the same inbox against a pool of three to reach the answer the first one gives. The next boundary is computed from `now`, not from the one that was missed, which IS the coalescing. The run/skip test is **lateness > one tick**, not the missed count — a daily job slept through for eight hours has no boundary between its due time and now, so a count-based test would call it on time and fire it as though nothing had happened. Default off, preserving what every existing job was created under; the skip log names the remedy.
  - **`catchUp` is settable by the `cron` tool, unlike `writePaths` and `toolPermissions`.** Those are authority, and `cli.ts` states the rule that a model must not widen what it may do. This is not: a caught-up run executes under exactly the posture the job already had. It changes _when_, never _what_.
  - **`nextRunAt` is persisted**, so a stopped daemon — or a machine that was off — is a missed fire like any other on restart rather than a silent re-seed from "now". That also forced a pre-existing bug to be fixed: `reconcile` skipped any job it already held, so an edited schedule took effect only after a restart or a `cron-bounce`, and with the boundary now on disk the stale one would have survived that too. **Upgrading is quiet by construction**: an existing job has no `nextRunAt`, so the first reconcile seeds it from _now_ and nothing reads as missed — no catch-up storm on the first daemon start after this lands.
  - **`missedRuns` resets on an on-time run** rather than accumulating forever, so it answers "how much has this job dropped lately", which is actionable, rather than "since it was created", which is not. `MISS_COUNT_CAP` bounds the walk and the count renders as `500+` rather than quietly claiming 500.
  - **Nothing deduped, and 42 identical jobs were the result (#401)** — same name, same `0 0 * * *`, same `"do the thing"`, all enabled, all still armed months later. `duplicateJob` keys on **schedule and prompt, never the name**: the 42 shared a name too, and a name is a label a model invents afresh each time — the key `watchers/` already settled on for the same reason. An enabled twin is **refused**, which is stronger than the issue's "warns": the tool has no confirm channel, and a warning that still writes the row is exactly what would have happened 42 times. A disabled twin creates and points at it, because that is probably the job the caller meant to enable.
  - **`src/cron/health.ts` is the signal table**, in the `permission-consent.ts` shape and for its stated reason: a job's health renders on four surfaces (`cronList`, and the tool's `list` / `get` / `status`), and a rule written at four call sites is four rules that drift. Keyed by `JobSignalId` so a declared signal with no detector is a compile error, and `health.test.ts` walks the table to every surface — adding a signal and forgetting one is otherwise silent, since the surface simply keeps saying nothing is wrong. Two rows today: `failing` (three consecutive failed runs — `runJob` already retries three times internally, so three entries is nine attempts) and `missed`.
  - **`failureStreak` short-circuits on `lastRunStatus`**, which is what makes it affordable in a listing: `CronLogStore.getEntries` reads a job's whole JSONL — up to 5 MB — so asking 43 jobs would read every log to answer a question that is zero for all but the broken ones. A persisted counter was rejected instead because `lastRunStatus` has five write sites across three files, and a counter maintained at three of them is the "wiring is the half that fails silently" shape.
  - **`JobUpdate` is derived from `CronJob`.** `updateJob` took a hand-written union of thirteen field names, so every field added to the record since had to be remembered there as well — and one that was not simply failed to compile at whichever call site tried to write it, which reads as "that field is not persisted" rather than "the list is stale". `Partial<Omit<CronJob, 'id' | 'createdAt'>>` keeps the two facts a job is identified by out and costs nothing for the next four fields.
  - **A repeated hour is traversed or stepped over according to the EXPRESSION, which is Vixie's rule.** Local-time setters cannot name the second occurrence of a fall-back hour — `setMinutes(m + 1, 0, 0)` from 01:59 EDT yields 02:00 EST, jumping the whole of 01:00–01:59 EST — so the first cut lost a fire there, and silently: `countBoundaries` walks the same function, so the boundary that was never _named_ was never _counted as missed_ either. The one class of drop this feature could not report was the one it introduced. Measured, `0 * * * *` fired 24 times that day instead of 25 and `*/30` 48 instead of 50. The sub-minute steps are epoch arithmetic now when the expression recurs within the day (`hour` or `minute` unrestricted, Vixie's `HOUR_STAR || MIN_STAR`), and stay on setters otherwise — because the two kinds of job want opposite answers and a single rule gets one of them wrong: "half past one" means half past one, not half past one and again, so traversing the fold for every expression would double-fire every fixed-time job once a year, which is worse than the bug. The **entry** step is epoch-based under both rules: `setSeconds(s + 1)` from 01:00:00 EST names a local time JS resolves to the EDT occurrence, an hour _earlier_ than the instant it was asked to advance past, so the walk re-derived a boundary it had already returned and `*/30` went backwards.
    - **The hour step was tried as epoch arithmetic too and reverted, on measurement.** An expression that traverses the fold has `hour` either unrestricted (the step is never taken) or paired with an unrestricted `minute` (the fold is crossed by the minute step first), so it changed no answer in five zones — and introduced one wrong answer in `Australia/Lord_Howe`. A surviving mutation is what surfaced that; the branch was untested because it was unreachable.
    - **Known gap, measured rather than assumed:** in the two zones whose transition is not on a local hour boundary — `Pacific/Chatham` (+12:45/+13:45) and `Australia/Lord_Howe` (+10:30/+11:00) — an expression naming specific hours with an unrestricted minute still loses the part of the repeated span the hour step jumps. Closing it needs the hour step to _search_ for the next local-hour change rather than compute it, which is a different shape of code for a population of about a thousand people.
    - **`*.dst.test.ts` runs in the `forks` pool** (`poolMatchGlobs`), because these assertions are unobservable eleven months a year and in half the world's zones, so the zone has to be set — and under Vitest's default worker-THREAD pool `process.env.TZ` is a thread-local copy that never reaches the OS `setenv`, so V8's timezone cache keeps whatever the process started with and the assignment is silently ignored. Four of the assertions happen to hold in `America/Los_Angeles` as well, so the file carries a guard that fails loudly if the zone did not take: without it, dropping the pool entry would leave the file passing for the wrong reason.
  - **`nextRunAt` is invalidated at the WRITE, in `CronStore.updateJob`.** It is computed from `schedule`, so changing the input has to invalidate the cached output — and at the store rather than at each caller, because a caller that forgets leaves a boundary belonging to an expression that no longer exists. The `reconcile` re-seed covers a job the scheduler is _holding_; two ordinary paths are not held, and the second is the sharp one. A job **edited while disabled** is not in the map to compare against, so with the daemon up the whole time the re-enabled job kept its old boundary — and when that boundary was in the past the miss report fired and named three causes (asleep, stopped, powered off), none of which had happened. For the one feature whose point is telling the truth about dropped fires, a confident false positive is worse than the silence it replaces: it is the report a user acts on by turning `catchUp` on for a job that never needed it.
    - **`seed` additionally checks that a stored boundary MATCHES the current expression**, which the store's clear cannot cover: `jobs.json` is a file the daemon watches and users edit, and an edit made while the daemon was down never passes through `updateJob`. A boundary is only ever written from `nextMatchAfter`, so one the expression does not match was computed from a different one — which answers exactly the question that matters, where comparing it against `nextMatchAfter(now)` could not tell a stale boundary from a legitimately distant one.
  - **`MAX_TICK_WAIT_MS` doubles as the lateness threshold**, so for a schedule whose period is at or below 30 s the threshold equals the job's own period and such a job is never classified late. That is the right answer anyway — a job due every ten seconds has no useful notion of a fire worth catching up — but it means the miss reporting is meaningfully about minute-granularity schedules and coarser.
  - **What the scheduler test asserts, and what it cannot.** No test can suspend an operating system. `vi.setSystemTime` moves the wall clock while leaving each timer its original remaining delay, which is precisely what a suspend does to a monotonic clock — so the divergence is real and the assertions are about the wrapper: does the scheduler notice, count, coalesce, record and re-arm. libuv's behaviour across an actual suspend is the premise, measured on the issue, not something this suite re-establishes.
  - **Not done, and not claimed.** The daemon still has no OS-level wake; nothing prunes a failing job automatically (it is surfaced with the command that disables it, which is the `runner.ts` repeat-alert posture rather than acting unasked); and the 42 rows on the reporting machine are the user's data and were left alone.

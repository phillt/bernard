# A RAG store per specialist (#501).

- **A RAG store per specialist (#501).** `RAGStoreConfig` gained a `dir`, its sixth knob, and that is the whole change — because `maxMemories`, the 0.92 dedup scan and `prune()` are all per-INSTANCE already, so separate directories make each of them per-owner with no further work. That is what a namespace column could not have done: the cap, the scan and the prune are global, so a namespaced specialist would have competed with the user's own history in one score sort and lost, with no per-namespace floor to design around it. It is the same argument #516 made when it rejected `RAGStore` as a corpus substrate, applied one level down. Cost is small and measured: `getEmbeddingProvider()` is a module-level singleton so N stores share one ~196 ms model load, and a fresh per-specialist store is empty so `load()` and `pruneExpired()` cost nothing. **Sweeping on delete is then removing a directory rather than selecting rows** — which matters, because `RAGStore` can only delete by id and has no owner axis to select on, so a namespaced sweep would have meant loading the whole 31 MB store, filtering, and re-serializing it. The producer is the specialist-recall arm: the three existing RAG writers all read the MAIN transcript, so without it a per-specialist store would be an empty store forever.
  - **It is READ as well as written, and the first cut was not.** The worker wrote into `specialistRagDir(id)` and `deleteSpecialist` removed it, and **nothing anywhere constructed one to search** — so the pass paid a ~196 ms model load and ~13 ms per fact to embed facts no dispatch could ever retrieve. A write-only store is worse than none, because it looks done. `resolveRetrieval` searches it **alongside** `ctx.rag` and re-ranks on `similarity`, never instead of it: the store exists so `maxMemories`, the dedup scan and `prune()` become per-owner, not so a specialist stops seeing the user's conversational facts — replacing `ctx.rag` outright would be a silent behaviour change for every specialist that already exists. **Re-ranked, not re-capped**: each store already applied its own threshold and cap, so a second cap could only drop a fact for the accident of which file it lives in.
  - **The surfaces that inspect facts and memory are no longer main-only.** `bernard facts` / `bernard clear-facts` had **no flags at all** and constructed a bare `new RAGStore()`, and `clear-facts` printed the imported `MEMORIES_FILE` — which names the wrong path the moment a flag exists, on the one screen whose whole job is to say what is about to be destroyed. Both take `--specialist <id>` now; the only change inside is which `dir` the store gets. An unknown id is refused with the ids that DO exist and nothing is opened, so a typo cannot delete from the wrong store. `listSpecialistRagIds` is a `readdir`, deliberately **not** a loop over `specialistRagFor`: that accessor's `RAGStore` constructor `mkdirSync`s its directory, so enumerating through it would materialise an empty store for every id it touched — a listing that writes. `/memory` and the debug report count what is on disk through `MemoryStore.listAllByOwner`, **the one reader that crosses the owner fence on purpose**, and the reason is what the fence is for: it stops an AGENT reading another agent's notes, and a person reading their own machine is not an agent. Keys only, never content, so it cannot become a route into a note's body — and **it throws from a narrowed view**, because #511's design is that the fence is a property of the OBJECT, and `createTools` is handed a `MemoryStore`: without the guard, one method call from any fenced dispatch would reach every other specialist's keys. `/rag` and the bare `facts` listing name the other stores, suppressed when there are none — so output is byte-identical on every install until a specialist learns something. **`/clear --save` is main-only and always will be**, recorded at the write site rather than given a flag with nothing to read: it extracts by DOMAIN from the user's REPL transcript, and a specialist's facts come from its own dispatches.
  - **A specialist consolidates its OWN notes, in the recall arm.** `runMemoryConsolidation` is handed a bare `new MemoryStore()`, so owned records are excluded from it **permanently** — and not merely per run: the `changed` predicate is computed over the same list, so an owned note cannot even trigger a pass. Meanwhile the recall arm writes owned notes every session, which recreates the condition #529 exists to fix one fence down. It cannot live in the user's pass: `main` cannot apply a retirement to an owned key (`assertOwns` refuses, correctly), so routing it through `MemoryCandidateStore` would need the proposal to carry the note's CONTENT past the fence for review. It **writes where the user's pass proposes**, on `writeOwnedNotes`' own asymmetry — private to one specialist, deleted with it, and reviewing N proposal queues at every startup is a queue nobody drains — and stays reversible on identical terms, since `retire` archives in place. `merge` is never applied: it is the one disposition that writes NEW text, so a wrong call invents a note nobody wrote. `duplicate` supersedes toward the keeper rather than retiring, keeping `MemoryRecord`'s distinction between "X replaced this" and "this was never worth keeping". Reuses `proposeConsolidation` and `validProposals` — the same judgement over a different corpus — and bills a separate `specialist-consolidator` site, because the two run at completely different rates and folded into one `bernard usage` cannot say which is costing you. Gated at 8 notes.
  - **`src/specialist-rag.ts` is the cache, and `AgentContext.ragForOwner` the seam.** A factory on the context rather than a resolved store, because the owner is not known until `runDefinition` reads the dispatch's `recordId` — and supplied by whichever composition root already imports `rag.ts` (`index.ts`, `headless.ts`), so the framework keeps a type-only edge to that graph. Fail-closed by omission: a process with RAG off supplies none. Cached per id following `apps/store.ts`, because a specialist that runs four times in a session must not re-read its embedding file four times; `deleteSpecialist` evicts the entry before removing the directory, or a re-created id inherits the deleted one's in-memory facts.

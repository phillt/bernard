# Attachments reach a dispatch (#427).

- **Attachments reach a dispatch (#427).** `ImageAttachment` used to reach only `Agent.processInput`, and it never travelled through `buildUserMessage` at all — it rides on `opts.seedMessages`, the escape hatch only the main agent uses — so `src/framework/` contained **zero** image handling and no dispatched agent could be handed a file.
  - **`src/framework/agents/user-message.ts` is the carrier for every producer, the main agent included.** `agent.ts` hand-assembled the same parts, so the SDK's image-part shape was encoded twice — and the duplicate was the one whose messages _persist_, so an SDK bump would have silently missed it. `DispatchAttachment` is structural, so `ImageAttachment` satisfies it as-is. A leaf on `import type { CoreMessage }` and nothing else. Deliberately NOT importing `src/image.ts`, which reaches `providers/catalog.js` and would hand the framework an edge to the provider catalog — the edge `tool-bytes.ts` and `mcp-names.ts` exist to refuse. Loading paths into bytes is `src/tools/attachment-args.ts`, at the tool boundary, where touching the filesystem is ordinary. Split into `renderTaskText` / `attachTo` because the PAC phases stack `Plan:` / `Prior plan:` sections and cannot use the task renderer.
  - **`attachTo` returns a plain string when there is nothing attached.** The array form is a shape change, and applying it on the zero-attachment path would be blast radius for a feature that turn is not using — it is also what keeps every `toEqual({role:'user', content:'Task: …'})` assertion true. Collapsing the seven duplicated builders was verified as a pure refactor: the whole suite passed with no test edits.
  - **The carrier is on `TInput`, not `RunDefinitionOpts`**, so a definition that never declares `attachments?` cannot receive bytes — the same fail-closed-by-omission shape as `headlessToolOptions`. On the opts bag every definition would be opted in by default.
  - **The capability check lives in `runDefinition`, and that is a finding rather than a preference.** `specialist-run.ts` and `tool-wrapper-run.ts` each do a pre-flight `resolveProviderAndModel` — override → pin → `config.provider/model`, no lineup, no `SITE_ROLE`, no tier — while the model that actually runs comes from `resolveSiteModel`. The two disagree by construction whenever there is no pin and no override, which is exactly the population #423 enlarges. A gate checking a different model than the one that runs is decoration. It sits beside `resolveToolSurface` for the reason that one gives, and runs on the **materialized** seed, since the function form of `seedMessages` is the main agent's live history.
  - **Two arms, split on `historyMode`, and the split is the safety property.** An ephemeral dispatch throws (nothing billed; the five dispatch boundaries shape a throw into each tool's own contract). A persistent history **must never throw**: `this.history` carries image parts across every `/model` switch forever, so a throw would brick every later turn of a conversation that once held a screenshot — it sanitizes with the same `[Image attached]` placeholder used before persisting to disk. Separate functions rather than one branch, because the persistent arm's guarantee is what it does _not_ do.
  - **The scan is `hasImagePart`, shared with `stripImagesFromHistory`.** They were briefly separate and had already disagreed: the gate matched any NON-TEXT part while the sanitizer replaced only `image` ones. `{role:'tool', content:[{type:'tool-result'}]}` is present from the first tool call onward, so **every** subsequent main-agent turn went through a capability lookup and a full sanitize pass — and a part kind only one of them knew about would trip the gate and then survive the sanitize. One predicate makes that unrepresentable. The capability verdict is memoized per dispatch: it is loop-invariant, `getSeed` is called at three sites and up to five times a turn, and the catalog-miss path (every custom provider) costs ~8 µs.
  - **Attachment resolution is two-phase.** `validateImagePath` is a `statSync` plus an extension check, and is what makes a bad path cost nothing; the read is up to 4 × 10 MB of **synchronous** I/O — measured 17.3 ms warm — blocking the Ink render loop and every concurrent dispatch. `resolveAttachments` therefore validates up front and hands back a thunk the caller invokes once the dispatch is committed, past its own refusals and past `withSlot`, which does not queue.
  - The UI's attach-time warning asks about the model the turn will actually run on (`mainVisionCapable`), not `config.model`. Under a lineup those differ, and inline images were being **silently dropped** for a model that could read them — the same staleness #233 fixed for the context-window math.
  - `isVisionCapableModel` is now **provider-scoped first**: it looked up by name across every built-in provider, so a custom-provider model whose name collides with a catalog entry (an Ollama `llava`) inherited a stranger's capability tags. Name-only stays as the fallback a custom provider needs, and unknown providers are still optimistically allowed — a best-effort check, stated as such. The gateway catalog's `modalities.input` is deliberately **not** parsed: across all 84 shipped entries, every one carrying `modalities.input: image` also carries a `vision`/`file-input` tag and vice versa, so plumbing it buys zero information while invalidating every user's cache.
  - **PAC forwarding shipped with the producers, not after them.** `runPAC` is reached from `subagent` behind `config.subagentPac`, so a pipeline that dropped attachments would make that toggle silently decide whether a sub-agent can see an image. It goes to the **Planner and Actor, not the Critic** — the Actor because an image task with no image at the Actor is undoable, the Planner because blind planning mis-specifies, and not the Critic because its message already stacks task + context + plan + actor output and `PAC_MAX_RETRIES = 1` would carry the bytes up to six times per dispatch.
  - **Known gap:** `runDefinition` still computes no token estimate for its seed, so a large attachment on a small-context pinned model fails at the provider rather than early. `IMAGE_TOKEN_ESTIMATE` has one production consumer (the main agent's compression preflight); a dispatch-side budget is net-new work.

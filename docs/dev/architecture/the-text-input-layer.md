# The text-input layer (#354/#355/#356)

- **The text-input layer (#354/#355/#356)** — three modules, split the way `mouse.ts`/`useMouseWheel.ts` and `viewer-util.ts`/`ViewerShell` already are: **src/ui/line-geometry.ts** is pure string math with no React or Ink (boundary math + display windowing, so its tests drag in neither), **src/ui/use-line-editor.tsx** is the shared buffer+cursor hook plus `LineWithCursor`, and **src/ui/BoundedLine.tsx** is the both-axes-bounded renderer that `Prompt` and `TextInputOverlay` share. `LineWithCursor` used to render the whole buffer with no bound, which was one defect on two axes: unbounded horizontally (#354) and vertically (#355).
  - **Readline chords** are matched on decoded `Key` flags verified empirically against Ink's parser, not guessed. Two consequences are load-bearing. **`Home`/`End` cannot be bound here at all** — they reach `useInput` as empty input with _no_ flags, indistinguishable from noise, so `Ctrl-A`/`Ctrl-E` stand in _as chords_. Since #399 the keys themselves work, decoded off stdin by `useRawKeys` and delivered to `LineEditor.toLineStart`/`toLineEnd` rather than through `handleKey` — the raw-stdin listener this note always prescribed. See **Input escapes** below. And **`Alt-Backspace` arrives as `{delete, meta}`**, so word-delete is tested _ahead of_ the plain `key.backspace || key.delete` branch — behind it, it would never fire. `Ctrl-A`/`Ctrl-E`/`Ctrl-U`/`Ctrl-K` are **line**-wise, not buffer-wise: that is what readline means and what a multiline buffer (Shift+Enter) needs; for a single-line buffer — every `TextInputOverlay` caller — the two are identical.
  - **Input escapes: Ink parses them and then throws them away (#399).** Two user-visible defects, one cause. `ink/build/parse-keypress.js` maps **every** Home/End encoding (`[H`/`OH`/`[1~`/`[7~`, `[F`/`OF`/`[4~`/`[8~`) to the name `home`/`end` — and `use-input.js` then builds its `Key` from a hard-coded field list with no `home`/`end`, and blanks `input` because those names are in `nonAlphanumericKeys`. `PgUp` survives only because `Key` happens to have a `pageUp` field, which is what isolates the gap. Separately, Ink's `fnKeyRe` cannot match a `;`-separated parameter list ending in `u`, so kitty/foot/ghostty's Shift+Enter (`ESC [ 13 ; 2 u`) has its ESC stripped and arrives as the printable text `[13;2u` — which the editor typed into overlay fields.
    - **Upgrading is the expensive option, not the cheap one.** `ink@6.6.0` adds the `home`/`end` fields and requires **React >= 19** against our 18.3; `ink@7` additionally requires Node >= 22 and parses CSI-u unconditionally. A React major across the whole render path, for one `Key` field.
    - **So `src/ui/keys.ts` + `src/ui/useRawKeys.ts`** — the `mouse.ts` / `useMouseWheel.ts` split, pure parser and thin hook, which is exactly what this file already prescribed ("a raw stdin listener alongside Ink the way `mouse.ts` parses SGR mouse reports"). The escape table mirrors Ink's own because Ink's parser is **not importable**: its `exports` map exposes only `./build/index.js`, so a deep import would break on any patch release. All **twelve** rows Ink recognises are supported (six per key: xterm `CSI`, SS3, vt220, rxvt, and rxvt's modified `$`/`^` forms) — terminals genuinely disagree, and shipping only the one on the author's machine is how this reads as "works for me". The mirror shipped its first draft with four of those rows missing under a docstring claiming completeness, so `keys.test.ts` now reads Ink's `keyName` table out of `node_modules` by file path and fails if a row is unhandled — a test may depend on the installed tree that way where production must not. A literal-prefix table still cannot express **modified** Home/End (`ESC [ 1;5 H`); that needs a regex, not another row.
    - **`useMouseWheel`'s explanation of why this is safe is wrong about the mechanism**, though right about the outcome, and the copy in `useRawKeys` corrects it. There is no flowing mode: attaching a `'readable'` listener pins `state.flowing` to `false` and a later `'data'` listener does not resume it. The `'data'` event fires anyway because `Readable.read()` emits it for the chunk it returns — so the handler runs **synchronously inside Ink's own `read()`**, ahead of Ink's dispatch, on the identical string. Nothing is starved, and we get first look. `setRawMode(true)` is then load-bearing rather than ceremony: besides being ref-counted, it is what keeps the count off zero, since Node _would_ resume the stream if the last `'readable'` listener went away while a `'data'` listener remained — delivering keystrokes to us **instead of** Ink.
    - **We cannot consume the sequence** (Ink has no stop-propagation), so the bytes still reach every mounted `useInput`. Harmless for Home/End precisely because of the defect — `input` is `''`, which no handler acts on. For CSI-u it is not harmless, which is why the editor strips it beside the `looksLikeMouseReport` swallow. **Stripped, not swallowed whole:** a chunk can coalesce the keypress with real typing (`[13;2uabc`) and discarding all of it would silently eat the `abc`.
    - **Chunk coalescing is a live Ink 5 defect this works around rather than fixes.** A TTY read returns whatever was buffered, and Ink anchors its parse at the start of the whole chunk — measured, `"abc" + Home` arrives as the literal text `abc\x1b[H` (raw ESC typed into the buffer) and `Home + "abc"` **loses the `abc` entirely**. `parseNavKeys` therefore scans rather than whole-chunk matches, so our decoding does not inherit the bug; what Ink does with the same bytes is beyond reach without a consumption model. Reported fixed upstream in 6.8.0/7.0.0's incremental tokenizer — from their release notes, not measured here, unlike everything else in this block.
    - **Precedence is the rule that was already written down.** `promptEmpty` — with text in the prompt Home/End belong to the line editor, otherwise they jump the transcript. That is the gate the dead branch already chose; the overlap when the prompt _is_ empty is harmless, since Home/End on an empty buffer move a cursor already at 0. An open overlay unmounts both `Prompt` and `TranscriptViewport` in full-screen, so no overlay competes.
  - **Height bounding windows by slicing the string, NOT by `TranscriptViewport`'s `marginTop`/`overflow` box.** `LineWithCursor` returns a bare `<Text>` used _inside_ a `<Text>` flow and Ink forbids `<Box>` inside `<Text>`; introducing one means splitting the prompt's input row into sibling flex items, which is exactly the #354 defect. The window is **pre-wrapped**, and that is the point: Ink word-wraps, which yields a different row count than the arithmetic driving the window, so the cursor would drift out of view. Below the cap the buffer is returned untouched, so ordinary typing keeps Ink's own word-wrapping and looks unchanged. `wrapRows` carries **indices**, not strings, so the cursor rebase is exact. It deliberately does not reuse `viewer-util.wrapText`, which word-wraps, collapses whitespace runs and re-injects indentation — each of which destroys the character-index → `(row, col)` mapping a cursor depends on. Width is read from `useDimensionsCtx()` rather than `useStdout`, because under the test renderer those disagree (context falls back to 80 columns, ink-testing-library's stdout reports 100). Bounding lives in `BoundedLine`, used by **both** inputs rather than in `Prompt` alone. They share the editor, so they shared the defect: fixing only the prompt left `TextInputOverlay` reaching **85 rows for an 8k-character answer** inside the same fixed-height modal frame. Reachable precisely where it hurts, since `insert()` strips newlines for single-line editors, so a pasted `ask_user` answer becomes one long soft-wrapped line. Each caller passes its own `reserveColumns` because only it knows what box it sits in. **The prompt box's other child is bounded the same way (#358).** `PlanPanel` renders _inside_ the prompt's border via `renderAbove` and was separately unbounded on both axes: `PlanStore.create`/`add` push without limit and the `plan` tool's schema declares no `.max()`, while `STEP_FIELD_MAX` caps a description at 400 characters per FIELD, not per row — so one maximal step soft-wrapped to 7 rows and a 10-step plan of them reached ~72, three terminal-heights inside a `height={rows}` frame. Fixing only the step count would have left a 3-step plan able to occupy 21 rows; the horizontal cap is also what makes windowing over step INDICES valid (one step is one row), so `clampOffset`/`listPosition` apply unmodified — the move `HelpOverlay` made in #392 with `descriptionWidth`. The geometry is the React-free **src/ui/plan-window.ts**, deliberately neither `windowBuffer` (single string, character cursor, cursor pinned to the last row — right for an input, wrong for a step list) nor `overlayViewport`/`viewerFrameHeight` (both baseline at `rows - 1` because their component owns the whole frame; the panel owns a slice). `renderAbove` became a **render prop** so the budget flows down: `Prompt` is the one component that sees both children and the border, so the box's height reads as an expression in one file rather than an emergent sum of two files' private constants — the same ownership rule as `reserveColumns`. The two caps stay **independent** (a shared pool would need both children to lift their demand into `Prompt`, and the plan lives behind `PlanPanel`'s own store subscription), but the plan's is deliberately the smaller: a quarter of the frame against the input's third, and the plan pays its three chrome rows out of that budget while the input's `▲`/`▼` affordances are siblings outside its own (they count **rows**, not "lines" — the buffer is frequently one logical line, and the 901-character message behind #435 wraps to ~13 rows with no newline in it). The window seeds on the `in_progress` step — a plan's implicit cursor — and is stateless, since the panel has no scroll keys. The position row is reserved unconditionally (`OverlayFooter`'s rule) so the panel's height never depends on the budget that decides what is hidden, and `listPosition` returning `null` IS the suppression rule rather than a second `total <= size` test that could drift from it.
  - **The slash-command picker is the third thing in this dock, and it was unbounded (#589).** `SlashHints` rendered one `MenuRow` per match inside a bare `<Box marginLeft={2}>` — no border, no header, and **no height bound of any kind**: no `maxRows`, no slice, no window. `matchSlashCommands('/')` returns the whole 38-entry catalogue, so typing a bare `/` produced a **42-row frame** at the 24-row fallback. Exactly #358's defect (the plan panel, unbounded in the same box) and #354/#355's (the input, unbounded on both axes); this was the one selectable list that never got the fix, because it lives in `Prompt.tsx` rather than in `overlays/`. **src/ui/slash-picker.ts** is the React-free geometry, a sibling of `plan-window.ts` rather than part of it — the three frame constants it needs are exported from there, so nothing is duplicated, and a module named for the plan should not accumulate a second surface's arithmetic. Everything else is reused unmodified: `MenuRow`, `viewer-util`'s `clampOffset` / `listPosition` / `formatPosition`, and `truncate`. It stays **below** the prompt box and draws its own border: the rounded box means "the plan and the input are one container", and a completion list that moved inside it would change what that box says.
    - **The budget charges the input ONE row, where `planPanelMaxRows` charges it ten, and that is a fact rather than optimism.** `matchSlashCommands` returns nothing once the buffer holds a space and nothing once the token outruns every name it could match, so while the popover is up the buffer is a **prefix of a command that exists** — at most 17 characters today, pinned by a test. `inputRegionRows` charges `BoundedLine`'s cap because the plan panel is persistent and has to hold for a buffer it cannot see; charging the cap here is not conservative but fatal, leaving the picker **two command rows out of 38** at 24 rows, the size most people run.
      - **It is NOT an argument that the picker may then ignore the plan panel, and the first cut of #589 shipped believing it was.** That cut took the two budgets independently, on the reasoning that the plan's over-charge of the input was slack the picker could spend for free. It holds only while `planPanelMaxRows` is clamped by its `quarter`; the moment it is clamped by `room` the plan has already taken the whole remainder and there is no over-charge left. Measured against the real functions, the transcript got **0 rows at 22 and 23** and **1 at 24** — `FALLBACK_DIMENSIONS`, the height the module's own comment calls the one most people run — against a `MIN_TRANSCRIPT_ROWS` of 3, recovering only at 27. That is the #392/#396 failure class every bound in this family exists to end, and borrowing below a floor another module enforces while a comment says the overlap is free is worse than not having the bound.
      - **So the picker fits into what the plan left, and the plan does not resize when the popover opens.** `slashPickerMaxRows` charges `planPanelMaxRows(termRows)` in full, whether or not a plan exists — the panel owns its own store subscription, so `Prompt` has its budget and not its height, and charging the budget is the conservative direction. The ORDERING is the one `FRAME_CHROME_ROWS` already argues for one module over: resizing the plan panel because an unrelated surface appeared is a worse artifact than one row of over-reservation, and the plan is the surface **already on screen** when the picker opens — taking its rows makes it move, and gives them back on Esc. The picker has no "before" state to disturb. It also keeps the result a function of `termRows` alone, so the popover does not resize when a plan appears or completes. Cost, stated: with no plan on screen the picker is smaller than the frame could afford — six command rows at 24 rather than eight.
      - **`slashPickerMaxRows` is therefore NOT monotonic in `termRows`**, and that is the shape of the fix rather than a defect: at the height where the plan panel first appears it claims its floor and the picker gives up those rows in the same step. What is monotonic is what the two claim TOGETHER, which is what the test asserts — plus that every row the picker gives up went to the plan rather than back to the frame.
      - **The guard has to charge the same frame the production path does, and the first one did not.** It restated the chrome by hand — correct, per `plan-window.test.ts`'s rule that importing the constants makes an assertion self-consistent with whatever they say — and then restated `FRAME_CHROME_ROWS` as `1` where it is `1 + 2` (the hint/status row **plus the busy spinner**), and dropped `MIN_TRANSCRIPT_ROWS` entirely. So it asserted against a frame two rows shorter than the budget itself charges for: at 24 it computed 21 ≤ 24 and passed while the real sum was 26. `Prompt.test.tsx` could not catch it either, because it mounts `Prompt` alone and there is no transcript there to squeeze. Measured after the fact, the old guard passes **20/20 with the defect fully present**. A guard computing a different invariant from the one it is named for is worse than no guard. `MIN_TRANSCRIPT_ROWS` is imported rather than restated, because it is the thing being ASSERTED rather than a term of the sum — the split `plan-window.test.ts` makes in its own sibling of this test.
    - **It never returns 0, which is its one divergence from `planPanelMaxRows`.** That one yields the plan panel entirely on a short terminal, and can, because a plan is reference material. Rendering nothing here would leave `/ex` showing no completion while Enter still ran `/exit` — a silent action. So on a terminal too short for the transcript floor as well, the picker borrows from the transcript, and the rows come straight back on the next keystroke. That is the whole difference between this surface and a persistent one, and it is why the priority ordering inverts.
    - **The header is the position row, reserved unconditionally**, per `OverlayFooter` — a row rendered only when something is hidden makes the popover's height depend on the budget that decides what is hidden. `listPosition` returning `null` IS the suppression rule (no second `total <= size` test to drift from it); the row then degrades to the bare noun, which is what lets it double as the title: `commands` when everything fits, `commands 1–8 of 38` when it does not. **No glyph in it**, per `glyph-width.ts` — and a width assertion written with `.length` **cannot see** that defect, which was measured: with an emoji in the header the `.length` version passes 15/15 while the `stringWidth` one fails.
    - **One command is one row**, which is what makes windowing over command INDICES valid so `clampOffset` applies unmodified — the move `PlanPanel` made for steps and `HelpOverlay` for descriptions. **Measured in display COLUMNS, not UTF-16 units**, and the rows are not a closed set: `App.tsx` synthesizes a completion per saved routine whose description is `${kind} · ${r.name}`, and `RoutineStore` stores `name` raw with no validation anywhere — unlike the id, which `ID_PATTERN` holds to ASCII. Counting units let a CJK gloss pass the budget and render at twice it: measured through the real component, a 40-character CJK description made the popover **6 rows where its budget said 5**, one past the `maxRows` it was handed, with `clampOffset` and `listPosition` both quietly describing something that was no longer one row per index. `widthOf` / `truncateToWidth` / `padToWidth` are the three sites, in `slash-picker.ts` rather than beside `text.truncate`, whose file is a declared zero-import leaf — and deliberately not Ink's `wrap="truncate"`, which this file records as a second broken `slice-ansi` copy that over-runs rather than over-cuts, the dangerous direction for exactly this invariant. **The equal-width test cannot catch it** — Ink wraps INSIDE the fixed-width box, so every line is still 74 columns and there is simply one more of them; only a row count sees it, and that fixture was `'x'.repeat(400)`, all narrow. The `widthOf` fast path is pinned by comparing against `stringWidth` for **every code point** rather than a fixture list, because widening the range by one block silently admits the C1 controls, which measure 0 columns and 1 unit. `splitSlashRowWidth` gives the NAME the row when the two cannot both fit, because the name is what the buffer is a prefix of, so a row that has cut the name has cut the only part answering "did I type enough?". The popover's width is fixed rather than sized to the widest current match: content sizing changes the box's width on every keystroke as the list narrows, which is the horizontal twin of the "window that visibly breathes" `menu-geometry.ts` refuses. `Box`'s `width` is the OUTER width, so the row budget has to be handed back its own chrome — off by two and every maximal row wraps, which breaks the one-row invariant rather than merely looking wrong.
    - **The fifth hand-rolled keymap, now on the shared one.** #266 unified four selectable overlays onto `list-nav.ts` + `use-list-cursor.ts` after they had drifted; this one was missed for living outside `overlays/`, and routing it through deletes the manual clamp AND the `useEffect` that chased a stale index down a shrinking match list. Two options are load-bearing and neither is the default: **`digits: false`**, because a digit in this buffer is TEXT (`/2` is the start of a routine name, not "run the second row"), and `total: matches.length`, because `listNavIntent` answers `null` for every key once that is 0 — which is what lets `handleListKey` sit ahead of the literal-buffer Enter without claiming Enter when nothing matches. **Ordering is the part that fails silently**: it must sit AFTER the history rail, or the second ↑ of a recall moves the picker instead of the history, since `listNavIntent` claims ↑ whenever anything matches. That was written wrong on the first cut and an existing test caught it.
    - **Wrap is kept, and is now a decision rather than an accident.** It wrapped because it was the list nobody had unified, not because anyone had chosen it; kept because a completion popup is something the user cycles the way every shell completion menu does, and reaching the tail of a 38-entry catalogue should not mean holding ↓ thirty-seven times. It lives as `wrap` on **`ListCursorOptions`, not in `list-nav.ts`** — that module's own split is that the keymap answers "which way, and by how much?" and the consumer answers what that means here, and a delta is the same delta whether the list cycles or not. Default off, so the four form-shaped overlays are untouched. `%` is remainder and not modulo in JS, so stepping up off row 0 gives `-1` and clamps straight back to 0: the wrap silently does nothing in the one direction nobody tests first.
    - **Not done:** the file is still called `SlashHints.tsx` though it is no longer a hint strip. Renaming means touching `App.tsx`, which imports the `SlashCommand` type from it, for no behavioural gain.
  - **A question is a header, not a field label.** `ask_user`'s free-text path passed the model's whole question as `ValuePromptOptions.label`, putting a full sentence on the input's own row; it now goes through `headerLines`, which Ink soft-wraps on its own. The choice path already did this correctly via `requestMenu(entries, {title})`. `ask_user` is the worst case but not the only one — the custom-provider wizard's 66-character API-key label overflowed the same way with no model involved, which is why the structural fix (stacking label above input) is the one that matters.
  - **What a numeric prompt ACCEPTS is one decision, and it was five (#440).** `parseInt` reads a prefix — `parseInt('8192abc', 10)` is `8192` — and five prompts in `App.tsx` each spelled their own guard against that, arriving at four different answers. The registry-driven `/options` one had none, so `max-tokens` stored half of what was typed with nothing on screen saying so. `acceptInteger` / `acceptInRange` (exported from `App.tsx`, since `buildResumeSeed` and `isScaffoldingMessage` already are) are the one decision, and they hand back **a value or `null`** rather than a boolean or a toast: the five callers report a refusal three different ways — a toast, a silently-returned `undefined` that the profile wizard reads as "field left alone", and a `continue` inside the model-params loop — so the decision is shared and the telling is not, the `apps/manage.ts`-returns / `app-cli.ts`-prints split applied to a prompt. `null` rather than `undefined` because **`0` is a legitimate answer** (`token-window` disables itself with it) and a guard written as `if (!value)` refuses the exact entry the field documents; every call site tests `=== null`.
    - **The float half is closed too, and the rule is per-FIELD rather than per-type.** The first cut kept every float prompt on `parseFloat` and argued the integer round trip could not be transplanted — true (`String(Number.parseFloat('0.50'))` is `'0.5'`, which would refuse the commonest temperature entry) and being read as _"no predicate exists"_, which is a different claim and a false one. **`Number` is the predicate**: it keeps `0.50` and rejects `0.15abc`. So three of four float prompts take `acceptNumber`, and `/agent-options → Scratch subject-change threshold` really was storing `0.15` for `0.15abc` — the same defect as `/options`, one type over, which nobody had looked for because #440 only names the integer half.
      - **`runThresholdPrompt` is the single exception**, and the test is whether a trailing suffix MEANS anything at that field. It is the dual-scale 0-100 box whose own toast offers `0.8 or 80` and whose value runs through `normalizeThreshold`, so `parseFloat('80%') → 80 → 0.8` is a reading someone plausibly meant — verified live. Nowhere else: `80%` is nonsense at a 0-1 threshold and at `temperature`, where a swallowed suffix silently runs the model at a number nobody chose. The exception is one line calling `acceptInRange` directly, which is what `acceptInRange` taking an already-parsed number buys — the strict and lenient prompts differ by one visible token at the call site.
      - **A second reason for the exception was offered in review and does not hold**, recorded so it is not re-adopted: that `Number('') === 0` would turn a blank submit into a stored `0` at a 0-100 field. `TextInputOverlay`'s `cancelOnEmpty` defaults to `true`, so a blank Enter resolves `cancelled` and never reaches a parse — measured at both threshold prompts, setting untouched. Exactly the shape of #440's own trim claim: a hazard the overlay had already closed. `acceptNumber` guards empty anyway, because its three callers are each safe today by a **different** accident (`val.cancelled`, `if (!trimmed)`, `if (raw === '')`).
      - **Two functions were exported for tests, and a mutation check is why.** `pickWizardField`'s `float01` and `pickGenerationParamsInk`'s float branch — the second being `temperature`/`topP`, the fields this is really about — were the two swaps nothing could see: this file's test header records `/profiles` and `/model` as deliberately not driven through Ink, and both functions take every dependency as a parameter, so a stub drive is the cheap honest route. A test that cannot fail is worse than none, and without these two the change would have shipped with its headline site unpinned.
    - **#440's trim half is not real, and the correction matters more than the claim.** It says the `/options` prompt "does not `.trim()` … so `' 8192'` slips through too". `TextInputOverlay` trims on commit, so `raw` is already trimmed for every one of these callers — which also means the four sites that trimmed before parsing were each doing it redundantly. `acceptInteger` trims anyway, so its contract holds on its own terms rather than by a property of one producer, and the test that pins it says plainly that no production caller can reach it.
    - **The refusal says what the entry must LOOK LIKE, not what it must be.** `/options` now refuses `007` and `+8192` where it used to store 7 and 8192, and the old toast — "Must be a positive integer" — is false of both: `007` IS one. A refusal that misstates its own reason is this PR's defect one layer over, since the user re-types the same thing having been told nothing wrong with it. The other three integer prompts word theirs the same way and are left alone: they refused `007` before this change too, so the imprecision is pre-existing rather than newly minted here.
    - **Two more spellings live in `setup-wizard.ts` and are deliberately left there.** That module is pure by contract — questions and decode rules over an injected context, testable with no terminal — so importing `App.tsx` would hand it the whole Ink tree, the edge `tool-bytes.ts` and `mcp-names.ts` exist to refuse. A pure leaf beside `line-geometry.ts` takes all seven; it belongs with #441's unification of the three settings registries rather than ahead of it. For the same reason no `max` was added to `OPTIONS_REGISTRY` even though `WIZARD_FIELDS` carries one for the same four settings — `settings-coverage.test.ts` reconciles them in the meantime.

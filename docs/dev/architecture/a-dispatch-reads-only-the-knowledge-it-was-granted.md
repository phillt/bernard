# A dispatch reads only the knowledge it was granted (#511).

- **A dispatch reads only the knowledge it was granted (#511).** #508 reserved `memoryScope` and `knowledgeScope` and refused to declare them, on its own rule that _"a declarable field with nothing enforcing it is a lie on disk"_. This is the enforcer. A scope is a **narrowing view over the live store instance**, derived once in `runDefinition` onto a shadowed `ctx` — so the context block and the tool half are fenced by the same object, and neither `context-message.ts` nor `createTools` ever learns the word "scope".
  - **Shadowing is the mechanism, not a style choice.** `runDefinition`'s parameter is `rootCtx`, and one line after `resolveDispatchProfile` a `const ctx = scopeContext(rootCtx, profile)` takes the name back. Every `ctx` below is then the scoped one with no reference touched — including `def.tools(ctx, …)`, where six of the ten `createTools` call sites read `ctx.stores.memory`. A second name would leave "reach the unscoped context below line N" merely discouraged; shadowing makes it unrepresentable. `scopeContext` returns `rootCtx` unchanged when nothing is declared, so `main` keeps **object identity** and the byte-stable tool block the prompt cache needs (#269) is untouched.
  - **`pac-critic` needs a zero-line diff, and that is the proof the fence is in the right place.** It returns `contextInputs: () => null` — no memory block at all — _and_ builds `createReadOnlyMemoryTool(ctx.stores.memory)` inside its own `tools()`. So it ends up read-only **and** scope-filtered, the two wrappers composing because one fences actions and the other fences rows. A fence in `getContextMessages` misses it entirely; a fence in `createTools` misses it too. Only a fence on the store catches both — the critic is not an awkward exception, it is the test case that says where the fence goes.
  - **A view, not a second store, and `AppletStore(appId)` does not transfer.** `MemoryStore.scratch` is a per-**instance** in-memory `Map`, so a `new MemoryStore(scopeDir)` hands every scoped dispatch an **empty scratch** — `<scratch_notes>` renders blank, `scratch.read` returns nothing, and nothing errors. Applet data has no shared session state; memory does. `scoped()` shares `scratch` and the mtime `cache` by reference and pins that with a test, which is what catches a later refactor back to a directory.
  - **Narrowing is monotone and widening is unrepresentable.** The intersection happens inside `scoped()`, so no public method takes a scope argument and `a.scoped(x).scoped(y)` admits only what both allow. That is also what makes it **idempotent**, which is what licenses the two-reader treatment below.
  - **`knowledgeScope` is the existing RAG `domain` axis — no new field, no migration, no re-embedding.** 3,586 records are already labelled (`general`/`conversations`/`tool-usage`/`user-preferences`, measured) and `scoreAndRank` already _groups_ by domain, so the filter goes in **front of** a grouping the ranker was built around: a scoped search is the same ranking over a smaller corpus, not a truncation of a wider result. The axis has been populated and ranked on since day one and never once filtered on.
  - **`memoryScope` matches the SANITIZED key, and that ordering is the correctness argument.** `MemoryStore` repairs names rather than rejecting them and cannot stop — `CronNotesStore.sanitizeJobId` imports `sanitizeKey` — so `"pro j-secret"` and `"proj-secret"` address one file and must get one verdict; checking the raw key gives two. That is the inverse of `AppletStore`'s reject-don't-repair rule, and the inversion is the point: that store _can_ reject, because its ids are repaired nowhere. The pattern language is deliberately tiny (an exact key, or a prefix ending in `*`) — anything richer is a language, and a fence written in a language is one nobody can read at a glance.
  - **Scope constrains WRITES too, which the issue only asks about for reads.** A write you cannot read back is incoherent, and an unscoped write from a fenced worker turns the fence into a **publishing** channel: the worker writes `user-preferences`, `main` renders it next turn. `MemoryScopeError` is caught at the `memory`/`scratch` tools and returned as a `permission` error rather than allowed to become an AI SDK `ToolExecutionError` — the model asked to save something and must be told, in words it can act on, that it did not happen.
  - **`resolveDispatchProfile`'s fallback rule INVERTS here, and the file says so.** For `stepRatio` an invalid value falls back to the site default, which is safe; for a fence the fallback **is full access**. So a non-array resolves to `[]` (deny-all), an array with some invalid entries keeps the rest (dropping from an allowlist already narrows, and rejecting a whole scope over one typo buys nothing), and `memoryScope: []` is honoured as deny-all. That last diverges from `targetToolsScopeError`, which rejects `targetTools: []` — correctly, because "no tools" is incoherent while "verify against the task and nothing else" is a coherent posture.
  - **Two places a `runDefinition`-only fence fails OPEN, both closed by a two-reader `declaredScope`.** `dispatchToolWrapper` assembles `childTools` **and** the four ctx-bound dispatch tools before the runner sees the input, and `toolWrapperDefinition.tools()` returns `input.childTools` verbatim — so a scoped wrapper would be fenced in its block and hand the **unscoped** root ctx to every child tool. `apps/dispatch.ts` has the same shape. Both scope early and let `runDefinition` re-derive, which is safe because narrowing is idempotent; it is the treatment that file already documents for `declaredToolSurface`, for the same reason. Pinned against what `createTools` is **handed**, because everything downstream inherits that argument.
  - **`RAGStore.turnSearchCache` is keyed on the query string alone**, so a scoped view carries **no** search cache: `main` searching "deployment process" unscoped caches fifteen results, and a scoped child searching the same string would get the unscoped ones back with no code path ever consulting a domain. The embedding cache, where the real cost is, stays shared.
  - **Cron's pre-connect search needed its own application.** `runHeadless` starts the RAG search **before** `assembleContext` on purpose, to overlap the ~1.1-1.6 s MCP connect — so it is the one retrieval a ctx-level fence cannot reach, and `RunHeadlessOpts.scope` applies at both points. That field is **optional**, diverging from `writeScope`/`toolPermissions`, and the divergence is what the default means: an omitted write scope was an accident nobody decided, while unscoped is the deliberate system-wide default for every dispatch including `main`.
  - **Unset means unscoped, on `Specialist` and on `CronJob` both.** Deny-by-default is the stronger position in the abstract and is rejected: silently blanking every existing job's memory surfaces as "the job answered worse", which #510 already records as the quietest failure mode in this tree — and cron, with no operator watching, is where it would be quietest. What makes it deliberate rather than inherited is that the fields exist with the default in the doc comment and a test is named for the decision. Declared on the two **records**, never on `AgentDefinition`: a definition is code, and putting it there creates a precedence question whose only safe answer is intersection, which nobody will remember.
  - **`text.scopeList` renders a fence, and is deliberately not `nameList`.** A fence must be shown WHOLE — `+N more` would hide the very entries someone is reading the line to check, and the one thing worse than a fence you cannot see is a fence you think you can. Shared because `[]` is a real posture (deny-all) that must READ as one, and the three sites had already spelled it two different ways on the day the idiom was introduced.
  - **The security test is a unit test, not an eval** — "cannot reach what it was not granted" is a property, not a measurement. Three assertions carry it: a **canary over the whole serialized request** (a sentinel must appear nowhere in system + messages + tool results, asserted on the whole payload rather than on named channels, because a two-halved fence's real failure is a leak through a channel nobody enumerated); a **behavioural sweep over every registered definition**, which is what would catch a definition building its own store; and **scratch is shared, not blanked**. The sweep carries its own guard-the-guard case, since every assertion in it is a `not.toContain` that passes trivially if no memory tool was reached.
  - **A caller-applied fence reaches the record through `RunDefinitionOpts.declaredScope`.** Cron's fence lives on a `CronJob`, which is not a specialist record — so `cronDefinition` has no `recordId`, `resolveDispatchProfile` returns the empty profile, and a fenced job would be recorded as **unscoped**: the worst possible gap for a field whose entire purpose is that a fence and a bad retrieval look identical from outside, on the one dispatch nobody is watching. It is reporting only; the ctx handed in is already narrowed. Reading the applied fence back off the scoped stores is the more general answer and was tried — it requires around thirty memory and RAG test doubles to grow a scope accessor to satisfy one diagnostic line, which is the design saying the runner should not interrogate a store to find out what it was told. The two store accessors that experiment added are correspondingly gone, and every scope assertion is behavioural: what a view can REACH, not what its bookkeeping says.
  - **The fence is recorded, in `DispatchContextRecord` and in `specialist inspect`.** A fence and a bad retrieval look identical from outside — both surface as a standing instruction simply not being there — and `memoryKept` alone cannot tell them apart, since an empty list reads the same whether the store had nothing to give or the dispatch was not allowed to ask. The Dispatch Context tab renders "Scoped to:" **above** the memory listing, because the fence is what explains the listing and a reader who meets the short list first has already drawn the wrong conclusion.
  - **A refusal reaches the model as a `permission` error, on every action, through one guard.** `storeErrorGuard` wraps both tools at the RETURN, so an action added later cannot land outside it. It replaced three inline `try`s, one of which had already produced the failure it invites: `supersede`'s catch-all reported a FENCE refusal as `invalid_args` — a model told it called wrong when it was told it was fenced, on the one action where the difference matters most, and it would retry with a different spelling forever. That also required `MemorySupersedeError`: the store threw a bare `Error` for "no memory with that key exists", which is precisely what forced the catch-all.
  - **`runDefinition`'s fail-soft `contextInputs` catch now logs.** It widens `null` to `{}`, so a definition that opts out of the context block entirely starts rendering one if its thunk ever throws — a contract change reported nowhere. The fence itself is unaffected either way: scoping happens above, on the store that line falls back to.
  - **A fence is authorable, and the sentinel is `''`.** #511 shipped without this and recorded the blocker: `undefined` means "don't change" and `[]` already means deny-all, so removing a fence had no spelling — and an authoring surface with no way to un-fence a record is how you get one nobody can fix. The answer was already in the tree; `role`, `strategy` and `toolSurface` all clear with `''`, and it cannot collide with a declaration here because it is not an array. So each of the three states is spelled differently: omit to leave a fence alone, `[]` to deny everything, `''` to remove it. The store applies all three through the existing `setOrClear`, over `SCOPE_AXES` rather than three more lines, so a fourth axis is declarable the day it exists.
    - **Refused at the creation boundary, dropped silently at the resolver** — the division `targetToolsScopeError` already makes. `declaredScope` runs before every dispatch including `main` and must never throw, so it falls back per entry; that is right for a resolver and useless as feedback, and a fence is the field where a silent drop is worst, since an entry that never matches is indistinguishable from a store with nothing to say. `scopeDeclarationError` reuses `declaredScope`'s own predicates rather than a second copy — a boundary that accepted what the resolver rejects would be worse than no boundary — and quotes a new `ScopeAxisSpec.hint`, which lives on the table beside the `validate` it explains.
    - **The zod keys are hand-written and a test walks the table to them.** Generating them with `Object.fromEntries` widens the parameter type to `Record<string, …>` and unpicks the typed destructuring, so the list stays manual; `specialist.scope-authoring.test.ts` asserts every `SCOPE_AXES` field appears in the schema — the record-to-surface direction, which is the one the mistake is made in.
    - **`/specialists` shows it, at two grains.** The list row appends `· scoped` when any axis is declared (that it is fenced, not to what — it is one line beside a name); `read` prints each declared axis in full through `scopeList`, no `+N more`, since the entries someone is reading the line to check are exactly what an elision would hide. And `buildSpecialistEditSeed` — the Edit hand-off, which tells the agent to change only what was asked — echoed six of the twelve fields a record can declare, so `role`, the three #508 execution fields, the three fences and `boundTo` were all invisible to the agent about to rewrite the record.
  - **Not in this change.** Actually scoping `pac-critic` (`memoryScope: []` is arguably right for it, but that is a behaviour change to the verdict path), namespacing memory keys, a `domain` field on `MemoryRecord`, scoping `provenance` (shared by reference on purpose, #173), and `delegates`/posture/`outputSchema` (still reserved, #501/#505).

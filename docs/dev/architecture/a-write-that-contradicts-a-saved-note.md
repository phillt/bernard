# A write that contradicts a saved note (#373).

- **A write that contradicts a saved note (#373).** Same key is fine, and a different raw key that sanitizes onto an existing file has been refused since #513. The bad case is a **different key with contradicting content**: both stay, both are injected into `<persistent_memory>` on every dispatch, both are the user's own words, and nothing separates them. It is also the case a user is most likely to create, because a correction is naturally written under a new descriptive name rather than the old one.
  - **Most of the issue was already discharged and the plan says so rather than re-doing it.** #513 and #529 landed `writtenAt`, `supersededBy`, `retiredAt`, `readRecord`, archive-in-place, and the key-collision guard — all four things the issue lists as prerequisites. Its "`MemoryStore` has no metadata at all" is now simply false. What remained is the one thing it is actually about: nothing compared new content against **other** keys.
  - **It fails OPEN, which is the opposite of its two nearest neighbours.** `claim-verifier` and `memory-consolidation` both fail closed, correctly, because their neutral outcome is "assert nothing" and "propose nothing". Here the neutral outcome is _losing a memory the user asked to keep_, so an error, a timeout, an unparseable reply, an invented key and a missing `config` all resolve to no-contradiction and the write proceeds exactly as before.
  - **It never refuses.** `tools/memory.ts` already argues against a refusing memory tool — a false refusal silently loses a standing fact at the moment the user asked to keep it — and that argument is why the verdicts are _supersede_ and _ask_ with no _no_. Even "discard what I just saved" **retires** the note that is already on disk rather than un-writing it, which one deleted front-matter line undoes.
  - **`contradictionNote` returns a string, never a decision**, and it reports what HAPPENED rather than what was decided: a `supersede` whose `store.supersede` throws says "both are kept", because a result that claims a retirement that did not occur is worse than no check at all.
  - **It runs AFTER the write, and that ordering is a correctness constraint rather than a preference.** `supersede` refuses a replacement that does not exist, so the incoming key must be on disk before any acting verdict can land. The first cut ran it before the write, where every one of the three acting branches fell through to "both are kept" — the check spent a full round trip and could only ever produce a sentence, **indistinguishable from the model having declined**, and the `DISCARD` branch's own comment ("the note is already on disk by now") described a state the call site did not produce. It was invisible because the tests mocked `store.supersede`, which is why `memory.contradiction.disk.test.ts` drives a real directory instead. The ordering also means a write refused by the collision guard costs no model call at all.
  - **The import is dynamic, and that is load-bearing.** `tools/memory.ts` sits in `createTools`' eager `audience:'any'` group, and #529 measured **+17 ms** on every tool-registry build when a `generateText`-owning module was pulled in from there statically — which is why `memory-proposal.ts` exists as a leaf. Same trap, one file over.
  - **`renderMemoryCorpus` IS reused**, and is exported from `memory-consolidation.ts` for it. The write-time check needs the same bounded, whole-records-only rendering of the same corpus under the same budget, and writing it again would have made a **fourth** memory budget loop in the tree (`context-message.packMemory`, `recall-filter.buildMemoryBlock`, #529's, this) — where #528's own finding was that two of those had already drifted apart. The incoming note goes in as `head` so it is CHARGED against the budget: it is caller-supplied and unbounded, and a head that did not count could push the whole message past the cap. The consolidation caller's "Here are N saved notes" line stays outside, because the count names what was actually SENT and cannot be written until the budget has decided.
  - **`ProposalSchema` is deliberately NOT reused**, though it looks like the obvious fit. Encoding "this write supersedes `X`" as a `duplicate` proposal fails by construction: `validProposals` gates every key on existing in the store, and the incoming key does not exist yet — that is the premise. The question is a different shape too: one candidate against N yielding one verdict, not a list of up to five. `consolidationInputs`, `parseStructuredOutput`, the site/`traceLlm`/usage shape and `MAX_PERSISTENT_MEMORY_CHARS` all transfer unchanged.
  - **Two plumbing gaps were solved rather than discovered.** `createMemoryTool` received neither `ToolOptions` nor `BernardConfig`; it now takes an optional `deps` bag, and each absence is a deliberate degradation — no `config` means no check, no `askUser` means keep both (the headless answer `headlessToolOptions` gives for free by omitting the callback), no `onUsage` means the spend is unrecorded rather than unmade. And **`ToolExecOptions` carries no usage handle at all**, so a tool that calls a model had nowhere to report what it cost — the exact defect `claim-verifier` complains about, one layer down. `ToolOptions.onUsage` is derived by `withUsageRecorder` in `runDefinition`, beside `scopeContext` and for the same reason: that is the single place with both a `ctx` and a route to every definition, so no dispatch site has to remember. **On `ToolOptions`, not `CreateToolsOptions`** — the first cut put it there and had to argue in its own docstring that it does not vary the tool bytes, which is the tell that it was in the wrong bag: that one is a decision about which built-in SURFACE a dispatch receives, guarded by a prompt-cache byte-stability rule, while this is a per-dispatch callback a tool reaches back through, which is exactly what `askUser` / `confirmAction` / `getToolPermissions` already are. The consequence was visible in the same commit — `createMemoryTool`'s three deps arrived from three different places.
  - **Its own model site, not a reuse of `memory-consolidator`.** Same role, same tier, same temperature policy — verified identical — but the two run at completely different rates (once per session in a detached worker versus once per write inside a turn), and collapsing them makes `bernard usage` unable to say which is costing you.

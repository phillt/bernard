# One rule about role and pins, obeyed by both creators (#519).

- **One rule about role and pins, obeyed by both creators (#519).** `specialist-creator` and `agent-builder` both implement create → execute → assert `ok` → roll back or commit, and they **disagreed about the single most important model-selection field**: `agent-builder` requires a `role` and forbids a pin, `specialist-creator` mentioned neither. That silence is not neutral — `createSpecialistTool` auto-assigns a policy-resolved `provider`/`model` when a create declares neither, so the older and more-used creator has been minting **persisted pins nobody chose**, which is exactly what the off-lineup guard exists to drop.
  - **The blocker #519 does not name: a bundled record cannot be updated at all.** `copyBundledJsonIfAbsent` returns early when the file exists ("never overwrite a user-edited copy"), `seedOnce` returns early once its marker is written, and `permissionsFor` gives builtins `canEditDefinition: false` — so editing `specialist-creator.json` in place reaches **only fresh installs**, i.e. almost nobody. A `-v2` filename plus a `POST_V1_BUNDLED` entry reaches an existing install but leaves the old record on disk beside it: two creators with one job, which is worse than the divergence being fixed. So "one rule, obeyed by both" is a hollow claim without a re-seed mechanism, and the mechanism is the change.
  - **Re-seed the definition, keep what was learned.** `refreshBundledDefinitions` rewrites an installed bundled record's definition when the shipped bytes differ, preserving `goodExamples`/`badExamples`/`createdAt`/`disabled`. Overwriting is safe **because of** the authority model rather than in spite of it: `canEditDefinition: false` means a user cannot legitimately have edited the definition, and `appendExamples` is the one carve-out — which is precisely what is preserved. Keyed on a hash of the shipped file, so it runs once per shipped change and never on an unchanged one, and per id, so one record's edit does not rewrite another's. Only records that already **exist** are touched: a bundled specialist the user deleted stays deleted, which is the promise `POST_V1_BUNDLED`'s own markers already carry. This is what makes every future bundled-prompt fix reach an existing install instead of accumulating `-v2` files.
  - **The auto-pin is gone, which is the only enforceable form of the rule.** `createSpecialistTool` used to mint a policy-resolved `provider`/`model` and persist it whenever a create declared neither — the cause this issue diagnoses, left in place while the remedy shipped as prose. Prose in two bundled prompts binds a model that read them; removing the writer binds every path: a hand-written record, `/specialists`, a future creator, or `agent-builder` on a turn where it forgets. `resolveSiteModel` already treats "declares neither" as the site default, so the resolved model is unchanged — decided live rather than frozen, which is the whole difference between a binding and an intent. Its old justification (byte-for-byte back-compat for existing callers, `specialist-creator` named explicitly) expired the moment that creator was the thing being fixed.
  - **`ROLE_NOT_PIN_RULE` is a constant for the reason `PLAIN_LANGUAGE_RULE` is**, and it cannot be interpolated into a bundled JSON record — so `bundled-manifest.test.ts` asserts both prompts contain it verbatim, the same shape that pins the interview playbook. Copies of a rule do not fail, they diverge.
  - **`targetTools ⊇ toolAllowlist` is enforced at BIND, which is the only place both halves exist.** A specialist is created before its applet action is known — `agent-builder` deliberately creates unbound, validates by execution, then binds — so there is no `toolAllowlist` in scope at create; at bind there is, exactly. `grantedToolNames` hands a dispatch the intersection, so a tool the action allows and the specialist does not target is simply **absent**, and the run fails as a bad ANSWER rather than an error. Reuses `uncoveredTools` / `uncoveredToolsMessage` as a fourth consumer; the VERDICT is deliberately not shared, per that module's own note, and this one **refuses** for the reason `checkDispatch` refuses — a model mid-authoring will not come back to it. Both doors carry it, since a create may bind directly.
  - **It fails OPEN, and `inspect` reports rather than refuses.** A missing app, an unparseable manifest or an unreadable registry means the check could not run, not that the binding is wrong; refusing a legitimate bind because a manifest was mid-write is worse than the defect. And a binding that already exists must still be describable — refusing to describe it is how the one command that could diagnose it becomes useless.
  - **One marker for the whole bundle, keyed on stat metadata.** The first cut wrote a `.definition-<id>-<hash>` per record per shipped change and left every previous one behind, forever, in the directory `list()` and `getSummaries()` `readdir` — unbounded, unlike the `.seeded-<id>` markers beside it. And keying on file CONTENT meant the read could not be skipped: 77 KB re-read and SHA-256'd on every seeding construction, which is every REPL start, every `assembleContext`, and the `bernard script` path #452 got to 17 ms. Stat metadata instead, the same assumption `MemoryStore`'s read cache already documents, with old markers swept when the bundle moves. Measured: **0.279 ms → 0.086 ms** per construction.
  - **`specialist { action: 'inspect' }` answers what a record cannot say about itself**: the model a `role` resolves to right now and by which `SiteModel.source`, the steps a `stepRatio` actually buys against the live `maxSteps`, the surface, and any coverage gap in a binding. That is the concrete form of #519's "diffed against a target profile", and it is only expressible once #508's fields exist — which is why this stacks behind it. It goes through `resolveDispatchProfile` and the dispatching definition's own `stepBudget`, never a second implementation: re-deriving the arithmetic is the failure this action exists to catch, one level down — it would report an out-of-range `stepRatio` as though it will be honoured, miss a `tool-wrapper`'s `Math.max(2, …)` floor entirely, and re-hardcode `SPECIALIST_STEP_RATIO` as a literal. Saying "declared X is invalid and is ignored" is the single most useful line it has, and it is exactly the line a second implementation gets backwards.
  - **Not re-keyed as an action-scoped tool.** `specialist` is `kind: 'write'` wholesale and is a documented non-adopter of `ToolMeta.actionScoped`, because users may hold persisted rules keyed on the bare name. `inspect` inherits `write` exactly as `list` and `read` already do; re-keying the family needs its own change with a migration.

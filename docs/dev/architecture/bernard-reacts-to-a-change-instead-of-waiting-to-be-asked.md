# Bernard reacts to a change, instead of waiting to be asked (#479/#201/#493/#202).

- **Bernard reacts to a change, instead of waiting to be asked (#479/#201/#493/#202).** Nothing in the tree could do that: there was no path by which an external or asynchronous event started a turn — every `runAgentTurn` call sat on a user-interaction stack. `src/watchers/` is the mechanism, and the four issues are one feature because every durable-execution runtime implements them as one: Inngest's `step.sleepUntil` beside `step.waitForEvent`, Temporal's timers beside signals, LangGraph's `interrupt()` + checkpointer. **A sleep is a watcher whose trigger is a clock.**
  - **Level-triggered, and that is the design rather than an implementation detail.** A watcher reads CURRENT state and compares it against a snapshot taken when it was created; it never consumes an event stream. That is the Kubernetes controller pattern, and it buys the property that makes an unreliable poll clock acceptable — a watcher that misses eleven consecutive polls still fires correctly on the twelfth, because the snapshot is what it compares against, not the gap. **That is why #400 (cron silently dropped fires during OS sleep) was not a prerequisite**, and why none of this touches the cron scheduler — the argument stands unchanged now #400 is fixed, since a level-triggered watcher needed no help from it either way. The watcher poller and the cron scheduler are separately clocked and neither reads the other. The honest limit is a genuinely TRANSIENT event — one that appears and is gone between two polls — where the answer is a durable log at the source (Gmail's `historyId`) reached through an `mcp` target, never a faster poll.
  - **The poller lives in the REPL, not the cron daemon.** It borrows the session's already-connected `MCPManager`; cron connects MCP **per job run** at a measured 1.1-1.6 s, which a 60 s poll cannot pay. Three borrowing rules are load-bearing: re-take `snapshot()` every poll rather than caching `tools` (caching the flat bag is exactly the #305 regression that silently zeroed every `delegate_<server>`, and a captured bag cannot see a server that reconnected); never call `close()`, which tears down every client for the whole session; and hold the manager from `stores.mcp`, not a frozen `ctx.mcp`. Structurally it is `InboxWatcher` again — plain class, mount-once effect, `unref()`ed timer, re-entrancy guarded, never throws — and it looks once immediately on `start()` rather than waiting a full tick, so a `time` target that came due while no session was running does not sit unnoticed.
  - **No model in the poll loop.** A 60 s watcher polls 1,440 times a day; dispatching an agent to answer "nothing changed" is the shape this must not take (`CronJob.prompt` runs a full agent per fire, ~49k prompt tokens). A probe is a fetch, a `stat`, or one tool call, and the agent runs only when the predicate fires. Probes are restricted to READ-classified tools via `watchableToolRefusal`, which delegates to `isReadOnlyMCPToolName` — the same gate `mcp.ts` classifies a server's tools with, so there is one answer to "what is safe to call without a person" rather than two that drift.
  - **The wake carries two channels, and the split is a compile error rather than a convention.** `bernard say` deliberately never starts a turn, and CLAUDE.md calls that structural; a watcher DOES, so the guarantee is re-established on different ground by asking who wrote each byte. `instructions` were authored by this session when the watcher was created and go in the instruction slot; whatever the watcher then OBSERVED — an email body, a page — travels as `UntrustedData` through the new `ProcessInputOptions.data`, rendered last under its own banner. #509's brand is minted in exactly two places and a plain string cannot be assigned there, so the natural mistake (concatenating the observation in because it is "just context") does not type-check. A watcher wake never touches the inbox transport at all, so `bernard say`'s two tests pass **unchanged**.
  - **The transcript shows an abstract of the wake, not the wake.** The two channels were being rendered TWICE: `WakePanel` announced the turn correctly, and then `agent.ts` joined the wrapped instruction with the fenced observation into one `role:'user'` message that `commitNewHistory` painted seconds later as a right-aligned bubble behind the `❯` chevron — a ~40-line instruction plus ~4 KB of somebody's inbox, attributed to the user. The panel's docstring had stated the correct rule all along ("it can be megabytes of somebody's inbox, and the panel's job is attribution, not disclosure"); it was simply not the only render. **Every existing wake test used a `time` target**, which has no data block, which is how it shipped.
    - **The summary is minted where the bytes are, and the payload never reaches the panel.** `observationOf` computes `renderObservation(value)` ONCE and derives both the block and an `ObservationSummary` (`bytes`, a 200-char `excerpt`, `clipped`) from it, so the panel's "3.2 KB observed" cannot disagree with what the model was handed. A `StaticItem` lives in an append-only array for the whole session, so a cap enforced at the mint is the version of "don't hold the inbox" that survives a refactor — carrying `data.text` and truncating at render is not.
    - **`splitObservationBlock` is the inverse, and it has two consumers precisely so it is not a parser written for one call site.** Two readers only ever meet the JOINED form: `buildResumeSeed` rebuilds the transcript from `CoreMessage[]` on disk, and `rag-query.ts` composes a retrieval query from recent user turns — which was therefore retrieving against a JSON dump of a chat thread on **every** woken turn (`stripProfileWrapper`'s `$` anchor cannot match text with a block appended after the closing tag, so the whole wrapper leaked too). Both take the same fix and it is an ORDERING, not a regex change: split first, and what remains ends in the closing tag again. `renderObservationBlock` builds its first line from `OBSERVATION_BANNER_PREFIX` so producer and detector cannot drift — the `session-markers.ts` pattern — and it is **deliberately not used on the live path**, which already has the summary.
    - **The size is a FLOOR when the observation was itself bounded.** `renderObservation` caps at `MAX_OBSERVATION_CHARS`, so `bytes` saturates at ~4 KB — a watcher that read a 2 MB page and one that read a 4 KB one reported identically, on the one surface whose job is saying how much is held back, with the `(truncated, N chars total)` marker sitting far past the 200-char excerpt where no reader meets it. `renderObservation` returns the flag rather than leaving it in the string for `summariseObservation` to find, which would be the module parsing its own prose. It is deliberately a FLAG and not the pre-truncation total, which is not knowable on the branch that matters: `boundedStringify` bounds the WORK, so a bounded walk never visits the rest of the value and the true size would cost exactly the traversal the bound exists to refuse — reporting a total available only on the cheap branches would make the panel quieter precisely when the observation was largest. The parameter is **required**, so a caller states it rather than inheriting "complete" by omission; the resume path, which has no bounding step in scope, reads the marker through `redact.ts`'s own `looksTruncated` — beside its producer so the two cannot drift.
    - **The excerpt is DETACHED, and that is the cap rather than a nicety.** `String.slice` returns a V8 `SlicedString` — a pointer to its parent, not a copy — so a 200-character excerpt transitively pins all 4 KB of the flattened observation, on an object that lives in an append-only array for the whole session and outlives the copy in history (`compressHistory` can replace those messages while the panel still holds the bytes). Measured over 2,000 summaries of a realistic ~3.5 KB observation: **3,653 B retained per summary against 285 B**, a 12.8x overshoot. The obvious spellings do NOT detach — `.concat('')`, `.repeat(1)`, `.normalize()` and a head-first `slice(0, 2*CAP).replace(...)` all still measured 6,230 B, because a head slice is itself a `SlicedString` and `replace` returns its input UNCHANGED when the regex finds no match, which is the common case since `renderObservation` JSON-escapes and emits no whitespace at all. Only an explicit `Buffer` round trip works. This is the exact hazard the module's own docstring claims to have closed; the FIELD is 200 chars, the string REPRESENTATION was not.
    - **`collapseWhitespace` is one rule with two reasons.** `summariseObservation` had re-spelled `normalizeForDigest` byte for byte, in the same package. They describe the SAME bytes — the digest decides whether a `changed` predicate fires, the excerpt decides what the panel then says about it — so a change to one that missed the other would make the panel describe a string the digest never saw. Renamed for the OPERATION rather than for either caller, since the motivations legitimately differ (validator churn versus a newline smuggling an extra row into a bordered panel).
    - **The Agent hands back the message it pushed; `App` does not go looking for it.** `getLastUserMessage()` is a per-turn snapshot beside `lastUserInput`, set at the `history.push` and cleared by `clearHistory`. The predecessor captured a history length, re-read the array after `processInput` and scanned the range for a `role:'user'` entry — forensics on somebody else's private array for a message it had just created, resting on two facts stated nowhere in `agent.ts`: that the push is synchronous before the first await, and that there is exactly one of it. The sibling producer `injectAskUserHistoryMessages` already RETURNS its messages for the same WeakSet. Identity is the contract, not equality — the WeakSet cannot be keyed on a structural match — and a mutation replacing the recorded object with a spread copy is caught.
    - **Suppression keys on the RENDER that happened, not on a text feature.** `runAgentTurn` gains `extra.announced` and `drainNextTurn` passes it for every queued turn, so a `time` wake (panel rendered, nothing observed) and a `say --run` prompt are covered by the same rule rather than by a data-block sniff that correlates with it. `askUserRenderedRef` generalised to `alreadyOnScreenRef`: "already on screen" is one concept and a second WeakSet beside it would be two spellings of it. Unlike the `ask_user` echo the item is **not** withdrawn on an aborted turn — that echo claims something reached the model, while the panel claims a watcher fired, which stays true.
    - **Detail follows `config.toolDetails`**, no new setting. `StaticItem.toolDetails` was **required** and hard-coded `false` at the wake push, four lines from a sibling item passing the real value; a required field carrying a hard-coded lie is worse than an absent one. The forward lives in the single `StaticItemView` ladder, which is what gets both transcript surfaces right by construction. `TranscriptPanel` gained a generic `detail` slot ABOVE the footer — `children` renders below it, so a disclosure about the body would read as an afterthought about the panel.
    - **Resume renders a panel with a degraded source (`'a watcher'`).** The persisted message is all there is, so the name and reason are unrecoverable — attribution is the invariant and the name is a nicety, while replaying a woken instruction as a `❯` bubble re-creates the confusion #493 exists to prevent with no live panel above it to correct the reader. **`splitObservationBlock` THEN `parseUserMessage`, and it looks commutative**: a panel does not run the latter, so reversing them renders `<user_request>` inside the border. Splitting first also repairs an existing wart — `parseUserMessage` strips a _trailing_ closing tag, which a woken message never has. Two consequences stated rather than left to be rediscovered: a `time` wake replays as an ordinary bubble, and a user who pastes the banner gets a panel on resume only.
    - **A finished watcher is off the list.** `list()` is the raw reader and `sweep()` keeps a terminal record for 24 hours, so "what watchers do I have?" had no single answer and both `/watchers` and `watcher {action:'list'}` answered _"everything that happened today"_ — Bernard cancelled six and reported them cleared while the list showed six `cancelled` rows. `listableWatchers` is the one shared rule: `cancelled`/`fired`/`expired` go, and **`failed` stays**, because `lastError` is the only diagnostic that path writes and `sweep`'s retention exists specifically to protect it. The poller, `sweep` and `findDuplicate` keep the raw reader.
  - **The queue was a prerequisite, not polish.** A turn started while one was running hit `submittingRef` and returned SILENTLY — right for a second Enter, fatal for a watcher, which would have marked itself fired and told the user nothing. `src/ui/turn-queue.ts` is a plain FIFO drained from `runAgentTurn`'s `finally`, and every non-keystroke producer goes through `requestTurn` rather than `runAgentTurn`. A wake arriving mid-turn queues as a NEW top-level request (#202's answer, not #200's): a watcher's instruction is a new job, not a correction to whatever the user is asking about right now. Note the contrast with `src/inbox/`, which states that nothing queues because "a notice contends for no singleton" — still true of a notice; a turn contends for all three.
  - **`+ <request>` is here now (#202), and the blocker really was the input path.** `<Prompt disabled={busy}>` gated every keystroke, so the branch was unreachable; dropping `busy` from that expression — which is the whole of the enabling change — puts the Prompt's own Esc (dismiss the picker) against App's (abort the turn), and Ink broadcasts every key to every mounted handler with no stop-propagation, so neither can consume it. **The arbitration is App DECLINING, not Prompt consuming.** `Prompt` reports through `onEscapeGuardChange` the one boolean that IS its own Esc guard (`matches.length > 0 || historyCursor !== null`) rather than two flags App recombines, so "Esc was handled" and "Esc will be handled" cannot answer differently; App skips only the ABORT while it is set, never the voice stop, which both handlers already performed on every idle Esc. So the first Esc dismisses and the second interrupts. The value App reads is the PRE-Esc one by construction — `Prompt` reports from an effect, which runs after both handlers have been called — and that is correct rather than a race to work around: what was on screen when the key was pressed is what decides what the key meant.
    - **The queue itself needed nothing.** `TurnQueue`, the FIFO ordering, `drainNextTurn` re-triggering from `runAgentTurn`'s `finally`, and the per-turn lifecycle all carried over untouched; `list()`/`remove(id)` for `/queue` are eight lines. The new arm is `{kind:'user'}` on `QueuedTurnSource`, whose `switch` has no `default` — so it was a compile error until every consumer had something to say.
    - **`describeSource` became `announcementFor`, returning the TITLE as well as the origin.** "◷ Woken" is true of a watcher and of a `say --run`, and false of a request the user queued themselves — so a source that supplied only the meta row would have been announced under a title contradicting it, on the one surface whose whole job is provenance. Title and meta come from one table, so the two halves of one row cannot drift. `WakeData.title` is carried on the item rather than derived in the panel for the reason `source` is already a phrased string: a `StaticItem` lives in an append-only array for the session and is re-rendered from it, so it has to be self-contained. `WOKEN_TITLE` is exported for `buildResumeSeed`, which rebuilds a panel from the persisted message alone and would otherwise hand-write a second copy of a cell in that table.
    - **Bare mid-turn text steers the turn in flight (#200); it is neither refused nor queued.** It was refused while #200 was open, precisely so the plain keystroke would not acquire #202's meaning and then flip under anyone who learned it. `agent.interject` puts it in a per-turn inbox and the runner delivers it before the next model request. Whatever the turn never reaches — typed during the final text step — comes back through `takeUndeliveredInterjections` in `runAgentTurn`'s `finally` and runs next as the user's own request, with a toast saying so. After an Esc it does NOT run, since starting a turn off a correction to the work just stopped would undo the stop; the interrupt notice names it, and `Prompt` calls `onRecordInput` before `onSubmit`, so it is one `↑` away.
    - **Every other slash command is refused mid-turn too, by allow-list.** Enabling the prompt reaches the whole dispatch chain, and all ~45 of those branches were written against an idle REPL — several mutate `agent.history` or swap the model under a running loop, and `/clear`'s own re-entrancy guard returns SILENTLY, which is the invisible no-op this change exists to remove rather than multiply. `BUSY_ALLOWED_COMMANDS` holds `/queue` alone and the default is refusal, so a command added later is refused until somebody decides it is safe there. **Enter on an EMPTY buffer deliberately does not meet that gate** — `Prompt` routes it to `onEmptySubmit`, so acting on a delivered message queues silently mid-turn where typed text is refused. It is not text: it reaches `requestTurn` and nothing else, so none of the branches the list guards is reachable from it. And it keeps #202's meaning rather than #200's, because a delivered message is a new request from somewhere else, not a correction the user is typing into their own turn. What counts as a command is `isSlashCommand`: whatever the idle chain would dispatch — a member of `DISPATCHED_COMMANDS` (the legacy pointers are members) or a saved routine. Anything else the idle chain hands to the agent, so mid-turn it goes to the turn: `/tmp is full` means the same thing busy or idle. An earlier cut judged by shape and refused it.
    - **Dropping a queued wake releases the watcher, through the same writer the drain uses.** `outstandingWakesRef` is cleared in `drainNextTurn`'s `finally`; a `/queue` removal that did not do the same would leave that watcher marked outstanding for the life of the session and it would never fire again — the silent inertness the whole watcher feature exists to remove, reintroduced by a menu row. `releaseWake` is the one writer, because the second copy is the one that gets forgotten. **Two callers is a convention rather than a property, so the removal is pinned** — and it takes a REPEATING watcher to pin at all: `releaseWake` early-returns for anything that is not a watcher, so the obvious test (drop a `+` turn) covers precisely the case where the call does not matter, and a one-shot watcher marks itself terminal on its first fire and would never have woken again regardless.
    - **`+` is uniform, never forked on `busy`.** `requestTurn` already owns "run it now when idle, queue it when busy"; deciding again at the call site would be a second copy of that decision keyed on `busy`, which lags `submittingRef` by a render. The cost is that an idle `+` renders a `◷ Queued` panel for a turn that starts immediately — truthful, since it really did go through the queue. The acknowledgement toast fires only when it is genuinely waiting behind something, and it is a toast rather than a transcript notice because the durable record is that panel; writing both would put two entries in the transcript for one request.
    - **The prefix requires whitespace (`/^\+(?:\s+|$)/`).** Without it `+1 to that` and a pasted diff hunk both become deferred instructions, and a line the user meant literally silently becoming one is the worst outcome available here. A bare `+` matches so the prefix can explain itself rather than being submitted as a one-character question.
    - **#200 shipped by having Bernard own the streaming step loop.** Its three candidate mechanisms were checked against the installed `ai@4.3.19` and **none of them exists**: `experimental_continueSteps` is a boolean gating auto-continue on `finishReason: 'length'`; `experimental_prepareStep` is absent from `streamText` and, even on `generateText`, returns `{model, toolChoice, experimental_activeTools}` and cannot touch `messages`; and `onStepFinish` runs inside a transform on the CONSUMER stream while the step recursion happens producer-side, so awaiting there gates our read rather than the next request. Abort-and-reissue was rejected as a race rather than a contract. So `runStreaming` now issues one `streamText({maxSteps: 1})` per step and asks `AgentSpec.takeInterjections` before each one.
      - **It costs no tokens and changes no bytes, and that is measured rather than argued.** The SDK already re-sends the whole conversation on every step, as the initial messages plus the accumulated response messages, which is exactly what each call is handed. `runner.owned-loop.test.ts` drives the REAL `streamText` both ways with a scripted model and asserts every prompt the provider receives is deep-equal, along with the aggregate. It never mocks `ai`, which is the point. **It does cost CPU**: `standardizePrompt` validates the prompt against the SDK's message schema once per `streamText` call, which was once per turn and is now once per step — measured at ~0.12 ms per message, about 130 ms over a typical ten-step turn and a 30-70 ms pause before each late step of a 150-step one. The public API has no way to skip it; SDK 5 removes it.
      - **The continuation rule and the aggregate are copied, not approximated.** Continue iff the step made tool calls, every call has a result, and the budget has room — the condition in `streamText`'s own `flush`. The aggregate is `streamText`'s, which differs from `generateText`'s in two fields: `text` is every step's text concatenated, and `sources` accumulate. `usage` is summed raw, so a missing count stays `NaN`. The step payload handed to `onStepFinish` gets its cumulative `response.messages` prefix put back, because `partialObserver.onStepMessages` keeps partial work on Esc by that contract.
      - **Scoped to the streaming branch, which is the main agent alone.** Nothing else takes user input mid-run, so every dispatch on `runNonStreaming` keeps the SDK's own loop. `runDefinition` forwards the drain only when it streams, so the type says what the behaviour is; the REPL always registers a sink, so a non-streaming main agent with a pending message does not arise in practice. SDK 5's `prepareStep` can rewrite messages and would replace this loop with one function when the bump happens.
      - **The safe point is "before a request", which is what makes it safe.** Tools execute inside a step, so a drain between steps cannot land mid-tool-call; `never drains in the middle of a tool call` pins the ordering. It runs before step 0 too, so something typed during the pre-turn pipeline reaches the first request — which is why the inbox is not cleared at turn start.
      - **The message reaches history with no plumbing of its own.** It rides the loop's cumulative `response.messages`, so the existing flush persists it in position. Two edges needed handling. `runDefinition` reports a drained message to the partial observer (`onInterjections`), because the snapshot only refreshes when a step finishes, and an Esc during the step it rode would otherwise lose a message the user watched land. And `commitNewHistory`'s compression re-anchor used to land on the LAST user message, which stops being the turn's opening message once a turn holds user messages of its own; it anchors on `agent.getLastUserMessage()` by identity now. The length-continuation notice already put a user message mid-turn, so that was latent before this.
      - **One component renders it, live and committed.** `runDefinition` wraps the drain the way it wraps `onTextDelta` and the tool callbacks, so the framework emits the `user-interjection` stream event itself and the Agent has no listener of its own. The event carries the exact history message, so `StreamingAssistantMessage` renders it with `UserMessage` between the blocks around it, and the turn-end commit renders the same object from history in the same place. `INTERJECTION_NOTICE` is the model-facing line that says it arrived mid-work and asks what can and cannot still change; `parseUserMessage` and the RAG query strip it through `stripInterjectionNotice`, and the bubble's footer says "sent while working" instead. It is deliberately not in `BOUNDARY_PREFIXES`: it is the user's own words, not scaffolding.
  - **A woken turn is an ordinary turn.** It inherits the session's configured `toolMode`/`confirmMode` with nothing threaded, because `processInput` resolves `policyDecision` from `this.config` on every turn and a wake reaches it through `runAgentTurn` like any other. No watcher-specific posture, no strict-by-default exception. The consequence is stated rather than hidden: under the default `confirmMode: 'auto'` only high-risk calls prompt, and an MCP email send classifies medium — the same exposure a typed turn has. If that is wrong it is wrong everywhere and the fix belongs to the global levels, not to an exception that makes watchers behave unlike the rest of the product. A test asserts a wake resolves the same decision a typed turn does, which guards against someone later "helpfully" adding an override.
  - **Targets and predicates are closed sets**, the argument `apps/manifest.ts` already makes for its arg types: an open language is an open injection surface, and a watcher is frequently authored by a model. Targets are `mcp` / `http` / `file` / `time`; predicates are `changed` / `appeared` / `matches`. **`appeared` is the one that expresses "tell me when John replies"** — `changed` would also fire when something is DELETED, and an existence test would fire instantly against a mailbox that already has a match. Two details decide whether it behaves sanely: the baseline is captured **at creation** (deferred to the first poll, a real digest compares unequal to an absent one and every watcher wakes the moment it is made), and an unreadable `idPath` mid-flight means "cannot evaluate", never an empty list — an empty baseline makes every pre-existing item look new and fires a false wake naming things that were always there. A `304` is safe to act on; a `200` is **not** proof of change, so the body is still digested, with whitespace collapsed at the string LEAVES (collapsing after `JSON.stringify` is too late — a newline is already the two characters `\` and `n` by then).
  - **A watcher can stay armed, and it re-arms in the SAME pass that fired it.** One-shot was the original shape and it loses messages in normal use: the agent must create a fresh watcher after every wake, which costs a turn each time and — the part that actually loses things — leaves a GAP, because anything arriving between the fire and the re-create is already present when the new baseline is captured and is therefore never reported. Observed across six hand-made re-arms, with replies landing in the window. `repeating` advances the baseline to the ids THIS poll saw, inside `pollOne`, so the window does not exist. It is bounded in work as well as in time: `expiresAt` is the clock, `maxFires` is the ceiling (default 50, clamped at creation like `intervalMs` and `ttlMs` — the one bound that exists to stop a runaway was the one a model could set to a million).
  - **A probe is never shaped, and that is now a declared contract rather than an omission (#572).** `MCPManager.snapshot(shaping?)` treats an absent config as pass-through, so the two watcher call sites were already correct — by saying nothing, while `index.ts` and `headless.ts` both pass one. "Make them consistent" is a one-line edit with no compile error and, before this, no failing test. Measured against the real shaper at its real 8,000-char default on a chat page: `capArray` drops from the **BACK**, so an `appeared` id set **saturates at about twelve ids however large the page is** — 10 items yields 10, 20 yields 12, 100 yields 12. A 30-message chat baselines at 13; a 20-message burst between two polls then reports 13 new items and loses **7 permanently**, because `evaluate` advances `baselineIds` to the ids it kept and the rest can never re-enter the window. It looks healthy throughout, and works today only because beeper is called `direction: "before"` (newest-first) — a server paginating oldest-first would make `appeared` inert from birth. `unshapedTools()` is the accessor, **named for the property and not for the watcher** so a second consumer does not grow a second name, and it must never take a parameter. It delegates to `getTools()`, not `snapshot().tools` — that is not a second assembler but the shared flatten one level below the three-field bag #305's rule is about, and going through `snapshot()` built a full `makeAliasResolver` index the probe path never reads (0.041 ms of a 0.136 ms call, per watcher, per tick). Shaping is right for a result entering a model's context, which is what it was built for; a probe result is hashed for `changed`, id-scanned for `appeared`, and reaches a turn only as a separately-bounded excerpt. The guard is a PAIRED test — the shaped bag must be shown to really cut the same payload, or the unshaped assertion could pass because shaping had quietly become a no-op.
  - **The probe's own ceiling REFUSES where the HTTP one truncates.** `probeHttp` has always sliced at `MAX_HTTP_BODY_CHARS`; `probeMcp` had nothing, and `unwrap` runs `JSON.parse` on arbitrary server text — the one place this module amplifies a string into an object graph (measured at 12.25 MB: parse 14 ms, `changed` digest 90 ms, on a background timer). `MAX_PROBE_RESULT_CHARS` is 1 MB, a safety valve rather than a budget: across 265 real results on the tool watchers actually poll the median is 13.5 KB, p95 32 KB and the max 72 KB. **Truncating is not available here in either form** — slicing the encoded text breaks `JSON.parse` and degrades to hashing a mangled prose blob, while slicing the parsed value drops ids from the end of an `appeared` set with nothing to say so, which is the silent inertness `idPathRefusal` exists to kill. So it is a probe FAILURE, which `MAX_PROBE_FAILURES` turns into a stopped watcher carrying a readable `lastError` — and because `captureBaseline` runs the same `probe`, the refusal reaches the authoring model at CREATE time, where it can still narrow the call. Measured on `only.text.length`, which is O(1); the shapes that arrive already parsed by the MCP client are deliberately **not** bounded, since the only way to size them is the serialisation this exists to avoid, and a test pins that non-goal so nobody "completes" it.
  - **`matches` bounds the work without moving a byte, and `boundedStringify` is the trap.** It serialised the whole value and then kept 4 KB — 61 ms for a 12 MB payload, the anti-pattern `renderObservation` was already fixed for. That fix is **not** reusable: `boundedStringify` walks through `JSON.stringify`'s replacer and so does not SORT KEYS, and it drops array elements past 100 regardless of the character budget. Both change what a regex sees. Concretely, for `{zebra:'MATCHME', alpha:'a'.repeat(5000)}` the first 4,000 characters contain `MATCHME` under `boundedStringify` and do not under `stableStringify`; and 150 short ids serialise well under the budget today, where the item cap would drop the last fifty and make a watcher matching one of them silently inert. So `stableStringify` gained its own `maxChars` instead, whose contract is `bounded(v, N).slice(0, N) === unbounded(v).slice(0, N)`. **Every token the walk emits is charged, not only the string leaves** — the first cut counted strings alone, so a payload of numbers and booleans never tripped the budget at all: 40,000 rows of `{id, ts, ok}` came back at the full 1,548,900 characters in 51 ms, byte-identical to the unbounded walk and slower for the bookkeeping, which is precisely the shape `MATCH_INPUT_MAX` exists for. Object KEYS are the other half of that hole, reachable with empty-object values. Structural punctuation is still uncharged, so the budget stays a deliberate under-estimate — same bytes, bounded work, both loops breaking rather than joining megabytes of separators. **`digestOf` stays unbounded and a test says so**: a digest over a prefix cannot see anything past it, so a `changed` watcher would poll cleanly forever and never fire. That is the one a later symmetry-seeking cleanup would get backwards.
  - **A watcher holds ONE outstanding wake at a time, and the QUEUE is the wrong place to enforce that.** Coalescing two entries in `TurnQueue` was the first attempt and it folds almost nothing: `drainNextTurn` calls `take()` BEFORE awaiting the turn, so while a turn runs the queue is EMPTY and a repeat fire has no sibling to fold into. Checked against the very trace it was written for — 02:00:44 fires, the turn starts at 02:01:04, 02:02:44 fires against an empty queue, and so on for **five consecutive turns over six minutes**, each an 800-character instruction at 500k-900k prompt tokens answering a message the previous turn had already read — it would have folded **zero** of them. "One outstanding wake" is a fact about the watcher's LIFECYCLE, not about queue membership, so it lives in `App`'s `outstandingWakesRef`: added on accept, cleared in the drain's `finally` so an aborted turn still releases it. The second fire is refused, and the **poller's existing refusal path then does the rest for free** — it `replace`s the record it was holding, whole, so the baseline is never advanced past items no turn acted on, and the next poll fires once, cumulatively. That is strictly better than folding, which discarded the older observation. Refused **silently**, unlike the queue-full case: this is ordinary operation for a watcher on a live conversation, and a panel per suppressed fire is the noise the refusal exists to remove. The dangerous direction is over-refusal — a flag rather than a per-id set silences every OTHER watcher for the duration of one turn — so the test seeds two due watchers and asserts both fire, mutation-checked against exactly that.
  - **`ProviderStallInfo.producedOutput` means "unsafe to re-issue", and the decline says `work-already-done`.** The transport mints it meaning "bytes of THIS response reached the consumer", which is all a `fetch` wrapper can know; `runner.ts` widens it to the dispatch's own answer, since a stall on step 7 is unsafe whether or not anything was printed. The decline message did not follow, and read `output-already-emitted` for every case — so a real session carried `provider:stall {producedOutput: false}` and `stall:recovery:declined {reason: 'output-already-emitted'}` at the same millisecond for the same event: two true lines reading as a contradiction, on the one path somebody triages a lost turn from. The fix is a reason true in **both** cases rather than a second field to keep in sync with the first — which half it was is already recoverable from the `step:end` rows sharing that `dispatchId`. **Four of six stalls in that session declined**, all multi-step, which is the honest shape of this feature: recovery helps a dispatch that stalled before doing anything and cannot help one that stalled at step 7, because re-issuing would re-run six steps of tool calls including writes.
  - **A refused wake puts the record back WHOLE, not by patch.** The queue is bounded and may say no, and a watcher is marked terminal before delivery — otherwise a wake sitting behind a long turn fires again on the next tick — so a refusal has to undo that, or one full queue permanently consumes the watcher the user was waiting on. It undoes it with `WatcherStore.replace(w)`, handing back the record the poll was holding, which is by construction the state before any of the fire and so cannot be an incomplete list of what to undo. The enumerated patch it replaces was **correct, and only for a reason nobody should have to hold in their head**: it named five fields, and the other four came back because `update` merges onto the `known` record it was passed — which was that same held record — rather than onto disk. Redundant rather than wrong, while reading as the thing doing the work: drop the `known` argument as an optimisation nobody needs and an advanced `etag` silently survives a refusal, sending the next poll's `If-None-Match` for a body this watcher never acted on. A patch also cannot express the `firedAt` half at all, since a merge adds and overwrites but never REMOVES.
  - **Two watchers on the same thing are a duplicate; two watchers on the same INSTANT are not.** `findDuplicate` keys on target + predicate — never the name, which is free text a model invents fresh each time, and never `instructions`, which is exactly what legitimately differs between two watchers on one chat. Same target AND same instructions is refused with the existing id; same target with different instructions is created, with a warning naming the other, because "tell me when John replies about dinner" and "tell me if anyone mentions the deploy" are both wanted. It matters more since watchers repeat: a one-shot duplicate wakes you twice and is done, while two repeating ones wake you twice for every message, indefinitely, with nothing in the transcript saying why — six were created on one chat in a single observed session. `duplicateKey` returns `null` for a `time` target rather than mixing a random term into the string: a random term makes an equality function non-deterministic, so the same record compared against itself is unequal, and the next caller to hold two keys is silently wrong with nothing in the expression saying so.
  - **A dead `idPath` is refused at creation AND named at every poll.** The silent-inertness failure this feature is most prone to: a path that names no list polls cleanly forever and can never fire, looking perfectly healthy — three real watchers sat in that state for an hour, because Beeper returns `{items:[…]}` while the tool's own example said `$.messages.id`. `idPathRefusal` is one wording with two callers, and it reads working alternatives off the payload in hand so a wrong guess is self-correcting. It was written twice, byte-identically, and only the creation-time copy named alternatives — so the failure that actually strands a LIVE watcher was the one told nothing. `Evaluation.unreadable` correspondingly carries the reason rather than a boolean: `evaluate` is the one place holding both the predicate and the payload it failed against, and as a boolean the poller had to re-derive a message from the predicate alone. A poll that cannot read its predicate counts as a probe failure, so it trips `MAX_PROBE_FAILURES` and stops with a `lastError` instead of polling forever.
  - **`bernard say --run` (#493) is the other trust case, and it is gated differently.** A watcher's instruction comes from a record the session itself wrote; a `--run` message's comes from any local process that can write the state directory. So it is **opt-in per session, never per message**: `--accept-remote-prompts` makes the session advertise `capabilities: ['notice','prompt']`, and `sendToSessions` filters on the RECORD, so a sender cannot upgrade itself. **The advertisement is not the control, though, and reading it as one is how this shipped with a hole.** `send.ts` is a courtesy to well-behaved callers; anything that can write `sessionInboxDir(sessionId)` can drop a message file straight in and never call it — which is the threat model `inbox/types.ts` states in as many words. So the receiving session checks `config.acceptRemotePrompts` itself at `onMessage`, and a `prompt` that arrives at a session which never opted in is **degraded to a notice** rather than dropped: the text really was delivered and the user should see it, and silently discarding it makes a refused prompt indistinguishable from one that never arrived. The refusal says so in the panel. A prompt against a plain session is refused at the sender with `not-accepted` — deliberately distinct from `none-running`, because telling someone staring at a running REPL that nothing is running sends them after the wrong problem. `isInboxMessage` now tests MEMBERSHIP of `INBOX_KINDS` rather than the literal `'notice'`: as a literal it happened to refuse everything, which looked like the "fail loudly against an older binary" property holding while actually making a second kind undeliverable rather than refused.
  - **Records persist across restarts; polling does not.** A watcher set at 09:00 for a reply that lands at 16:00 must survive the restart in between, and losing it silently is the failure the whole feature exists to remove. What is deferred is polling while **no session is running** — that needs the daemon to host watchers, a warm long-lived `MCPManager` (`headless.ts` already names that as an additive option shape), and a cross-process wake with replay protection, since a wake file any local process can write must not re-trigger an arbitrary watcher. Orphans whose owning session died are adopted on **every tick**, not only at `start()`, using `kill(pid,0)` — a stale pid can only fail to match. Every tick rather than once, because an owner that dies while this session is running otherwise leaves its watchers reading as active and never firing until the next restart — precisely the state adoption exists to remove. It costs nothing: the tick already lists the directory, and adoption takes that listing rather than sweeping it a second time.
  - **One file per watcher, not one `watchers.json`** — the one place this diverges from `CronStore`, whose single-file read-modify-write has no locking. Several sessions can each hold watchers and each writes `lastCheckedAt` every interval, so concurrent writes are the normal case here rather than the exception. `WATCHERS_DIR` is under `DATA_DIR` for the reason `APPLET_BRIEFS_DIR` states: a watcher is the user's own content, not regenerable bookkeeping.
  - **Two bugs fixed on the way.** `mcp.ts`'s reconnect notice was a `printInfo` straight to stdout while Ink owns the screen — it corrupted the live frame and was painted over on the next ~32 ms render, so the line deliberately made loud was the one least likely to be read; a background poll calling MCP tools between turns made it far likelier, and it is now a `debugLog`. And `meta-coverage.test.ts`'s hand-written `{ debugLog }` mock silently asserted that nothing under `createTools` uses any other logger export — it spreads `importActual` now, so the failure lands on whatever adds an import rather than here.
  - **Known gap: #201 is only half-served.** A `time` watcher gives "wake me at T and do X", but not #201's _resume the same run_ with a plan/scratch pointer. Within one session scratch and the plan store are still live, so a same-session sleep resumes with both in place — but a restart loses that, and full run-state resumption is net-new work.

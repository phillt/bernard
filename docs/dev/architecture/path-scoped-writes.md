# Path-scoped writes (#340)

- **Path-scoped writes (#340)** — an unattended write needs a **where**, not just a _what_. `src/permissions/write-scope.ts` is the pure containment leaf (`node:path` + `node:fs` only): a `WriteScope` is a `workspace` the dispatch may always write to plus optional `grants`, and `checkWritePath` decides. Enforced as a third gate in `augmentTools` (`runWriteScopeGate`) beside the block and confirm gates, so it covers every caller rather than one tool, and it runs **first** — an out-of-scope write is refused before anyone is prompted about it.
  - **This is what let cron have the write-capable file tools back.** #337 withheld them wholesale because of a risk-tier asymmetry: `shell` (`dangerous` → high) had write-shaped invocations denied headlessly while `file_edit_lines` (`write` + `local` → medium) would pass unprompted — an unbounded filesystem write through the one door that wasn't gated. The tiers cannot express the distinction that matters, because a write into the job's own workspace is low risk regardless of which tool made it. `cron.ts`'s `FILE_TOOLS` filter is gone; `tool-surface.test.ts` now asserts their **presence**, with a note that presence is not the safety property.
  - **The scope is an axis of `HeadlessPosture`, not a sibling option.** `HeadlessPostureInput.writeScope` is **required** (`WriteScope | null`) for the same reason `toolMode` and `confirmMode` are: an optional field lets a caller inherit "unrestricted" by omission, which is exactly what happened — applet actions shipped with no scope while being the _less_ trusted origin (browser-triggered, caller-supplied arguments). Stating `null` is a decision; omitting a field is an accident. Being an axis also means **`skipPermissions` dissolves it**, like the other two: leaving it in place made a job the user explicitly marked unrestricted still refuse `file_write` outside its workspace while `shell` in that same job stayed wide open, i.e. steering the model toward the less safe tool.
  - **Per-dispatch, not per-cron-job.** `CronJob.writePaths` populates a general mechanism rather than owning one. Cron was where the problem was found, but an applet action (#445) is a second unattended writer — triggered from a browser, with a caller supplying the arguments, i.e. a materially less trusted origin. Attaching the grant to a `CronJob` record would mean building it twice.
  - **A scope is opt-in, and absence means unrestricted.** That is what keeps the interactive REPL unchanged: scoping writes the user is watching themselves make is obstruction, not safety. `ToolOptions.writeScope` is a plain value, deliberately: it comes from a `HeadlessPosture`, exists only on one-shot unattended dispatches, and nothing user-facing mutates it mid-run — so unlike `getToolPermissions` / `getShellTimeout` it needs no live reader. (This line used to promise a `getWriteScope` thunk that was never built, which is plausibly what suggested a getter was the house style for #477's shell timeout — where a getter is actively wrong, since `withUsageRecorder` spreads `toolOptions` and a spread flattens a getter into a snapshot.)
  - **Containment survives symlinks and `..`, or it is decoration.** `resolveForComparison` resolves the nearest **existing** ancestor and re-appends the missing tail — the target of a write usually does not exist yet, so `realpathSync` on it would throw, and without this a symlinked parent (`~/safe/link -> /etc`) lets the write land anywhere. `isContainedIn` is separator-aware because a bare `startsWith` matches `/safe-dir-evil` against a `/safe-dir` grant. Grants are resolved the same way, so a grant that is itself a symlink still compares correctly.
  - **The refusal names the workspace**, and cron's system prompt states it up front. The caller is generated code with no operator watching: a bare "denied" is retried against the same path forever.
  - **The workspace layout is one convention in one place.** `runWorkspace(namespace, id)` (`paths.ts`) yields `<WORKSPACES_DIR>/<namespace>/<stable id>` — keyed on a _stable_ id (cron job id, app id) rather than a run id, because the point of a workspace is that output is still there next run. Each new unattended writer inherits the layout instead of re-deriving it. `writeScopePrompt` lives in `write-scope.ts` beside the refusal it prevents: the two are halves of one contract, and split apart they drift silently — a job with no operator retries a rejected path until its steps run out. **They are bounded by AGE now (#585), and `jsonl.ts` was the wrong idiom.** `pruneFileGroupsByMtime` cannot prune a directory and fails silently twice over: `listFilesByMtime` filters `e.isFile()`, so directories are dropped before they are ever ranked, and its `fs.unlinkSync` would throw `EISDIR` into an empty `catch` if one reached it. Handing it a workspace root is a no-op that looks like retention. The directory-shaped pair lives in `fs-utils.ts` beside `listSubdirectories`, whose own doc already drew that boundary (_"`jsonl.listFilesByMtime` owns the file-shaped sibling"_): `pruneSubdirectoriesByAge` and `atomicRemoveDirectorySync`.
    - **Age, not count or size, and the axis is the decision.** A count cap ranks peers against each other — right for `MAX_SESSIONS`, wrong here, because fifty hourly cron jobs are all live and a count would evict one live job's output to make room for another's. Size needs a recursive walk of every workspace on every sweep and still reclaims the biggest rather than the one nobody uses. The bound is `WORKSPACE_MAX_AGE_MS` (30 days), stated in `paths.ts` beside `runWorkspace` because the layout and its retention are one decision; the mechanism is `src/workspaces.ts`, since `paths.ts` is imported by nearly everything including leaves and stays `node:path` + `node:os`.
    - **`ensureRunWorkspace` stamps the directory on every run, and that is what makes the axis honest.** A directory's mtime moves when an entry is added to it, so unstamped, "age" would mean _time since the last file landed directly in here_ — and a job that writes its output once and reads it back on every later run would have that output reclaimed while it was still live. Stamped, it means _time since a run was last handed this_. **The stamp happens before the sweep**, and that order is load-bearing rather than incidental: a dormant workspace being picked up again IS older than the bound at the moment it is picked up, so sweeping first would delete the very output the run is re-using and then hand it a fresh empty directory, silently. Stamping first removes the case **within a process** by construction instead of by an exclusion the next editor can drop. **Across two it is a narrow residual, not a guarantee**: a sweep decides from a `statSync` and acts with a `renameSync` that never re-reads the mtime, so another process's stamp landing between those two changes nothing. It needs a workspace already past the bound, picked up in the microseconds between one `stat` and one `rename`, while another process's hourly window is open. Deliberately not chased — re-`stat`ing after the rename catches only the half where the stamp lands first, so it would be a narrowing wearing the shape of a fix.
    - **Retention is applied by the module that owns workspaces, never from `index.ts`** — `work-queue.ts` records what the other arrangement costs, and this is the same argument: the predecessor swept from `index.ts`, one line got written for the recall queue, and the correction queue was never swept at all. It hangs off **both** entry points, `ensureRunWorkspace` and `removeRunWorkspace`, for the reason `WorkQueue.ensureSwept` hangs off both `enqueue` and `peek` — the sweeper has to ride the same path as the grower, and a process that only ever deletes should still bound what it can see. A timestamp rather than a boolean, again: the cron daemon and the applet host hold a process open for days. Cost is two `readdir`s and a `stat` per workspace, at most hourly, against a `runHeadless` whose MCP connect alone is 1.1-1.6 s; `workspaces.ts` adds **0.81 ms** to `apps/tool-dispatch.ts`'s 494 ms graph — it is a leaf over `fs-utils.ts` and `paths.ts`, and `fs-utils.js` is already on that graph via `memory.ts`, its own ~20 ms being almost entirely the first `node:crypto` load.
    - **Nothing in a workspace needs to survive, and that is stated rather than assumed.** It is agent output written by an unattended run. The write-scope gate points an agent there precisely because it is the disposable place; user content lives in the other `DATA_DIR` stores, and `bernard cron-grant` is how a user says "write somewhere that matters". The bound is env-overridable nowhere, deliberately: a user who needs to tune it has output in the wrong place.
    - **Removal renames before it walks.** `fs.rmSync(dir, {recursive: true, force: true})` is depth-first and not atomic, so an `EBUSY`/`EACCES` part-way through leaves the directory under its ORIGINAL name holding whatever was not reached — a half-removed workspace the next run adopts as its own output. `atomicRemoveDirectorySync` renames to a `.<name>.<pid>.<hex>.removing` sibling first (a same-directory rename IS atomic). The predicate requires the leading dot AND the suffix: either alone matches something a user could legitimately own. `deleteApplet` was moved onto it for its data directory too, so directory removal has one implementation rather than two — and that is the site with the most to gain, since the SQLite handle may be held by the DAEMON rather than the deleting process, Windows blocks removal on an open handle outright, and WAL means the store is `data.db` + `-wal` + `-shm`, so a walk that dies part-way can leave an orphan WAL beside a deleted database for a re-added applet of the same id to open.
      - **The second half of that contract is in the HELPER, not in the callers, and it got there the hard way.** The first cut documented it — the JSDoc named `pruneSubdirectoriesByAge` as the collector — which was true of the one call site under `WORKSPACES_DIR` and **false of `deleteApplet`**, whose tombstone lands in `DATA_DIR/applet-data/` where nothing sweeps: a failed removal there would have held an applet's entire SQLite store forever, under a name nothing lists, and a third call site could have repeated that silently. It is also the _more_ likely site to fail. `atomicRemoveDirectorySync` now calls `collectRemovalTombstones` on the parent before minting one, so every removal clears whatever a previous interrupted removal left beside it and there is no call-site obligation left to forget. `pruneSubdirectoriesByAge` keeps its own unconditional tombstone branch as the PERIODIC collector — what makes a workspace tombstone hourly rather than "whenever the next job is deleted" — so a directory wants both. Residual, stated: a directory that sees neither another removal nor an age sweep keeps its tombstone until one happens, which is strictly less than the bare `rmSync` it replaced leaks under the live name. The applet case is pinned end to end by a `chmod 0o500` test in `apps/lifecycle.test.ts`, because there is no lifecycle hook there to hang a collector on and the assertion has to come from the remover.
    - **A deleted cron job no longer leaks, and there were FOUR callers, not three.** `CronStore.deleteJob` is a pure `jobs.json` filter, and the `cron` tool, `cronDelete`, `cronDeleteAll` **and the REPL's `/cron` menu** each paired it with `deleteJobLogs` and nothing else. `src/cron/lifecycle.ts` is `apps/lifecycle.ts`'s sibling and owns the whole sweep — row, logs, notes, workspace — rather than a method on `CronStore`, which would give a filter-and-save an edge to three other subsystems (that module's own header raises the objection about `AppRegistry`). It closes the notes leak this file already recorded: `CronNotesStore.clear()` had no production caller at all. **The artifacts are swept even when the row is already gone**, because every install that predates this has orphans from jobs deleted the old way, and a sweep gated on the row can never reach them; the boolean return is only what the `cron` tool needs to say "no job found". Deps are required rather than self-constructed, unlike `deleteApplet` — all four call sites already hold both stores. **`CronStore.deleteJob` now has exactly one caller in the tree**, which is what makes the sweep unbypassable rather than merely applied: a module every caller happens to use is a convention, a method with one caller is a property, and a fifth door has to come through it.
    - **`removeRunWorkspace` takes a namespace and an id, not a path, and validates both.** It is a recursive delete whose id arrives straight off a model's `cron {action:'delete'}` call, and `path.join` resolves `..` — so `runWorkspace('cron', '../../memory')` names a real directory outside the workspaces root. Nothing supplies such an id today (cron ids are UUIDs, app ids are schema-validated), which is exactly the kind of thing that stops being true quietly.
    - **Known gap: an empty namespace directory is left in place.** `workspaces/cron/` survives its last workspace, deliberately — removing it would only mean recreating it on the next run, and a namespace is structural rather than a thing anyone accumulates.
  - **`WRITE_PATH_TOOLS`' completeness is a test, not a comment.** Its incompleteness is silent and **fail-open** — a fourth path-taking write tool, or `file_write`'s `path` argument renamed, would ship unscoped with every other test green. `meta-coverage.test.ts` walks the constructed registry and fails if any `write`/`dangerous` tool with a `path` parameter is missing from the set. (`FILE_TOOLS`' incompleteness is at least user-visible; this one is only ever noticed by the write it failed to stop.)
  - **Grants come from the user, never the model.** `bernard cron-grant <id> [paths...]` (`--clear`, or no paths to show) is the producer; paths are stored resolved so a grant made from one working directory still means the same place later. Deliberately absent from the `cron` tool: letting an agent widen its own write scope is the escalation the gate exists to prevent.
  - **`shell` is deliberately NOT covered.** Extracting write targets from an arbitrary command line is not reliably possible, and a containment check that is sometimes wrong is worse than none — it grants confidence it has not earned. `WRITE_PATH_TOOLS` (`permissions/matchers.ts`, declared beside `FILE_TOOLS` so the two cannot drift) holds only the tools that write through a `path` argument. Reads are ungated: this bounds writes, and read scoping is a separate decision #340 leaves open. So #340's "does this subsume shell?" is answered **not yet**, on purpose.

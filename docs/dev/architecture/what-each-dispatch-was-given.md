# What each dispatch was given (#512).

- **What each dispatch was given (#512).** You could not see it. `ContextViewer` reads `agent.getTurnContext()`, and `turnContext.push` happens at exactly one site — inside `Agent.processInput` — so **no sub-agent, task, specialist, delegate or cron dispatch's context assembly was recorded anywhere**. The only trace was `context:section-sizes`, which is debug-only and carries no agent identity, so a main-agent line and a sub-agent line are indistinguishable in the JSONL. `src/dispatch-context-history.ts` is the record and the third `PerTurnStore` subclass; `DispatchContextViewer` is the fourth Shift+Tab tab.
  - **An observer, not a return value.** `ContextMessageInputs.onReport` follows `shapeMCPResult`'s idiom for the reason that one gives: the module is a pure function of its inputs, its single return is the message, and nothing should be computed when nobody is listening. Every caller but `runDefinition` omits it, and a test asserts the assembly is byte-identical with and without one.
  - **The pack moved up out of the renderer**, because the renderer was the only thing that ever knew which keys were dropped and it threw that set away. `buildContextMessage` now packs once and hands `memories` + `pack` to `renderPersistentMemory` — the same single store read as before, with the decision available to the observer as well as to the text.
  - **The dispatch id flows IN, not back out (`AgentSpec.dispatchId`).** A caller cannot get it from the ALS — `runDefinition` assembles its context message _before_ calling `runAgent` and would read whichever ancestor's scope it happens to be nested in, attributing a sub-agent's context decision to its parent's dispatch. The first cut had the runner hand it back through a callback, which forced the caller to hold its report in a mutable slot spanning two closures and clear it by hand so iterate N's report could not attach to iterate N+1's id; minting the id at the call site removes the slot and the hazard with it. One row per **LLM call** rather than per dispatch, and that is the right grain: a multi-step dispatch reassembles its context every iterate, and `agent:dispatch:start` is logged per call too, so the ids line up with the trace this is meant to be read beside.
  - **`resolveRetrieval` returns `{query, results}`.** The recorder used to call `def.retrievalQuery(input)` a second time to capture the string — running a definition-supplied thunk twice per dispatch, **outside** that function's guards, so the record claimed a `retrievalQuery` for dispatches that retrieved nothing (no `ctx.rag`, or a search that threw). A re-derived measure drifting from the real one is the class #528 had just fixed in `recall-filter`, and it has no business in the module whose whole job is to be a trustworthy record of what happened.
  - **Recording is off until a reader turns it on.** `recordDispatchContext` fires per LLM call in _every_ process, and only an interactive REPL ever reads the rows back — so a cron daemon or applet host would accumulate and retain the bound's worth of records, plus a reference to every pack's key arrays, that nothing will ever look at. `enableDispatchContextRecording()` is the same shape as `def.streaming && getOutputSink()`: a producer that stays quiet until something is listening.
  - **Flushed once at exit, and the module owns the whole surface.** `persistAgentState` runs in every turn's `finally` on the Ink render path, and `PerTurnStore.save` pretty-prints and rewrites the whole array — 0.65 ms and 354 KB at the record bound, per turn, for a record nothing reads until the session ends. The store instance is also module-private now: threading it through `AppProps` bought nothing, since a holder still had to fetch the data from the module, which is how `/clear` ended up needing two calls to be correct.
  - **Module-level, following `providers/request-counter.ts`.** `runDefinition` is a free function with no field to hang state on, and threading a sink through `AgentContext` would make every context builder — including four in tests — opt in to pure diagnostics. Bounded at 200 and flushed **once at exit**, never per dispatch: this sits inside the step loop's caller, and a `writeFileSync` there would put disk I/O between assembling a prompt and sending it. The bound is real rather than defensive — `withSlot` allows four concurrent dispatches, each MCP delegation adds another, and every LLM call records, so this grows far faster than the two per-turn stores beside it, whose `save` is uncapped and pretty-printed.
  - **A new tab, not a section inside `ContextViewer`.** That component's test fake is a single-method `{ getTurnContext }`, so a second data source there breaks it — and the two answer different questions: a turn's pre-turn pipeline versus one assembly's output. Neither subsumes the other. The **list row** names a memory drop rather than hiding it behind a keystroke, for the reason #528 removed the same silence from the render path.
  - **Dropped keys are named at every layer**, which is the through-line with #528: the model gets `### (truncated)`, the log gets `droppedKeys`, the REPL gets a once-per-session notice, and this record gets the list. "2 entries were dropped" cannot be acted on.

# One brief, and the data channel is a type (#509).

- **One brief, and the data channel is a type (#509).** Every one of the five delegation doors — `agent`, `task`, `specialist_run`, `tool_wrapper_run`, `delegate_<server>` — passed a task string and an optional context string. What compensated was **prose in a tool description**: `subagent.ts` instructs the model to include _"(1) specific objective and expected output format, (2) exact file paths…, (4) what 'done' looks like"_. That WAS the contract — a string, unvalidated, uninspectable. `DispatchBrief` (`framework/agents/user-message.ts`) is the type, `renderBrief` the one renderer.
  - **Three hand-rolled instances is what makes it a primitive rather than a speculation.** The three PAC phases stacked labelled sections directly, the two applet planner briefs compose their own, and applet actions split instruction from data **by comment**. The vocabulary now lives in one place, which is how `pac-critic`'s two divergences — a leading `Original task:` where its siblings say `Task:`, and a trailing paragraph with no label at all — became visible instead of buried in a third builder. They are preserved as data rather than normalised: making the labels agree moves the bytes and needs an eval.
  - **The bytes do not move, and that invariant is what makes the refactor safe.** `renderTaskText`'s literal output is load-bearing in five test assertions (including an exact `toEqual` in `mcp-delegate.test.ts`), in `policy/scratch.ts`'s `TASK_PREFIX_RE`, and in `App.tsx`, which feeds the rendered string to the policy engine so the decision cannot diverge from the real dispatch. Changing the wire format is a behavioural change across every dispatch in the product, unmeasurable without evals. So the change is to the TYPE; `user-message.test.ts` writes out the previous builders' literals by hand rather than computing them from the new renderer, which is the one thing such a test must not do.
  - **`UntrustedData` makes the two-channel split a property instead of a promise.** `apps/dispatch.ts` keeps author-written instructions and caller-supplied args apart precisely so caller bytes never reach the instruction slot — and both channels were `string`, so the only thing standing between an applet's arguments and that slot was that nobody had yet written the assignment. It is a `unique symbol`-branded type minted **only** by `renderArgsBlock`, so `ToolWrapperInput.input` (typed `string`) cannot accept it and `.data` cannot accept a plain string. It closes the accident, not the attack: `renderArgsBlock`'s own docstring remains the authority that prompt-level framing is insufficient and that tool authority is the load-bearing control.
  - **The brand is asserted in PRODUCTION code, because a test cannot assert it.** `tsconfig.json` excludes every test file from the program, so a `@ts-expect-error` in one is compiled by nothing — it looks like a guard and is decoration. `user-message.ts` carries a three-arm conditional type whose `true` assignment fails to compile if the type collapses to `string`, if `string` becomes assignable to it, **or if the symbol is dropped** and a bare `{ text }` literal starts satisfying it structurally. All three arms mutation-checked against `npm run build`. The data channel also renders **last**, after every instruction section, so caller bytes can never be read as a clause of an author's sentence.
  - **`Request:` is kept, and the recorded reason for it was false.** `tool-wrapper.ts` said prompts and tests read the label verbatim; measured, `grep "Request:"` over `src/` and `docs/` returns **nothing**. The real reason is byte stability — every wrapper dispatch in the product has read that word — which is a better reason than the one that was written down.
  - **Two things deliberately not migrated, both recorded beside the code so they are not "finished" later.** The applet planner briefs produce the envelope's `task`, not a second envelope — they are a prompt body, and forcing their paragraphs into `BriefSection`s would either move bytes or add a per-paragraph separator knob to a type with one meaningful distinction (`block`). And `task.ts`'s `Additional context:` glue renders byte-identically as a section, but `task` is also what `retrievalQueryFor` embeds, so moving it out of the string silently changes what every saved-routine dispatch retrieves for.
  - **One builder, and the data channel on all five doors.** The first cut left two parallel APIs for one job — `TaskMessageInput`/`buildTaskUserMessage` for four definitions and `DispatchBrief`/`buildBriefUserMessage` for the rest — with the first a strict subset of the second and its renderer already a shim over the other, which is the state in which a new definition author picks between them and the stated payoff goes uncollected. Worse, only `ToolWrapperInput` gained a `data` slot: a nominal type prevents the _accident_ on one door and leaves the other four with **no correct option at all**, so the natural code for an applet action dispatched through `specialistDefinition` (which #423's `boundTo` already contemplates) is `context: renderArgsBlock(args).text` — the exact assignment `UntrustedData` exists to prevent, reintroduced because the right field does not exist there. `DispatchInput` is now the shared base every dispatch input extends, so the channel exists everywhere by construction; `renderTaskText` survives only as `App.tsx`'s policy shim.
  - **The return side is not decided here.** #509 asks where a per-specialist result schema lands; it needs a record field, so it belongs with #508's field table. `types.ts` already records the harder half — the verdict lands in six different places, and a step-limited run reads as a failure at two of six formatters and a success at four.

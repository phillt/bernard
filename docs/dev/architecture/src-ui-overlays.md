# src/ui/overlays/

- **src/ui/overlays/** — One file per ephemeral overlay (`MenuOverlay`, `TextInputOverlay`, `ConfirmDialog`, `HelpOverlay`, `InfoOverlay`, `SourcesViewer`, `StatusViewer`, `ContextViewer`). The Shift+Tab **viewer tabs** (`StatusViewer` / `SourcesViewer` / `ContextViewer` / `UsageViewer`, cycled in the order declared in `overlays/viewer-tabs.ts`) share pure nav/wrap helpers in `overlays/viewer-util.ts` (`navDelta`, `clamp`, `clampOffset`, `listPosition`, `wrapText`, plus `viewerFrameHeight` / `viewerViewport`, which moved out of `ViewerShell.tsx` so pure geometry stops dragging React and Ink into tests that need neither) and the `ViewerShell` chrome. All chrome legends — the bottom-left `HintBar`, the bottom-right `StatusBar` readouts, and the `ViewerShell` key legend / tab strip — render through the shared atoms in **src/ui/hints.tsx** (`KeyHint` type, `HINT_DIVIDER`, `HintDivider`, `HintEntry` = accent key/label + muted value, `HintRow` = dividers + entries) so a keystroke hint or labeled stat reads identically everywhere in **theme** colors (accent + muted), never the terminal's raw `dimColor` (which ignores the active theme). `ViewerShell`'s `keyHints` prop is a structured `KeyHint[]`, not a pre-joined string, and its position/rule lines use `colors.muted`; `MenuRow`'s `dimUnselected` (tab strip) uses `colors.muted` too. `ContextViewer` is the "Prompt & Context" tab: a two-panel drill-down (turn list → per-turn sections Original input / Rewritten prompt / Resolved references / Recalled facts) reading `agent.getTurnContext()` — it surfaces what the pre-turn pipeline actually fed the agent that turn (original vs. rewritten input, resolved entities, injected memory facts). It deliberately does **not** capture the system prompt (internal infra — not persisted to disk or shown in the UI). All use `useInput` for keyboard handling; `ConfirmDialog` / `TextInputOverlay` short-circuit a pre-aborted `AbortSignal` to cancel/deny without prompting. `MenuOverlay` is the analogue of the legacy `selectFromMenu` — Arrow keys move highlight, Enter commits, Esc/q cancel, digits 1-9 commit immediately, sections render but skip on arrow movement.
  - **One keystream (#266)** — every selectable overlay routes its navigation through `overlays/list-nav.ts` (pure `listNavIntent`, type-only `Key` import so its tests need neither React nor Ink) plus `overlays/use-list-cursor.ts` (`useListCursor`, `useListWindow`). Four overlays had hand-rolled the same clamped ↑/↓ + digit-commit keymap and drifted: `SettingsOverlay`'s down-arrow carried a lower clamp the others lacked, `ConfirmDialog`'s highlight was unclamped. Three properties are load-bearing and tested: it never claims `Esc` / `Ctrl-C` / `q` / Shift+Tab (which is what makes it safe inside `SettingsOverlay`, whose dismissal keys belong to `ViewerShell` — dismissal stays in `overlay-contract.ts`, now with `isShellOwnedKey`; the two modules compose, never merge); `total === 0` yields `null` for every key, subsuming the grid's empty-list early-out and Settings' extra clamp; an out-of-range digit returns `null`, not a rejected intent. The hook returns `handleKey` and deliberately does **not** own a `useInput` — Ink broadcasts to every mounted handler with no stop-propagation, so a second subscriber would turn "dismiss beats digit" from a readable if-chain into a registration-order accident. `onCommit` takes an **index**, never a `MenuItem`, which is what lets `ConfirmDialog` in (it has rows and an index→side-effect `commit`, no `MenuItem[]`); multi-select's digit-toggles difference is the **value** of `onDigit`, not a mode flag in the shared module. The cursor is clamped at **render**, not only in the setter, and moves via a functional updater because Ink can deliver two keystrokes in one React batch.
  - **Windowing (#266)** — `MenuOverlay` and `ModelGridOverlay` bound their content to the frame via the pure `overlays/menu-geometry.ts` (`entryIndexOfItem` / `countItemsBefore` — the only conversion between the cursor's ITEM space and the window's ENTRY space; `chromeRows`, which counts wrapped rows because a title or the grid's catalog footer soft-wraps; `overlayViewport`, deliberately not `viewerViewport`, which charges for `ViewerShell` chrome neither overlay renders; `pullBackSection`). Unwindowed, a 58-model provider rendered 58 rows at ≤50 columns. The simplification worth keeping: MenuOverlay's rows only _look_ non-uniform — every entry is one row except the highlighted one, which adds a second when it has a description — so **reserving one row for the description makes `clampOffset` apply as-is**, deleting a bespoke variable-cost algorithm and its worst failure mode (a window that breathes as the highlight passes described rows). `MenuList` seeds its item counter with `countItemsBefore`, never `0`: the printed number, the digit shortcut's target and `checked.has(i)` all read it, so a zero seed ticks the wrong box in a scrolled multi-select. Digits stay **absolute**. Both render a scroll position in `colors.muted` and **always reserve the row** (blank when the list fits), so layout height never depends on its own output. `reserveRows` is a prop passed by `App.tsx` — the alert banner (which can appear while an overlay is open, so the budget is derived every render) and legacy inline mode — the same shape as `BoundedLine`'s `reserveColumns`. `SettingsOverlay` is not windowed yet (it sits inside `ViewerShell` and is a uniform list).
  - **Overlay cancellation belongs to the request helper, not the component (#266).** `MenuOverlay` / `ModelGridOverlay` used to carry a `signal` prop no caller ever passed, while the abort that does happen — an agent turn cancelled with an `ask_user` menu on screen — left the menu up, because `requestMenu` took no signal and `requestAskUser` only polled between questions. `requestMenu` / `requestMultiMenu` / `requestTextInput` now take an optional **trailing** `signal` using `requestConfirm`'s idiom (pre-check, `settled` guard, `onAbort` that tears the overlay down before resolving, `{once: true}`, `removeEventListener` on the normal path). `InkHandlers.requestMenu` had to change too: the bridge shim took two parameters and silently dropped a third. `SettingsOverlay` is the **interactive** analogue of the read-only viewers: it reuses the `ViewerShell` chrome with two tabs (`Options` / `Agent options`, `overlays/SettingsOverlay.ts` `SETTINGS_TABS`) so `/options` and `/agent-options` open the same frame on their respective tab and Shift+Tab cycles between them in place. It owns the ↑/↓ / Enter / digit keystream (ViewerShell owns Esc → close and Shift+Tab → cycle). App drives it via the `requestSettings` bridge + a `runSettings(tab)` loop: both tabs' entries are built up front (`buildOptionsMenu` from `OPTIONS_REGISTRY`, `buildAgentOptionsMenu` for the agent-behavior toggles), an item pick resolves with `{tab, index}`, its action runs (opening sub-overlays like value prompts), then the loop re-shows on the same tab/cursor with entries rebuilt so annotations refresh from the mutated config.
  - **The turn viewers open on the newest turn, and tabulate what they can (#248).** `SourcesViewer` and `ContextViewer` both list turns in append order — oldest-first, because `agent.ts` pushes each completed turn — and both seeded the cursor at 0, so opening Sources landed on the FIRST turn of the session and the newest was reachable only by knowing `G`. `viewer-util.openAtNewest` is the shared seed (cursor + a `clampOffset`-derived offset, since a cursor at `total - 1` with `offset: 0` highlights a row scrolled off the bottom); shared, not written twice, because the two viewers are near-line-for-line siblings and a local copy is how one ends up recent-first and the other doesn't. Neither auto-drills: the level-1 list is the only view of the session's shape, and drilling on open would spend the viewer's first Esc on "back to the list" (`escClosesViewer={false}` while drilled), so Shift+Tab → Esc would stop closing anything. **`overlays/table.ts`** is the pure auto-column renderer behind the citation card's excerpt: an array of flat-ish objects (the shape of an MCP list result) becomes a header + one row per element instead of `JSON.stringify(v, null, 2)`. Columns are auto-selected by field frequency, capped at what fits, remainder named in a `+N more fields` line — hide/reorder is deliberately not built, being a fourth focus state and a persisted per-tool preference for a read-only panel. **Every emitted line is exactly one terminal row**, the invariant both viewers window against, which is why table lines bypass `wrapText` and why the preview is `RichLine[]` (spans carrying semantic color ROLES the viewer resolves against `getThemeColors()` — a hex here would hard-code one theme into a module #320 exists to re-skin) rather than a string. Degenerate shapes — empty arrays, arrays of scalars or arrays, wholly-nested objects, arrays too ragged to grid — return `null` and keep the pretty-printed JSON, because a bad table is worse than readable JSON; a _sometimes_-nested field is dropped as a column, not as a table, and named in the sentinel. `cell()` is lifted from `UsageViewer`, the house table idiom, and shared. The card header also finally renders `SourceItem.timestamp` (recorded since the store was written, never shown) on the existing `kind · cited` row rather than a new one — rows here are the excerpt's rows — via `formatFriendlyTimestamp`, moved out of `Thread.tsx`'s private scope into `output.ts` beside `formatElapsed`.

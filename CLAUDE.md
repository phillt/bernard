# Bernard — Local CLI AI Agent

## Quick Reference

```bash
npm run build        # Compile TypeScript → dist/
npm run dev          # Run via tsx (no build needed)
npm link             # Install "bernard" command globally
bernard              # Start the REPL
bernard -p openai -m gpt-4o  # Use specific provider/model

# Programmatic invocation (#419) — an app id, a named action, typed args.
# Never a free-form prompt; that shape is the security boundary.
bernard script --describe                       # list registered apps
bernard script --describe --app demo            # that app's action schemas
bernard script --app demo --action web_answer --args '{"question":"..."}'

# An action may also name a TOOL, which runs with no model at all (#445).
bernard script --app demo --action search --args '{"question":"..."}'

# Per-app permission rules (#420) — the user's producer, never an agent's.
bernard app-grant demo                    # show this app's rules
bernard app-grant demo --deny web_read    # applies to the next invocation
bernard app-grant demo --clear

# Applets have a write side now (#453). The `applet` tool authors them from
# the REPL; the CLI owns the authority half and deletion.
bernard app list                            # yours only — bundled examples are not mixed in
bernard app list --bundled                  # -b, only what Bernard ships
bernard app list --all                      # -a, both, grouped
bernard app allow demo greet --tools web_search   # toolAllowlist / toolMode / confirmMode
bernard app csp demo                              # what it may reach outside its own origin
bernard app csp demo --img-src https://cdn.example.com --sandbox links
bernard app csp demo --clear
bernard app delete demo                     # sweeps every store keyed on the id
bernard app open demo                       # starts the host, opens the origin
bernard app path demo

# The host can run as a per-user service (#428).
bernard applet-host install
bernard applet-host uninstall
```

## Architecture

- **src/index.ts** — CLI entry point (Commander, shebang). Constructs the agent + stores + MCP manager, mounts `<App>` from `src/ui/App.tsx` via `ink`'s `render`, and awaits `waitUntilExit` before running cleanup (history save, MCP close, optional correction-agent pass).
- **src/agent.ts** — Agent loop using AI SDK `generateText` + `maxSteps` + auto-continue on truncation
- **src/config.ts** — .env loading, defaults, validation
- **src/ui/App.tsx** — Top-level Ink component. Owns the REPL lifecycle: turn submission (`handleSubmit`), the pre-turn pipeline (reference resolver → prompt rewriter → inline-image detection), busy/spinner state, overlay queueing, `historyVersion` bumps, alert-banner dismissal, and Esc handling (Ctrl-C is Ink's — it quits the app before any `useInput` runs; see `overlays/overlay-contract.ts`). All slash commands dispatch here. Overlay-request closures are exposed to the tool layer via the module-level bridge in `src/ui/ink-handlers.ts` so pre-mount `ToolOptions` callbacks (`requestConfirm`, `requestBlock`, `requestAskUser`, `requestMenu`, `requestTextInput`) forward to the live React tree.
- **Full-screen rendering** (`BERNARD_FULLSCREEN`, default on) — the REPL runs in the terminal's **alternate screen buffer** so it owns a fixed-height frame (like vim/htop) instead of scrolling printout.
  - **src/ui/withFullScreen.ts** — single owner of the terminal-state escapes: enters the alt buffer (`?1049h`), hides the cursor (`?25l`), and enables mouse tracking (`?1000h ?1006h`) on start; registers `exit`/`SIGINT`/`SIGTERM`/`SIGHUP`/`uncaughtException`/`unhandledRejection` handlers that always restore (mouse off → cursor on → leave alt buffer, reverse order). Returns a `teardown()` that `src/index.ts` calls **before** `cleanup()` so post-unmount prints land on the restored normal screen. In-repo (not the `fullscreen-ink` npm package) precisely for that teardown-ordering control.
  - **src/ui/useDimensions.ts** + **src/ui/DimensionsContext.tsx** — one reactive source of `{columns, rows}` for the whole tree, subscribed to `stdout`'s `'resize'` (SIGWINCH). `DimensionsProvider` wraps `<App>` (in `src/index.ts`); every consumer reads `useDimensionsCtx()` instead of an un-reactive `useStdout()`, so the frame reflows live. Fallback `{80, 24}` when no provider / non-TTY (tests). `Thread.tsx`'s `MarkdownLines` was the last straggler still on `useStdout` — it sizes the markdown body, and it serves **both** render paths, so in full-screen the frame reflowed on resize around a body still laid out for the old width. The one remaining `useStdout` in that file is the legacy `<Static>` path, which does not reflow at all.
  - **src/ui/TranscriptViewport.tsx** — the alt-buffer transcript. Replaces Ink's `<Static>` (which writes to native scrollback, unavailable in the alt buffer) with a fixed-height, line-scrollable window: the full content renders in an inner column shifted by `marginTop={-offset}` inside an `overflowY="hidden"` box, with `measureElement` giving real content/viewport heights so the offset clamps exactly and "stick to bottom" tracks streaming growth. Reuses `<MessageBlock>` / `<StreamingAssistantMessage>` from `Thread.tsx` verbatim (no second render path to drift). Scrolls via mouse wheel + PgUp/PgDn (+ Home/End when the prompt is empty — see the input-escape note below; that claim was false from #288 until #399, because it matched a raw escape `useInput` never delivers). `App.tsx` renders this in full-screen and the legacy `<Thread>` (`<Static>`) otherwise.
    - **`overflowY`, not `overflow` (#464).** A URL rendered as `https://phone`, cut from `https://phoneburner.zoom.us/my/philllt`, with the full URL intact in history. `overflow: 'hidden'` sets **both** clip axes, and Ink's horizontal clip runs every line through `sliceAnsi(line, from, stringWidth(line))` — and **`slice-ansi@7` cannot parse OSC 8**: `parseAnsiCode` reads at most 19 bytes looking for a terminating `m`, so for a hyperlink it swallows the escape opening plus the first URL characters as "an ANSI code" and then counts the rest of the URL _and the BEL_ as visible characters, reaching the true width after ~13 real characters. Different URLs cut at different points, which is why it read as intermittent. The box only ever wanted to clip the scroll window **vertically**, so dropping the horizontal clip fixes the whole class rather than one escape, and keeps hyperlinks clickable instead of removing them as collateral. It is the whole class because nothing in the repo sanitizes escapes out of tool results — `shell` against `eza`, `delta` or `ls --hyperlink=auto` reaches the same clip. **Upstream fixed this in `slice-ansi@8`** — measured against the same line at the same budget, 5.0.0 and 7.1.2 corrupt it (`Zoom: https://phoneburner.zoo` and `Zoom: https://phone`) while 8.0.0 and 9.0.0 return it whole. We cannot simply take that: `slice-ansi` is **Ink's** transitive dependency, pinned `^7`, so consuming the fix means an `overrides` entry forcing a major bump on a package Ink resolves itself — a dependency change with its own blast radius, deliberately not made here. The honest framing is "the upstream fix exists and we are not on it", not "there is nothing to upgrade to". Nothing bleeds under Ink's default wrapping: `<Text wrap="wrap">` bounds every line to the box width, measured with a 120-character unbroken token and confirmed against a hyperlinked line.
      - **`wrap="truncate"` is a SECOND broken copy, and it is still standing.** Ink routes truncation through `cli-truncate@4` → `slice-ansi@**5**`, vendored independently of the 7.x that the clip path uses, and it fails in the _more_ dangerous direction: a hyperlinked line given a 10-column budget measured **39 visible columns**, i.e. it over-runs rather than over-cuts. Three sites use it — `PlanPanel.tsx`, `HelpOverlay.tsx`, and this file's own position row, whose "exactly one row" reservation it would silently break. **Latent, not live:** only `renderMarkdown` emits OSC 8 and it flows solely into `MarkdownLines` → `MessageBlock`, so no truncated surface can carry one today. Do not read the fix above as retiring this; the invariant that would actually pin it is "no horizontal clip or truncate around content that can carry arbitrary escapes", and the repo's idiom for that is a `meta-coverage`-style source scan rather than a comment. Note this copy is **two** majors behind the upstream fix, so an `overrides` bump would have to reach `cli-truncate`'s `@5` as well as Ink's `@7`. The issue's own diagnosis had ruled `slice-ansi` out by round-tripping the line at a _fixed_ width — which passes; it is `stringWidth(line)` as the bound, the value Ink actually passes, that fails. The regression test therefore has to drive the **real Ink tree with the clip in place**: a `renderMarkdown`-level assertion passes while the bug is fully present, which is how this shipped.
      - **It is also a large performance win**, worth knowing before anyone reinstates `overflow`. Ink's horizontal early-out runs `widestLine()` on every write op _before_ the vertical `continue` skips off-screen rows, and `MarkdownLines` emits one `<Text>` per line — so the cost was O(whole transcript), not O(viewport). Measured: `Output.get()` **17.76 ms → 0.67 ms** at 958 rows (16.1 µs per `widestLine` × 958 accounts for 15.4 ms of it), and 43.1 → 25.2 ms end-to-end per frame. Ink throttles rendering at 32 ms, so the old code spent over half that budget measuring lines nobody could see, on every streaming delta.
    - **Link styling: `href` carries the colour, `link` carries the underline (#464).** marked-terminal applies `href` to the link TEXT and then wraps the result in `link`, so the two compose — underlining in both nests underline inside underline. Measured at `FORCE_COLOR=3`: 3 opens / 2 closes, with the teardown re-enabling it. **Deleting `href` is not the fix**, though it reads as one: marked-terminal falls back to its own `chalk.blue.underline`, which underlines just the same _and_ hard-codes blue, losing the theme — the exact TTY-and-theme blindness `normalizeColor` and the forced-level chalk exist to avoid. The three variants measured: `href: accent.underline` 3/2 with the accent kept; `href` absent 3/2 with links blue; `href: accent` **1/1** with the accent kept. Independent of the OSC 8 truncation above, and testable only with colour forced — under `vitest run` marked-terminal's own chalk sits at level 0, so its `href` emits nothing and the nesting is invisible. That is why `TranscriptViewport.hyperlink.test.tsx` forces **both** `FORCE_HYPERLINK` and `FORCE_COLOR`, and why `ink` is a dynamic import there: importing it statically constructs chalk before the env is set, and chalk caches its level — with `ink` static the assertion passes with the theme-loss defect fully present.
    - **`flexBasis={0}` on the measured outer box is load-bearing (#435).** Ink 5 never maps `overflow` onto Yoga — `styles.js` has no `setOverflow`, and `render-node-to-output.js` consumes it only at paint time as a clip rectangle — so with the default `auto` basis the outer box's flex base size is its **content** height, i.e. the whole inner column (`flexShrink={0}`, hundreds of rows). That base size enters the frame's negative-free-space distribution against the chrome, so `measureElement` returns a height that depends on the **current scroll offset** and `maxOffset = contentH - viewportH` is understated in the same breath. The viewport becomes a damped iteration: measured at 24 rows against an 8-row chrome, `viewportH` walked 21 → 17 → 16 → 15 over four passes while the chrome rendered at **3 of its 8 rows on the first frame** — a prompt box losing five rows, its bottom border overwritten by the hint bar, and the plan panel's header clipped. Streaming restarts it on every delta, so it never settles while output is flowing. A zero basis removes content from the calculation: the box grows into exactly the free space the chrome leaves, correct on the first frame, in one measure pass. It also sets the right priority under a too-tall chrome — a zero basis carries zero **shrink** weight, so the transcript yields rows to the prompt rather than the prompt being squashed, which is what makes `plan-window.ts`'s `MIN_TRANSCRIPT_ROWS` the thing that actually protects the transcript. Pinned by `Thread.test.tsx` → "leaves the chrome its full height on the very first frame" / "settles its window in a single measure pass", which mount the viewport in a `height`-pinned frame **beside a chrome sibling** — the three older tests mount it standalone, and with nothing to compete against there is no negative free space, which is exactly why this had no coverage.
    - **The position row is reserved unconditionally, sits above the content, and states one fact.** It used to render only while `scrolledUp`, which was two defects at once: the viewport lost a row the moment you scrolled (layout height depending on the budget that decides what is hidden — `OverlayFooter`'s rule), and **at rest it said nothing at all**. Stuck at the bottom is the normal state after every turn, so a reply taller than the frame opened mid-thought with no marker and read as a worse answer rather than a scrolled one — the user-visible half of #435, and the reason TTS could be heard reading more than the screen showed (both read the same `agent.getHistory()`; the transcript renders strictly more, since TTS speaks only the last assistant message). Reuses `viewer-util.listPosition`, whose `null` IS the "everything fits" suppression rule, and `wrap="truncate"` so the row it reserves is always exactly one row.
      - **#470 moved it above the content and cut it in half.** It read `▲ 923 more rows above · rows 924–958 of 958` — below the thing it describes, so the reader travelled past the cut content to learn it was cut, and saying the same number three times: `listPosition` returns `first = offset + 1`, so the count above is always `first - 1`, and at rest `last === total`. Under `wrap="truncate"` a narrow terminal then lost the right half, i.e. the half that was not redundant. It is now `formatPosition(...)` alone, the spelling every other windowed surface uses. `↓ new output` stays on that same row rather than moving to the bottom, and that is a **budget** decision: splitting them costs a second permanently-reserved row, and `plan-window.ts` calibrates `MIN_TRANSCRIPT_ROWS` against the transcript spending exactly one — while a conditionally-rendered bottom row would make layout height depend on the state it is reporting. `moreRowsLabel` is deliberately **not** touched: it still serves `BoundedLine`'s prompt affordance, where #435's "rows, not lines" reasoning is exactly right.
      - **"N more messages" was asked for and is not deliverable**, which is worth writing down so it is not re-attempted casually. `commitNewHistory` pushes **every** history entry into `items` with no role filter, and `MessageBlock` renders nothing for `system` messages and — with `toolDetails` off, the default — nothing for `tool` messages, so a turn with five tool calls contributes seven items of which five occupy zero rows. `items.length` counts nothing the user can see, and the error silently changes when `toolDetails` is toggled. Making it honest requires knowing which items rendered, and **visibility is a measurement result, not a property of the data**, so the total itself becomes measurement-dependent: per-item refs, a reach past `measureElement` into Yoga's `getComputedTop()` (nothing here does that), special cases for the welcome header and the live streaming turn (both occupy rows and are in neither `items` nor a stable height), and a second measurement axis on the one measure loop #435 exists to have stabilised.
    - **The frame budget must count the chrome outside the prompt box.** `planPanelMaxRows` (`plan-window.ts`) counted the input, the prompt border and `MIN_TRANSCRIPT_ROWS` but not the unconditional `HintBar`/`StatusBar` row or the busy spinner, so with a plan panel open the transcript reached **4 rows idle / 2 while busy** at 24 rows and 3 / **1** at 20 — below the floor the budget claims to hold, and against that module's own stated rule that "a plan panel that squeezes the transcript to zero is worse than no plan panel". `FRAME_CHROME_ROWS` is a constant rather than live rows threaded down from `App` (the `overlayReserveRows` shape) on purpose: the precise instrument would resize the plan panel whenever an unrelated toast appeared. Its test restates the chrome rows by hand instead of importing the constant, for the same reason the sibling bound restates `BoundedLine`'s formula — importing it would make the assertion self-consistent with whatever the constant says, and lowering it back to zero would still pass.
  - **src/ui/mouse.ts** + **src/ui/useMouseWheel.ts** — pure SGR wheel parser (`parseSGRWheel`, button 64/65) + an Ink hook that attaches a stdin `'data'` listener alongside Ink (which only reads `'readable'`) to feed wheel events to the viewport. Gated by `config.mouse` (`BERNARD_DISABLE_MOUSE`).
  - In `App.tsx` the modal overlays (menu/confirm/grid/help/info/text-input) **replace** the transcript+chrome as a full-frame modal layer in full-screen (extending the legacy `viewerActive` pattern), rather than appending below the prompt.
- **The text-input layer (#354/#355/#356)** — three modules, split the way `mouse.ts`/`useMouseWheel.ts` and `viewer-util.ts`/`ViewerShell` already are: **src/ui/line-geometry.ts** is pure string math with no React or Ink (boundary math + display windowing, so its tests drag in neither), **src/ui/use-line-editor.tsx** is the shared buffer+cursor hook plus `LineWithCursor`, and **src/ui/BoundedLine.tsx** is the both-axes-bounded renderer that `Prompt` and `TextInputOverlay` share. `LineWithCursor` used to render the whole buffer with no bound, which was one defect on two axes: unbounded horizontally (#354) and vertically (#355).
  - **Readline chords** are matched on decoded `Key` flags verified empirically against Ink's parser, not guessed. Two consequences are load-bearing. **`Home`/`End` cannot be bound here at all** — they reach `useInput` as empty input with _no_ flags, indistinguishable from noise, so `Ctrl-A`/`Ctrl-E` stand in _as chords_. Since #399 the keys themselves work, decoded off stdin by `useRawKeys` and delivered to `LineEditor.toLineStart`/`toLineEnd` rather than through `handleKey` — the raw-stdin listener this note always prescribed. See **Input escapes** below. And **`Alt-Backspace` arrives as `{delete, meta}`**, so word-delete is tested _ahead of_ the plain `key.backspace || key.delete` branch — behind it, it would never fire. `Ctrl-A`/`Ctrl-E`/`Ctrl-U`/`Ctrl-K` are **line**-wise, not buffer-wise: that is what readline means and what a multiline buffer (Shift+Enter) needs; for a single-line buffer — every `TextInputOverlay` caller — the two are identical.
  - **Input escapes: Ink parses them and then throws them away (#399).** Two user-visible defects, one cause. `ink/build/parse-keypress.js` maps **every** Home/End encoding (`[H`/`OH`/`[1~`/`[7~`, `[F`/`OF`/`[4~`/`[8~`) to the name `home`/`end` — and `use-input.js` then builds its `Key` from a hard-coded field list with no `home`/`end`, and blanks `input` because those names are in `nonAlphanumericKeys`. `PgUp` survives only because `Key` happens to have a `pageUp` field, which is what isolates the gap. Separately, Ink's `fnKeyRe` cannot match a `;`-separated parameter list ending in `u`, so kitty/foot/ghostty's Shift+Enter (`ESC [ 13 ; 2 u`) has its ESC stripped and arrives as the printable text `[13;2u` — which the editor typed into overlay fields.
    - **Upgrading is the expensive option, not the cheap one.** `ink@6.6.0` adds the `home`/`end` fields and requires **React >= 19** against our 18.3; `ink@7` additionally requires Node >= 22 and parses CSI-u unconditionally. A React major across the whole render path, for one `Key` field.
    - **So `src/ui/keys.ts` + `src/ui/useRawKeys.ts`** — the `mouse.ts` / `useMouseWheel.ts` split, pure parser and thin hook, which is exactly what this file already prescribed ("a raw stdin listener alongside Ink the way `mouse.ts` parses SGR mouse reports"). The escape table mirrors Ink's own because Ink's parser is **not importable**: its `exports` map exposes only `./build/index.js`, so a deep import would break on any patch release. All **twelve** rows Ink recognises are supported (six per key: xterm `CSI`, SS3, vt220, rxvt, and rxvt's modified `$`/`^` forms) — terminals genuinely disagree, and shipping only the one on the author's machine is how this reads as "works for me". The mirror shipped its first draft with four of those rows missing under a docstring claiming completeness, so `keys.test.ts` now reads Ink's `keyName` table out of `node_modules` by file path and fails if a row is unhandled — a test may depend on the installed tree that way where production must not. A literal-prefix table still cannot express **modified** Home/End (`ESC [ 1;5 H`); that needs a regex, not another row.
    - **`useMouseWheel`'s explanation of why this is safe is wrong about the mechanism**, though right about the outcome, and the copy in `useRawKeys` corrects it. There is no flowing mode: attaching a `'readable'` listener pins `state.flowing` to `false` and a later `'data'` listener does not resume it. The `'data'` event fires anyway because `Readable.read()` emits it for the chunk it returns — so the handler runs **synchronously inside Ink's own `read()`**, ahead of Ink's dispatch, on the identical string. Nothing is starved, and we get first look. `setRawMode(true)` is then load-bearing rather than ceremony: besides being ref-counted, it is what keeps the count off zero, since Node _would_ resume the stream if the last `'readable'` listener went away while a `'data'` listener remained — delivering keystrokes to us **instead of** Ink.
    - **We cannot consume the sequence** (Ink has no stop-propagation), so the bytes still reach every mounted `useInput`. Harmless for Home/End precisely because of the defect — `input` is `''`, which no handler acts on. For CSI-u it is not harmless, which is why the editor strips it beside the `looksLikeMouseReport` swallow. **Stripped, not swallowed whole:** a chunk can coalesce the keypress with real typing (`[13;2uabc`) and discarding all of it would silently eat the `abc`.
    - **Chunk coalescing is a live Ink 5 defect this works around rather than fixes.** A TTY read returns whatever was buffered, and Ink anchors its parse at the start of the whole chunk — measured, `"abc" + Home` arrives as the literal text `abc\x1b[H` (raw ESC typed into the buffer) and `Home + "abc"` **loses the `abc` entirely**. `parseNavKeys` therefore scans rather than whole-chunk matches, so our decoding does not inherit the bug; what Ink does with the same bytes is beyond reach without a consumption model. Reported fixed upstream in 6.8.0/7.0.0's incremental tokenizer — from their release notes, not measured here, unlike everything else in this block.
    - **Precedence is the rule that was already written down.** `promptEmpty` — with text in the prompt Home/End belong to the line editor, otherwise they jump the transcript. That is the gate the dead branch already chose; the overlap when the prompt _is_ empty is harmless, since Home/End on an empty buffer move a cursor already at 0. An open overlay unmounts both `Prompt` and `TranscriptViewport` in full-screen, so no overlay competes.
  - **Height bounding windows by slicing the string, NOT by `TranscriptViewport`'s `marginTop`/`overflow` box.** `LineWithCursor` returns a bare `<Text>` used _inside_ a `<Text>` flow and Ink forbids `<Box>` inside `<Text>`; introducing one means splitting the prompt's input row into sibling flex items, which is exactly the #354 defect. The window is **pre-wrapped**, and that is the point: Ink word-wraps, which yields a different row count than the arithmetic driving the window, so the cursor would drift out of view. Below the cap the buffer is returned untouched, so ordinary typing keeps Ink's own word-wrapping and looks unchanged. `wrapRows` carries **indices**, not strings, so the cursor rebase is exact. It deliberately does not reuse `viewer-util.wrapText`, which word-wraps, collapses whitespace runs and re-injects indentation — each of which destroys the character-index → `(row, col)` mapping a cursor depends on. Width is read from `useDimensionsCtx()` rather than `useStdout`, because under the test renderer those disagree (context falls back to 80 columns, ink-testing-library's stdout reports 100). Bounding lives in `BoundedLine`, used by **both** inputs rather than in `Prompt` alone. They share the editor, so they shared the defect: fixing only the prompt left `TextInputOverlay` reaching **85 rows for an 8k-character answer** inside the same fixed-height modal frame. Reachable precisely where it hurts, since `insert()` strips newlines for single-line editors, so a pasted `ask_user` answer becomes one long soft-wrapped line. Each caller passes its own `reserveColumns` because only it knows what box it sits in. **The prompt box's other child is bounded the same way (#358).** `PlanPanel` renders _inside_ the prompt's border via `renderAbove` and was separately unbounded on both axes: `PlanStore.create`/`add` push without limit and the `plan` tool's schema declares no `.max()`, while `STEP_FIELD_MAX` caps a description at 400 characters per FIELD, not per row — so one maximal step soft-wrapped to 7 rows and a 10-step plan of them reached ~72, three terminal-heights inside a `height={rows}` frame. Fixing only the step count would have left a 3-step plan able to occupy 21 rows; the horizontal cap is also what makes windowing over step INDICES valid (one step is one row), so `clampOffset`/`listPosition` apply unmodified — the move `HelpOverlay` made in #392 with `descriptionWidth`. The geometry is the React-free **src/ui/plan-window.ts**, deliberately neither `windowBuffer` (single string, character cursor, cursor pinned to the last row — right for an input, wrong for a step list) nor `overlayViewport`/`viewerFrameHeight` (both baseline at `rows - 1` because their component owns the whole frame; the panel owns a slice). `renderAbove` became a **render prop** so the budget flows down: `Prompt` is the one component that sees both children and the border, so the box's height reads as an expression in one file rather than an emergent sum of two files' private constants — the same ownership rule as `reserveColumns`. The two caps stay **independent** (a shared pool would need both children to lift their demand into `Prompt`, and the plan lives behind `PlanPanel`'s own store subscription), but the plan's is deliberately the smaller: a quarter of the frame against the input's third, and the plan pays its three chrome rows out of that budget while the input's `▲`/`▼` affordances are siblings outside its own (they count **rows**, not "lines" — the buffer is frequently one logical line, and the 901-character message behind #435 wraps to ~13 rows with no newline in it). The window seeds on the `in_progress` step — a plan's implicit cursor — and is stateless, since the panel has no scroll keys. The position row is reserved unconditionally (`OverlayFooter`'s rule) so the panel's height never depends on the budget that decides what is hidden, and `listPosition` returning `null` IS the suppression rule rather than a second `total <= size` test that could drift from it.
  - **A question is a header, not a field label.** `ask_user`'s free-text path passed the model's whole question as `ValuePromptOptions.label`, putting a full sentence on the input's own row; it now goes through `headerLines`, which Ink soft-wraps on its own. The choice path already did this correctly via `requestMenu(entries, {title})`. `ask_user` is the worst case but not the only one — the custom-provider wizard's 66-character API-key label overflowed the same way with no model involved, which is why the structural fix (stacking label above input) is the one that matters.
- **src/ui/overlays/** — One file per ephemeral overlay (`MenuOverlay`, `TextInputOverlay`, `ConfirmDialog`, `HelpOverlay`, `InfoOverlay`, `SourcesViewer`, `StatusViewer`, `ContextViewer`). The Shift+Tab **viewer tabs** (`StatusViewer` / `SourcesViewer` / `ContextViewer` / `UsageViewer`, cycled in the order declared in `overlays/viewer-tabs.ts`) share pure nav/wrap helpers in `overlays/viewer-util.ts` (`navDelta`, `clamp`, `clampOffset`, `listPosition`, `wrapText`, plus `viewerFrameHeight` / `viewerViewport`, which moved out of `ViewerShell.tsx` so pure geometry stops dragging React and Ink into tests that need neither) and the `ViewerShell` chrome. All chrome legends — the bottom-left `HintBar`, the bottom-right `StatusBar` readouts, and the `ViewerShell` key legend / tab strip — render through the shared atoms in **src/ui/hints.tsx** (`KeyHint` type, `HINT_DIVIDER`, `HintDivider`, `HintEntry` = accent key/label + muted value, `HintRow` = dividers + entries) so a keystroke hint or labeled stat reads identically everywhere in **theme** colors (accent + muted), never the terminal's raw `dimColor` (which ignores the active theme). `ViewerShell`'s `keyHints` prop is a structured `KeyHint[]`, not a pre-joined string, and its position/rule lines use `colors.muted`; `MenuRow`'s `dimUnselected` (tab strip) uses `colors.muted` too. `ContextViewer` is the "Prompt & Context" tab: a two-panel drill-down (turn list → per-turn sections Original input / Rewritten prompt / Resolved references / Recalled facts) reading `agent.getTurnContext()` — it surfaces what the pre-turn pipeline actually fed the agent that turn (original vs. rewritten input, resolved entities, injected memory facts). It deliberately does **not** capture the system prompt (internal infra — not persisted to disk or shown in the UI). All use `useInput` for keyboard handling; `ConfirmDialog` / `TextInputOverlay` short-circuit a pre-aborted `AbortSignal` to cancel/deny without prompting. `MenuOverlay` is the analogue of the legacy `selectFromMenu` — Arrow keys move highlight, Enter commits, Esc/q cancel, digits 1-9 commit immediately, sections render but skip on arrow movement.
  - **One keystream (#266)** — every selectable overlay routes its navigation through `overlays/list-nav.ts` (pure `listNavIntent`, type-only `Key` import so its tests need neither React nor Ink) plus `overlays/use-list-cursor.ts` (`useListCursor`, `useListWindow`). Four overlays had hand-rolled the same clamped ↑/↓ + digit-commit keymap and drifted: `SettingsOverlay`'s down-arrow carried a lower clamp the others lacked, `ConfirmDialog`'s highlight was unclamped. - **src/speech-text.ts** + **src/speech-examples.ts** + **src/speech-normalizer.ts** — **speech text normalization** (#432): the readback used to speak the last assistant message _verbatim_, so a TTS backend read raw markdown aloud — `**bold**` markers, fenced code, `[^S1]` citation markers, URLs spelled character by character, tables cell by cell, and a phone number as one giant cardinal ("two hundred nine million…"). The problem has a name — converting a **written form** into the **spoken form** a person would say — and its unit is the **semiotic class**, the category that decides how a token is read. (The inverse direction, "twenty-five dollars" → `$25`, is _inverse_ text normalization and belongs to STT; the planned voice-conversation follow-up must not be pointed at these modules.)
  - **The layer boundary is ambiguity, not difficulty**, and getting that backwards is what makes the LLM half decoration. A class is either decidable from surface form — `$` names its own class, `ddd-ddd-dddd` names its own, `e.g.` is a closed set — or it is not: whether `2026` is a year, a quantity or an identifier, what a URL is actually _a link to_, and which rows of a table matter are all semantic. So stage 1 (`speech-text.ts`, a pure leaf with no `ai`/`config`/React/`node:*`) resolves the decidable classes **and deliberately PRESERVES the rest verbatim**, recording them in `unresolved`. Reducing a URL to its host in stage 1 would leave the model nothing to name.
  - **Never touch a bare digit run.** A TTS engine's default reading of a number is a cardinal, which is _correct_ for a quantity — so the only numbers worth rewriting are the ones carrying a class marker. A digit-grouping heuristic over unmarked runs reads `1,200 users` as "one two zero zero users"; leaving it alone yields "one thousand two hundred users". This is also why almost nothing here spells a number into words: it re-shapes numbers so the engine's own reading lands correctly, and inserts digit separators only for phone numbers. The tagging scan therefore runs **before** comma stripping — and the currency pass deliberately leaves its commas in — or `$1,200` becomes `1200` and a quantity gets mis-tagged as ambiguous.
  - **The deterministic layer is unconditional; only the LLM half is the toggle** (`voiceNormalizer`, default **on**). That gives the fail-open path a real destination rather than "fall back to the audio we already agreed is bad", and it is why turning Natural speech off still strips markdown. `code` is deliberately **not** tagged as unresolved: stage 1 drops fenced contents by design, so no model could act on it and tagging it would send every reply containing a fence on a round trip that could not improve the result.
  - **`speech-examples.ts` is a prompt input, not only test data.** One table with two consumers — `speech-normalizer.ts` renders every row into its few-shot block (including the `avoid` readings, which is what stops a small model reverting to the wrong one), and `speech-text.test.ts` drives the `layer: 'deterministic'` rows as its expectation table. A class the deterministic stage claims is pinned by the same fixture the model is taught from, so the two cannot drift into disagreeing about what `$12.50` sounds like.
  - **Plain text out, not strict JSON** — a deliberate departure from `prompt-rewriter` / `recall-filter` / `claim-verifier`, which return JSON because the model makes a real structured decision. Here it makes none: it always produces a script, and "produced nothing usable" is an error the module already handles. JSON would buy one extra failure mode and a quoting surface over multi-line prose headed for argv, in exchange for a discriminator with one value. Shape and length guards replace the parser; the `< 0.25x` one is what mechanically enforces _re-translate, don't summarize_. It **fails open** where `claim-verifier` fails closed, because the neutral outcome here is audible and harmless rather than a lie.
  - **The seam is the App call site, not `VoiceService.speak`** — putting the LLM call inside the leaf would give a module that imports only `node:child_process`/`fs`/`path` an edge to `ai` + `config` (the edge `tool-bytes.ts` and `mcp-names.ts` exist to refuse) and would break `bernard voice-test`, whose documented property is that it works with no provider configured. So `/voice test` and `bernard voice-test` speak `toLiteralSpeech` — the user typed those words and is checking that audio works at all; the menu's **Speak a test phrase** row is the affordance that demonstrates the setting.
  - **Cancellation needs its own `AbortController` (`cancelPendingSpeech` in `App.tsx`).** `VoiceService._epoch` covers only the warmup window _inside_ `speak()`; it cannot touch a normalization that has not reached `speak()` yet. Without the guard, starting a new turn — or `/voice off`, Esc, or a profile switch — while the previous reply is still being normalized speaks that previous reply afterwards. A controller rather than a counter, because the signal has to reach `generateText` to stop the round trip rather than merely discard it. Torn down in `resetVoiceService`, at the top of `runAgentTurn`, on Esc, and from the menu's Stop row. Esc now also silences in-flight speech, which it never did before.
  - **The readback stays fire-and-forget, and that decides its accounting.** `runAgentTurn`'s `finally` calls `finalizeTurnStats()` + `commitNewHistory()` + `setBusy(false)`, so awaiting a round trip there would hold the spinner and delay the transcript commit by ~1 s on every voiced turn. The spend therefore lands after the ledger closed, which makes `makeUsageRecorder` wrong — its rows would be stranded and then wiped by the next `beginTurnStats()`, taking the cost out of the session total. `makeOutOfTurnUsageRecorder` (`framework/hooks/token-stats.ts`) is the shared answer, extracted from the copy `compactHistory` was carrying for the same between-turn reason.
  - `clampForSpeech` also closes a latent bug: `buildSpeakCommand`'s `windows-speech` branch interpolates the whole text into a PowerShell `-Command` argument, and Windows caps a command line at 32,767 characters — nothing bounded an assistant reply before this.

- **Path-scoped writes (#340)** — an unattended write needs a **where**, not just a _what_. `src/permissions/write-scope.ts` is the pure containment leaf (`node:path` + `node:fs` only): a `WriteScope` is a `workspace` the dispatch may always write to plus optional `grants`, and `checkWritePath` decides. Enforced as a third gate in `augmentTools` (`runWriteScopeGate`) beside the block and confirm gates, so it covers every caller rather than one tool, and it runs **first** — an out-of-scope write is refused before anyone is prompted about it.
  - **This is what let cron have the write-capable file tools back.** #337 withheld them wholesale because of a risk-tier asymmetry: `shell` (`dangerous` → high) had write-shaped invocations denied headlessly while `file_edit_lines` (`write` + `local` → medium) would pass unprompted — an unbounded filesystem write through the one door that wasn't gated. The tiers cannot express the distinction that matters, because a write into the job's own workspace is low risk regardless of which tool made it. `cron.ts`'s `FILE_TOOLS` filter is gone; `tool-surface.test.ts` now asserts their **presence**, with a note that presence is not the safety property.
  - **The scope is an axis of `HeadlessPosture`, not a sibling option.** `HeadlessPostureInput.writeScope` is **required** (`WriteScope | null`) for the same reason `toolMode` and `confirmMode` are: an optional field lets a caller inherit "unrestricted" by omission, which is exactly what happened — applet actions shipped with no scope while being the _less_ trusted origin (browser-triggered, caller-supplied arguments). Stating `null` is a decision; omitting a field is an accident. Being an axis also means **`skipPermissions` dissolves it**, like the other two: leaving it in place made a job the user explicitly marked unrestricted still refuse `file_write` outside its workspace while `shell` in that same job stayed wide open, i.e. steering the model toward the less safe tool.
  - **Per-dispatch, not per-cron-job.** `CronJob.writePaths` populates a general mechanism rather than owning one. Cron was where the problem was found, but an applet action (#445) is a second unattended writer — triggered from a browser, with a caller supplying the arguments, i.e. a materially less trusted origin. Attaching the grant to a `CronJob` record would mean building it twice.
  - **A scope is opt-in, and absence means unrestricted.** That is what keeps the interactive REPL unchanged: scoping writes the user is watching themselves make is obstruction, not safety. `ToolOptions.getWriteScope` is a live reader for parity with `getToolPermissions`.
  - **Containment survives symlinks and `..`, or it is decoration.** `resolveForComparison` resolves the nearest **existing** ancestor and re-appends the missing tail — the target of a write usually does not exist yet, so `realpathSync` on it would throw, and without this a symlinked parent (`~/safe/link -> /etc`) lets the write land anywhere. `isContainedIn` is separator-aware because a bare `startsWith` matches `/safe-dir-evil` against a `/safe-dir` grant. Grants are resolved the same way, so a grant that is itself a symlink still compares correctly.
  - **The refusal names the workspace**, and cron's system prompt states it up front. The caller is generated code with no operator watching: a bare "denied" is retried against the same path forever.
  - **The workspace layout is one convention in one place.** `runWorkspace(namespace, id)` (`paths.ts`) yields `<WORKSPACES_DIR>/<namespace>/<stable id>` — keyed on a _stable_ id (cron job id, app id) rather than a run id, because the point of a workspace is that output is still there next run. Each new unattended writer inherits the layout instead of re-deriving it. `writeScopePrompt` lives in `write-scope.ts` beside the refusal it prevents: the two are halves of one contract, and split apart they drift silently — a job with no operator retries a rejected path until its steps run out. **Known gap: nothing prunes workspaces yet**; `pruneFileGroupsByMtime` (`jsonl.ts`) is the existing idiom when it matters.
  - **`WRITE_PATH_TOOLS`' completeness is a test, not a comment.** Its incompleteness is silent and **fail-open** — a fourth path-taking write tool, or `file_write`'s `path` argument renamed, would ship unscoped with every other test green. `meta-coverage.test.ts` walks the constructed registry and fails if any `write`/`dangerous` tool with a `path` parameter is missing from the set. (`FILE_TOOLS`' incompleteness is at least user-visible; this one is only ever noticed by the write it failed to stop.)
  - **Grants come from the user, never the model.** `bernard cron-grant <id> [paths...]` (`--clear`, or no paths to show) is the producer; paths are stored resolved so a grant made from one working directory still means the same place later. Deliberately absent from the `cron` tool: letting an agent widen its own write scope is the escalation the gate exists to prevent.
  - **`shell` is deliberately NOT covered.** Extracting write targets from an arbitrary command line is not reliably possible, and a containment check that is sometimes wrong is worse than none — it grants confidence it has not earned. `WRITE_PATH_TOOLS` (`permissions/matchers.ts`, declared beside `FILE_TOOLS` so the two cannot drift) holds only the tools that write through a `path` argument. Reads are ungated: this bounds writes, and read scoping is a separate decision #340 leaves open. So #340's "does this subsume shell?" is answered **not yet**, on purpose.
- **src/headless.ts** — `runHeadless`: the whole no-user-present recipe, extracted from cron's `runJob` (#419). Owns `registerBuiltinDefinitions()`, `loadConfig()`, the RAG store + fail-soft search, the MCP lifecycle (connect → `snapshot()` → **close in `finally`**), `assembleContext` with the fail-closed headless `toolOptions`, the `ctx.policyDecision` wiring, the wall clock, and the `runDefinition` call. Top-level rather than under `src/framework/` on purpose: it must import `config`/`mcp`/`rag`, and putting it in the framework creates exactly the edge `tool-bytes.ts` and `mcp-names.ts` exist to refuse. It is a composition root, and those live beside `agent.ts`.
  - **It never throws for a run failure and never classifies one.** A failed dispatch comes back as `{ok: false}` so each caller reacts in its own idiom; `classifyError` stays at the call site, because the message worth classifying is one only the caller can mint — cron's timeout text names `job.timeoutMs / BERNARD_CRON_JOB_TIMEOUT_MS` and escalates severity to `critical` because a hung job was holding a scheduler slot, neither of which is true of a script invocation.
  - **`definition` is a thunk, not a value.** `runHeadless` owns `registerBuiltinDefinitions()` and `definitions.get(id)` throws on an empty registry, so a resolved definition would require every caller to remember to register first — the first cut of the refactor tripped exactly that, in 20 tests at once. Deferring the lookup makes the ordering a property of the signature.
  - **`resolvePosture` requires `toolMode` and `confirmMode` explicitly.** The old `write` + `auto` defaults are cron's _history_ — every cron job opted in to writes at creation — not a general policy. `resolveCronJobPosture` supplies them now, so a new entry point cannot silently inherit them; a script action defaults to `read-only`, because an external caller has opted in to nothing.
  - **The fail-closed `toolOptions` shape is the reason a headless entry point is safe at all**, and omission is the mechanism: `augmentTools` auto-denies when `blockAction` is absent under `toolMode:'read-only'`, and an absent `getToolPermissions` means no persisted grants apply. `askUser` and `sessionToolAllowlist` are omitted for the same reason. A test asserts the four are absent rather than merely that `confirmAction` is present — a test of the latter alone passes while the gates silently open.
  - **The RAG store is constructed only when the caller passes a `ragQuery`**, not merely when `config.ragEnabled`. The constructor is not a lazy handle — it reads and parses the whole embedding file, writes the session date, prunes and stats the temp dir, measured at ~190 ms and ~128 MB on a 31 MB / 3,660-record store — and every `bernard script` action paid all of it for a store it never reads, then held the embeddings resident via the returned `env`. The search is also started **before** the MCP connect rather than after, since the two are independent and connect measures ~1.1-1.6 s. `initShellParser()` is deliberately not warmed either: the parser is reached only through `resolveGrant`, and `augmentTools` returns `'ask'` before calling it when `getToolPermissions()` yields no rules — which a headless run guarantees by omitting the callback.
  - `HeadlessTimings.mcpConnectMs` is reported on both branches rather than only logged, since `debugLog` is a no-op unless someone already suspected a problem. Measured ~1.1–1.6 s across four stdio servers against ~9–10 s for a whole invocation. Context assembly is additionally guarded so a throw there closes the connected manager rather than leaking its stdio children — for the cron daemon, for the life of the process rather than one run.
- **src/host/** — the applet host (#421) and the capability bridge (#420). Bernard's **first HTTP server**: `node:http` was never imported before this, and no new dependency was added. `bernard applet-host status|start|stop|install|uninstall`.
  - **The host runs as a per-user service (#428), and every branch is a pure string builder.** `service.ts`'s `serviceUnit(platform, opts)` follows `voice-service.ts`'s `resolveBackend(platform, …)` exactly — platform is a **parameter**, filesystem probing is injected — because the alternative writes into a real home directory during tests. `BERNARD_HOME` redirects Bernard-owned paths and deliberately does not redirect `~/.config/systemd/user` or `~/Library/LaunchAgents`, so a test that derived its target from `os.homedir()` would install a unit into the developer's login session and into CI's. `service-cli.ts` therefore takes `homeRoot` and `run` as injected parameters, and the isolation test asserts nothing is written outside the injected root. **`ExecStart` is `process.execPath` plus the absolute path to `dist/host/daemon.js`**, never the `bernard` shim: that is what `startHost` already does, it sidesteps resolving an npm bin link, and it is the one path `startHost` already errors on when missing. **Windows uses the Startup folder, not `schtasks`** — the more capable mechanism is also the one most likely to need elevation depending on policy, against #428's own rule that nothing here should need admin. Linux carries `Restart=on-failure` with `StartLimitBurst=3` so a unit pointing at a deleted `dist/` fails quietly instead of error-looping forever. **Uninstall-on-`npm rm` is not deliverable and is not claimed**: npm ≥7 does not run `preuninstall` for global packages in most flows, and the repo has no `postinstall` hook to pair it with — `bernard applet-host uninstall` is the answer, and `install` is idempotent.
  - **`isHostRunning()` conflated two facts and reported the wrong one.** It required the PID alive _and_ an applet answering health, so a service started at login before any applet existed reported "stopped" — and `appletHostStart`'s 10 s poll then spun and lied. Split into `isHostProcessAlive` / `isHostServing` / `isHostRunning`, where the last returns true when **zero** applets are registered: a host with nothing to serve is running correctly. The status output already printed both facts separately, which is what made the conflation invisible.
  - **`/__bernard/tokens.css` is served, not copied (#424).** The four `docs/*.html` files were said to share a byte-identical `:root`; measured, there are three variants — the six **colour** tokens are identical everywhere and `--accent` is `bernard.accent` from `src/theme.ts`, but `--mono` has drifted and `index.html` carries an extra `--nav-height`. So the palette is extracted and typography is left alone; the drift is the evidence for a served artifact over a prompt. Copying a stylesheet into every `appletAssetDir` would re-create the drift one level down, and a generated applet is exactly the thing that cannot be trusted to keep a copy in sync. **`style-src` dropped `'unsafe-inline'`** at the same time, which is what makes the stylesheet mandatory rather than advisory — `csp.ts`'s justification for `'unsafe-inline'` was written about scripts only, and the style half never had a stated rationale. It lands _with_ the demo's rewrite, since the demo was entirely inline.
  - **`/__bernard/applet.js` — the client an applet page talks to Bernard through.** The same "served once, never copied" argument `tokens.ts` makes for the palette, and a stronger one: a page that gets the stylesheet wrong looks wrong, a page that gets the protocol wrong does not work, and it fails as an opaque 403 the guard makes deliberately indistinguishable from a rebinding attack. Before it, the whole SDK was a ~30-line `fetch` trio inside the bundled demo's HTML, and the `applet` tool's `page` description pointed a model at "the bundled demo applet" — naming no path, never mentioning the token, and pointing at a file the tool's own `read` action could not return. A generated page duly omitted `x-bernard-token` and every button 403'd. **A classic script, not an ES module**: `type="module"` is always deferred, so the shape a model actually writes — a `<script src>` followed by an inline `<script>bernard.invoke(...)` — would get `bernard is not defined`. **`invoke` throws rather than returning the envelope**, because the forgotten `if (!body.ok)` is what leaves a dead button; a forgotten `catch` is an unhandled rejection, which the client's one error floor renders. Loud beats silent. **The 403 explanation lives in the client**: `guard.ts` stays terse because a per-cause message on the wire is an enumeration oracle, so the diagnosis sits in a file a prober can already `GET`, where it discloses nothing new and tells the developer everything. No CSP change was needed — `script-src 'self'` already permits it.
  - **A generated web manifest and icon (#429).** Both are routes, not files: a static `manifest.webmanifest` cannot know its own `start_url`, because the port is assigned at runtime by `HostRegistry` and lives in `APPLET_HOSTS_FILE` rather than beside the page. `AppManifest` has no icon field and the schema is `.strict()`, so adding one is a schema-version decision — a generated SVG letter on the accent colour avoids it and is one fewer thing a generated applet has to get right. Two narrow CSP additions: `manifest-src 'self'` (without it `<link rel="manifest">` falls through to `default-src 'none'` and is never fetched) and `.webmanifest` in the content-type table (without it `nosniff` serves it as a download). **The `sandbox` header is deliberately untouched, and it turned out not to matter.** It was the likeliest blocker for installing a top-level document and it is #421's decision, so it was left alone and install was recorded as unverified rather than claimed. **Since verified: Chrome installs an applet with `sandbox allow-scripts allow-same-origin` in place**, so no relaxation was needed and the shortcut-file fallback is unnecessary. Worth keeping the shape of that decision in mind — the header's real costs are elsewhere (popups and top-level navigation, #468; external resources, #467), and refusing to relax it on a guess is what kept those separable.
  - **One origin per applet, and a port is how.** A shared origin means shared `localStorage`, so a hostile applet reads another's data (confirmed in five independent systems). `<applet-id>.localhost` cannot deliver it: [WebKit 160504](https://bugs.webkit.org/show_bug.cgi?id=160504) is RESOLVED MOVED and `*.localhost` resolves in Safari only on **macOS 26**, with the fix in the macOS system resolver so no browser update backports it. A port is a real origin and works everywhere. **The origin is doing security work, not tidiness** — an applet needs `allow-scripts` to be an app at all, and `allow-scripts` + `allow-same-origin` on a _same-origin_ frame lets it delete its own `sandbox` attribute ("no more secure than not using the sandbox attribute at all"). `csp.test.ts` asserts the pair never co-occurs.
  - **Ports are persisted and stable, because an origin change silently destroys that applet's browser storage.** `HostRegistry` (`STATE_DIR/applet-hosts.json`, mode `0600`) assigns from a hash of the app id so a fresh install lands on the same ports, probing linearly on collision. Port and token are deliberately **not** in the manifest: `AppManifestSchema` is `.strict()` with `schemaVersion: z.literal(1)` so a field there makes an older binary reject the whole app; the manifest is bundle-seeded and user-editable, so a token in it is settable by any local process; and it is validated on read, i.e. trusted at exactly the wrong moment. Tokens are memory-only and per-process — a restart correctly invalidates pages holding handles the new process never minted.
  - **`guard.ts` is pure, and that is what makes the rebinding cases testable.** DNS rebinding is the live threat (Vite's [CVE-2025-24010](https://github.com/advisories/GHSA-vg6x-rcgg-rjx6): "even applies to users that only run the dev server on the local machine"). The request arrives on an ordinary socket from the browser's own stack; the only tell is `Host`. It accepts `127.0.0.1:<port>` and **rejects `localhost:<port>`** — `localhost` resolves through the system resolver, which is precisely what an attacker influences here. A duplicated header is rejected rather than resolved; every refusal returns the same terse reason, since a gate that says which check failed helps enumerate them.
  - **`fetch` cannot forge `Host`** — it is a forbidden header and undici drops the override, so a rebinding test written with `fetch` passes because the request was legitimate, proving nothing. Caught when the test passed for the wrong reason; those cases use `node:http`. Same module is why `probeApplet` uses `node:http` with `agent: false`: undici's global keep-alive pool holds the event loop open, and `applet-host start` printed its output and never exited.
  - **`spawn`, not `fork`, for the daemon.** `fork` always opens an IPC channel, and that channel keeps the **parent** alive past `child.unref()`. `src/cron/client.ts` forks and survives only because its callers keep running anyway — the same hazard is latent there.
  - **`assets.ts` reuses `write-scope`'s containment** rather than growing a second path check: serving a file from a directory is the same question, symlink escape and the `/safe-dir` vs `/safe-dir-evil` prefix trap included. Decoding happens **before** any containment reasoning, since `%2e%2e%2f` is `../`. Every refusal is `404`, never `403` — distinguishing "outside the root" from "not there" tells a prober which paths exist. Unknown extensions serve as `application/octet-stream`, which with `nosniff` means an unanticipated file cannot be coerced into running as script.
  - **`src/apps/capabilities.ts` is #420's core.** An opaque CSPRNG handle encoding nothing, keyed to a server-side record — not macaroons, because in one process the minter, attenuator and verifier are the same code, so attenuation buys a class of caveat-parsing bugs and no property. An **instance**, not the module-level `Map` the two existing TTL caches use, because revocation and per-app clearing need a handle to the table. On R2's "minted before untrusted data is in scope": an applet's args come from user interaction and cannot all be frozen at mint, so `action` handles freeze the **designation** (which action, which arg schema, minted at serve time) while `frozen` handles bind values for R8's confirmation flow. The Action-Selector property rests on the designation being unforgeable.
  - **The endpoint never reads the action from the request body.** It resolves handle → record and dispatches what the record says; taking a designation from the caller is the ambient-authority mistake R3 forbids. A frozen handle's values beat anything the page sends. **The test that matters most** is the residual risk `docs/research/applet-sandbox.md` §3 names by hand — a handle minted for applet B, presented by applet A — asserted both on the table and over a real socket. A failed binding check consumes no use, so it cannot probe whether a handle exists.
  - Integration tests are the first here to bind a port. **Port `0` is non-negotiable** so two concurrent `vitest` runs cannot collide (the problem #319's run-scoped temp root solved for directories); it also forced the handler to resolve its port at request time rather than capture it.
- **src/apps/** + **src/script/** — `bernard script`, the programmatic entry point (#419). `bernard script --app <appId> --action <name> --args '<json>'`; the caller supplies **an app id, a named action and typed arguments, never a prompt**. That is the security boundary, not a convenience: a string crosses as _instruction_, read by a model holding the user's tool authority (Hardy's confused deputy — the attacker supplies the designation, the agent supplies the authority), while a named action crosses as _data_ and one the caller invents simply does not resolve. The published name is the Action-Selector Pattern (arXiv:2506.08837); OWASP LLM06:2025 recommends it directly. #420 hardens this — opaque capability handles, TTL and use counts, session binding, provenance tagging, and persisted per-app permission rules — and `ResolvedInvocation` is written down with one producer today precisely so that landed as an addition rather than a rewrite.
  - **`manifest.ts`'s arg types are a tiny closed set, not JSON Schema.** An open schema language re-opens what the named action closed. `number`, `boolean` and `enum` admit no prose at all, so an action built only from them is **structurally uninjectable** — prefer that shape; a test feeds an injection string to each of the three and expects rejection. `.strict()` on every object is load-bearing: a misspelled `toolAllowlist` silently ignored yields an app that reads as scoped and is not, and on a call it stops a caller smuggling a `prompt` field alongside the declared args. Manifests are validated on **read**, not only on write — the file is user-editable between runs, so a write-time check alone is a time-of-check/time-of-use gap (#420 R6's complete mediation).
  - **Resolution is split from dispatch.** `src/apps/invocation.ts` (`ResolvedInvocation`, `InvocationFailure`, `resolveFromManifest`, `renderArgsBlock`) reads the registry, validates args and freezes a record, depending only on `manifest.ts` + `registry.ts`; `dispatch.ts` reaches the whole agent runtime through `runHeadless`. Together they made asking a pure question cost a full agent-runtime import, and made the tests mock the tool registry to exercise functions that never touch a tool — the edge `tool-bytes.ts` and `mcp-names.ts` exist to refuse. The split is also what #420 needs: its capability mint, a manifest lint and a validation endpoint on the #428 host all want to resolve without running.
  - **Two channels.** `action.instructions` is author-written and is the only thing in the instruction slot; the validated args travel separately as a labelled, fenced JSON block. The banner on that block is documented in code as a **mitigation, not the control** — prompt-level framing is known-insufficient. The load-bearing property is that `buildActionTools` grants the **intersection** of the action's `toolAllowlist` and the specialist's `targetTools` on the `'worker'` surface, so an action can narrow what the specialist already targets and never widen it: the agent can be fooled and still cannot act. The injection test asserts on the resulting registry, not on model behaviour.
  - **Dispatch reuses `toolWrapperDefinition` through `runHeadless`, not `dispatchToolWrapper`.** That path takes an agent-pool slot, writes the reasoning log, and — the disqualifying part — enqueues correction candidates on failure. An external caller's failed invocation must not shape a local specialist's few-shot examples; that queue was designed for the user's own mistakes. `skipPermissions` is deliberately absent from the manifest schema: an app must not be able to declare itself exempt.
  - **stdout purity is structural.** `withStdoutRedirectedToStderr` (`src/script/stdout-guard.ts`) wraps the run, because `src/tools/augment.ts` writes to stdout from inside any dispatch that records a profile error and is reachable from every tool an action can call — auditing print sites does not survive contact. Captured unbound so the restore is identity-preserving (binding would accumulate wrappers on nesting), restored in a `finally`. The single JSON object is written afterwards on a restored stdout.
  - **One failure path, and one exit-code table.** `EXIT_FOR` maps every `ScriptErrorCode` to its status, so adding a code is a compile error until its exit status is decided; the predecessor compared `code === 'run_failed' || code === 'timeout'` inside the pre-dispatch helper, where neither value can occur, so the arm that looked like the classification rule was dead. A single `fail()` owns the envelope and the log row — the three hand-rolled copies it replaces had already diverged, one classifying the wrapper error twice against two different strings, so the category in the log could disagree with the one handed to the caller for the same failure. Only a failure that actually ran gets a taxonomy category: classifying "No such app" yields `unknown`, which is noise dressed as a diagnosis. `src/index.ts` is correspondingly a declaration shim over `scriptMain`, like every neighbouring subcommand; it previously hand-rolled two envelopes of its own that omitted `invocationId` and `durationMs`.
  - **Three exit codes**: `0` success, `1` the work failed, `2` the _request_ was wrong — unknown app or action, unparseable args, a schema violation, or an action naming a specialist that does not exist (a pre-flight, so a broken manifest costs no model call). An applet host needs to tell "my integration is broken" from "retry might help". `--timeout` may only **shorten** the action's clock, never extend it — the budget belongs to the app, not the caller. `--args-file -` reads stdin, keeping values off `ARG_MAX` and out of `ps`. `--describe` prints the action schemas without dispatching, which is what a host reads to build its buttons. The invocation JSONL at `SCRIPT_LOG_FILE` records arg **keys only, never values**, and carries an always-null `capabilityId` so #420's mint↔invoke correlation is a value fill rather than a schema migration (R9).
  - **Manifest revisions are a union, never a bump.** `AppSchemaVersionSchema` accepts `1` and `2`, because `AppManifestSchema` is `.strict()` in both directions: an older binary meeting a field it does not know rejects the **whole app**, and a newer one must still read the v1 manifests on disk. v2's `AppAction.dispatch` is a discriminated union; a v1 manifest's flat `instructions`/`specialistId` are **lifted into the agent arm on read**, so nothing downstream branches on the version and no file is rewritten. Declaring both forms is rejected rather than merged — they can disagree — and `dispatch` on a v1 manifest is rejected too, so a manifest cannot half-declare itself. The refinement and the lift both hang off **`AppActionSchema`**, not off the manifest: that schema is exported and parsed directly, and when the rules lived on the manifest alone a bare action parse skipped every one of them _and_ the lift, yielding `dispatch: undefined` typed as `AppAction` — the exact shape this is meant to make unrepresentable, invisible because `tsc` excludes tests. Only the `schemaVersion < 2` gate stays on the manifest, since after the lift every action has a `dispatch` and the question is no longer answerable — which is why the manifest's `actions` record holds the raw schema.
  - **An action may call a tool directly, with no model (#445).** Three tiers: pure computation belongs in the applet's own JavaScript, judgment needs an agent, and **effects on the machine with a known shape are a function call**. Only the third existed. Paying a model to move a file is not only waste, it is _nondeterministic_ — an agent may skip a file or invent a path, where a loop does neither. Eligibility is `ToolMeta.directInvocable`, an **opt-in flag on the tool** beside `actionScoped` and declared for the same reason (a separate name list can disagree with the tool it describes, and here the disagreement is fail-open); an allowlist, not a denylist, so a tool added later is ineligible until someone deliberately marks it. Granted to `file_read_lines` / `file_write` / `web_read` / `web_search` / `memory`. **`shell` never gets it**, and the guard is an invariant rather than a name: `meta-coverage.test.ts` walks the constructed registry and fails on any `directInvocable` tool classified `dangerous`, or taking an argument a manifest cannot express — the shape check alone would admit `shell`, whose `{command: string}` is a perfectly representable scalar. `file_edit_lines` and `time_range_total` are excluded because `ArgSpec` produces only scalars and their nested arrays cannot be named from a manifest; excluding them is honest, and a template layer for nested args is its own change.
    - **Args are mapped, never passed through.** Each tool parameter names `$.<declaredArg>` or a literal, so a caller's object never reaches a tool wholesale — the same reason `validateActionArgs` is `.strict()`. A reference to an undeclared arg is a **parse-time** error, so a typo is a broken manifest rather than a parameter arriving as the literal `$.dset`.
    - **`src/apps/tool-dispatch.ts` deliberately does not go through `runHeadless`.** That owns MCP connect (~1.1–1.6 s), a RAG store and context assembly, none of which a tool call needs — paying an agent runtime's startup gives back most of what skipping the model saved, and the point of this tier is that it costs nothing. It also does not call `loadConfig`, which throws without a provider API key: an action that makes no model call must not require one (the property `bernard voice-test` also holds; the shell timeout comes from `loadPreferences` so the user's setting still applies). What it **does** keep is `augmentTools`, so the deny, write-scope and confirm gates all fire — skipping the model must never mean skipping the gates, and a test asserts a tool action writing outside its workspace leaves no file. Two things the AI SDK would otherwise have done are done explicitly: the mapped args are `safeParse`d against the tool's own schema (a direct call skips the SDK's pre-execute parse), and an ineligible tool is a **request**-shaped failure (exit 2), not a run failure. Both refusals are **non-throwing** — the gates return an `Error: `-prefixed string — so the result goes through `detectResultFailure` (#363); without it a denial came back as `ok: true` carrying the refusal, and the caller read it as success.
    - **`src/headless-posture.ts` is the leaf both paths share.** `resolvePosture` and `headlessToolOptions` lived in `headless.ts`, which imports `MCPManager`, `RAGStore` and the agent-definition registry — so the module whose whole premise is not paying for an agent runtime was importing **161 ms** of module graph to call a function whose real dependencies cost 3 ms. The other half is that `headlessToolOptions`' security property is what it **omits**: `augmentTools` auto-denies a write under `read-only` when `blockAction` is absent, and an omission cannot be type-checked, so two hand-written copies is how one quietly grows the field and stops failing closed with every test green. Pinned on the tool path by "a read-only action cannot write, with nobody to ask". Measured: the leaf imports in **3 ms** against `headless.ts`'s 169. **Known gap:** the total is unchanged, because `createTools` itself costs ~167 ms — `src/tools/index.ts` statically imports `./cron.js`, which pulls `cron/runner.ts` and the whole agent runtime, even though `surface: 'worker'` never constructs that group. Making the `main`-audience groups' `make()` bodies dynamic imports would recover it for every worker dispatch, not just this one, which is why it is its own change.
  - **Grants are enforced, and it took a third gate (#420).** An app's `toolAllowlist` decides which tools are _constructed_ — `grantedToolNames` intersects it with the specialist's `targetTools`, which is what makes a refused call fail because the tool is absent rather than because the model declined. That stays the primary control; rules cannot express "deny everything else", since `scanRules` answers `'ask'` when nothing matches. The refinement on top is `ProfileSettings.appToolGrants` (`src/apps/app-grants.ts`), `PermissionRule[]` per app, produced only by `bernard app-grant` — **never from the manifest** (the app's own user-editable file, the same reasoning that keeps `skipPermissions` out of the schema) and **never `config.toolPermissions`** (the _user's_ grants; an app inheriting "always allow `shell rm *`" is the confused-deputy widening this exists to prevent). Read per dispatch, so revocation applies to the next invocation with no restart. Absent from every agent-callable tool, like `cron-grant`.
    - **Supplying `getToolPermissions` was necessary and not sufficient.** `resolveProfileGrant` had exactly two callers and both sat behind a short-circuit — `runBlockGate` returns early unless `toolMode === 'read-only'` **and** the tool is a write, `runGate` unless the risk crosses the threshold. An applet runs `read-only` at threshold `high`, so a `deny` on a **low-risk read tool** (`web_search`, `web_read`, `file_read_lines`, `memory{action:'read'}`) matched and never ran. `runDenyGate` is unconditional, shaped like `runWriteScopeGate` (refusal string, not a boolean) and folded with it into one `runUnconditionalGates` so a call site cannot run some of them. Only `deny` is acted on: `allow` keeps meaning "skip the prompt in the gate that would raise one". A rule deny now answers with the rule as the reason rather than borrowing whichever downstream gate caught it — which produced "cancelled by user" when nobody cancelled and "read-only mode" when the mode was not why.
    - `HeadlessPostureInput.toolPermissions` is **required** (`PermissionRule[] | null`), for the reason `writeScope` is: an optional field lets a caller inherit "no rules" by omission. Cron states `null`; `skipPermissions` dissolves it with every other axis. The shell parser is now warmed when rules are present — uninitialised, `parseShellCommand` reports a compound command as `parse-error` and `resolveGrant` matches only a no-specifier `shell` rule, so `deny shell:rm` would miss `ls && rm -rf /`: safe for `allow`, fail-**open** for `deny`.
    - **Every mint is logged (R9).** `CapabilityTable` takes an optional `MintObserver` — a callback, not an import, so the module stays a `node:crypto`-only leaf with no I/O — handed the **record**, never the handle, since `CapabilityRecord.id` exists precisely so a log line need not slice a live credential. Observed in `mint` and not `handleFor`, so a reused designation is not counted as a new capability. `CAPABILITY_LOG_FILE` is a **sibling** of `SCRIPT_LOG_FILE`, not rows in it: that file rotates at 2,000 rows, so interleaved mints would be evicted before the invokes they correlate with — the correlation would be the first casualty under load. The invocation log's `toolsGranted` also now records the **post-intersection** set through the same `grantedToolNames`; it recorded the declared allowlist, which overstates the grant in the one record that is an audit trail.
  - **An applet asks, and the user grants (#467, #468).** An applet is served a deny-by-default CSP, so it cannot load an external image or open a link. Widening that globally was refused on the record already in `csp.ts`: _"`img-src` and `form-action` are exfiltration channels `connect-src` does not cover"_, and an applet holds capability handles and a private store. So the widening is **per applet, per directive, and the user's**.
    - **Three channels, and only one is authority.** A **declaration** (`AppManifest.permissions`, schemaVersion 3) is what the applet ASKS for and why — written by the `applet` tool, i.e. by a model, and it reaches no header. A **grant** (`ProfileSettings.appCspGrants`, `src/apps/app-csp-grants.ts`) is what the user ALLOWED, and it is the only thing `cspFor` reads. **Feedback** (`src/host/violations.ts`) is what the browser BLOCKED, a hint that a grant might be wanted. Pinned by one test: an applet that declares `imgSrc` and holds no grant is served the byte-identical ungranted header. Android is the exact precedent — the app's manifest declares `<uses-permission>`, the OS asks, the OS stores the answer — and it is SEP-1865's rule (_"MUST construct CSP headers based on declared domains"_) with Bernard one step stricter, since declared is necessary here and not sufficient.
    - **A declaration in the manifest is safe precisely because it is not authority**, which is what makes it a different question from `toolAllowlist`. `app-grants.ts`' rule that _"a grant stored there would be settable by the app"_ is about grants; the ask is the app describing itself. Without it a permission prompt has nothing to show, and the alternative is what #467 originally imagined — a line of prose telling the user to go and type a CLI command, which is homework rather than a request.
    - **`src/host/csp-grant.ts` is a pure leaf**: the grantable tables (the `AUTHORITY_ACTION_FIELDS` idiom — a written-down enumeration a test can assert against) plus the parser. **Per-directive separation is structural**: key `k`'s sources are emitted into `DIRECTIVE_NAMES[k]` and nowhere else, so an `img-src` grant cannot widen `connect-src` — stronger than remembering not to. Header splitting gets a grammar **and** a character-class belt, asserted separately, because these strings are concatenated into a response header: a `;` would add a directive nobody granted, and a CR would make `res.writeHead` throw and kill the socket rather than serve the applet. Bare `https:` is accepted **loudly** (#467: it "should be possible but should look as alarming as it is"); bare `http:` is refused, being that breadth plus cleartext.
    - **`cspFor(grant?)` takes the grant optionally, and that is load-bearing.** Every existing assertion in `csp.test.ts` calls it with no argument, so "an ungranted applet is served exactly what it was served before" is a passing test rather than a hope. A grant only ever **appends** — it cannot drop a directive or a sandbox token — and sources are re-validated in `cspFor` as well as at the store, so an in-process caller that hand-builds a grant still cannot widen `script-src`.
    - **Read per request, never cached**, the rule `server.ts` already follows for the manifest (#420 R6). It is what makes a **revoke apply to the next request with no restart** — measured on the live host, and pinned by a test that fails when the header is captured at `startApplet` time. Resolved _before_ the guard, since the grant depends only on `appId` (the server's own closure, never request data), so the refusal path carries the same policy as everything else. A corrupt profile degrades to the ungranted header rather than taking the applet down.
    - **"Allow all" cannot cover `connect-src`.** `src/apps/permission-consent.ts` is pure — three surfaces render the same decision, and a label written three times drifts — and phrases each ask as what the applet does ("Show images from 6 sites"), not as a directive. `PendingPermission.ownScreen` marks the asks that must be answered individually: a two-way channel that can send data out, and any whole-scheme wildcard. The blanket row is the one people press without reading, which is the whole reason for the split; a test fails when the carve-out is removed. The applet's own `reason` is model-written prose being used to influence a security decision, so Bernard renders the structural fact it can verify and quotes the sentence beneath it, attributed — the `<available_sources>` posture.

- **Curator memory reconciliation (#371)** — `recall-filter` also receives the `MemoryStore` as **read-only** input and returns two extra fields beside its selection. `reconciliation` is one sentence on how curated memory bears on the facts it kept — rendered as a `### Reconciliation with curated memory` block _inside_ `<recalled_context>`, beside facts that stay **verbatim**, because strict-selection is what keeps provenance `rawRef`s and `[^Sn]` citations valid. `memoryPriority` ranks memory keys for this turn and is consulted **only** as packing order in `renderPersistentMemory`. The safety property is narrower than "memory is never eliminated", which would be false: under budget nothing is dropped and the ranking is unused (it is not even requested — see below); over budget `renderPersistentMemory` drops the tail regardless, and the ranking only decides _which_ tail. The curator never causes a drop, it only chooses among drops that were happening anyway — where Phase 3 would have filtered memory on every turn, budget or not. The residual risk is that a topical ranker puts a standing rule ("never email the client directly") last by construction, so the ranking prompt names that case explicitly. The ranking is requested **only when memory is over budget**: asking unconditionally made the model echo every key verbatim each turn (~250 serial output tokens on a pass that blocks the user's turn) for a result that is discarded whenever memory fits, and — sharing `RECALL_FILTER_MAX_TOKENS` with `keep` — could truncate the JSON mid-array and take the _selection_ down with it, scaling against exactly the users the ranking exists to help. That is the distinction from #307 Phase 3, which routed memory _through_ the filter on every turn and was deferred precisely because a curated entry could then be dropped for looking off-topic. The motivating defect for the ranking half: `renderPersistentMemory` packs in Map order, which traces to readdir, so for any user over `MAX_PERSISTENT_MEMORY_CHARS` **which curated facts survive is decided by filename** — `aaa.md` in, `zzz.md` out, no relevance judgement in the path. A malformed `reconciliation` or `memoryPriority` degrades to `undefined` rather than discarding the selection, and unknown keys are filtered so a hallucinated one cannot reorder real entries around a ghost. The system prompt states the precedence explicitly (memory outranks recalled context, override only the conflicting clause) so the fail-open path — no note produced — still has a rule.

## Custom Providers

Users can register named **custom providers** that wrap one of the installed SDKs (`openai`, `anthropic`, `xai`) and point it at a non-default endpoint — Ollama, LM Studio, OpenRouter, internal proxies, etc. Multiple custom providers can coexist with the built-ins.

```bash
# CLI:
bernard add-provider ollama --sdk openai --base-url http://localhost:11434/v1 --model llama3.2 [--key <api-key>]
bernard remove-provider ollama
bernard providers                # lists built-ins and custom side-by-side

# REPL:
/provider                        # menu now ends with "+ Add custom provider…" (interactive wizard)
/model                           # for a custom provider, menu ends with "+ Type a new model name…"
```

Keys for custom providers are stored in `keys.json` (same path as built-ins) and never injected into `process.env`. Built-in providers are unaffected.

## Model Mode (multi-model assignment)

`config.modelMode` (#170) tiers the (provider, model) used by each LLM call site within the active provider's model lineup. Four presets:

- `off` (default) — every site uses `config.provider`/`config.model`. Legacy behavior, zero overhead.
- `optimize-tokens` — aggressive cost-saving. Main uses **mid**, every sub-agent/wrapper/router site uses **cheap**.
- `balanced` — main **premium**; specialist/tool-wrapper/compressor **mid**; rewriter/reference-resolver/reference-lookup/recall-filter/specialist-detector **cheap**.
- `optimize-performance` — every site uses **premium**.

Per-provider tier → model mapping (in `src/model-policy.ts`):

| Provider  | premium                 | mid                        | cheap                     |
| --------- | ----------------------- | -------------------------- | ------------------------- |
| anthropic | claude-opus-4-6         | claude-sonnet-4-5-20250929 | claude-haiku-4-5-20251001 |
| openai    | gpt-5.2                 | gpt-4.1                    | gpt-4.1-mini              |
| xai       | grok-4-1-fast-reasoning | grok-4-fast-non-reasoning  | grok-3-mini               |

Custom providers fall back to `config.model` for every site (no tier mapping). Invocation-level overrides and per-specialist `provider`/`model` records always win over the policy. When `modelMode !== 'off'` and a specialist is created with **neither** an explicit provider/model **nor** a `role`, the policy-resolved `specialist`-tier model is persisted onto the new record so later mode changes don't silently re-tier it.

**A specialist declares either a binding or an intent, never both (#423).** `provider`/`model` is a binding — a specific model was chosen. `role` is a `RoleId` (`src/model-roles.ts`) — a kind of work was chosen, and the active profile picks the model, now and after every re-tier. Declaring both is rejected at the `specialist` tool rather than merged, because a record carrying both would behave according to `resolveSiteModel`'s internal ordering rather than anything anyone declared; setting a role via `update` clears any existing pin, or the state `create` refuses is reachable through the back door. Declaring neither is the legacy third state above, kept so existing callers are unaffected.

The rung is one line at `model-policy.ts`: `SITE_ROLE[site]` becomes `specialist.role ?? SITE_ROLE[site]`, below the pin short-circuit — so `override > pin > record role > site` is a property of the existing control flow rather than a rule imposed on it. The role is **validated against `ALL_ROLE_IDS`, not trusted**: it comes off a user-editable JSON file, and `lineup.roles[<garbage>]` is `undefined`, so `undefined[tier]` would throw inside the function every dispatch calls — it falls back and logs `model-policy:unknown-role`, the same posture as the `isKnownMode` normalization two lines above. Two consequences worth knowing: a dropped off-lineup pin now falls through to the record's role rather than the site default (strictly better — the specialist's own intent beats the generic one), and a role-declaring specialist resolves on the `'policy'` branch, so it gets a **real tier bucket** in `bernard usage` where an auto-pinned one was bucketed `pinned`.

**`Specialist.boundTo` ties a specialist to one applet action (#423)**, so an agent built for a button is reachable only through that capability. Three call sites, **one decision** — `invocationRefusal` in `specialist-authority.ts`, the invocation counterpart to `permissionsFor`. `specialist_run` and `tool_wrapper_run` refuse a bound record outright; an app dispatch does the **inverse** — it permits the matching `(appId, action)` and refuses every other caller, which is the one place this is easy to write backwards, so the permit case is tested first. A mismatch is `specialist_not_bound`, not `unknown_specialist`: the record exists, and saying it is missing sends an integrator after the wrong bug. Discovery is closed at `getSummaries()` rather than in `matchSpecialists`, because that one function feeds **both** the matcher and the `<specialists>` prompt block — filtering only the matcher would leave a bound specialist advertised and unmatchable, inviting a refused call every turn. `list()` is untouched, so `/specialists` still shows it: a user must be able to see what an applet is running. Binding is **one-way**: settable at create, or on update for a record that is not yet bound, and refused on one already bound. The property that matters is that a model cannot RE-bind — stealing a specialist from the applet it belongs to is a model writing a policy field. Forbidding `update` outright, as the first cut did, made the builder's own loop impossible: validation goes through `tool_wrapper_run`, which refuses a bound record, so a create-bound specialist could never be validated by execution. `agent-builder` therefore creates unbound → validates → binds, and its record test pins that order. Sharing the decision also **closed a pre-existing hole**: an applet action dispatches through `runHeadless`, not `dispatchToolWrapper`, so the `disabled` refusal never covered it and a specialist the user disabled in `/specialists` kept running behind every applet button. Writing a new gate beside a check that was already missing a door is how three copies become four; the call sites keep only their own error _shapes_, which is the sole thing that legitimately differs.

```bash
bernard set-model-mode balanced            # CLI
# REPL: /agent-options → Model mode
```

The single source of truth is `resolveSiteModel(config, site, opts?)` in `src/model-policy.ts`. Every `generateText` call site routes through it. Set `BERNARD_DEBUG=1` to see `model-policy:resolve` log entries per site.

Every `BERNARD_DEBUG=1` session log starts with a `model-policy:snapshot` event capturing the full `{site → {tier, provider, model, source}}` baseline for the active lineup (emitted by `logSiteModelSnapshot(config, 'session-start')` in `src/ui/App.tsx`). Mid-session mutations — `/lineup` save, `/lineups` create/edit/switch, `/agent-options` model-mode change, `/profiles` switch — each emit a follow-up `model-policy:snapshot` with a per-site diff (or `changed: []` when nothing moved). `model-policy:resolve` lines also now fire when a specialist's persisted `provider`/`model` overrides the lineup, so off-lineup calls (e.g. an OpenAI 429 surfacing on an xAI-only lineup because a specialist hardcoded `provider: 'openai'`) are visible in the log without code reading.

**Off-lineup specialist pin guard**: when `config.activeLineupId` is set and a specialist's persisted `provider` isn't bound to any tier of that lineup, `resolveSiteModel` drops the pin (provider + model together) and falls through to the policy tier instead. This catches stale pins from specialists created under a different lineup or provider — e.g. a tool-wrapper specialist baked at `provider:'openai', model:'gpt-5.5'` during an OpenAI session, surfacing as 429s on an xAI-only lineup because the OpenAI quota is exhausted. Invocation-level overrides bypass the guard (those are explicit and trump persisted intent), and the guard never fires when no `activeLineupId` is set (no explicit lineup → the pin is the strongest signal). Emits `model-policy:specialist-off-lineup {site, specialistProvider, specialistModel, lineupId, lineupProviders, reason}` to the debug log on each drop.

## Dispatch Observability

When triaging a hang from the session JSONL alone, start from the event shape — every `runAgent` invocation emits a correlated chain under a 4-byte hex `dispatchId`:

- `agent:dispatch:start {dispatchId, model, streaming, maxSteps, …}` — entry.
- `step:start {dispatchId, n}` / `step:end {dispatchId, n, finishReason, toolCalls, textChars, promptTokens, completionTokens, cacheReadTokens, cacheWriteTokens, ttlms}` — per-step boundaries on **both** branches (#253). The streaming branch was once excluded as "redundant" with the sink's per-token events, but `StreamEvent` carries no usage, so that suppressed every per-step token and cache counter for the main agent — the one dispatch that streams. `step:start` still comes from `prepareStep`, which only the non-streaming branch passes.
- `agent:dispatch:stuck {dispatchId, model, ms, sinceLastStepMs, stepsCompleted}` — fires every 30 s from a debug-only watchdog while a dispatch is still alive. Recurring `stuck` lines with monotonically growing `ms` are the hang signature.
- `agent:dispatch:timeout {dispatchId, model, ms}` — fires when `BERNARD_DISPATCH_TIMEOUT_MS` is set and elapses.
- `agent:dispatch:end {dispatchId, durationMs, steps, finishReason, …}` or `agent:dispatch:error {dispatchId, durationMs, message}` — exit.

HTTP-level events (debug-only, install via `installInstrumentedFetchIfDebug()` in `src/index.ts`) tag the same `dispatchId` through `AsyncLocalStorage` (`src/framework/dispatch-context.ts`): `http:request:start {reqId, dispatchId?, host, path, method}`, `http:response:headers {reqId, status, ttlms}`, `http:response:end {reqId, bytes, ttlmsTotal}`, `http:request:error {reqId, ms, message}`. **Privacy contract**: we log only host, path, method, status, byte counts, and timings — never query strings, headers, or bodies (API keys / prompts / user content live there).

The triad `step:end {n:1, finishReason:'tool-calls'}` → `step:start {n:2}` → `agent:dispatch:stuck {ms:30_000}` localizes the bug: step 2 never made its HTTP call. Add a missing `http:request:start` → it's a network hang. Add `http:request:headers` without `http:response:end` → it's a stream that never closed.

`process:dump` events come from `SIGUSR2` (debug-only handler). `kill -USR2 <pid>` writes `{activeHandles, activeRequests, resources}` to both the session log and stderr — useful when a dispatch is stuck and you want to know what the event loop is holding.

The non-streaming branch (`runNonStreaming` in `src/framework/runner.ts`) races `generateText` against the abort signal — always on, not debug-gated — so an Esc unwinds the runner even when the AI SDK provider leaves an internal await pending after the underlying fetch is cancelled. The streaming branch has carried the same defensive race since its inception.

## Settings Profiles

User-tunable settings are organized into named **profiles** (#207). Bernard always has at least one (`default`); `activeProfileId` in `~/.config/bernard/profiles.json` nominates which one is live. Every `savePreferences` call writes to the active profile, so any settings change made via `/agent-options`, `/model`, `/provider`, `/theme`, `bernard set-model-mode`, etc. is automatically profile-scoped. API keys (`keys.json`) and custom providers (`custom-providers.json`) stay global.

- `/profiles` — list profiles (active one marked), switch, or launch the wizard to create a new one.
- `/manage-profiles` — rename or delete (guards against deleting the active or last-remaining profile).
- `bernard profiles` — read-only listing from the CLI.

`src/profiles.ts` is the disk-backed store (CRUD + atomic writes); `src/profiles-wizard.ts` defines `WIZARD_CATEGORIES` (Agent behavior / Tool safety / Output style / Limits / Advanced) and the `runProfileWizard()` orchestrator, both built on the existing `selectFromMenu` / `promptValue` primitives — no new UI components.

Migration: the first read of `profiles.json` is lazy; if the file is absent but `~/.config/bernard/preferences.json` exists, its contents seed the `default` profile and a `.migrated-to-profiles` marker is dropped (subsequent loads consult the marker to avoid re-ingesting stale legacy settings if `profiles.json` is later removed). The legacy `preferences.json` is left in place (no destructive delete) so users can roll back. Brand-new users (neither file present) get the wizard at REPL start to customize their `default` profile.

Resolution precedence in `loadConfig` matches the pre-profiles behavior: **CLI overrides > active profile (stored prefs) > environment variables > built-in defaults**. The profile is the preferences layer — storing a value in the active profile shadows the matching env var (e.g. `BERNARD_MODEL`, `BERNARD_MODEL_MODE`). To let an env var take effect again, reset the field from `/agent-options` or use a fresh profile that omits it.

Profile switching mid-session calls `applyProfileToConfig(config)` (`src/config.ts`) which re-runs `loadConfig()` and copies only the profile-scoped fields back onto the live `config` reference, so subsystems holding that reference (agent loop, tool augment layer) see the new values without reinitialization. `setMaxConcurrentAgents()` is re-fired inside `loadConfig()` so the shared agent pool reflects the new cap.

## Key Patterns

- **Worker tool surface (#253, #322)** — `createTools(..., { surface: 'worker' })` drops the tools a dispatched worker has no business using: `routine`, `lineup_edit`, `specialist`, the `cron` family, and `mcp_config` / `mcp_add_url` / `mcp_verify`. Measured 35 tools → 11, ~24.1k chars → 6.4k (≈4.4k tokens per dispatch end-to-end; ~3.7k of that is the surface option itself, the rest the cron consolidation below). Unlike the main agent's block this is billed at full rate every time, because ephemeral dispatches are never prompt-cache-marked. It is also a containment fix: `createRoutineTool(undefined)` falls back to `new RoutineStore()`, so a worker handed no store still got a live one pointed at the user's real routines. The registry is a table of **lazily-constructed, audience-tagged groups** (`ToolGroup` in `src/tools/index.ts`): `audience: 'main' | 'any'` is a REQUIRED field, so omitting it is a compile error rather than a silent per-dispatch leak, and a filtered-out group's thunk is simply never invoked — which is what lets the declaration be the single source of truth despite those constructors touching disk. The distinction is "who owns this decision", not "is this a write": `shell` and `file_edit_lines` are `'any'`. (Meta can't answer this — `ToolMeta` lives on a _constructed_ tool, and not constructing is the whole point — which is why the declaration sits beside the constructor.) Which surface a dispatch gets is **not** opted into per call site: `runDefinition` resolves it (see **Dispatch tool surface** below). Groups spread in declaration order and MCP merges last, so a colliding MCP tool still wins.

- **Cron tools are action-enum (#253)** — `cron{action}` (10 actions), `cron_logs{action}` (4), `cron_notes{action}` (4) replaced 18 single-purpose tools, matching the shape `routine` / `specialist` / `memory` / `scratch` already use. Two consequences: per-action argument requirements are enforced in the handler (`CRON_ACTIONS`), not the shared zod schema, because one schema cannot say "id is required, but only for six of ten actions"; and permission grants key per action (`cron:delete`) so an "always allow" granted while listing jobs cannot authorise deleting them. Read actions still pass the read-only gate via an `isWriteAction` refinement. The discriminator is declared on the tool as `ToolMeta.actionScoped` (#322) — set once by `attachActionMeta` for the whole family, and read through the single `actionOf()` reader by `permissionKeyFor`, `breadthOptionsFor`, and `attachActionMeta`'s own `isWriteAction`, rather than from a name list elsewhere that could disagree with it. Deliberately a flag, not a configurable field _name_: the persisted rule specifier is literally `action:<value>` (minted in `permissions/breadth.ts`, matched in `permissions/engine.ts`), so a tool dispatching on some other field would mint grants the engine could never match. Scoped to the cron trio — `routine`/`specialist`/`lineup_edit` have the same shape but predate this and users may hold rules keyed on the bare name, so they simply don't declare the field; re-keying them needs its own change with a migration.
- **Dispatch tool surface (#315, #322)** — two cross-cutting facts about what a dispatch is entitled to (the built-in registry scope, #253; the MCP bag, #296/#305) are resolved ONCE by `runDefinition` via `resolveToolSurface(ctx, def)` (`src/framework/agents/tool-surface.ts`) and handed to `def.tools` as a `ResolvedToolSurface` (which `extends CreateToolsOptions`, so it passes straight through to `createTools` — an explicit `extends` rather than accidental structural compatibility). `def.systemPrompt` then receives the registry `tools()` just returned, so a definition that advertises its tool list in prose (`task`) names the exact set it was handed instead of assembling a second registry — which had already drifted once. Definitions consume these; they never re-derive them. Previously five definitions each called `mcpToolSurface(ctx)` and four hand-passed `{ surface: 'worker' }` — both defaulting to the expensive option, so a missed call site failed silently and expensively. `runDefinition` is the same chokepoint the confirm gate uses, for the same reason. The scope derives from `historyMode` (ephemeral → `'worker'`), so the default is now the cheap one; `AgentDefinition.toolSurface` is the declared opt-out and `tool-wrapper` is the only definition that uses it (its `childTools` are scoped by `specialist.targetTools`, and three bundled wrappers target tools the worker surface removes). Because a definition can ignore its third parameter and still typecheck, the guard is behavioural: `tool-surface.test.ts` pins both what each definition resolves to and that it actually consumes the value. Layering note — `run.ts` now depends on `tools/delegate.ts`, so the dispatch half lives in `tools/delegate-dispatch.ts` and `createDelegateTool` reaches it through a deferred `import()` inside `execute`; building the delegation surface is pure and must not depend on the agent runner. That defers the edge rather than removing it — see #332 for putting the resolved bag on `AgentContextMCP` instead.
- **Agent-pool slots (#317)** — `withSlot(fn, onExhausted)` (`src/tools/agent-pool.ts`) owns acquire _and_ release for five call sites (`subagent`, `task`, `specialist-run`, `tool-wrapper-run`, and the REPL's `/task`); `withUncappedSlot(fn)` serves the sixth, `delegate-dispatch`. `releaseSlot` took no argument, so a hand-paired acquire/release could drift silently rather than throw. **Nesting is inferred, not declared**: an acquire from inside a slot-holder is free, tracked by a dedicated `AsyncLocalStorage<true>` in that module. It deliberately does **not** key on `getCurrentDispatchId()` — `runWithDispatchId` is established for every dispatch and the AI SDK invokes `tool.execute` inside it, so that test would exempt every ordinary sub-agent acquire, which is the cap's entire purpose. Holding a slot and being inside a dispatch are different facts. `onExhausted` is a thunk rather than a discriminated return because the call sites report exhaustion in four shapes (bare string ×2, `err()` envelope, `pool_exhausted` `WrapperResult`, a toast), each dictated by its tool's own return contract and asserted verbatim by tests — they already converge where it matters, since `error-taxonomy.ts` classifies all of them as `pool_exhausted`. **`withUncappedSlot` exists because the ALS is not sufficient**: delegation must never be starved, and the main agent holds no pool slot at all, so a `delegate_*` call issued by _main_ is not ALS-nested — routing it through the capped path would let four parallel sub-agents starve main's own MCP access, the exact failure #305 fixed, and a regression #317 would otherwise have introduced while removing the old unconditional `nested: true` bypass. Two consequences: nested slots are still counted (so release stays symmetric and `getActiveCount()` may exceed the cap — no longer bounded at +1, since the exempt set grew from one declared path to every dispatch below a slot-holder), and the cap bounds nesting **depth**, not width.
- **Delegate tools bind to the live context (#332, won't-fix)** — the resolved per-server delegate bag is rebuilt on every dispatch and **must not be cached**. A delegate tool closes over the `AgentContext` it was built from, and `Agent.processInput` re-points `this.ctx` every turn (`{...this.ctx, policyDecision}`), so a bag built once at session start would forward a context whose `policyDecision` is permanently `undefined` — silently disabling the read-only block gate (#179) and the confirm gate (#144) on every delegated MCP call. That killed #332's proposal to hang the bag off `AgentContextMCP`; `ctx.mcp` is never re-assigned and so looks like a stable cache key, which is exactly the trap. Pinned by `delegate.test.ts` → "delegate tools bind to the live context". Two lesser reasons the issue's premise did not hold: removing the `tool-surface.ts → tools/delegate.ts` edge would not stop the framework importing the tool layer (~45 other such value imports exist; that one is merely the only _cyclic_ one), and a required field on `AgentContextMCP` yields one compile error, not a call-site sweep, because `AssembleContextInput.mcp` is `Partial<>` with `??` defaults and tests are excluded from `tsc`.
- **A dispatch has an inbound token budget (#451).** `budgetSeed` (`src/framework/agents/seed-budget.ts`) wraps `getSeed` in `run.ts` exactly as the vision gate does, and inherits its three arguments verbatim: it is a cross-cutting entitlement, it must read the **materialized** seed rather than `input`, and the estimate must be computed **once per seed** — `getSeed` is called at three sites and up to five times per main-agent turn, and the estimator is O(chars) with a `JSON.stringify` per non-string part.
  - **Ephemeral only.** `historyMode: 'persistent'` — the main agent — already runs its own preflight `emergencyTruncate` with the full prefix including the per-turn context message. A framework check that also truncated would double up on the one definition that does not need it. So ephemeral dispatches get the new check and **throw**; persistent histories are left to the preflight they have.
  - **The estimate under-counts by exactly the context message**, and says so rather than presenting itself as exact: `toolBytes()` and `system` are in scope at that point, but the context message is resolved inside `innerIterate`, after the check. That is acceptable for a refusal threshold set at 80% of the window, and it is documented in the module rather than discovered later.
  - **`src/token-estimate.ts` is a new leaf, and `run.ts` importing `context.ts` was never an option.** That module pulls `generateText`, `config`, `model-policy` → `lineups` → `providers`, `rag`, `domains` and `image` — 43 ms measured against 7 ms for the leaf, and exactly the edge `tool-bytes.ts` and `mcp-names.ts` exist to refuse. `getContextWindow` / `estimateMessageTokens` / `estimateMessagesTokens` moved there and `context.ts` re-exports all three, so no call site changed. Scoped to seeds, not attachments: text can overflow a small pinned model, images only made it easy to hit.
- **`createTools` is async, and nine tool modules are deferred (#452).** The filed issue blamed `cron.js` for 167 ms; measured, the cost is a strongly-connected component, not a leaf. Deferring the cron trio alone recovers ~33 ms — `cron-logs.ts` and `cron-notes.ts` both import `./cron.js`, so three of the ten group entries hold the same door open — and deferring all nine `main`-audience modules gets 167 → **76 ms**. The remaining floor is dominated by `web.js` at 64 ms, which is `audience: 'any'` and so unreachable by the surface filter. `ToolGroup.make` returning `Record | Promise<Record>` is what lets the declaration stay the single source of truth: a filtered-out group's thunk is still never invoked.
  - **Six of nine callers needed nothing.** `AgentDefinition.tools()` was already declared `Promise<…> | …` and `runDefinition` already awaited it. The one genuine blocker was `RunHeadlessOpts.buildInput`, called synchronously; widening it to `TInput | Promise<TInput>` covers `apps/dispatch.ts`, and `cron/runner.ts` — the only other implementor — does not call `createTools` at all.
  - **The second static edge is the one that mattered for #445**, and #452 does not mention it: `apps/invoke.ts` → `apps/dispatch.ts` → `createTools` is a static chain, so `bernard script` loaded the entire agent runtime **before** reaching the `kind === 'tool'` branch that dynamically imports the cheap path. Fixing `tools/index.ts` alone fixes nothing there; `invoke.ts` now reaches `dispatchAction` through a deferred import too, exactly as it already reached `dispatchToolAction`.
  - **Deferring `cron.js` at the group level deadlocked the test suite for 60 s**, and the fix is one layer down. The cycle `tools/index → cron → cron/runner → framework/agents → main → tools/index` was previously resolved at **load** time; deferring the group turned it into a **call**-time cycle, which hangs under `vi.resetModules()` (plain Node resolved it in 173 ms). `cron.ts` now defers `runJob` inside its own `execute` — the `delegate.ts` idiom — which breaks the cycle at its real edge and independently drops `cron.js` from 160 ms to 45 ms. Note for anyone re-measuring: `meta-coverage.test.ts` calls `vi.resetModules()` per test, so a deferred import re-executes rather than hitting Node's warm cache — the "already-cached lookup" claim holds in production, not under `resetModules`.
- **`toolBytes`** — `agent:dispatch:start` logs the wire size of the tool block alongside `toolCount` (debug-only). Counting tools misleads when sizing prefix cost: the 18 `cron_*` tools were 37% of main's tool _count_ but 27% of its _bytes_, and `lineup_edit` alone outweighed six of them. Since #323 `toolBlockBytes` lives in the leaf module **src/tool-bytes.ts**, not privately behind the runner's debug gate where it could only ever be a log line. (`context.ts` owns "how big is what we're about to send" and was the obvious home, but that would make the generic runner import `context.ts` — dragging in `config`, `model-policy` → `lineups` → `providers`, `rag` and `domains` for a measurement whose only real dependency is `ai`. Same edge #315 refused. `context.ts` doesn't import it at all: `emergencyTruncate` takes a number, not a registry.) It is now a real budget input: `emergencyTruncate` takes a single `prefixChars` count — SYSTEM prompt + per-turn context message + tool block — having previously subtracted **nothing** for tools — ~21k chars / ~5.3k tokens on the main agent, unaccounted for on the one path that runs _because_ a token limit was already exceeded. One count rather than one argument per contributor, because the caller is the only party that knows the full list — and the previous shape encouraged smuggling: it took a `systemPrompt` string it used only for `.length`, so `agent.ts` padded it with `'\n'.repeat(contextMsgChars)` to get the context message counted. `estimatePrefixTokens` is exported so the caller's "are we over?" test and the truncation's "what fits?" answer can't disagree about the divisor. Neither `emergencyTruncate` call site (`agent.ts`) has a tool registry in scope, so `RunDefinitionResult.toolBytes` is a **lazy memoized accessor** (`() => number`) and `Agent` caches the first call in `mainToolBytes`. Lazy rather than an eager field or an opt-in flag: eager charges every dispatch for a number almost none read, and a flag puts the cheap-but-wrong answer in the default position — the shape #315/#322 exist to remove. Measured **once per session**: the conversion is O(schema size) and the main tool block is session-stable, the same invariant `BERNARD_PROMPT_CACHE` relies on. Known gap: a **resumed** session's turn 1 carries a full loaded history but still budgets tools at 0, since the value only arrives after the first dispatch returns.

- **Compaction economics (#310)** — `compressHistory` (`src/context.ts`) splits on `countRecentMessages`, which counts **user turns**, and a tool-heavy turn can be dozens of messages carrying several near-`MAX_TOOL_RESULT_CHARS` results. So "everything older than the last `RECENT_TURNS_TO_KEEP = 4` turns" is routinely a small slice of the weight: one observed run compressed **8** messages while keeping **54**, recovering ~10k of a 101k-token history for the price of two LLM calls (summarizer + per-domain fact extraction). Two guards now exist. `MIN_COMPRESSION_RECLAIM_TOKENS` (2,000) is a floor on the compressible region — below it the run is skipped before any LLM call, logging `context:compress:skipped`, because the summary replacing the region is a meaningful fraction of the region itself. And `context:compress` now reports `tokensBefore` / `tokensAfter` / `reclaimed` / `reclaimedPct` rather than message counts alone, which were blind to whether anything shrank — derived from the already-computed region size and gated on `isDebugEnabled()`, since the estimator `JSON.stringify`s every non-string content part and the payload is discarded when debug is off. `compressHistory` also takes an `onStart` callback so the REPL announces compaction only once the work is committed to: a skipped run leaves the trigger unchanged, so printing before the call showed the message every turn for a compaction that never happened. Separately, the **automatic** path now re-baselines `lastPromptTokens` after a successful compaction the way the manual `/compact` path always has (`agent.ts`); without it `shouldCompress` keeps firing off a prompt size that describes a history that no longer exists. The deeper directions in #310 — budget-driven retention instead of a fixed turn count, and compressing tool results inside _retained_ turns — remain open; they matter less now that the catalog fix lets a 500k-window model compact at 375k rather than 96k.
- **MCP server stderr never reaches the terminal.** `Experimental_StdioMCPTransport` defaults `stderr` to `'inherit'`, so a third-party MCP server's output goes straight to Bernard's terminal, outside Ink — into the alternate screen buffer Ink believes it owns under `BERNARD_FULLSCREEN`, and interleaved with the transcript even inline. Nothing routed it anywhere: connect failures are already reported via `serverStatuses` / `mcp_verify`, so those bytes were pure noise, up to and including a crashing server's stack trace scrolling over the REPL (`@browsermcp/mcp@0.1.3` recurses `server.close` into itself on stdin close — i.e. every time Bernard shuts down — and dumps a `RangeError`). `startConnect` passes `mcpStderrTarget()`, and is the single transport-construction site, so the isolated `verifyMCPServer` probe is covered by the same call. **`'pipe'` is not the fix**: the transport keeps its child private, so nothing can drain the pipe and a chatty server blocks for good once the ~64 KB kernel buffer fills — a hang traded for a cosmetic bug. It must be a real descriptor, which needs no reader. The file itself is minted by `openSessionSidecarFd` (`src/logger.ts`) rather than here: the session id, the directory latch and the retention budget are all owned there, and a caller opening its own file would re-derive the naming convention and then have to be separately remembered by rotation — which is exactly how the first cut of this ended up with a literal `.log` in `rotateSessionLogs` coupled to a filename in `src/mcp.ts` by nothing. Retention is correspondingly per **session**, not per file: `pruneFileGroupsByMtime` (`src/jsonl.ts`) ranks a session's files as one unit, so a new sidecar is covered the day it is added, a sidecar is never retained past the transcript it belongs to, and `MAX_SESSIONS` keeps meaning what it says instead of silently becoming a per-extension budget. Sidecars are debug-only and unbounded _within_ a session — rotation counts sessions and runs once at startup, so a long-lived cron daemon with a chatty child accumulates one large file until it restarts. Every other child-process spawn in the repo (`voice-service.ts`, `cron/notify.ts`, `cron/client.ts`, `index.ts`'s rag-worker, `tools/shell.ts`) already passes an explicit `stdio`, so this was the one leak, not an instance of a general one.
- **MCP tools are namespaced per server (#413).** `MCPManager` used to keep one flat `tools` bag plus a parallel `toolName -> server` map, both last-writer-wins, so two servers exporting `browser_click` could not coexist — and the loser did not merely lose priority, it vanished from its own per-server list, because `getServerToolMap()` built that list by **inverting** the collapsed map. Measured on a real four-server config, `playwright` reported 24 tools and kept 17; the seven it lost to `browsermcp` were click, type, hover, navigate, snapshot, select_option and press_key, so `delegate_playwright` was a browser agent that could resize and screenshot but not click or open a URL — advertising in its system prompt exactly the tools it no longer had. Now `serverTools: Map<server, Record<name, tool>>` is the **one authored registry** and everything flat is derived from it by `flattenServerTools`; the flat bag and the per-server map cannot disagree about a key because there is only one place a key is written. Same config after: 62/62, 2/2, 24/24, 12/12, and the flat bag grew from 93 tools to 100.
  - **The join is deleted, not policed.** `dispatchServerDelegate` used to iterate a name list and pull each object out of the flat bag behind an `if (t)`, so any disagreement produced a helper holding only `ask_user` while its prompt still listed the tools — the #305 failure shape. `serverTools` carries the tool **objects**, so `childTools` is a spread with nothing left to mismatch. `flattenServerTools` lives in the pure leaf `src/mcp-names.ts`, not beside `MCPManager`: importing `mcp.ts` for a pure object operation drags `@ai-sdk/mcp`, `node:fs` and the whole `config` chain behind it (it broke `delegate.test.ts` at import time on the first attempt), which is the edge `tool-bytes.ts` and `tool-result-shape.ts` exist to refuse. Both delegation fixtures derive `mcp.tools` through that same function, so a fixture cannot encode a disagreement the real assembler could never produce.
  - **`<sanitizedServer>_<6hex>__<tool>`, and both halves of that are load-bearing.** **Prefix, not suffix**: `isReadOnlyMCPSuffix` (`risk.ts`) is end-anchored, so a prefix is transparent to risk classification while a suffix would silently reclassify every read-only MCP tool as a write. **The hash buys stability, not collision-avoidance**: server names are already unique as `mcp.json` object keys, but their _sanitized_ forms are not (`my.server` and `my-server` both collapse to `my_server`), and the previous answer was a numeric suffix assigned in iteration order — so editing `mcp.json` could renumber a **different** server's key, and that key is persisted in permission grants and tool-profile filenames. `mcpToolName` guarantees ≤ 64 characters (Anthropic and OpenAI enforce that server-side, and neither SDK validates locally, so a violation is a runtime API 400 rather than a startup error) via a three-rung ladder: R0 readable, R1 drops the human label but keeps the hash and the whole tool name, R2 cuts the tool through the middle around a 4-hex hash of the original. Today's worst case is R0 at 54 chars. Risk is classified from the **raw** name kept on a `RegisteredTool` envelope rather than re-derived from the key, because an R2 key ends in the tool's tail, not its verb.
  - **Two invariants that would fail silently.** `meta.name` must move with the registry key — the permission and block gates key on the registry key while `framework/tools/result-cache.ts` keys on `meta.name`, so namespacing one without the other splits them; a test asserts they are equal for every registered tool. And `getLiveRegistration` maps probe names **forward** (`own[mcpToolName(name, t)]`): `verifyMCPServer` probes a server in isolation and reports the **raw** names it exports, so comparing them against namespaced keys reports every tool of every healthy server as `missing`, which `mcp_verify` renders as ⚠ — the signal the `mcp-manager` specialist has previously answered by deleting a correct config (see **Verdicts and Step Limits**). `mcp-verify.test.ts` mocks `getLiveRegistration`, so it cannot catch that; the guard is an integration test in `mcp.test.ts` driving the real function with real raw probe names.
  - **`LiveRegistration.shadowed` is gone**, along with the "Name collision / last-writer-wins" copy in `mcp-verify.ts`. It could only ever have been `[]`, and a permanently-empty field feeding user-facing prose about a mechanism that no longer exists is worse than no field. An MCP tool also can no longer shadow a Bernard **built-in** through `createTools`' trailing spread (`shell`, `memory`, `web_search`, `wait`, `cite`, `file_write` were all reachable, replacing Bernard's gated implementation _including its risk metadata_) — that hazard closed for free rather than needing a guard.
  - **Migration is a lazy alias, never a rewrite.** Four persisted surfaces name a tool as a plain string: profile permission grants (`profiles.json`, matched by strict equality in `permissions/engine.ts`), specialist `targetTools` (exact lookup, **silent** drop — `{}` is a supported state since #331), tool profiles, and `BERNARD_LOOKUP_TOOLS`. A stored bare name resolves only when exactly one live server exports it; ambiguous fails closed and the user is asked again. `mcpAliasResolverFor` (`framework/agents/mcp-alias.ts`) builds the index from `ctx.mcp.tools` — **the whole live surface, never the caller's registry**: inside a `delegate_<server>` helper the dispatch's registry holds one server, so a locally-built index would call an ambiguous name unambiguous and honour a grant the user made while a different server owned it. Tool profiles additionally seed forward (`ToolProfileStore.ensureSeeded`), because `resolveProfileKey`'s `includes('__')` branch was **dead** — Bernard registered bare names — so 109 profiles on one real install were keyed indistinguishably from built-ins and would have been orphaned wholesale. Seeding runs in its own try: sharing `recordOutcome`'s catch meant any failure silently skipped the record that followed. `buildToolProfilesPrompt` now takes `liveKeys` and drops superseded and orphaned `mcp.*` profiles — it is otherwise unfiltered and sorts by `errorCount` descending, so a dead high-error profile outranks live tools at the 4000-char budget. Its comment claiming "the registry is not in scope here anyway" was stale; the live call site `framework/agents/main.ts` has `ctx`.
- **Claim↔source verification (#417).** A research answer's factual claims are checked against the sources they cite, in code, and an unsupported claim **fails the run**. The measured failure mode is not fabricated URLs — SourceCheckup found ~100% URL validity alongside **55% response-level support**, with ~30% of statements unsupported by the page cited: the citation looked right and the page did not say it. So `extractCitationMarkers`' existing check (does the cited id exist in the store?) is necessary and nowhere near sufficient.
  - **`src/claim-verifier.ts` fails CLOSED**, which is the deliberate difference from every other sub-call. `prompt-rewriter` / `recall-filter` / `reference-resolver` fail OPEN because their neutral outcome is "today's behaviour"; here the neutral outcome would be an unchecked answer wearing a checked answer's clothes, so an unparseable verdict, an unregistered source id, and a thrown error all yield `fail`. Same reasoning as `pac-critic`'s parse handling. Empty claims yields `warn`, not `pass` — an answer asserting nothing checkable has nothing to verify, and that is a fact worth surfacing.
  - **The quote check is not an LLM call.** String containment against `SourceItem.verifyText` is deterministic, free, and cannot be argued out of its answer. Only the softer "does this text support this claim" judgement needs a model. Whitespace is collapsed on both sides because markdown conversion rewraps lines and a faithfully copied span can differ by line breaks alone; nothing else is normalised. Claims are checked **independently and in parallel** — batching invites the model to rationalise a weak claim from a strong neighbour, which is the failure the pass exists to catch.
  - **`SourceItem.verifyText` is why the quote check is possible at all**, and is deliberately NOT a bigger `contentPreview`. The preview is capped at 2,000 chars _because `<available_sources>` re-sends every source's preview to the model every turn_, so raising that cap multiplies per-turn context cost across the whole store. `verifyText` is never rendered into context (cost is memory, not tokens), capped at 20,000 to match `web_read`'s own return so the text a quote could have come from is the text the check runs against. Before it, the only copy addressable by source id was 2,000 chars — roughly a page's first tenth — so a quote from character 12,000 read as fabricated. Two leaks are closed at the boundaries: `cite get` returns the item **without** it (returning it would put 20k of page text into context, defeating the point), and `TurnProvenance` snapshots strip it (they persist to `provenance-history.json` and reload on resume; verification runs in the turn that retrieved the text).
  - **`SourceItem.publishedAt` is separate from `timestamp`, never a fallback for it.** `timestamp` is when _Bernard looked_; conflating the two makes a decade-old page look fresh. Most of this was omission rather than absence — Brave returns `page_age`/`age` and Tavily returns `published_date`, and both mappers read three keys and dropped the rest. `page_age` wins over `age` because the latter is prose. Formats pass through verbatim: a date we cannot parse is still usable information, and guessing at an ambiguous one is worse. `file_read_lines` uses mtime. HTML date extraction in `web_read` is deliberately deferred — Carbon Date's six-signal fusion managed 32.78% exact accuracy, and a confidently wrong date is worse than a missing one.
  - **Wiring is opt-in by shape**, not by a flag: `verifyWrapperClaims` (`src/tools/tool-wrapper-run.ts`) runs only when a wrapper's `result` reports a `claims` array, so every existing specialist is untouched and pays nothing. A `claims` key that parsed but held nothing usable is an **error**, not "nothing to check" — passing it through would present an unverified answer as a verified one. Per-claim `Check`s are pushed into `ctx.postWriteChecks` so they land in the turn rubric beside plan and post-write checks, reusing the existing renderer.
  - The bundled `research-agent` specialist carries the contract in its **structured `result`** rather than in inline `[^Sn]` markers, and that is not stylistic: `REASONING_FAMILIES` suppresses `CITATIONS_PROMPT` entirely for OpenAI-reasoning and xAI-reasoning models, so on those families a marker-dependent design would silently produce zero claims. `toolWrapperDefinition` now appends `CITATIONS_PROMPT` for wrappers whose **resolved** registry contains `cite` (it previously attached to the main agent only, so a dispatched specialist registered sources and was never told the convention). Its `name` is short on purpose — `matchSpecialists` scores `identityHits / identityTokens.length`, a **ratio**, so extra words _lower_ the score; "Research Agent" measures 0.51-0.53 on research-shaped input where a six-word keyword-stuffed name scored 0.17 against a 0.4 threshold.
  - Seeding a new bundled specialist is **two edits**: the JSON file _and_ its filename in `POST_V1_BUNDLED` (`src/specialists.ts`). `.seeded-v1` short-circuits `seedOnce` before the v1 loop, so the file alone reaches only fresh installs — i.e. almost nobody. Do not bump `SEED_MARKER`; that resurrects v1 specialists users deleted on purpose. The filename must equal the `id`, since `roleOf()` derives ids from filenames and `get(id)` reads `<id>.json` — a mismatch makes the record unreachable _and_ unprotected.

- Per-turn execution-strategy selection (#167): `config.coordinatorMode` is tri-state (`on | off | auto`, default `auto`). The Policy Engine's `strategyPolicy` (`src/policy/strategy.ts`) short-circuits on `on`/`off` and delegates to the **Qualifier** (`src/qualifier/`) on `auto`. `DefaultQualifier` is rule-based with feature extractors grounded in LLM-routing research (`src/qualifier/signals.ts`: tool-invocation verbs from Topaz/MoMA, multi-step phrasing + numbered lists from RouteLLM, token tiers from RouterArena/RouterBench, question count from FrugalGPT, Bloom's-Taxonomy levels from RouterArena). The decision tree escalates on multi-step language, tool-keyword + complexity, 2+ sub-questions, or Apply/Analyze/Evaluate Bloom levels; otherwise defaults to Normal (FrugalGPT-style "try the cheap path first" cascade). `isReactEffective` (`src/policy/effective.ts`) is the single source of truth for "is React active right now" — main-agent tool-set assembly (`framework/agents/main.ts`) gates `evaluate` on the same value the strategy uses, so qualifier decisions never drift from the wired tool surface. **`plan` is exposed in every mode** (not just ReAct) because tool membership must stay session-stable for the prompt cache. Enforcement is a separate axis, and since #303 it is **split**: _reconciliation_ (a plan that exists must reach a terminal state) runs on the main agent in **any** mode via `PlanReconcileStrategy`, while _plan creation_ stays coordinator-only — nagging a trivial Normal turn into planning is cost with no benefit. Both call the same `enforcePlan` helper (`framework/strategies/plan-enforcement.ts`), and the two wrappers are gated on opposite polarity of `isReactEffective`, so exactly one enforcement pass can run per turn. Before the split a Normal turn could record a plan, render it in the plan panel, and abandon it — two turns in one observed session did. `aborted` / `stepLimitHit` still suppress enforcement in every mode. Scope is main-only via `BuildStrategyOpts.enforcePlanReconcile`; specialist sites don't set it. **The qualifier's `hasMultiStepLanguage` recognises a bare `then`/`next` sequencer** (#385), not just the `and then` bigram or `first … then` — `X, then Y` is an ordinary two-step phrasing that previously matched nothing and routed real multi-step work to Normal. Conditional clauses (`if X then Y`) are stripped first, since they carry tool verbs and would otherwise escalate. Telemetry: `debugLog('policy:decide', …)` records the decision + reason map every turn, plus the qualifier's raw `signals` feature map — `reason` names the branch that won, `signals` names what was live when it did, which is the difference between diagnosing a misclassification from the log and reconstructing it from source; `debugLog('qualifier:outcome', …)` adds `{strategyId, reason, steps, hitStepLimit, coordinatorMode}` at per-turn stats flush.
- Dangerous-command safelist: shell commands whose target path starts with `BERNARD_TMP_PREFIX` (an internal constant exported from `src/tools/shell.ts`, equal to `path.join(os.tmpdir(), 'bernard-')` — not a user-facing env var) and contain no shell metacharacters skip the confirmation menu. Intentionally narrow so Bernard's own scratch-script cleanup doesn't pop a prompt; arbitrary `rm` still confirms.

## Environment Variables

- `BERNARD_PROVIDER` — anthropic | openai | xai (default: anthropic)
- `BERNARD_MODEL` — Model name (default: provider-specific)
- `BERNARD_MAX_TOKENS` — Response token limit (default: 4096)
- `BERNARD_SHELL_TIMEOUT` — Shell command timeout ms (default: 30000)
- `BERNARD_TOKEN_WINDOW` — Context window size for compression, 0 = auto-detect (default: 0)
- `BERNARD_MAX_STEPS` — Max agent loop iterations per request (default: 25)
- `BERNARD_HOME` — Override all XDG directories with a single flat path
- `BERNARD_MCP_CONNECT_TIMEOUT_MS` — Per-server MCP connect + handshake + tool-listing timeout at startup and reconnect (default: 15000). A server that never completes the MCP `initialize` handshake (e.g. an HTTP/SSE server misconfigured as stdio) is marked failed and skipped — its spawned stdio child is killed and the REPL starts without it — instead of blocking startup forever (#254). Applies to both the REPL and the cron daemon. A slow server (e.g. a cold `npx @playwright/mcp@latest` that takes >15 s the first time) can time out at startup yet connect fine on a later fresh probe — the "healthy but not there" trap. To surface it, the `mcp_verify` tool reconciles its fresh isolated probe against the **live** session via `MCPManager.getLiveRegistration(name, probeToolNames)` (registered per-process by `setActiveMCPManager`, returning a `LiveRegistration`): each probed tool is classified `live` (routed to this server now), `shadowed` (another server exported the same name and won the last-writer-wins race in `connect`), or `missing` (not in the session's tool-set snapshot). So a server that is healthy in isolation but not actually loaded/callable is reported as such, instead of a misleading "✓ 23 tools". `knownAtStartup` (from `serverConfigs`, which is written once at launch — not from a `serverStatuses` row, which `doReconnectServer` can push to at runtime) then says whether being unloaded is a _fault_: see **Verdicts and Step Limits**.
- `BERNARD_DISPATCH_TIMEOUT_MS` — Opt-in per-`runAgent` wall-clock cap (default: unset). When set to a positive integer the runner chains a fresh `AbortController` off `spec.abortSignal`, fires `agent:dispatch:timeout {dispatchId, model, ms}` to the debug log, and aborts the dispatch. Useful when triaging hangs — turns a 5-minute Esc-wait into a clean automatic abort. Leave unset in normal operation: reasoning models can legitimately sit on a single step for 60–90 s. Sub-dispatches inherit independent timers (one per `runAgent` invocation).
- `BERNARD_PROVIDER_STALL_TIMEOUT_MS` — Time-to-first-byte cap on every LLM completion (#302), default `90000`; `0` or a non-numeric value disables it. A provider can accept the POST and then go silent — no headers, no bytes, and no error for the SDK to surface. Nothing bounded that: the only backstop was **undici's 300 s `headersTimeout`**, and since the AI SDK retries by default a single stall could wedge a turn for ~15 minutes (observed: a 300,837 ms request, then a retry, then the user pressed Esc). The guard (`src/providers/stall-guard.ts`) is injected as a custom `fetch` into every built-in and custom client from `src/providers/index.ts`, and covers only the **header** await — once the response exists the body streams untimed, so a reasoning model generating for minutes is never killed. 90 s is 3.3x the worst legitimate TTFB measured across 1,230 real requests (p50 1.8 s, p99 13.3 s, max 27.4 s). A dead connection now costs **one** budget, not three: the guard throws a plain `Error`, and the AI SDK only retries a `TypeError('fetch failed')` that it wraps as a retryable `APICallError` — so a stall is never retried. (That is also what produced the original ~15 min: undici's timeout _does_ surface as `TypeError: fetch failed`, so it was retried twice.) Both the budget and the underlying `fetch` are resolved **per request**, never captured at module load — `.env` is parsed later by `loadConfig`, and `installInstrumentedFetchIfDebug()` patches the global later still, so capturing either one broke it silently (the second disabled the `http:*` events documented above for diagnosing this very failure). The thrown error is deliberately **not** an `AbortError` — the REPL treats those as "user pressed Esc" and renders nothing, so a stall surfaced that way would silently swallow the turn; it is a plain `Error` whose message contains "timed out", which `error-taxonomy.ts` classifies as `timeout` for free. A caller's own abort still propagates untouched, so Esc keeps reading as Esc.
- `BERNARD_STREAM_STALL_TIMEOUT_MS` — Mid-stream stall cap on the streaming branch (#325), default `120000`; `0` or a non-numeric value disables it. The sibling of the first-byte guard above: that one bounds the wait for _headers_, this one bounds the silence _after_ they arrive. A stream that dies mid-body was previously bounded only by undici's 300 s `bodyTimeout` — five minutes of a dead turn, unattended. The guard reuses the existing `agent:dispatch:stuck` watchdog, which needed two changes to work. First, **its progress signal was wrong**: `lastStepEndAt` moves only at step boundaries, so it climbs monotonically while tokens pour in and aborting on it would kill healthy long steps. `runStreaming` now stamps `lastProgressAt` on every part pulled off `fullStream` — the one point in the process that knows a byte arrived — stamped _before_ per-part branching so part types the switch ignores (`reasoning`, `step-start`) still count as liveness. Second, **the watchdog was debug-gated**, which would have meant the guard protected only sessions someone already suspected, never the unattended cron run that needs it; it now runs whenever a budget is set (still `unref()`ed, so it cannot hold the event loop open). The clock **pauses while a tool is executing** (`inFlightTools`, counted from `tool-call` / `tool-result` parts): `fullStream` goes silent for the whole span of a `task` / `subagent` / MCP call, which is legitimately minutes, so pausing keeps the guard's teeth instead of raising the budget past the false positive. A tool-result that never arrives leaves the count above zero and disables the guard for the rest of that dispatch — fail-open, because losing the guard costs a slow failure while a false abort costs completed work. 120 s is deliberately **above** the 90 s first-byte budget: an agent loop runs every step inside one `streamText` call, so the HTTP round trip opening step N+1 happens _inside_ the stream with no parts flowing, and a lower budget would race the first-byte guard and misreport a slow-but-live request. The watchdog tick tracks `min(30 s, budget)` so a user-configured small budget isn't silently rounded up to the 30 s period. **Scope, precisely: this is main-agent-only.** `useStreaming` is `sink !== null` and the sink is registered only by `<App>`; `streaming: true` is declared on exactly one definition (`main`). So the guard covers the main agent in a mounted Ink REPL and nothing else — not cron, sub-agents, tool wrappers, PAC phases, or delegate helpers, which are all non-streaming and resolve `stallMs === null` (and therefore register no watchdog at all). That is the opposite of where an unattended hang hurts most, and it is a property of the layer rather than an oversight: a per-part clock can only exist where parts exist, and `generateText` is one opaque await. Those paths stay covered by the first-byte guard plus step boundaries. Covering them properly means moving body-inactivity detection down to `providers/stall-guard.ts`, which already wraps every client's `fetch` for the first-byte case and would also make `inFlightTools` unnecessary — each agent step is its own HTTP request, so at the fetch layer there is no tool-execution silence to pause for. Filed as a follow-up. Like #302 the abort is re-shaped into a plain `Error` containing "timed out" rather than surfacing as a bare `AbortError` (which the REPL renders as nothing), so `error-taxonomy.ts` classifies it as `timeout` for free.
- `BERNARD_CRON_JOB_TIMEOUT_MS` — Per-job wall clock for headless cron runs (#326), default `1800000` (30 min); `0` disables. Overridden per job by `CronJob.timeoutMs`. Cron used to call `runDefinition` with **no `abortSignal`** — it had none to give — and nothing in `src/cron/` was a job-level clock (`shellTimeout` is per-tool). Two consequences, the second much worse than the first: `runNonStreaming` skips its defensive abort race entirely when the signal is undefined (`if (!abortSignal) return gen`), so headless runs had _less_ protection than interactive ones; and `Scheduler.executeJob` increments `runningCount`, awaits, and decrements only in `finally`, so a hung job held its slot forever — once `runningCount` reached `maxConcurrent` every later fire went onto `this.queue` and never drained, because `drainQueue` only runs from a completing job's `finally`. One stuck job silently stopped the whole scheduler, with no operator present and the store row reading `lastRunStatus: 'running'` until the next daemon restart's stale sweep. Defaulted rather than opt-in because every job that exists predates the field, and those are exactly the ones that can wedge the scheduler. The abort is re-shaped into a message the taxonomy reads as `timeout`, and **severity is escalated to `critical` at that one site**: `timeout` is `low` in `error-taxonomy.ts`, which is right for an ordinary tool timeout and wrong for a job that was holding a scheduler slot and queueing every later fire behind it. Escalating in the cron runner rather than in the shared table keeps the taxonomy from having to know about cron — `Classification.severity` is documented on the interface as "Drives cron alert severity", and cron is in fact its only live consumer today (the other consumer is the in-thread failure hint added by #353, which colours `category · recovery hint` by severity). Severity and the user-facing alert text are keyed on the same fact and so are resolved together; split across two ternaries, an edit to one reads as complete. The scheduler carries a second, longer backstop (`SLOT_RELEASE_GRACE_MS`) that releases the slot even when the hang is somewhere the job's own abort cannot reach — the timer starts after `mcpManager.connect()` and the pre-run RAG search, and `mcpManager.close()` runs after it is cleared, so a stdio child ignoring SIGTERM would otherwise still wedge the queue. The two layers answer different questions: the abort stops the _work_, the race guarantees the _slot_ is freed.
- **Child dispatch cancellation (#327, #351)** — `subagent`, `specialist-run`, `delegate-dispatch`, `task` and `tool-wrapper-run` each wrap their `runDefinition` call in a catch-all that shapes the error into a tool result. That is right for a work failure — a failed MCP call is a legitimate tool result the model should see, and stringifying it preserves the useful behaviour where a model recovers from a failed sub-task on its own — and wrong for a cancellation, which arrives at the parent as a _successful_ tool result it reads as data and loops on. Most visibly, a user's Esc during a child dispatch became `Sub-agent failed: Aborted` while the parent kept running until its own signal tripped. Note there are **five** such boundaries: the first pass patched three, and the two it missed (`task`, `tool-wrapper-run`) both pass `abortSignal` too — an identical two-line paste missing 40% of the sites is the signature of a fix that wants to be one layer down. **Since #351 that layer exists**: `runDispatchOrFail(fn, onFailure)` (`src/tools/dispatch-failure.ts`) owns the try/catch, the re-throw and the `err instanceof Error ? err.message : String(err)` extraction, and delegates only the shaping; the five sites read `withSlot(() => runDispatchOrFail(work, shape), exhausted)`. `onFailure` is a callback for the same reason `withSlot`'s `onExhausted` is: three sites owe the model a string whose `Error:` prefix `detectResultFailure` reads (#364), `task` a `ToolResult` envelope, `tool-wrapper-run` a `WrapperResult` — shapes their own contracts dictate and tests assert verbatim, converging only in that `error-taxonomy.ts` classifies all of them. It is a sibling module of `agent-pool.ts` rather than part of it: the two compose at every site but answer different questions (slot lifecycle vs. failure shaping), and `agent-pool.ts` is a leaf with nothing behind it but `node:async_hooks`. It does **not** own the try SCOPE — `delegate-dispatch` deliberately protects its tool-registry assembly and PAC self-escalation branch too, so each site passes the region it means to protect. The guard against a sixth boundary omitting it is behavioural, not structural: a call site can still hand-roll a catch and typecheck, so each of the five pins the re-throw with its own cancellation test (removing the re-throw from the combinator fails all five). #351 also deleted `framework/dispatch.ts`'s `createDispatchTool` — a zero-caller "shared factory" with no try/catch, no pool handling, no pre-flight guards and no `telemetrySite` passthrough, which two of these files already carried comments explaining why they could not use. `isDispatchCancellation` (`src/error-taxonomy.ts`) is the single predicate all five consult, and it matches on `Error.name` only: a real `AbortError` (the user's signal or a provider-side cancellation), or `DISPATCH_ABORT_NAME`, which the runner stamps on aborts it fired itself (the stall guard, `BERNARD_DISPATCH_TIMEOUT_MS`). **"Any timeout" is deliberately not the rule.** It was, briefly, and an existing test caught it: `new Error('network timeout')` classifies as `timeout`, and the taxonomy itself marks that category `retryable: true` — a provider network blip is exactly the failure a model should be told about and work around, not a reason to unwind the turn. Our own aborts therefore need a distinct **name**, because neither alternative works: not `AbortError`, since the REPL renders nothing for those and the turn would vanish silently; and not the message, since ours and the provider's both say "timed out". `classifyError` alone cannot answer even the `AbortError` half — a `DOMException` named `AbortError` carries the message `"Aborted"`, matching neither `\bcancelled\b` nor `aborted by user`, so it classifies as `unknown`. Re-throwing is safe for the pool because `runHoldingSlot` (#317) releases in a `finally`. The predicate **walks `cause`**, because one of these boundaries can sit inside another and the AI SDK rewrites the error in between: a throw out of `tool.execute` is wrapped in `ToolExecutionError` (`name: 'AI_ToolExecutionError'`) — directly on the non-streaming path, and via an `error` part that `runStreaming` re-throws on the streaming one. Reachable today as main → `agent` → `delegate_<server>`, since sub-agents carry delegate tools; without the walk a cancellation stops propagating after exactly one level — the same bug, one frame up. The walk is depth-bounded rather than `while (cause)`: error chains are built by providers and MCP servers, and a cycle would hang the catch handler.
- `BERNARD_COORDINATOR_MODE` — Tri-state execution-strategy selector: `on | off | auto` (default: `auto`). `on` runs ReAct every turn (think → act → evaluate → decide loop with plan tool + enforcement, per-turn step budget `min(BERNARD_MAX_STEPS * 3, 150)`, up to 2 extra re-prompts if the plan still has unresolved steps — worst-case step count `effectiveMaxSteps * 3`, subagent budgets unaffected). `off` runs Normal every turn — single-shot, except that the main agent still reconciles an unresolved plan it created (#303, up to 2 re-prompts). `auto` runs the per-turn Qualifier (`src/qualifier/`) which classifies the user message via rule-based features grounded in LLM-routing research (RouteLLM, FrugalGPT, Topaz, MoMA, RouterArena) and emits `strategyId: 'normal' | 'react'` plus a kebab-case reason that flows through `policy:decide` + `qualifier:outcome` debug logs.

- `BERNARD_MCP_RESULT_SHAPING` — Structure-aware MCP result cap (#297, #458): `off | cap` (default `cap`). `cap` bounds an over-budget MCP tool result before it enters an agent's context so a large list/body doesn't re-bill on every subsequent step. Small results (≤ budget) pass through untouched, by identity. Applied in the `MCPManager.getTools()` execute wrapper right after `normalizeToolResult`. `summarize` (LLM digest on the cheap tier) is a documented follow-up, not wired.
  - **The structure-aware paths were dead for the shape that actually arrives (#458).** A `CallToolResult` is `{content: [{type:'text', text:'<json>'}], isError?}` — the payload is JSON encoded **as a string**, so there was no structure to walk: the envelope is a plain object whose only array is `content`, `capArray` will not drop a sole leading element, and the whole thing fell to the `{_truncated, preview}` wrapper, whose preview was a **front slice**. For a Gmail `messages.get?format=full` the front is SMTP noise (`Received`, `ARC-Seal`, `DKIM-Signature`) and `From`/`To`/`Cc`/`Subject` sit after it. Measured on a real-shaped payload at the 8,000-char budget: 27,233 chars in, 4,344 kept, **no `Cc`**. Bernard reported that a CC it had sent was dropped, **sent a duplicate email to fix it**, and reported it dropped again. The failure is silent and indistinguishable from a real answer — a truncated body reads as a truncated body, a truncated header block reads as a message with no CC.
  - **Parsing `content[].text` was necessary and NOT sufficient**, which is the part worth knowing before "improving" this again. The same payload **already parsed** measured 26,882 → 4,182, still no `Cc`: `largestArrayKey` is **top-level only**, and a Gmail message keeps its bulk nested (`payload.parts[].body.data`, a base64 blob) and its identifying fields nested too (`payload.headers`). The top-level scan finds `labelIds`, saves nothing, and falls through. Head-and-tail preview alone does not fix it either — the `Cc` sits ~6 KB into a 27 KB payload, neither head nor tail.
  - **So the order is: unwrap → existing top-level paths → recursive shrink → wrapper.** `shrinkLargest` walks the tree for every array/long-string slot, sorts by size, and spends the **largest** one first, repeatedly. That ordering is what protects the small identifying fields: the blob is orders of magnitude bigger than any header, so it is consumed long before a header is reached. It is a property of these payloads, not a guarantee — hence the `null` return that hands anything it cannot bound back to the wrapper rather than returning it over budget. Result: 7,982 chars kept, all 34 headers intact. The wrapper is now the **last** resort and keeps head **and** tail.
  - **Re-emitting the envelope, rather than returning the bare payload,** is what keeps `detectResultFailure`'s `mcpFailureText` walk working and `isError` meaningful downstream (#363). Per-entry fields are preserved (`{...entry}`), because a real server flags `isError` on a `content` entry as well as on the envelope. Only a **single** text entry is unwrapped: a multi-entry result is several values whose relative importance this module cannot know, and shaping them from one object would have to invent that ordering. Non-JSON text is left alone — plenty of servers return prose.
  - **Two costs, stated rather than discovered.** The `JSON.parse`/`JSON.stringify` round trip is **lossy** — insignificant whitespace and number formatting are gone, and an integer past `Number.MAX_SAFE_INTEGER` loses precision; it is paid only by results that were going to be truncated anyway. And shrinking a base64 blob leaves a **non-decodable** string carrying a marker — more honest than silently losing `Cc`, but not a body a caller can decode.
  - **The budget is re-measured on the ENCODED envelope.** The shaped payload goes back as a JSON string _value_, so its quotes and backslashes are escaped a second time — the same ~2x inflation `truncatedWrapper` already documents. Budgeting the payload alone let the envelope overshoot (measured 8,294 against a 8,000 cap); the loop re-budgets by the observed overshoot ratio and converges in one or two passes.
  - **The feasibility bail is budgeted against the passes that are left.** One pass shrinks exactly one slot, so the most still reclaimable is the sum over the largest `MAX_SHRINK_PASSES - pass` slots — and the slot list is sorted descending, so that slice IS the best case. Summing _every_ slot instead answers a question nobody asked: 30 fields of 200 KB can clear a 6 MB gap in principle and cannot in 24 passes, so the shrink ran all 24, re-serialising a 6 MB tree each time, and returned `null` to the wrapper that was the answer from the start — **317 ms of pure loss**, against 66 ms with the bail, on the browser accessibility-snapshot shape this file already names as reachable. Outcome-identical: across a sweep over the 24-pass boundary only the kept LENGTH changes, never whether a payload shrinks or wraps. Still an over-estimate (nested slots are counted twice), which is the safe direction — it can decline to bail on something it might have shrunk, never bail on something it could have. `MIN_SHRINK_SLOT` alone catches neither case: 500 eighty-character fields each clear the floor individually and only their sum does not (11.8 ms → 1.3 ms).
  - **The top-level scans are a fast path, not distinct coverage**, and the comment says so because the mis-statement is what invites a fourth special case. Measured, the recursion **subsumes** the object path and the large-element array path; the one shape it cannot reach is a bare root array of small elements, because `collectSlots` visits root's children and never root itself. They are kept because they land in one exact-budget pass where the recursion pays a `structuredClone` and a re-serialise per pass on inputs that can be megabytes — and for their honest strategy labels.
  - **Never throwing is an invariant, so the clone is guarded too.** `JSON.stringify` DROPS a function silently, so a result carrying one measures finite, clears the cycle guard and makes `structuredClone` raise `DataCloneError`. `mcp.ts` calls the shaper inside the try whose catch reconnects the server, so a throw is indistinguishable from a failed tool call and tears down a healthy stdio connection — the reason `truncatedWrapper` and the observer each carry a catch, and the reason the new hot path needed one.
  - **Single-entry unwrap is conservative, not principled.** The rule the code actually wants is "if a text entry carries JSON, unwrap it", which has no arity in it — unwrapping each entry needs a budget split, not the ordering the restriction is usually justified by. Single-entry is what Gmail and the common servers emit. A multi-entry result is still bounded by the ordinary paths and nothing is lost unnamed, but its inner payload is cut as opaque text, so "never severs JSON mid-token" holds for the envelope and not for that inner value.
  - **Termination and untrusted input.** A cyclic value measures `Infinity`, so the shrink refuses it up front and lets the wrapper's own `catch` handle it; the walk is depth-bounded and the pass count is capped. `__proto__` is never taken as a slot: MCP output is untrusted and `JSON.parse` — which the unwrap now runs on a server's own text — makes `__proto__` a genuine own property, unlike an object literal. Benign today (the own property shadows the inherited setter), which is exactly why it is refused rather than relied on. Shaping is non-mutating; the under-budget path returns the caller's value by identity.

- `BERNARD_COST_GUARDRAIL_TOKENS` — Provider-aware cost guardrail (#298, milestone 9): token threshold (default `60000`; `0` disables). Once per session, when the active provider has **no prompt-cache discount** (`providerSupportsPromptCache` is false → custom endpoints; `anthropic`, `openai` and `xai` all cache, the last because every xAI catalog entry publishes a `cacheReadPerMTok` rate) and a completed turn's main-agent prefix (`spinnerStats.latestPromptTokens`) exceeds the threshold, the REPL flashes a one-time toast that the prefix is being re-billed at full price every step (suggesting delegation or a caching provider). Pure decision in `src/cost-guardrail.ts` (`noPromptCacheHint`); latched via a session ref in `App.tsx`. `cacheReadTokens` is already captured per step and inspectable via `bernard usage`.
- `BRAVE_API_KEY` — Optional: Brave Search API key for `web_search` (first provider tried)
- `TAVILY_API_KEY` — Optional: Tavily API key for `web_search` (fallback when Brave is absent)

## Tool-Wrapper Specialists

Specialists have a `kind` field: `persona` (default, historic behavior), `tool-wrapper` (fronts a concrete tool or CLI with OS-aware examples and strict JSON output), or `meta` (operates on other specialists).

- **`tool_wrapper_run`** — Dispatch tool that the main agent uses to invoke tool-wrapper or meta specialists. Returns strict JSON `{status, result, error?, reasoning?}`. Isolates tools by `targetTools` so e.g. `shell-wrapper` cannot call `web_read`.
- **`web_search`** — Provider chain (Brave → Tavily → DuckDuckGo scrape); returns `[{title,url,snippet}]`. Used by `web-wrapper` and `specialist-creator`.
- **Bundled specialists** seeded on first run into `specialists/`: `shell-wrapper`, `file-wrapper`, `web-wrapper`, `correction-agent`, `specialist-creator`, `mcp-manager`. They are **protected** (see `src/specialist-authority.ts`): non-deletable, definition non-editable, and not enable/disable-toggleable — only the correction flow may append learned examples. `.seeded-v1` (+ per-file `.seeded-<id>`) markers prevent re-seeding.
- **Correction flow**: when `tool_wrapper_run` returns `status: 'error'`, the error is classified via `src/error-taxonomy.ts`; only **correctable** failures (call-shape mistakes: `invalid_args`, `exec_failed`, `not_found` in shell context) get enqueued in `correction-candidates/`. Environmental failures (HTTP 404, `rate_limit`, `auth`, `pool_exhausted`, `parse_failed`, etc.) are dismissed at the boundary and never pollute the queue. At REPL startup the store also runs `dismissNonCorrectable(classifyError)` to drain pre-existing non-correctable rows. At REPL shutdown the `correction-agent` proposes a fix and emits `proposedGoodCall: {specialistId, input}` alongside `applied: true`; the orchestrator (`src/correction.ts`) then **independently re-executes** that call via `tool_wrapper_run` and only marks the candidate `applied` if the re-run returns `status: 'ok'`. Otherwise it's marked `invalid` with a `re-validation failed` note. Good/bad examples are capped at 10 each, oldest drops.
- **Organic tool discovery**: the `specialist-creator` meta-agent researches unknown tools via `shell` (man/--help), `web_search`, and `web_read`, drafts a new tool-wrapper, validates it with `tool_wrapper_run`, and only then commits. Invoke via `tool_wrapper_run { specialistId: 'specialist-creator', input: 'create a specialist for jq' }`.

## Tool Augmentation Layer

A transparent layer that wraps every tool's `execute` function to observe errors and inject usage guidance into the system prompt. Completely separate from the specialist system.

- **Profiles**: Each tool gets a JSON profile at `tool-profiles/<key>.json` with guidelines, good/bad examples (max 5 each). Profiles are auto-created on first error — no pre-configuration needed for new tools or MCP servers.
- **Shell sub-categories**: Shell commands are classified by prefix regex (`git` → `shell.git`, `gh` → `shell.gh`, `docker` → `shell.docker`, `npm` → `shell.npm`, `ls`/`find`/etc. → `shell.fs`, `curl`/`wget` → `shell.http`). Each sub-category has its own profile.
- **Dismissed-failure counter (#366)**: `recordOutcome` records a bad example only when `classifyError(...).correctable`, and `errorCount` is bumped **only inside `recordBadExample`** — so before #366 a non-correctable failure moved _neither_ counter and the call vanished from the profile entirely. Detection (#363/#364) made those failures visible without making them countable: `delegate_browser-control` read 36 successes / 0 errors across sessions where its delegations demonstrably failed. `ToolProfile.dismissed` is a `{category: count}` map, bumped on the `else` branch, kept separate from `errorCount` because that one means "produced a bad example" and conflating them would make the learned ratio meaningless. Keyed by category rather than a bare total because the useful question is _why_ — a tool at `{unknown: 47}` is evidence the taxonomy may be too narrow for MCP-authored messages, which an integer cannot show. Surfaced live to operators via `bernard tool-profiles`, and to the model as an "Unreliable: N recent failure(s)… prefer an alternative" line in `buildToolProfilesPrompt`. **The prompt-side value is frozen per session.** The system prompt is rebuilt every turn (`run.ts` calls `def.systemPrompt` per dispatch) and is the Anthropic prompt-cache prefix (#269), so a live count would change the cached prefix on every dismissed failure — and dismissals are frequent, since every MCP, delegate and sub-agent failure lands there — trading the ~90% discount for a full re-bill, repeatedly. `buildToolProfilesPrompt` is deliberately **not** filtered by the live tool registry: doing so needs to tell an orphaned MCP profile from a built-in one, which needs the `ToolMeta.category` link proposed in #377, and the registry is not in scope anyway since `agent.ts` pre-renders the prompt before tools are built.
- **Error learning**: When a tool returns an error, the error is classified via `src/error-taxonomy.ts`; only **correctable** errors (call-shape mistakes) become bad examples — environmental failures (HTTP 4xx/5xx, `rate_limit`, `pool_exhausted`, etc.) are dismissed so the playbook isn't polluted with "things the model can't fix." Successful tool calls always bump `successCount` (via `recordSuccess`), and when the model retries successfully after a recorded error, the bad example's `fix` field is patched with the working args.
- **System prompt injection**: `buildToolProfilesPrompt()` renders a compact `## Tool Usage Profiles` block showing guidelines and the 2 most recent bad examples per tool (~800 tokens worst case).
- **MCP tools**: Augmented automatically. Identified by `__` in tool name (the `@ai-sdk/mcp` convention). Profiles stored at `mcp.<name>.json`.
- **Seeded defaults**: Guidelines for `shell.git`, `shell.fs`, `shell.npm`, `web_read`, `file_read_lines`, `file_edit_lines` ship built-in and are seeded on first run (`.seeded-v1` marker).

## Caching Layer

In-memory TTL caches (#171) cut latency and tokens across three layers. All are opt-in or opt-out via flags — never on by default for write-effecting tools.

- **Tool result cache** (`src/framework/tools/result-cache.ts`): a tool is cacheable only when its `ToolMeta` declares `deterministic: true` and either `sideEffect: 'none'` or `cacheable: true` (the `isCacheable` predicate). Per-tool TTL via `cacheTtlMs`, default 5 min; `cacheTtlMs: 0` = session-lifetime. Keys are stable JSON over the args; secrets in `meta.sensitiveArgs` are redacted before hashing. The cache check runs **after** the read-only block gate (#179) and risk-based confirm gate (#144), so policy guarantees are preserved on hits. Only `status: 'ok'` envelopes are stored, so errors/denies don't poison. Current opt-ins: `time_range`, `time_range_total`.
- **LLM subcall cache** (`src/llm-cache.ts`): standalone module keyed by `{siteName, modelId, providerOptions, system, userContent}` with a 10-min default TTL. Wired at three pure-deterministic call sites: `rewriter`, `reference-lookup:select`, `reference-lookup:interpret`. The `modelId` is pulled from the AI SDK `LanguageModel` so model-mode (#170) re-tiers automatically partition the cache.
- **RAG search cache** (`RAGStore.turnSearchCache` in `src/rag.ts`): per-turn, cleared at the REPL turn boundary (`ragStore?.clearTurnCache()` before `agent.processInput`) and whenever `addFacts` mutates the store. Avoids re-embedding the same query when both the agent and the reference resolver run a RAG lookup in the same turn. Read directly from `process.env.BERNARD_CACHE_ENABLED` so `RAGStore` doesn't carry a config dependency.

Hit/miss telemetry: every layer emits a `debugLog` line — `cache:tool:hit`/`miss`, `cache:llm:hit`/`miss`, `cache:rag:hit`, `cache:semantic:hit`/`miss` — visible with `BERNARD_DEBUG=1`. Global opt-out: `BERNARD_CACHE_ENABLED=false`.

**Provider prompt caching (#269)** is a distinct, lower layer from the application caches above: instead of skipping the call, it discounts repeated _input tokens_ on the call. `src/providers/prompt-cache.ts` marks the main agent's request with Anthropic `cache_control` ephemeral breakpoints — the system string is converted into a leading cached `{role:'system'}` message (which also caches the tool block that precedes it in document order; `@ai-sdk/anthropic@1.2.12` has no tool-level marker), plus a rolling breakpoint on the last stable message before the volatile `<system_provided_context>` block. Two prerequisites keep the cached prefix byte-identical so it actually hits: the per-turn timestamp was moved out of `buildSystemPrompt` into the `<current_datetime>` context section (`src/agent-prompt.ts`, `src/context-message.ts`, scoped to the main agent via `buildMainContextInputs`), and the tool set is session-stable (`evaluate` gated on `isReactPossible(config)` rather than the per-turn `isReactEffective`) — an invariant now pinned by `main.tool-block-stability.test.ts`, which asserts the serialized tool block is byte-identical across differing per-turn policy decisions. The rule is **main-agent-only**: `promptCacheActive` requires `historyMode === 'persistent'`, so `sub` / `task` / `specialist` / `pac-actor` / `cron` / `tool-wrapper` are deliberately not cache-marked (a one-shot dispatch would pay the 1.25x write surcharge for a read that never comes) and are therefore free to carry a reduced tool surface — which is what `createTools({surface:'worker'})` does (#253). Scoped to the built-in `anthropic` provider via `isAnthropicPromptCacheActive`; OpenAI caches automatically (and benefits from the same stable-prefix ordering), xAI/custom ignore the markers. Cache read/write token counts surface via `step.providerMetadata.anthropic.cache{Read,Creation}InputTokens` → the per-turn `SpinnerStats` odometer (`N⚡cached` in the spinner) and the `step:end` debug log. Gated by `BERNARD_PROMPT_CACHE` (default on).

**Semantic response cache (#269, Layer 3)** — `src/semantic-cache.ts`, opt-in via `BERNARD_SEMANTIC_CACHE` (default off). Reuses the local embedding stack (`getEmbeddingProvider`) to answer near-identical read-only Q&A turns from a prior response without a model call. Consulted/populated only for `isPureQuestion` turns with no images and no tool actions; cosine ≥ 0.95, 10-min TTL, 200-entry cap. Fails open when no embedding provider is available.

## Verdicts and Step Limits

Two mirror-image defects to #363, both found in one `mcp_config add` run that succeeded and was then undone by the agent that performed it.

**A success with a caveat must not read as a failure.** `mcp_verify` opened with `✓ … connected` and then appended a `⚠ … NOT loaded … Restart Bernard`, so a healthy just-added server produced output that was simultaneously success and warning. The `mcp-manager` specialist read the ⚠ as failure, **removed the config it had just written correctly**, then spent its remaining steps hunting a transport problem that never existed — guessing an SSE endpoint, then re-issuing `remove` on an already-absent key four times. Every result now leads with one unambiguous `VERDICT:` line and the detail lines are indented context, never a competing signal.

The root cause underneath it was in `MCPManager.getLiveRegistration`, which returned `connected: status?.connected ?? false` — conflating two opposite situations. A server **added since launch** has no `serverStatuses` row because this session never attempted it, so "not loaded" is the expected, healthy state and a restart is the ordinary next step; a server that was **in the config at launch** and is still not connected actually failed, and `error` says why. `knownAtStartup` (`status !== undefined`) separates them. A name collision is treated as needing attention in either case, because it needs a decision from the user: MCP registration is last-writer-wins, so two servers exporting `browser_click` means one silently shadows the other.

**Running out of steps must not surface as `parse_failed`.** A dispatch cut off at `maxSteps` never reaches the turn where it writes its JSON, so `wrapWrapperResult` sees empty text and reports "did not produce valid structured output" — true, and useless: it blames the output format for a budget problem. `runDefinition` already computes `stepLimitHit` (it is how MCP delegation decides to escalate); `tool-wrapper-run` was discarding it. `reclassifyStepLimit` now re-labels two shapes, both meaning "cut off with nothing to say": a `parse_failed`, and — for `wantStructured: false` specialists, which never parse — an `ok` whose result is absent, which otherwise hands the parent an empty **success**. Only an _absent_ result counts: testing `typeof !== 'string'` would sweep up every successfully-parsed structured result, discarding exactly the work the guard exists to preserve. A run that hit the limit but returned real content is left alone — the model may have wrapped up on its last step. `step_limit` is a real `ToolErrorType`, not a bare string. Adding the label without the taxonomy entry looked tidy and was a **regression**: `classifyError('step_limit')` matched nothing and returned `unknown` — `retryable: false`, playbook _"the error did not match any known pattern"_ — where the `parse_failed` it replaced was `retryable: true` with concrete advice. Three consumers act on that classification (`wrap-with-specialist`'s user-facing print, the `[failure: …]` hint prepended to what the model sees next turn, and cron alert severity), so the change would have improved the string a human reads in the JSONL while degrading the structured signal. It sits beside `pool_exhausted`, its exact sibling — an internal budget failure: `low` severity, retryable, **not** correctable, since exhausting a budget is not a call-shape mistake and must not enter the correction queue. The message in `reclassifyStepLimit` is read from that playbook rather than hand-written a second time.

## Non-Throwing Tool Failures

**src/tool-result-shape.ts** (#363) is the single structural answer to "did this tool call fail even though it returned?". A tool fails in two ways: it throws — which every layer already handles — or it returns, successfully, a value whose _contents_ say the work did not happen. The second kind is invisible unless something reads the shape, and the shapes differ per tool: `shell` uses `{is_error}`, the file tools use `{error}`, MCP uses the `CallToolResult` envelope's `isError`.

That answer used to be **two** predicates that had drifted. `detectToolError` (`tool-profiles.ts`) branched on tool _name_ — `{error}` for exactly `file_read_lines` and `file_edit_lines`, a `"Error"`-prefixed **string** for everything else. `augment.ts`'s inline pre-recording check tested `is_error === true || 'error' in result`. Neither read `isError`, and an MCP result is an object, never a string — so **no MCP tool could ever be seen to fail**. Measured on a real install: of 100 learned tool profiles the only ones that had ever recorded a failure were the handful whose shape was hard-coded; `open-browser-tab` sat at 84 successes / 0 errors across sessions where it demonstrably failed. `file_write` (#342) was uncovered for the same reason — its `{error}` shape is identical to `file_edit_lines`', which _is_ named. One observed session logged 254 consecutive `tool:execute:end status: 'ok'` including ~4 minutes of a dead browser socket returning `{content: [{text: 'WebSocket is not open'}], isError: true}`.

The costs were not only diagnostic. A failed result passed augment's `looksLikeError` gate, so it was **registered as citable evidence** (`registerEvidence`) — the agent could cite "WebSocket is not open" as a source — and it bumped `recordSuccess`, which also lets `patchLastBadWithFix` record a _failing_ call's args as the fix for a real bad example.

It is a leaf module for the same reason as `tool-bytes.ts`: three call sites in different layers need it (`detectToolError`, augment's inline check, `mcp-result-shaper`), and `tool-profiles.ts` opens `node:fs` + `paths.ts` at import, so making the shaper depend on it to ask a pure question about a plain object is exactly the edge #323 refused.

Details that are load-bearing:

- **Both MCP flag positions.** The spec puts `isError` on the envelope; real servers also flag an individual `content` entry and leave the envelope `false`. Both shapes were observed from one server in one session, so the envelope check alone is not enough.
- **`{error: null}` is not a failure.** The old `'error' in result` test read the key's _presence_, which misfires on what `structured-output`'s `nullableOptional` leaves behind (#341). The predicate requires a non-empty string.
- **The truncation wrapper re-stamps `isError`.** `mcp-result-shaper`'s `{_truncated, preview}` fallback replaces the envelope wholesale; without re-stamping, truncating an over-budget failure silently _upgrades_ it to a success. `isMCPErrorResult` therefore does not require a `content` array. Since #458 the wrapper is the **last** resort rather than the common path — the shrink and unwrap layers preserve `isError` structurally, by cloning the envelope — so the property is now pinned on **both** paths: the re-stamp is still live (cycles, and payloads whose fields are individually too small to shrink) and still required. The test that forces the wrapper is the one worth keeping honest; rewriting it to match whatever the common path now returns is how the #363 regression comes back.
- **Detection is not reconnection.** `MCPManager.getTools()`'s reconnect-and-retry stays in its `catch`, reached only by a throw. `isError: true` is the MCP-defined way to report an ordinary _tool-level_ error ("element not found"), and tearing down a server on every one of those would be far worse than the bug being fixed. Whether a transport-shaped `isError` should reconnect is a separate question needing its own signal.
- **`web_search` keeps a per-tool rule.** Its provider-chain failure is a bare diagnostic string with no structural marker, so it is the one case that cannot be inferred from shape.
- **Detection is upstream of correctability.** `recordOutcome` still gates bad-example recording on `classifyError(...).correctable`, and the observed messages ("WebSocket is not open", "ref 13 is a combobox, not a text input") classify `unknown` → dismissed. So this change makes failures _visible_ (status log, red in the thread, no evidence registration, no inflated success count); teaching the taxonomy to read them is separate work — the honest fix there is a dismissed-failure counter on `ToolProfile`, not a new taxonomy rule (#366).
- **The MCP snippet is extracted in one bounded pass.** Both the "prefer flagged entries" and "else the whole content" buckets stop growing at the 200-char cap, because accumulating past it means concatenating the entire payload to throw all but 200 bytes away — ~6 ms and a multi-megabyte transient for an uncapped accessibility snapshot (reachable with `BERNARD_MCP_RESULT_SHAPING=off`), on the path between a tool returning and its value reaching the model. The scan still visits every entry: a flagged entry may be last, so which bucket wins is not known until the array is exhausted.
- **`wrapMCPTool` (`framework/tools/mcp.ts`) is currently unwired** and carries the same detection so it stays the shape it should take. The live path is `MCPManager.getTools()`, which returns a raw object rather than a `ToolResult`, so MCP tools take `augmentTools`' _legacy_ branch and never reach the envelope one — which is why detection also had to be added downstream. Routing `getTools()` through the wrapper is the deeper fix (typed `ToolErrorType` instead of `classifyError` re-parsing a message string; the truncation-time `isError` re-stamp could then go away), with its own blast radius — filed as #365.
- **Every failure is decided by shape (#364).** `detectToolError` has no tool-name branches left, so it and `augment`'s shape-only inline gate now agree for every tool. Four producers were taught to emit the `"Error: "` prefix — `delegate-dispatch`, `subagent`, `specialist-run` (which #364 undercounted) and `web_search` — each of which previously returned prose that registered as citable evidence and bumped `successCount`. `delegate_<server>` mattered most: with `BERNARD_MCP_DELEGATION` on it _is_ the main agent's MCP surface, and it sat at 36 successes / 0 errors. In three of those files the prefix was already the convention for the _other_ failure returns — `subagent`'s pool-exhausted callback sits three lines below its catch and was always detected — so the fix made each catch match its own neighbours. `web_search` additionally splits two states its single string conflated: every provider unreachable is an `Error:`, while a provider answering with zero matches is a **success** (a real, citable observation), since marking it a failure would teach the profile that an obscure query is a usage mistake.
- **`tool:execute:end` records what the tool answered (#459).** It logged `{tool, durationMs, status}` — the question and the elapsed time, nothing about the reply — so any claim of the form _"the tool told me X"_ was unfalsifiable from our own logs. That is what kept #458 invisible for a whole session: twelve Gmail reads, every one `status: "ok"`, and no way to tell a server that never sent a `Cc` header from one Bernard had truncated it out of — opposite owners, opposite fixes, settled only by reproducing the payload by hand. It now also carries `resultChars`, `resultBounded`, a bounded `resultPreview`, and — on the legacy branch — `failureSnippet`, the text `detectResultFailure`'s verdict was actually derived from, which was computed and thrown away one line above the log call. `shapeMCPResult` reports every cap through an observer, which `mcp.ts` logs as `mcp:result:capped {server, tool, rawChars, keptChars, strategy, unwrapped}`; the pre- and post-shaping sizes are the pair that makes a silent truncation greppable.
  - **All of it is `BERNARD_DEBUG`-gated, because `debugLog` already was.** `tool:execute:end` never existed outside debug mode, so "always record the size" is not achievable through this sink and the issue's always/debug split does not exist. The whole payload is therefore built inside one `isDebugEnabled()` check — `debugLog`'s argument is an ordinary expression, evaluated whether or not it is written, and an unguarded preview would serialize every result on every call with debug off. An always-on audit trail is real work with its own retention and PII questions, and is **not** claimed here.
  - **`boundedStringify`, not `safeSerialize`.** The naive stringify-then-slice materializes the whole value before discarding all but a few hundred bytes (~39 ms / ~20 MB transient for a 10 MB `shell` result) and cannot be allowed to throw on a log-write path. It is not sufficient on its own: its budget decrements on **strings** and its item cap applies to **arrays**, so a number-heavy shape is bounded by neither — 300k numeric fields measured a **4,877,781-character** "preview" against a documented ~1,000, once per tool call into the session JSONL. The final slice at the call site is what makes the documented size true, while `resultChars` keeps reporting the pre-slice length.
  - **`failureSnippet` is keyed on the snippet's presence, never on the tool's sensitivity.** `detectResultFailure` returns `undefined` on success, so redacting on `sensitiveResult` alone stamped `[REDACTED]` beside `status: "ok"` on every successful call from such a tool — a line that reads as a failure whose reason is hidden. A log that invents a failure is what #459 exists to remove, not to add. `sensitiveResult` redacts the **preview** and the snippet when there is one; `resultChars` survives it, because a size is not a secret and it is the number that makes a truncated read visible at all.
  - **A cache hit is now counted.** It returned before either `tool:execute:start` or `:end` was reached, so a scan of the log undercounted tool calls — and undercounted exactly the ones that are free and therefore most repeated — while still registering the result as citable evidence. Both lines are emitted with `cached: true`, so a consumer pairing start with end stays balanced.
- **Known gap:** `cite` returns `JSON.stringify({error})` — an error object serialized into a string, which no shape check sees. Left alone deliberately: sniffing JSON out of arbitrary result strings costs a parse on every call to catch one low-traffic tool, and changing `cite`'s model-facing contract does not belong in a detection change.

## Failure Taxonomy

`src/error-taxonomy.ts` is a central classifier that turns a raw tool error (message, optional `toolName`/`errno`/`httpStatus`) into `{category, correctable, retryable, severity, playbook: {user, model}}`. Categories: `invalid_args | exec_failed | not_found | auth | rate_limit | permission | timeout | transient | parse_failed | pool_exhausted | cancelled | unknown`. `not_found` is correctable only when `toolName === 'shell'` (a command-not-found mistake the model can fix) — for web tools a 404 is "the URL is gone," not learnable.

The same classification drives four surfaces:

- **Correction queue gate**: `src/tools/tool-wrapper-run.ts` only enqueues a candidate when `cls.correctable === true`. Non-correctable failures are logged and dropped.
- **Profile gate**: `src/tools/augment.ts` only records bad examples when `cls.correctable === true`; success always bumps `recordSuccess`.
- **User render** (#353): `toolFailureFor` (`src/tool-failure.ts`) projects a result to `{category, hint: playbook.user, severity}`, and `<ToolFailureHint>` (`src/ui/Thread.tsx`) renders it as a `category · recovery hint` line under the red result, coloured by severity. **Derived at render, not carried on the sink event**: it is a total pure projection of the result, so caching it would need two producers — `commitNewHistory` and `buildResumeSeed`, which rebuilds from disk with no event to copy — and a drift bug between them. It also keeps one definition of "did this fail". Both render paths derive it, which matters because streaming events are replaced by static items at turn commit. Because it hangs off `detectToolError` rather than the wrapper shim, it covers **every** tool, not the four the shim routes. `classifyToolFailure` trusts an embedded `[failure: <category>]` marker over the patterns: re-classifying an already-annotated result is not idempotent (measured, `auth` round-trips to `unknown`, dropping severity `critical` → `low`), because the string then holds playbook prose rather than the original error. The predecessor `printToolFailure` was an empty stub from the Ink cutover, so this whole surface silently did not exist — and the _model's_ playbook leaked into the result the user read in its place.
- **Model hint**: the same shim prepends `[failure: <category>] <playbook.model>` to the error string the model sees on its next turn.
- **Cron alerts**: `src/cron/runner.ts` classifies any job-level throw and fires `sendNotification({severity, ...})` with the user-facing playbook so headless jobs surface failures with the right urgency.

Severity map — `critical`: `auth`, `permission`; `normal`: `rate_limit`, `not_found`, `invalid_args`, `exec_failed`; `low`: everything else.
